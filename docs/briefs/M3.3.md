## Behavior

1. **Routes:** `GET /api/dashboard/counts`, `/api/dashboard/charts`, `/api/dashboard/campaigns`, `GET /api/campaigns/analytics/:type` and `GET /api/lists/analytics/:type` with upstream's permissions, envelopes, parameters, types (`views`, `clicks`, `bounces`, `links`, `subscriptions`, `unsubscriptions` and whatever else the pinned commit has), date handling and group-by behavior, and `DELETE /api/maintenance/analytics/:type` only if M4.6 would otherwise need to reimplement it. Respect list-scoped permissions for every campaign and list ID requested.
2. **Results:** the same numbers as upstream for realistic data, including `privacy.individual_tracking` off (subscriber IDs null) and unique counts. Bounce analytics read the existing `bounces` table, which M3.4 fills; test them with fixture rows through the owning module or the contract suite's setup.
3. **Transactional and sequence sends:** 04 says they appear in analytics, grouped by template and by sequence step. Add `GET /api/sends/analytics` or the smallest equivalent, requiring a permission the design names, reading `campaign_views` and `link_clicks` by `send_id`. Say what you chose in 07. Do not change the shape of upstream's routes to carry them.
4. **Summary tables:** design says ordinary tables rebuilt by the maintenance loop, replacing upstream's materialized views. Build what the dashboard and list stats need, with an injected-clock loop, and refresh without holding the write lock for long: compute in reads, write in a short transaction. Report staleness the way upstream does when it caches. If a live query is fast enough at the sizes below, keep it live and say so; do not build a table without a need.
5. **Hot paths:** nothing here slows the pixel, redirect or send paths. Add indexes only with a measurement, because each slows writes.
