## Behavior

1. Accept JSON and listmonk's multipart form (`data` JSON field plus `file` attachments) within bounded limits that match the M2.2 payload bounds. Permission is `tx:send`, using the existing auth, CSRF/Origin and credential precedence.
2. Recipients follow 04-sending rules: any address can receive a transactional send without creating a subscriber. `subscriber_mode` default/fallback/external behave as documented. id, external_id and email resolve existing subscribers. Blocklisted subscribers never receive mail. Multiple recipients produce one `sends` row each.
3. Templates: `template_id` must be a `tx` template. Render subject and body with the M1.8 bounded renderer, using listmonk-compatible `.Tx.Data` and `.Subscriber` context as the template docs define. `content_type`, `from_email`, `headers`, `messenger` (only `email`; other values get a safe 400) and attachments match upstream results for realistic clients.
4. `idempotency_key`: a repeat returns the first result and sends nothing, including under concurrent requests. A key reused with a different request is a safe 409 or 400; document which and why.
5. `async: false` (default) sends before responding, through the outbox owner so the journal row and outcome are durable. `async: true` returns queued rows immediately. The response is `{data:{sends:[{id,uuid,status,smtp_message_id}]}}` (declared difference). Marketing is staged per D58.
6. Rendering, validation and recipient failures are atomic: no partial rows, no SMTP. Network I/O never runs inside a transaction.
