# B42: Fix the flaky runner test at its root

Common rules: [_state-common.md](_state-common.md). Branch `task/B42-runner-flake`. Lines from main at the commit that queued B42.

## Source

`test/campaigns/runner/runner.test.ts:573` ("tracked links personalized per subscriber do not accumulate across batches") times out intermittently. It hit the 30 s limit twice under `bun run check` (4 parallel workers) and the 5 s limit in a serial `bun test test/campaigns` run (#86, #90). It passes alone in about 1–17 s. A flaky test in the merge gate wastes every check run and hides real failures.

## What to do

1. **Find the cause, not a bigger timeout.** Do not raise any timeout, add retries, or mark the test skip/todo. Read the test and the fixture it uses. Common causes here are:
   - waiting on real time (`Bun.sleep`, polling loops) instead of the injected clock;
   - a loop that needs a clock advance the test never makes;
   - an unbounded wait for a sink message that never arrives;
   - work that scales with batch count and is slow under CPU contention;
   - shared state between tests in the file.
2. **Reproduce first.** Run the file many times, and under load, to get a failure rate before the fix. For example, run it 20× in a loop, and also alongside a CPU hog such as `bun run check` or a parallel run. Record the failure rate and the time per run, before and after.
3. **Fix the test, or the fixture it relies on.** If the cause is a real runner defect (for example, the runner stalls when a batch boundary meets a tracked-link insert), fix the runner instead, add a focused regression test, and say so plainly in the PR.
4. Check whether other tests in `test/campaigns` share the same pattern and fix them too, if the fix is the same.
5. Refresh `test/timings.json` only if test durations changed meaningfully (see AGENTS.md for the command).
