# B11: Event latency under mixed load

Goal: lower event commit latency under the M6.1 full mixed load (p95 51 ms in M6.1, 96.5 ms in B7 on a busier host; 10.5 ms with events alone) without weakening D22 durability, at-most-once marketing sends or the rule that no network call runs inside a transaction. If no change helps, record the evidence and close the line as owner-only (a D22 durability decision).

## Behavior

1. **Measure first.** Under the M6.1 mixed load, record per loop how many commits per second each makes and how long each holds the write lock: events, outbox claim, outcome/`skip_reason`, scheduler, campaign progress, sequences, tx. B7 reasoned that the event tail comes from the other loops' commits. Confirm or refute that with numbers before changing anything.
2. **Reduce the blocking.** Pick the smallest change the numbers support. For example: fewer, larger commits in the loops that commit most (coalesce campaign progress and post-send outcome rows), shorter lock hold times (prepare outside the transaction), or a shared commit point for writes that carry no ordering requirement. These never move:
   - The outbox claim commits before any network send (at-most-once).
   - No network call runs inside a transaction.
   - Every event still resolves after its own FULL commit.
   - Campaign and send results are unchanged.
3. **Prove it.** Run at least three before/after pairs back to back on the same host state with the same command (`M61_WINDOW_MS=120000 bun test/perf/m61/mixed.ts mixed`, compiled build). Report events in window, event p50/p95/p99/max, campaign rate and tx accept p95 for each. Keep a change only if event p95 improves in every pair and campaign rate and tx p95 don't get worse beyond noise.
4. If nothing qualifies, revert the experiment, record the measurements and reasoning, and rewrite the backlog line as owner-only (needs a D22 decision), naming the expected gain from the measurements.
