# B155: post-2.1.0 hardening (six parallel tasks)

The open backlog of the post-2.0.0 work (B149a–B154, PRs #232–#245), compiled by a helper for the lead on 2026-11-26 from the PRs' "Backlog" sections and review comments, the B149 lines of [`status.md`](../status.md) and the recovery file's `backlogAfterRelease`. Every item was checked against `origin/main` at 5b5aca9 (v2.1.0 published); items already fixed or documented are listed at the end with the reason, not carried. Split into six tasks with separate owners so they run at the same time (D133). Read [`_B97-common.md`](_B97-common.md) first (this host, file rules; decision records go in as "(B155x, lead, 2026-11-26)"). Each task: one worker, branch `task/B155<x>-<name>`, base `origin/main`, PR title "B155<x>: <title>". Each item names the review where it was found; read that PR's comment for the detail before changing anything. An item that turns out to be wrong or not worth a change is closed in the decision record with the reason, never silently dropped. Test first through public boundaries; each fixed defect gets a test that fails without the fix (name the mutant in the PR).

**Classes.** (a) consent, send correctness, data loss or security: highest priority. (b) correctness an operator can hit. (c) test gaps: untested branches, surviving mutants, fragile tests. (d) docs, UX, log noise, nits. **TO** marks an item the lead may record as an accepted trade-off instead of a change, with the proposed reason; the worker decides in the task's decision record (fix, or close as a trade-off with that reason) and the lead copies accepted ones into `status.md`.

**Shared rules for all six.** Do not edit a file another B155 task owns; if you must, stop and report it in the PR. Every acceptance list includes `bun run check` once (junit captured). Whenever `src/messaging/**`, `src/campaigns/runner/**`, `src/sources/send-time.ts` or shutdown code changes, every `sends:*` script; a migration adds the v2.1.0 upgrade check (start a v2.1.0 data directory on the new build). Throughput or latency measurements record the data directory's filesystem (disk or tmpfs) and the load.

## Proposed accepted trade-offs (no task)

The lead records these in `status.md` "Accepted trade-offs" unless a worker finds a cheap fix while in the file:

- **Entry assets keep fixed names** (B149e r2 item 2): a suite that imported the old manifest reads new contents of `admin/js/boot.js` and similar under the old `assetVersion` after a rebuild beside it. Each file is still whole and no test depends on the version; hashing entry names would change every embedded URL.
- **The PocketBase test binary is verified only on download** (B150a r1 item 3, `test/sources/pocketbase-binary.ts:69-93`): the cache is in the checkout's own `node_modules/.cache`, written only after the SHA-256 check; a test tool, not shipped.
- **An on-demand SES read during the loop's sleep adds one read** (B151 r1 item 3, `src/messaging/ses-account.ts:416-431`, `:454-459`): `fresh()`/`check()` move `lastAttempt` but not the loop's wake-up, so the loop may read once more. Harmless; at most one extra GetAccount per on-demand read.
- **A scheduler stall or `sending.hold` over 2 h during an outage restarts an enrollment's window** (B150c r4): it only lengthens retrying; nothing is sent without a successful read.
- **A manual enrollment with no trigger record is skipped `late` past the 72-hour window** (B150c r2): nothing is sent; documented in 05-sequences, spec 15 and D172.
- **The names check counts active enrollments per sequence every 15 s** (B150b r1, `src/sources/stream-names.ts` through `sequences-page`): bounded by the project's sequences and cheap at that size; a narrow query is worth it only when measured.
- **The stream and the scheduler use separate adapters, so two service-account tokens per project** (B150d): two sign-ins, no correctness cost; sharing needs the adapter's `stream` part exposed from `createSourceProvider`.
- **Test connection sees rows, not rules** (B150c): the service account cannot read collection rules (that needs a superuser), so a guest-readable collection with no rows passes and a later rule change is not re-checked. Spec 15 already requires service-account-only rules; B155d item 9 adds the operations sentence.
