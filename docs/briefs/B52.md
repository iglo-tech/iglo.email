# B52: Bind the HTTP port before any background loop starts

Common rules: [_state-common.md](_state-common.md). Branch `task/B52-bind-first`. Lines from main at the commit that queued this brief.

## Source

Found in the #101 review. In `src/main.ts` the background loops start while the app is being wired, before the HTTP port is bound:
- the outbox at :412;
- the campaign runner at :553;
- signup mail at :615;
- purge at :652;
- the scheduler at :664;
- webhook delivery at :685;
- the summary refresh at :748.

`startServer(app, router)` binds the port at :761. If the bind fails (the port is in use, which Bun reports as "Is port N in use?"), the process has already started loops that can claim sends, campaign batches and webhook deliveries. It then exits, and those claims are left for recovery to mark `unknown` (at-most-once). A failed start should do nothing.

The data-directory lock (`holdDataDirectory`, :132, D69) already comes first and must stay first.

## What to do

1. Restructure startup so the port is bound before any loop starts, and no request is served before routing is ready. Pick one of these options and justify it:
   - **(a)** Keep constructing stores, routes and loops in the same order, but split "create" from "start" for each loop. Bind the server after all routes are registered, then start the loops. The order: lock → open DB → wire everything (no loop running) → bind → start loops.
   - **(b)** Bind first with a handler that answers 503 until wiring is done.

   Prefer (a). It changes no HTTP behaviour.
2. Check each `start*` function. If it starts work as soon as it is called, give it a separate start step, or call it after the bind. The shutdown path (`shutdown` near :766) must still stop everything that was started. On a failed bind, it must close only what exists and release the lock.
3. Keep one module's ownership intact (AGENTS.md). Change only the call order and the small start/create split. Do not redesign the loops.
4. Update `docs/design/02-architecture.md` (startup order) with one short paragraph.

## Tests (public boundaries; the compiled executable as the bootstrap tests use it)

The process must exit non-zero with the port error. Afterwards the database must show the send still `queued` (not `sending`/`unknown`), the campaign's claim untouched, and no webhook delivery attempted. 3. Shutdown on SIGTERM after a normal start still drains as before. The existing bootstrap and crash tests (`test/bootstrap`, `test/scheduler/crash.ts`, `test/webhooks/crash.ts`) must pass.
