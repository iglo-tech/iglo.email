## Finding (MEDIUM, consent)

`POST /subscription/wipe/:sub` deletes the subscriber; `subscriber.deleted` arrives with `external_id: null` (D61), so the app cannot tell who wiped; on the app's next event the subscriber is re-created, `grant_lists` answers `added`, and marketing sequences restart, even one with `reentry: "never"`.

## D125 (implement exactly this; both parts)

1. **Suppression record.** A self-wipe (public wipe; also the admin's "delete and suppress" if it exists, otherwise only the public wipe) stores a suppression row: a keyed hash (HMAC-SHA-256 with a per-install secret kept in the database, never exported in plain) of the normalised email and, if set, of the `external_id`, plus the wipe time and the lists the person had. No plain address, name or ID. Owned by the subscribers module (table + SQL + migration).
   - When a subscriber is created or upserted (events API, `POST /api/subscribers`, import, public signup) and matches a suppression row by email or external_id hash: `grant_lists` answers a new result `suppressed` for every list and grants nothing; marketing sequence enrollment is refused (as for an unsubscribed subscriber); explicit double-opt-in signup by the person themself (public form, which sends the opt-in mail) clears the suppression once confirmed, because the person acted again. Transactional mail (tx, transactional sequences) is not affected: suppression covers marketing consent only.
   - An admin can see and remove a suppression only as a count and by email (typed, hashed, matched): `DELETE /api/suppressions` with an address in the body (permission `subscribers:manage`), so an operator can honour a later explicit request; no listing of hashes.
2. **Webhook.** The `subscriber.deleted` payload of a self-wipe carries `external_id` and the `list_ids` the person had, captured before the row is deleted (the receiver is the operator's own system, which must honour the erasure). Email and name stay cleared (D61 unchanged otherwise). Admin deletes are unchanged.

Considered (record): (a) alone (each integrating app must implement suppression, and any app that does not re-opts people); (b) alone (the app cannot mirror the erasure in its own records); keeping the plain address (D61 refused it).

## Tests (first, through HTTP + webhook receiver + sink)

The audit repro: grant → marketing mail; self-wipe → webhook carries `external_id` and lists, no email; same event again → new subscriber, `grants: [{result: "suppressed"}]`, no marketing mail, no marketing enrollment; a transactional sequence still sends; a matching import or `POST /api/subscribers` gets no marketing lists; public double-opt-in by the person clears it after confirmation; `DELETE /api/suppressions` with the address clears it; the suppression table holds no plain email or ID (assert through the API: no route reveals it; a table read only to prove absence, stated why). Idempotency replay of the event returns the same `suppressed` result.
