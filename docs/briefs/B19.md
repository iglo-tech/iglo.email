# B19: Subscriber consent invariants

Common rules: [_state-common.md](_state-common.md). Branch `task/B19-consent`. Decision records: **D81**, **D82**.

## Owns

`src/subscribers/*`, `src/lists/*`, `src/bounces/store.ts`, `src/public/*`, `src/unsubscribe/*`, their tests and contract suite marks.

## Behavior

1. **A blocklisted subscriber holds only unsubscribed memberships (D81).** Today about seven paths blocklist a subscriber, and they behave in three ways.
   - **No cascade** (memberships stay confirmed, so mail resumes the moment the subscriber is un-blocklisted):
     - automatic bounce action `blocklist`, `bounceBlocklist` (`src/subscribers/store.ts:573`, via `src/bounces/store.ts:235`)
     - PATCH with `status=blocklisted` and no `lists` (`store.ts:326`)
   - **Cascade without bumping the membership `updated_at`:** PUT with `status=blocklisted` (`membership-status`, `store.sql:26`).
   - **Cascade without bumping the subscriber `updated_at`:** public unsubscribe with the blocklist box (`subscriber-blocklist-only`, `store.sql:68`).

   Fix:
   - Every path into blocklisted goes through one store function. That function unsubscribes every membership and stamps the membership `updated_at` once for each row that actually changes (this is the date the unsubscribe chart uses).
   - Paths that add or confirm memberships must never give a blocklisted subscriber `unconfirmed` or `confirmed`:
     - PUT without `status` (`store.ts:331` passes `""`)
     - admin add by IDs (`store.ts:366-369`)
     - query add (`query.sql:11`)
     - the opt-in confirm page (`src/public/routes.tsx:332-348`)
   - Un-blocklisting then leaves memberships unsubscribed.
   - The bounce path is a deliberate difference from upstream's `record-bounce` block1. Record it in D81, in `07-api-and-ui.md` and in the contract marks.
   - `test/subscribers/fixtures.md:22` relies on a "blocklisted + confirmed" fixture. Change the fixture rather than the rule.
2. **A list's `optin` cannot change while the list has unconfirmed members (D82).** `src/lists/store.ts:167` changes it freely.
   - single → double silently stops delivery to unconfirmed members and makes them eligible for the "delete unconfirmed" purge.
   - double → single starts mailing people who never confirmed.
   - Fix: refuse the change with 400 and a clear message, and show that error in the admin UI. Other list fields still update.
   - Record it as a deliberate difference.
3. **Add by IDs and add by query must give the same result.** Admin add by IDs overwrites any membership status (`store.ts:369`). Query add does `ON CONFLICT DO NOTHING` (`query.sql:13`). Read upstream's two queries. Make ours match upstream where upstream itself agrees; otherwise make both follow the by-IDs result, and record that.
4. **The public form cannot subscribe to an archived list.** A hand-made POST can subscribe to one by UUID (`lists-by-uuid`, `src/lists/queries.sql:12`, used at `src/public/routes.tsx:138`). Check upstream, then ignore archived lists, as the form already hides them.

## Out of scope (decided)

- A public signup on a single opt-in list re-subscribes an unsubscribed member, as upstream does.
- `disabled` subscribers and `archived` lists still receive campaigns, as upstream does.
