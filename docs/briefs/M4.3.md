## Behavior

1. **Templates:** index, create, edit, preview, set default, clone and delete, for campaign and transactional types, with upstream's editors and wording.
2. **Campaigns:** index with search, status filter, paging, live stats and start, pause, resume and cancel controls; the campaign form with lists, template, from address, tags, headers, content types with conversion, the rich-text and code editors, media attachments, `data-embed` images, archive settings, send-later, preview and test send. Match upstream's appearance, i18n keys and `data-testid` values so the specs adapt with little change. Opt-in campaigns created from a list reach this form.
3. **Status controls:** the screen only offers transitions the API allows. A confirm stands before start and cancel. Stale state after another user's change shows the API's message, and a second click cannot send twice.
4. **Permissions:** each route gives `adminPage` the permissions its endpoint needs. `campaigns:get` and `campaigns:get_all` differ, as do `manage` and `manage_all`, and `campaigns:send` guards the status controls in the screen as the API does.
5. **Safety:** campaign and template HTML is the author's own content, and upstream's preview renders it: previews stay in a sandboxed frame so it cannot run on the application's origin with the admin's session. Names, subjects, tags and API messages are escaped. Editor libraries come only from the embedded assets.
6. **Live stats:** polling for running campaigns is bounded, stops when nothing runs and when the page is hidden, and does not slow the send path.
