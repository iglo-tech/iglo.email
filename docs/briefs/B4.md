## Behavior

1. **ALTCHA:** `GET /api/public/captcha/altcha` issues a challenge and `POST /subscription/form` verifies the solution, with the wire format, algorithm, expiry and replay protection upstream's library gives, so a page that embeds the upstream ALTCHA widget keeps working. Server side uses `crypto.subtle`/`Bun.CryptoHasher`, no runtime dependency. A replayed or expired solution is refused. Replay state is bounded in memory and in rows, and survives the single-instance model (D69) without a new table unless one is needed.
2. **Widget:** the public form shows a working widget when ALTCHA is enabled. Prefer a small in-house worker using Web Crypto over the upstream widget if it gives the same result; if you vendor the widget, its license must be AGPL-compatible and the decision record says why. The public pages' CSP, if any, must allow it without `unsafe-eval`.
3. **hCaptcha:** verification calls hCaptcha's `siteverify` with the stored secret, outside any transaction, with a timeout and a bounded body, and fails closed on any error. The verify URL is injectable so tests use a local fake; tests never call hCaptcha.
4. **Settings:** the `captchaUnavailable` note goes; both switches work and validation matches upstream (one at a time, required keys). The masked secret stays masked.
5. **Other routes:** `POST /api/public/subscription` stays without a captcha, as upstream. One-click unsubscribe stays without one (RFC 8058).
