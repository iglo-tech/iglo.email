## Schema requirements

Implement every kept table from 03-data-model.md: subscribers, lists, subscriber_lists, templates, campaigns, campaign_lists, campaign_views, media, campaign_media, links, link_clicks, settings, bounces, roles, users and sessions. Preserve meaningful upstream columns, enums, nullable behavior, indexes and FK actions under the explicit SQLite/design changes. Keep later-feature columns where needed to retain the v7 storage shape; this does not implement visual templates, archives, OIDC or provider integrations.

Also create events, sequences, sequence_steps, enrollments, sends, webhooks and webhook_deliveries; subscriber name/email FTS5 with transactionally maintained insert/update/delete triggers; and the four ordinary summary tables above. Summary rebuilds/refresh loops remain future work. Do not implement views that secretly compute product behavior instead of the designed stored summaries.

- IDs use SQLite integer primary keys and preserve safe signed-64-bit boundaries through existing helpers. UUIDs are TEXT, supplied by future application owners rather than a pgcrypto extension. Document any allocation choice that affects the campaign cursor/max-ID assumptions; do not silently weaken them.
- Translate enum types to appropriate TEXT CHECK constraints; booleans to validated SQLite values; JSONB/arrays to valid JSON TEXT with suitable object/array checks for columns whose schema requires them. settings.value may contain any valid JSON value, including scalars. Preserve legitimate SQL NULL distinctions and multiple unset idempotency/external IDs. A CHECK alone must not accidentally permit forbidden NULL states.
- Subscribers have case-insensitive unique email and nullable unique external_id. Do not claim Unicode-wide case folding from SQLite NOCASE. Keep representative upstream query-supporting indexes; new indexes follow 03-data-model.md's event lookup/idempotency, scheduler, outbox, cap and send-step uniqueness requirements.
- Enforce exactly one of campaign_id and send_id on campaign_views and link_clicks, with valid foreign references. Preserve analytics when subscribers are deleted as designed. Apply explicit and documented FK/delete behavior for all new relationships so event retention, nullable references, subscriber wipe, soft-deleted steps and send history remain possible. Do not invent automatic resend/recovery state transitions in triggers.
- Enforce unique (enrollment_id, step_id) sends and the specified event/tx idempotency keys. Do not enforce one lifetime enrollment per subscriber/sequence: reentry modes allow later runs. Keep the scheduler/status/due/lease data but start no loop. Skip/exit reasons can be extensible strings (event:<name>, and the scheduler's late reason must remain representable); do not impose an incomplete enum from a notes list.
- Keep session columns compatible with the source. No user, password, role/permission seed, live SMTP setting, subscriber, list, campaign or email template is created. M1.2 owns settings defaults/validation, M1.3/M1.4 auth/roles and M1.8 built-ins. An empty migrated schema is the intended baseline; summary rows are populated later by their owner.
- Timestamps use sortable UTC ISO-8601 TEXT. Preserve/document appropriate defaults in the translation; application fixture writes use explicit timestamps from the injected clock. No real-time sleeping in behavior tests. Connection pragmas, transaction boundaries and user_version are exclusively the existing helpers' responsibility; no such commands in the SQL file.
- Static fresh-install DDL must fail safely on conflicting unexpected user objects rather than destroying them or masking a partial schema with blanket IF NOT EXISTS. Keep productionMigrations explicit, embedded and contiguous at version 1. Restart at version 1 performs no reinstallation, seed replay or unnecessary snapshot.
