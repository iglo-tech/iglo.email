## Behavior

1. **Validation.** `validate(condition, {canUseSql})` returns precise, safe field errors. It enforces the documented shapes, `op` values, `since` forms (`trigger`, `enrollment`, `last_step` or an ISO 8601 duration), `count` comparators, `where` equality on `data.*` paths, `list` statuses and depth and size bounds against hostile nesting. A `sql` predicate is accepted only when `canUseSql` is true (the `subscribers:sql_query` permission) and its fragment passes M1.7's checks.
2. **Compilation.** A whole condition compiles to one parameterized SQL query that returns true or false for a single subscriber, given an evaluation context: subscriber ID, the trigger event's `occurred_at`, enrollment start, last step time and an injected-clock `now`. Values are bound, never interpolated. Attribute comparisons use SQLite JSON functions with clear type rules (numbers vs strings, missing attributes, `exists`, `in`); document them. `attr: "status"` reads the subscriber status. Event predicates use the events index; include `EXPLAIN QUERY PLAN` evidence.
3. **The `sql` escape hatch.** A condition containing `sql` is evaluated through M1.7's read-only child runner with its time, memory and concurrency limits. Conditions without `sql` run on the normal read path with no child process. Measure both.
4. **Evaluation API.** `evaluate(condition, context)` returns boolean, or a safe error for timeouts and limits, so the scheduler (M5.4) can decide what to do. It is never thrown into a transaction holding other work. Batch evaluation over many subscribers is not required.
