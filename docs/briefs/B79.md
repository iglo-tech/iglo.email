# B79: hand-written MCP tools take every field

Common rules: [_state-common.md](_state-common.md). Branch `task/B79-mcp-handwritten-fields`. Lines from main at 3dc9ca1 (B78 #130 merged). Source: the B78 review (#130, non-blocking): the 20 hand-written MCP tools accept only the filters and body fields they always had. For example, `create_campaign` has no `type`, so an opt-in campaign cannot be created through MCP, and `list_lists` has no `type` or `order_by`.

## Changes

1. Each hand-written tool in `src/mcp/tools.ts` that covers an operation (the coverage map in `src/mcp/coverage.ts`) accepts every query parameter and body field of that operation, with the same schema the generated tools build from `src/openapi/operations.ts` (reuse B78's schema builder in `src/mcp/generated.ts`; do not hand-copy fields). Keep each tool's existing argument names, read-modify-write behaviour and descriptions; where a tool's own argument already maps to an API field, do not add a second name for it.
2. Pass the new fields through unchanged, so the endpoint's validation and messages apply (D91).
3. A test, through `POST /api/mcp` `tools/list`, asserts that for every hand-written tool, each query parameter and body property of each covered operation is in its `inputSchema`. Plus round trips: `create_campaign` with `type: "optin"`, and `list_lists` with `order_by`.
4. D98 in `docs/design/09-decisions.md`: one sentence that hand-written tools take every field of their operations. Also (B78 r3 nits): make the "Which form is returned" paragraph part of the list instead of breaking it, and give the right reasons: `structuredContent` is kept because of D91 (the read-merge tools use it), the text copy because the MCP spec says a tool returning `structuredContent` SHOULD also return it as text.
5. B78 r3 nit: the `per_page=all` cap test in `test/mcp/` creates only 20 subscribers, under one 200-row batch, so it passes even if the stream is not cancelled. Make it create more than 200 rows (large enough to pass the cap) and call it at least three times, then a REST `per_page=all` call, so a leaked large-selection slot fails the test ("Too many large subscriber selections in progress"). Check it fails with the cancel removed, then restore it.
