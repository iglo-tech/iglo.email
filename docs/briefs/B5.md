## Behavior

1. **Reschedule:** an operator who changes a step's wait can apply the new wait to enrollments already waiting on that step, from the sequence editor, behind `sequences:manage`. One endpoint, e.g. `POST /api/sequences/:id/steps/:step/reschedule`, recomputes `due_at` from each waiting enrollment's step start and the current wait, in bounded batches with short transactions, and never sends or advances anything itself. Enrollments under a claim, test enrollments' 1-minute cap and `retry_at` keep their rules. Due times in the past mean "due now", not a burst of catch-up: the scheduler's normal batch limits still pace them. The response says how many changed. Default without the action stays as today: a new wait applies only to steps scheduled after the change.
2. **Live condition validation:** the condition editor checks a condition as it is typed, through one endpoint (e.g. `POST /api/conditions/validate`, `sequences:manage`) that runs the existing validator and compiler without touching data and returns the same errors a save would. Raw SQL conditions keep their permission gate. Requests are bounded in size and time. The editor shows the error inline and keeps save behavior unchanged.
3. **Activity tab:** the subscriber page gets upstream's activity tab over the existing `GET /api/subscribers/:id/activity`, and its clear buttons call `DELETE /api/subscribers/:id/activity` with upstream's permission and result. Match upstream's screen and API results; the extra transactional and sequence rows our API already returns are shown as well.
4. **Policy:** every new screen works under the admin CSP with no violation.
