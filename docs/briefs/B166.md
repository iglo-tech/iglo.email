1. **A subscriber moving onto a suppressed address keeps marketing the person withdrew** (blocker, `recipient-sync.ts` `applyRecipient`). When a user who withdrew consent (blocklisted, unsubscribed, or wiped) leaves, `removeLeaving` deletes the row and keeps a D125 suppression on the address and user ID. If another user's existing subscriber then takes that address in the view, the conflict is `none` (no holder row), the address is written, and nothing carries the withdrawal: the row stays enabled with its confirmed marketing memberships and enrollments, and campaigns and marketing steps reach the address. Had the holder row still existed, section 4's gone branch would have carried its blocklist and unsubscribes (`carryConsent`). Fix: in the same transaction, a subscriber taking an address a suppression names gets the withdrawal the suppression stands for, through the normal paths (blocklist path if the suppression records a blocklist, the unsubscribe path for the lists it records or for all marketing as D125 defines it), so marketing enrollments exit as they would after an unsubscribe and consent webhooks fire; transactional mail stays as D125 intends. Read D125, `src/subscribers/suppression.ts` and `removeLeaving` first; record the exact mapping in D194. Tests: a left-then-reused address and a wiped-then-reused address, each through a record and through a send-time lookup (campaign batch): no marketing send, the memberships as D194 says.
2. **Configuration refusals are classified as per-record failures** (major, `readRecipient`). Only `400`/`403`/`404` and a missing mapped field become `SettingsMismatch`. A private-address refusal (`status` undefined), a redirect, a `401` after re-auth, or a record without `id` stay plain permanent errors, so after an instance admin removes a host from `sources.private_hosts` the campaign runner skips every source-linked recipient and finishes the campaign unsent, the stream marks every arriving record terminal and advances past it, and the scheduler ends due steps with `source_error` at once. Fix: classify by exception: only the known per-record failures (the ID format, a single record too large, a malformed body or a non-text address field of that record) stay per-record; every other permanent failure of the view read is a `SettingsMismatch`. Also check the events and users reads for the same split. Tests: a private-address refusal mid-campaign pauses the campaign (nothing skipped, resumes once the host is listed again); the stream does not mark records terminal on it.
3. **A campaign batch keeps a stale recipient when the lookup finds nothing to write** (major, `runner.ts` `fresh()`). `recipients[i]` is refreshed only when the plan writes; when the stream or a sequence step updated the subscriber after the claim, the plan is `unchanged` but the batch still holds the claimed address and name, so `eligible()` sees "changed" and skips the recipient for good, or a name-only change sends the old name. Fix: when the plan is unchanged and present, take `recipients[i]` from the row the plan verified. Test: an update between claim and lookup sends once, to the new address with the new name.
4. **The realtime connect ignores its timeout and stop while DNS stalls** (minor, `realtime.ts` `openRealtime`). It awaits `guardedFetch` directly, while `pocketbase.ts` races it against the signal because the DNS lookup cannot be cancelled; a stalled lookup blocks the connect timeout, a settings switch and shutdown. Fix: race it against the signal as the adapter does and cancel a late response body. Test: a guard whose lookup never answers; stop returns within the connect timeout on the injected clock.
5. **An absent lookup reports "left" when the subscriber's external ID changed meanwhile** (minor, `send-time.ts`). `apply()` for an absent plan only checks the user ID's current row; if the claimed subscriber's `external_id` was cleared or changed during the read, it returns `left`, the runner skips the subscriber and the scheduler leaves the claim until its lease. Fix: when no row has the user ID, a still-existing claimed subscriber means `SubscriberChanged` (in `read()` and `apply()`). Test: change the external ID during the read; the caller reads again and sends once.
6. **`scan()` repeats an identical too-large request** (minor, `pocketbase.ts`). On `tooLarge` it shrinks `size` from the page limit, not from the `perPage` it sent, so with `cap - read < size` (an `exists`, a final page) it re-sends `perPage=1` up to six times, reading up to 192 MiB. Fix: shrink from `perPage` and stop when it was 1. Test: an oversized single matching record in `exists` makes one request before the too-large error.
