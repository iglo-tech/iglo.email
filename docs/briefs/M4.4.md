## Behavior

1. **Settings:** every tab upstream has that maps to a setting here: general, performance, privacy, media, SMTP with test connection, bounces, messengers, security, appearance. The Mailgun signing key, `security.trusted_proxies`, `security.public_rate_limit`, webhook-address blocking and marketing settings added in this project appear with the settings they sit beside. Settings that have no effect here (S3 and the other bounce providers) keep round-tripping and show as unavailable, not editable. A save sends the whole object the way the API expects and does not disturb values the form does not show. A setting that needs a restart says so, as upstream does.
2. **Secrets:** masked secrets stay masked in the page and the API response, and saving the form without touching one keeps the stored value. SMTP test connection uses the form's values without saving them.
3. **Users and roles:** users list, add and edit, with API users and tokens shown once; user roles and list roles with their permission grids. The last admin cannot lock itself out, and the screen shows the API's refusal. A user cannot raise their own permissions through the screen.
4. **Profile:** name, email, password change and the 2FA section from M4.1, with sessions behaving as the API does on a password change.
5. **Permissions:** each route gives `adminPage` the permissions its endpoint needs, and nav filtering is not authorization.
6. **Safety:** values from settings, users and roles are escaped everywhere. Appearance settings hold custom CSS and JS for admin and public pages. Upstream applies them as authored; say exactly who can set them and where they run, and do not widen that. The logo, favicon and root URL fields validate as the API does.
