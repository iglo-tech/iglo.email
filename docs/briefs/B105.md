# B105: Markdown cost model: ordinary campaigns render, pathological input refuses fast

Branch `task/B105-markdown-cost`. PR title "B105: Markdown cost model". Decision record: D112 (lead, 2026-11-19). Read `docs/briefs/_B97-common.md` first. Source: B104 review (PR #156, council comment of round 1). Both defects exist on v1.2.1; v1.3.0 is not tagged until this merges.

## Defects

1. **Ordinary Markdown campaigns are refused** (major). The D54 `reserve()` estimate in `src/templates/markdown.ts` over-reserves: 35 short sections refused at 2,220 B, 48 link bullets at 4,540 B, 8 stories with images and lists at 5,896 B, 22 prose paragraphs at 11,012 B. An 8-story newsletter saves (200), its preview answers 400 "invalid template", a test send 500, and a real send would fail for every subscriber.
2. **Block-level rescans are under-charged.** `patches/marked@15.0.12.patch` charges block tokens one step per KiB of remaining input while marked rescans the remaining input per block token: `"|\n-\n"` × 16 KiB answers 400 after 4,054 ms; five concurrent previews from one `campaigns:get` user block the server 20.5 s; `` "`\n-\n" `` ~1.7 s, `"--\n"` ~1.2 s.
3. **`reflinkSearch` is quadratic and uncharged** (same patch; runs when a link definition exists): 60 KiB of `[a]: /u` plus repeated `\[` from a Liquid loop, 3,288 ms over HTTP.

## Target (D112)

- A realistic newsletter up to 256 KiB of Markdown (headings, paragraphs, lists, links, images, tables, emphasis, code) renders through preview, test send and a real campaign send. Refusal is reserved for output over the 1 MiB output limit or genuinely pathological work.
- Every input up to the campaign body limit answers preview within ~200 ms on this host (measured), either rendering or refusing with the existing Markdown/work-limit 400, and never blocks the server longer; the cost model charges what marked actually scans (characters examined, including rescans), so cost is linear in work done, with no wall-clock deadline (D110).
- Output for ordinary documents stays byte-identical to today's for every document today's code accepts (B104's 33 pinned hashes, plus new larger realistic documents pinned against goldmark-compatible expectations where today refuses).

## Method

1. **Measure first.** A fuzz/benchmark script (extend B104's `test/templates/` helper) over: the B104 families, the reviewer's block shapes, reflink shapes, and a wider alphabet search (at least 6 characters including `|`, `` ` ``, `-`, `\n`, `[`, `]`, `(`, `)`, `*`, `_`, `>`, `#`, space) at 2–64 KiB. Record time and the charged work per input.
2. **Fix the cost model** so charged work tracks actual scanning (block rescans, reflink search, inline), then set the budget so the realistic 256 KiB newsletter passes and every pathological input refuses within the target. Replace the `reserve()` over-estimate with a bound that is still safe for the 4 MiB emission budget (memory), with a test that a document near the output limit is still refused before allocation.
3. **If patching marked cannot meet the target**, evaluate a linear-time alternative and record the evidence in D112: a newer marked (B104 found 17/18 share the block shape), or another CommonMark parser; a dependency change needs output parity on all pinned documents, a decision record and the lead's acceptance in the PR, so stop and report before switching.

## Tests (first, through HTTP)

Ordinary newsletters of 4, 16, 64, 256 KiB render in preview, test send (sink) and a campaign send to two subscribers; each reviewer shape and every family found in step 1 at 64 KiB answers within 1 s (generous real-time upper bound) and five concurrent such previews leave a concurrent `GET /api/health`-style request answering within 1 s, measured from **before** the previews start (B104's concurrency assertion could not fail; do not repeat that).
