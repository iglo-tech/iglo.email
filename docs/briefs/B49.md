# B49: Media cache-budget test broken by B42's drive bound

Common rules: [_state-common.md](_state-common.md). Branch `task/B49-media-drive`. Lines from main at the commit that queued this brief.

## Source

`test/media/media.test.ts:272`, "attachments over the cache budget are evicted and read again for the next batch", fails 3 of 3 in isolation on `main` and intermittently in `bun run check` (#95 r1, confirmed by the reviewer). The reviewer saw "wall 11 ms" in the failure, so the wait loop ended before any real time passed.

## Lead finding (verify first)

This is very likely a regression from B42 (#94, ead051f). B42 cut `drive` in `test/campaigns/runner/fixture.ts` from 20,000 to 2,000 iterations. Each iteration yields with `Bun.sleep(0)` three times and advances the injected clock. This test reads 8 MiB attachment files from disk (real I/O, not driven by the injected clock). It needed many zero-length yields before the reads completed, and 2,000 iterations × `sleep(0)` takes only milliseconds of wall time. Confirm the cause:
- run the test at `ead051f^` (before B42) and at `main`;
- or temporarily set the limit back to 20,000 and run it. Revert that afterwards.

## Fix (lead decision, adjust if the evidence says otherwise)

Keep B42's goal: a stuck wait fails fast with its state, not at the test timeout. The bound should cover real I/O, not a count of zero-length yields. Options, in order of preference:
1. Bound `drive` by wall time plus a generous iteration cap: for example, fail after 10 s of wall time or 20,000 iterations, whichever comes first, and keep the diagnostic error. While real I/O is pending, let real time pass. For example, after N consecutive iterations with no progress, yield with a short real `Bun.sleep(1)`, so file reads can complete.
2. Or wait for the specific I/O-bound condition in this test with a helper that awaits the file read (public boundary), and keep `drive` as it is.

Whatever you choose:
- no plain timeout bump with no diagnostic;
- the B42 regression test ("a wait that never completes fails with the stuck state") must still pass and still fail fast, well under the 30 s test timeout;
- the runner tests must not get noticeably slower: measure `test/campaigns/runner/runner.test.ts` time before and after.

Also check `test/messaging/send-rate.test.ts`, which keeps its own 20,000-iteration loop (B42 note), and any other `drive`-style loop that waits on real I/O. Report them, and fix them only if they share the same bug.
