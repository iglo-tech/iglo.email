## Behavior

1. **Screens:** subscribers list with search, list filter, advanced SQL query, paging, sorting, row and all-matching selection, bulk blocklist, delete, list add/remove/unsubscribe; the subscriber add and edit form with attributes, list memberships, bounces and export of a subscriber where the API supports it; lists index, the list add and edit form with type, opt-in, tags, description, and the list's analytics links. Match upstream's v7 appearance, wording, i18n keys and `data-testid` values so the specs adapt with little change.
2. **Permissions:** each route gives `adminPage` the permissions its endpoint needs, following the M4.1 notes: nav filtering is not authorization. List-scoped roles see only their lists. Controls a user cannot use are hidden or disabled as upstream does; the API remains the guard.
3. **Safety:** subscriber names, attributes, list names, tags and descriptions are escaped everywhere, including Alpine bindings, attribute values and JSON bootstraps. Destructive actions confirm first. API errors, such as a 400 over the delivery budget (D61), appear as a message.
4. **Scale:** list and subscriber pages stay responsive at 1,000,000 subscribers using the API's paging; no view fetches all rows. `GET /api/lists` blocks about 1.3 s at that size with `app.cache_slow_queries` off: note what the screens do and whether the screen should avoid it.
