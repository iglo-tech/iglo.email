## Behavior

1. **Backup:** `iglo.email backup [--output <path>]` writes a consistent snapshot with `VACUUM INTO` while the server runs, in a separate process, and includes `uploads` as a set the guide can restore. It exits nonzero and leaves no partial file on failure: write to a temporary name in the destination, sync, rename. It refuses to overwrite an existing backup unless told. D15 says one server process per data directory: a backup process is a reader, so say how it opens the database and why that is safe with a running server. Say what happens to checkpoints and disk while a snapshot runs, and check free space first where that is cheap.
2. **What a backup holds:** the database has secrets, tokens and personal data. The file is created with mode 0600 and the guide says so. Media files that exist only on disk are covered, and a crash-orphaned file is harmless.
3. **Restore:** a documented procedure, and a `backup` verification step (`--verify` or a `restore-check` of a file) that opens the snapshot read-only, runs `PRAGMA integrity_check`, and reports the schema version. Restoring into a newer executable runs migrations, and an older executable refuses it. Test both.
4. **Consistency with media:** a snapshot taken while uploads happen can name a file the copied set lacks or the reverse. Choose an order and state the outcome. A row without a file behaves as a missing attachment does.
5. **Operations guide,** `docs/operations.md`: install, data directory, environment variables, reverse proxy with `security.trusted_proxies` (D60), TLS, SMTP and DKIM, Mailgun webhook setup with its signing key, the `uploads` rules (D64), backups and restore with a nightly schedule, upgrades, monitoring `/health`, logs and where full errors go, sizes and capacity from `docs/perf`, and the defaults for every question in 10-open-questions.md. State clearly what is unverified: real Mailgun events, and anything else the status file lists. Commands in the guide must be ones you ran.

## Acceptance

Tests take snapshots through the compiled executable in temporary directories. Then, serially on this host: `bun install --frozen-lockfile`, `bun run check`, `bun test test/backup test/db`, `bun run contract:normal`.

- A backup taken while a compiled server is under write load restores, opens, passes `integrity_check`, and the restored server answers `/health` and shows committed data.
- Killing the backup process midway leaves no file that looks complete.
- Record snapshot duration, write-lock effect and disk use at 1,000,000 subscribers in docs/perf/M6.2-backup.md. Check `free -h` and `df -h /` first and remove the data afterwards.

`bun run check` should be clean; treat any failure as real. Report first failures and explain reruns. If a test fails intermittently, capture its name.
