## Behavior

1. **Sequence list:** each sequence with active, completed and exited enrollments, and sent, skipped, opened and clicked per step. Counts must not make the list slow at scale: use a bounded query, and run a heavy read through the analytics reader or a summary rather than on the server thread.
2. **Editor:** trigger, exit events, reentry, list, and steps as cards with wait, kind, template and condition. Conditions use the CodeMirror JSON editor with the API's validation messages and examples. Saving goes through the existing API, keeps fields the form does not show, and shows a refusal as a message. Raw SQL conditions stay permission-gated, as the API has them. Editing a sequence with live enrollments behaves as 05 says, and the screen says what will happen.
3. **Enrollment explorer:** filter by sequence, subscriber, status and exit reason, with paging, and each enrollment's timeline of trigger event, step decisions and sends. Manual enroll and cancel use the API.
4. **Subscriber page:** tabs for events, enrollments and sends for that person, on the M4.2 subscriber screen, scoped by the viewer's list permissions.
5. **Test mode:** enroll a test subscriber with every wait shortened to 1 minute, as 05 says. It runs through the real scheduler and sends for real to that subscriber, with a clear label. It must not change the sequence definition or other enrollments, and it can't reach a person who has not consented: check the same rules a normal enrollment passes. A test enrollment is marked as such in the explorer and the counts leave it out, or say where it is included. Add what the scheduler needs behind a single owner function. Time is on the injected clock in tests.
6. **Permissions:** every route gives `adminPage` the permissions its endpoint needs. Nav filtering is not authorization.
7. **Safety:** event payloads, step decisions, attribute values, sequence and template names render as text everywhere, including JSON displays. Template previews use the sandboxed frame from M4.3 and no authored HTML runs in the admin page.

## Acceptance

Tests use the injected clock and the SMTP sink. Then, serially on this host: `bun install --frozen-lockfile`, `bun run assets:build`, `bun test test/jsx test/ui test/admin test/sequences`, `bun run ui:verify`, `bun run check`, `bun run contract:sequences` if it exists, `bun run contract:normal`, `bun run worked-example`, and `bun run e2e` in the background with a wait.

- Test mode runs a sequence with 1-minute waits through the compiled executable to the sink, and a browser spec watches it advance on the timeline.
- A hostile event payload, attribute and sequence name render as text, covered by a test.
- Each screen is checked once with `agent-browser`, described in words in the PR body. Close it when done.
