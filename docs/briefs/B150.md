# B150: external sources, PocketBase first (five tasks)

Owner direction 2026-11-25 (relayed by another agent): sequences read user activity from a project's PocketBase instead of pushed events. Spec: [15-external-sources.md](../design/15-external-sources.md); umbrella decision [D169](../design/09-decisions.md#d169-external-sources-pocketbase-first-owner-2026-11-25). Target: the next 2.x minor (2.1.0), after B149. Read [`_B97-common.md`](_B97-common.md) first (this host, file rules; decision records go in as "(B150x, lead, <date>)" with the number below). Keep any adopter or product name out of code, docs, commits and PRs. Each task: one worker, branch `task/B150<x>-<name>`, base `origin/main`, PR title "B150<x>: <title>". Each task adds an "As built (B150x)" note to the spec section it implements and updates `05-sequences.md`, `07-api-and-ui.md` and the OpenAPI document for anything it changes there.

**Order.** B150a first. Then B150b and B150c in parallel (D133). Then B150d (needs both), then B150e. Then the 2.1.0 release.

**Shared rules.** No network call inside a SQLite transaction. Every loop and timer takes the injected clock. Marketing sends stay at-most-once. No new runtime dependency (the SSE client is `fetch`-based). Tests run against the real PocketBase 0.40.5 binary through the harness B150a adds; no protocol mocks except to force a transport error the binary cannot produce (say which). Do not edit a file another B150 task owns; stop and report it in the PR. Every acceptance includes `bun run check` once (junit captured) and every `contract:*` script whose corpus covers a route or page the task changes (grep the corpus) with its `:reference` variant; whenever `src/messaging/**`, the campaign runner or the scheduler's send path changes, every `sends:*` script.

## B150a: source settings, adapter and test harness (D170)

Owns `src/sources/**` (new: the `ExternalSource` interface, the PocketBase adapter, filter-literal escaping and date formatting), the `source.*` project settings keys and their validation (project keys, 14-projects section 4) and the settings admin view section for them, the `first_name` Liquid filter in `src/templates/**`, `test/sources/**`, the PocketBase test harness, D170.

1. Spec sections 1, 2 and 7 ("Names"). Settings with masked secrets, a "Test connection" action (auth, read one recipient-view page and one events page, report what is missing), `grant_lists` rules stored and validated (lists of this project).
2. The adapter: auth with the service account, token refresh before expiry, one re-auth on 401; `recipient`, `record`, `latest`, `count(upTo)`, `exists`, `scan` (keyset on `(occurredAt, id)`, `perPage` ≤ 1000, `skipTotal=1`); error classification (transient vs permanent); timeouts and `AbortSignal`; bounded response size. `subscribe`/`catchUp` are B150b's.
3. The source URL goes through `webhooks.block_private_addresses` (D122) at every connection, as webhook delivery does; reuse `src/webhooks/address.ts` by calling it, not by copying it. Add the instance key `sources.private_hosts` (spec section 2, D169 amended): exact case-insensitive host names, at most 20, instance settings page and `/api/instance/settings` only; a listed host may resolve to a private address while the block is on, every other host and every webhook target stay blocked. Tests: a listed host on loopback connects with the block on; an unlisted host is refused; a webhook to the listed host is still refused; a project-host `PUT /api/settings` naming the key is a 400.
4. Harness: download PocketBase 0.40.5 linux-x64 (and arm64 for the arm64 CI job) from the official release, verify a pinned SHA-256, cache under `node_modules/.cache/`, start it per test on a free port in a temp dir with a fixture schema (events collection, a users auth collection with a leaving field, a recipients view, a `services` auth collection), and a helper to create records. Document it in `test/sources/README.md`; add the download to `.github/workflows/ci.yml`.
5. Tests: every adapter operation against the binary, including the paging cap, `skipTotal`, escaping of hostile literals (quotes, backslashes, `&&`, unicode), 401 refresh, a stopped server (transient), a renamed field (permanent), the private-address refusal, and `first_name` (first word, letter start, no `@`, ≤ 24 characters, else empty).

Acceptance: `bun run check`; `contract:settings` and `:reference`; `contract:openapi`; `contract:projects`; `bun test test/sources`; an `agent-browser` pass over the source settings section and Test connection against a running PocketBase.

## B150b: realtime stream, catch-up and retry queue (D171)

Owns `src/sources/stream*.ts`, `src/sources/realtime*.ts`, the stream tables (markers, dedupe, retry queue) and their migration, the stream's attention lines, `test/sources/stream*`, D171. Needs B150a merged.

1. Spec section 4 except what a record does: the `fetch` SSE client (`PB_CONNECT`, `POST /api/realtime`, token refresh, reconnect with backoff, the 5-minute idle and 30-minute forced close, and a reset at any point treated as routine with no attention line; attention only after 15 minutes of failed connects or a permanent auth/subscription refusal, spec section 4), topics from the union of active triggers, active-or-paused `exit_on` and `grant_lists` names (read through `src/sequences` store functions; add narrow read functions there only if missing and list them), split past 2,500 characters, re-subscribe on a sequence or rule change; the users topic.
2. Subscribe-then-catch-up with the 15 s lookback, `created,id` keyset pages, buffer and drain, dedupe, marker advanced only after a committed batch, pruning relative to the marker, a new source starting at "now".
3. The per-record retry queue (attempts, next attempt on the injected clock, terminal state in attention) that never blocks the stream.
4. Records go to a `RecordHandler` interface (`event(record)`, `userLeft(record)`) that B150d implements; here a test handler records calls and can fail transiently or permanently. The handler contract: it does its source reads, then one write transaction that must include the dedupe entry the stream gives it.
5. Tests against the binary: live delivery, a disconnect with records created meanwhile (none lost, none twice), out-of-order commits inside the lookback, forced 30-minute close (injected clock or a short PocketBase setting, say which), a connection reset mid-stream and mid-catch-up (a small test proxy that cuts the stream; no attention line written), 15 minutes of refused connects writing one attention line, topic split and re-subscribe, retry and terminal failure, restart resuming from the marker, a new source ignoring history. Measure catch-up throughput and memory over 100,000 records (disk vs tmpfs recorded) into `docs/perf/B150b-stream.md`.

Acceptance: `bun run check`; `bun test test/sources`; `contract:projects`.

## B150c: sequences and conditions on a source (D172)

Owns `src/conditions/**`, `src/sequences/**`, the scheduler's sequence-step evaluation path, the enrollment columns and their migration, `src/events/aggregate.ts` only to share `AGGREGATE_LIMIT` and the strict comparison, the sequence admin UI, `test/conditions/**`, `test/sequences/**`, D172. Needs B150a merged; runs alongside B150b.

1. Spec section 6: `"source"` on sequences (validation, refusal without a configured source, `sql` refused, the `trigger.where` condition form refused and `trigger.condition` accepted only on external sequences); conditions and aggregates compiled to PocketBase filters with the strict re-check; the `recipient` condition kind; async evaluation.
2. Enrollment `trigger_external_id`, `trigger_occurred_at`, `error_since`; `since: trigger`, reschedule and windows on `trigger_occurred_at`; `trigger.data`, step preview and the timeline fetching the record; `trigger_missing`; preview, test sends and manual/test enrollments taking a string `trigger_external_id` with `latest()` as the default.
3. `trigger.condition` evaluation as a function B150d calls before its write transaction: `(source, userId, record) → true | false | transient error | permanent error`, `since` counted back from the record's `occurredAt`, counts including the trigger.
4. Failures: transient retried with the scheduler's backoff for at most 72 hours, permanent failing fast, terminal `source_error` exit shown in the sequence UI and attention; never advancing past an unevaluated condition.
5. Tests against the binary: every condition and aggregate form, the loose-JSON cases of spec section 9 each re-checked strictly (a mutant dropping the re-check must fail), date-window edges (strictly after), the `AGGREGATE_LIMIT` cap, hostile `where` values, `trigger.condition` with the trigger counted, `trigger_missing`, 72-hour transient then `source_error`, a 400 failing fast. Measure one condition and ten aggregates at the limit against the binary into `docs/perf/B150c-conditions.md`.

Acceptance: `bun run check`; `contract:sequences` and `:reference` if present, `contract:openapi`, `contract:projects`, and every corpus covering `/api/sequences` or the sequence pages; `E2E_WORKERS=2 bun run e2e`; an `agent-browser` pass over an external sequence's editor, preview and timeline.

## B150d: records into subscribers, consent and leaving (D173)

Owns the `RecordHandler` implementation (`src/sources/records*.ts`), narrow functions in `src/subscribers/**` for the existing `external_id` and the conflict paths (list each), the grant and conflict paths it adds, `test/sources/records*`, D173. Needs B150b and B150c merged.

1. Spec sections 3–5 for a record: source reads first (`trigger.condition` through B150c, the recipient lookup), then one transaction: subscriber upsert keyed on the existing `external_id`, with the name, `grant_lists` with every refusal of section 5, exit-then-trigger with `occurredAt` and the trigger reference, the dedupe entry.
2. Address conflicts exactly as section 4 lists, including the carried blocklist through the normal blocklist path and the two-live-users terminal conflict.
3. Leaving in real time: a users record matching the filter ends enrollments and removes the subscriber.
4. Tests against the binary through the running stream: an unsubscribed event name creates nothing; a grant refused for each reason; a zero-wait marketing step sees the grant; every conflict branch; a user leaving; a record whose recipient is absent; a transient failure going to the retry queue with nothing written. Mutants: grant over an unsubscribe; conflict re-point losing the blocklist; network read inside the transaction (a test proving the transaction is short is enough).

Acceptance: `bun run check`; `contract:subscribers`, `contract:lists`, `contract:sequences` and their `:reference` variants where present; `contract:projects`; every `sends:*`.
