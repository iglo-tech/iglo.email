1. **A confirmed-absent holder's withdrawal is not kept as a suppression** (major, `recipient-sync.ts` `conflictOf`/`applyRecipient`). When an address holder with a source `external_id` is confirmed absent from the recipients view, the conflict is `gone`, the same as an unlinked holder. Neither branch does what `leaveUser`/`removeLeaving` does for a leaving user: the carry branch calls `carryConsent` and `remove`, the re-point branch overwrites the holder's `external_id`; neither writes the D125 suppression of a user who withdrew consent. So the outcome depends on which path sees the leaving first: if the users stream handled it, B166's `took()` withdraws all lists from the row taking the address; if a gone-conflict handles it, only the carried lists are withdrawn, other marketing continues to that address, and the leaver's user ID is never suppressed, so a returning leaver is re-granted marketing. Fix: mark a gone holder that was a source user confirmed absent (`left`), as distinct from one with no or a non-source `external_id`; for `left`, write the same suppression `removeLeaving` writes (only when that user withdrew consent, as `removeLeaving` decides) before the carry's delete or the re-point's overwrite, so `took()` and the re-point's suppression check apply the withdrawal in the same transaction. Unlinked holders keep today's behavior. Tests: the carry and the re-point scenarios each end with the same consent outcome as when the users stream handled the leave first; a returning leaver is not re-granted.
2. **Test connection's probes accept a non-list or too-large 200 and read whole records** (minor, `pocketbase.ts` `probe()`/`guestProbe()`, `check.ts`). Unlike `list()`, `one()`'s collection probe and `eventsSchema()`, they omit `fields=id`, do not go through `notRecord`, and do not check the body is a list or not too large, so a proxy's `200 {}` reports every step ok, a first record nested past 64 levels fails the check on a valid collection, and a first record over 32 MiB reports "no records yet". Fix: `fields=id`, `notRecord`, and the list and too-large checks on a 200, in both probes. Tests: a proxy `200 {}` fails the check; a deep first record no longer fails it.
3. **Test connection does not check the users collection has `updated`** (minor, `check.ts`). The stream sorts and bounds users by `updated`; a users collection without it passes Test connection and then refuses every catch-up. Fix: the users step probes `updated` as the events step probes `created`, naming the missing field. Test: a users collection without `updated` fails the step by name.
