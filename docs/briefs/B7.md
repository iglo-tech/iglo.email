## Behavior

1. **Analytics egress budget:** a process-wide limit on bytes held for analytics responses not yet written (D62 says these are the one buffer the slots do not count). Many slow clients downloading near-cap reports cannot grow memory without bound. Over the budget a new read gets a clear 429 or 503 before it starts, never a partial body. Normal dashboard and report results stay unchanged.
2. **WAL under continuous polling:** analytics or report polling with no gap must not grow the WAL without bound. Pick the smallest mechanism that bounds it (for example a forced gap or a checkpoint window between helper snapshots, or snapshot reuse) and measure WAL size under continuous polling before and after. Update D62's WAL paragraph and operations.md.
3. **M1.7 disk-backed staging:** selections far above 100k IDs no longer need about 3.9 MiB in the parent per 100k IDs. Stage them on disk (a temp table or file the helper writes and the parent streams in bounded batches), with cleanup on success, failure, kill and restart. Results of bulk actions over a query selection (listmonk's query-based bulk endpoints) are unchanged.
4. **Event latency:** try shared write batching across loops so event p95 under full mixed load drops from 51 ms. Keep D22 durability unchanged: no owner decision is available, so do not weaken commit guarantees. If no change helps without that, record the measurement and reasoning in docs/perf and leave the line in the backlog with the evidence.
