## Behavior

1. Find the subscriber by `external_id`, then by `email`. Create one (`enabled`, no lists) only when it isn't found and `email` is given; otherwise return a safe 4xx. `attribs` merge at the top level, with `null` removing a key. `email` on a subscriber found by `external_id` updates the address. Conflicts are a safe 409 with no partial write, for example a new email that belongs to another subscriber, or `external_id` and `email` naming different subscribers. Blocklisted subscribers still get their events recorded.
2. A repeated `idempotency_key` for the same subscriber returns the first result and changes nothing, including the subscriber upsert and attribs. This holds under concurrent requests and after a restart.
3. `occurred_at` defaults to the receive time from the injected clock. Events older than 7 days are stored and flagged as not eligible to start sequences.
4. Processing happens in one short transaction. Sequences don't exist yet (M5.3), so leave one clearly named seam for "exit, then trigger" inside that transaction that returns empty enrollment lists for now. The response is the event ID, the subscriber ID and `{started: [], ended: []}`.
5. `/batch` takes up to 500 events with bounded total body size. State the atomicity choice in the PR (all-or-nothing, or per-item results) and test it. Prefer per-item results, so one bad event doesn't drop the others, as long as each item stays atomic.
6. Retention: a maintenance loop with an injected clock purges events older than the configured retention (default 400 days) in bounded batches, so it never holds a long write transaction.
