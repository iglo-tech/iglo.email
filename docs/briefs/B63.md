## What to do

Write `docs/design/13-e2e-coverage.md`:

1. **Journey inventory.** List every user-facing journey the app offers:
   - **Admin screens:** every view in `src/admin/views/` and its actions (create, edit, delete, bulk actions, filters, pagination, search, preview, test send, every tab).
   - **Public pages:** `src/public/` — subscription form, double opt-in confirmation, unsubscribe (link and List-Unsubscribe one-click), preferences, archive, message pages, CAPTCHA.
   - **End-to-end mail flows,** observed in the SMTP sink:
     - campaign send, including schedule, pause, resume and cancel;
     - open and click tracking reaching analytics;
     - transactional `POST /api/tx`;
     - sequence enrollment through the steps (injected clock, or whatever the e2e harness allows; check `test/e2e/helpers.js`);
     - opt-in mails, admin notifications (B38), bounces via the SES SNS webhook, webhooks to a local receiver.
   - **Operations visible in the browser:** first-run setup (fresh instance), login, 2FA, password reset, roles and permission limits per screen, restore hold banner (D67), maintenance, logs.
   - **MCP:** API only, already covered by `test/mcp`. Note it and do not plan browser tests for it.
2. **Coverage matrix.** For each journey, give the spec file and test names that cover it (`file:line`), and mark it **covered**, **partial** (say what is missing) or **none**. Base this on reading the tests, not their names.
3. **Gap plan.** Split the partial and none journeys into 4–8 implementation tasks of a similar size (about 10–25 tests each). For each task give:
   - the journeys it covers;
   - the spec file(s) to add or extend;
   - the fixtures it needs (SMTP sink, webhook receiver, a fresh instance, clock control);
   - any harness gap. Example: if the e2e stack cannot advance a clock for sequences or schedules, say what the smallest harness addition would be, and whether a test-only switch exists already in the compiled test shell. Do not invent production test hooks.

   Put the release-critical journeys first: sending, unsubscribe and consent, data safety.
4. **Release gate.** Say how long the full `bun run e2e` takes now (`docs/perf/e2e-speed.md`, or `dist/e2e-results/timings.json` if present), and recommend whether a 1.0.0 tag should require it. For example, an `e2e` job in `release.yml` before `publish`. Do not edit the workflow.
