## What to do

1. **Measure.** Use `bun run perf:mixed` (the M6.1 mixed load, as in `docs/perf/B11-event-latency.md` section 2). Run at least 3 FULL and 3 NORMAL runs, alternating (F N F N F N), each from a fresh data directory, with the pragma change applied only for the NORMAL runs and reverted afterwards. Record per run: event p50/p95/max, tx accept p95, tx delivery p50/p95, outbox throughput, 1-minute load before and after, and the source/executable hashes of each variant.
   - Hold both `flock ~/.local/state/iglo-email-cos/measurement.lock` and `flock ~/.local/state/iglo-email-cos/verify.lock` for the whole series.
   - "Quiet host": 1-minute load below 2 at the start of each run (other projects run suites on this host). If it is above 2, do not loop or sleep-poll: record the run as disturbed, and if fewer than 3 clean pairs result, finish with the partial evidence and say "needs another quiet-host series" so the lead can re-dispatch.
2. **Analyze safety before speed.** Under WAL, `synchronous = NORMAL` can lose the most recent commits on power loss or OS crash (not on a process crash). Work out for each writer what a lost commit means:
   - outbox/campaign claim (`sending`) lost → the row looks `queued` again after reboot → possible **second send of a marketing email**, which breaks at-most-once;
   - an outcome lost → a sent message recorded as still in flight;
   - an accepted subscriber event or tx send lost after a 2xx reply.
     Check whether a per-connection setting (a separate events connection at NORMAL while claims stay FULL) would actually keep the claim guarantees. In WAL, a later FULL commit syncs the earlier NORMAL frames too; check the SQLite docs for what an earlier NORMAL commit risks before that FULL commit.
3. **Decide and log D86.** Choose one: keep FULL everywhere; NORMAL only where a lost commit cannot cause a second send or a lost 2xx-acknowledged write; or NORMAL everywhere. At-most-once marketing sends are non-negotiable (AGENTS.md). A latency gain alone does not justify losing an acknowledged write. Update D22/D77 so neither says "Open (owner)". If the decision changes code, test it (a test that the claim path's connection is FULL) and include a before/after measurement.
4. Update the backlog line in `docs/status.md` with the result, or remove it.

Acceptance: `bun run check` if any code changes; the measurement series otherwise.
