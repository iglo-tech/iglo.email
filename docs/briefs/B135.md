# B135: Liquid authoring works the way template authors expect

Branch `task/B135-liquid-authoring`. PR title "B135: Liquid filters, object loops, date formats and plain-text fixes". Decision record: D134 (lead, 2026-11-22), appended at the END of `09-decisions.md`. Read `docs/briefs/_B97-common.md` first, then D9, D23, D54, D102 and D110 (the Liquid boundary and budgets) and `docs/design/06-templates.md`. Source: the adopter's differential runs on B134e and B134f (status item 1g); every item is pre-existing on main.

Filters are an allow-list by design (D23): `src/templates/renderer.ts` unregisters every LiquidJS default and registers reviewed, bounded-cost filters only. Keep that: each filter added here is reviewed for cost, charged to the existing D54 budgets where its output or work can grow, and covered by the budget tests the existing filters have.

## Items (lead decisions)

1. **`size`** (O(1)): the length of a string (in characters, as LiquidJS does), array or plain object (number of own keys); 0 for nil.
2. **`json`**: JSON text of the value, charged to the per-message emission budget before it is built (bounded by the D54 input size, so no unbounded work), with the plain-data boundary of D23 (no class instances or accessors reach it). Escaping follows the output context as every other value does.
3. **Common string filters**, each bounded and charged like `upcase` today: `downcase`, `capitalize`, `prepend`, `append`, `replace` and `replace_first` (literal strings, no regex), `split` (literal separator) and `join`, `slice` (string or array), `truncate` and `truncatewords`, `strip_html`, `escape` where the renderer does not already escape (check before adding). Anything else stays out; `template_reference` lists exactly the supported filters and tags, and the save-time error for an unknown filter names the filter and points to `template_reference`.
4. **Object iteration:** `{% for kv in data.obj %}` saves today and every send fails with 400 "invalid template". Make it work as LiquidJS does for plain objects (each item a `[key, value]` pair, `kv[0]`/`kv[1]`, `forloop` intact), within the D23 plain-data boundary and the D54 range/work limits. If that cannot be done inside the boundary, refuse it at save with a message that says so; never accept at save what fails at send. Add a save-time check that renders the template against a representative sample the way send does, if one is not already there, so this class cannot recur.
5. **`date` format `%%`:** the format check `/%(?![%YmdHMS])/` matches the second `%` of `%%`, so `"100%% %Y"` fails at send. Parse the format left to right so `%%` is a literal percent.
6. **`date` on impossible dates:** 2026-02-30 rolls over to 03-02 today. Treat an impossible calendar date as invalid input (the filter returns its input unchanged, or renders empty — follow what the filter does today for an unparseable value, and say which in 06).
7. **Large numbers in transactional `data`:** values above 2^53 lose precision when printed. Do not change JSON parsing; document it in 06 and `template_reference` as a JSON-number limit (send such ids as strings).
8. **HTML→text converter** (`src/messaging` plain converter, B120): decode `&notin;` and upper-case `&AMP;` (check the named-entity table for other gaps against the HTML spec's list, at least the common ones), and render `<ol>` items and Markdown `1.` lists as `1.`, `2.`, … instead of `- ` bullets (nested lists keep their indentation; `start` attribute honoured if cheap). Keep the converter linear (its ratio tests stay green).

## Tests

Per filter: output, nil and empty input, the budget charge (a filter that would exceed the emission or work budget is refused like the existing ones), and the escaping context. Object loop: keys and values, nested objects, an empty object, `forloop`, and the range limit. Save-time: a template that would fail at send is refused at save with a clear message. `date`: `%%`, an impossible date, existing formats unchanged. Converter: the entities, ordered lists (nested, `start`), Markdown ordered lists. `template_reference` lists exactly what the renderer registers (a test compares the two).
