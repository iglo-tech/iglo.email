# B104: Markdown rendering is super-linear on link syntax (server-blocking)

Branch `task/B104-markdown-time`. PR title "B104: bound Markdown link scanning". Decision record: D111 (lead, 2026-11-19). Read `docs/briefs/_B97-common.md` first. Source: B103 review (PR #155, comment by the council reviewer), reproduced on origin/main; not a regression.

## Defect

A user with only `campaigns:get` sends `POST /api/campaigns/:id/preview` with `content_type=markdown` and a body of `"[]("` repeated to 8 KiB: the request answers 400 after 38.6 s and blocks the whole server thread meanwhile (a concurrent GET waited 38.6 s). Direct renderer timings: 4 KiB 6 s, 8 KiB 44 s, 16 KiB 122 s (cubic), inside marked 15.0.12's lexer, reached from `src/templates/markdown.ts:85` (`Lexer.lex`) and `src/campaigns/content.ts:27` (content conversion). The same lexer serves every Markdown body: campaign preview and send, test sends, archive, content conversion, MCP `preview_campaign` / `convert_campaign_content`, tx/sequence templates if Markdown applies. The D54 work budget does not see this scanning.

## Task

1. **Find every super-linear path** in marked's inline tokenizer reachable from our options (links and reference links, images, emphasis delimiters `*`/`_` runs, autolinks, inline code backticks, HTML tags, nested brackets) with a small fuzz/benchmark script over pathological families (repeat each 1–64 KiB; record time per size). Store the script under `test/templates/` as a measurement helper, not a CI test.
2. **Fix so render time is linear (or bounded by the work budget) in input size**, with no wall-clock deadline (D110: host load must never fail a render). Preferred: extend the existing pinned patch (`patches/marked@15.0.12.patch`, already forwarding the budget to the lexer) so the scanning loops that rescan charge `budget.step` per character examined, making pathological input hit `Work limit` quickly; or replace the specific regex/loop with a linear one in the patch. Check whether a newer marked release already fixed this upstream; upgrading is allowed only if output for our existing tests and archived content is byte-identical, and is then recorded in D111 (runtime dependency version change, no new dependency).
3. Normal Markdown must render exactly as before (existing template/campaign tests unchanged); only pathological input changes, to a fast refusal (the existing Markdown/work-limit error, 400 on preview) or a fast render.

## Tests (first)

Through HTTP: the reviewer's request (8 KiB of `"[]("`) answers within 1 s, and a concurrent GET is not delayed beyond 1 s; the same for each pathological family found in item 1 at 64 KiB. Use real time only as an upper bound with large margin (these are 40 s+ today), and keep the request sizes so the test is fast on CI.
