## What to do

1. **Honest baseline first.** The concurrent modes of `test/tx/measure-memory.ts` still build every body before the baseline (`:89`, `:101`), which inflates their growth (B27 saw the serial row fall from ~260 to ~200 MiB when bodies were built at send time). Make the concurrent modes build each body inside its own request task, then re-measure the 40 × 4 MiB gated row 3 times. If it is already under 256 MiB, record that, update D87, and stop after item 4.
2. **Find the remaining copies.** Per send, list every live copy of the attachment bytes between request parse and SMTP answer: the decoded copy per recipient from `decodePayload` (`sends.ts:264-267`), the journal's base64 string, the encoded MIME the SMTP library builds, the outbox batch's `Claimed.message`. Check with heap snapshots or `Bun.gc(true)` + RSS sampling which of these overlap in time.
3. **Cut what is cheap and safe.** Examples: drop the request's parsed form and file references before the journal write; let recipients share one decoded buffer; release `Claimed.message` once its push settles. Do not change wire or stored formats, at-most-once behaviour, the no-network-in-transaction rule, or D78 fairness. If a copy cannot go cheaply, lower `MAX_ATTACHMENT_SENDS` or the budget so the measured gated burst stays under 256 MiB. The largest legal single send must still get 2xx on an idle server (existing test).
4. **Log** before/after (3 runs each, host load and hashes) and the decision in D87.

Hold `flock ~/.local/state/iglo-email-cos/measurement.lock` for measurements and the verify lock for full suites. Acceptance: `bun run check`, `bun test test/tx`, `bun run contract:normal`.
