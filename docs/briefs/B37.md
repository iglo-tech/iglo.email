# B37: One shared send-rate cap for SES

Common rules: [_state-common.md](_state-common.md). Branch `task/B37-send-rate`. Lines from main at the commit that queued B37.

## Source

B36 audit ([12-completeness-audit.md](../design/12-completeness-audit.md), #88). SES enforces one account-wide maximum send rate (messages per second, across every connection). Today only campaigns are paced: `app.message_rate` per worker × `app.concurrency` workers, plus the optional sliding window (`src/campaigns/runner/runner.ts:32-38, 472-540`, D59). Transactional and sequence sends from the outbox (`src/messaging/outbox.ts`, batch claims at :80-103 with parallel SMTP on the pool) are not paced at all, and nothing counts campaign and outbox sends together. When SES throttles (SMTP `454 Throttling failure: Maximum sending rate exceeded`):
- a transactional row retries a transient rejection up to 5 times with backoff (`src/messaging/sends.ts:312-316`);
- a marketing row, which includes every sequence step, is at-most-once (AGENTS.md) and is lost as failed;
- a campaign message counts toward `app.max_send_errors`.

## Decision (lead)

- **One new native setting**, `messaging.max_send_rate`: messages per second for the whole process, default `14` (the SES production default; the sandbox is 1/s), `0` = no cap. Validate it as an integer 0–10,000. Show it in Settings > SMTP (or Performance, wherever `app.message_rate` lives) with one help line: "Your SES account's maximum send rate. Every email (campaign, transactional, sequence) waits for it." Add it to `docs/operations.md` in the SES section and to OpenAPI as a native key (check how other native keys such as `bounce.ses_topic_arns` are listed and round-tripped in `src/settings/routes.ts`).
- **One limiter object**, created in `src/main.ts` with the injected clock and passed to whatever performs the SMTP push. First verify whether campaign sends and outbox sends both go through `createEmailer` (`src/messaging/email.ts:330`). If they do, put the wait inside the emailer, just before a message is handed to a pool. Otherwise both callers take the same limiter. No module-level state (AGENTS.md).
- **Algorithm:** a token bucket (or an equivalent sliding one-second window) with capacity = rate. Within any one-second window, no more than `rate` messages start. Waiting uses `clock.sleep` with an abort signal, so shutdown, the restore hold (D67) and tests work with the injected clock.
- **Priority:** outbox sends (transactional and sequence) are served before waiting campaign messages, so a large campaign cannot delay a password-reset mail by more than one token interval. Campaign workers keep their own `app.message_rate` and sliding-window pacing on top. The global cap only ever slows a send; it never makes one faster.
- **A setting change applies to the next wait.** It drops no waiters and loses no tokens.
- **No new retries.** Do not add a retry for marketing or campaign sends (at-most-once). The cap is what prevents the throttle.
- Log D92 in `docs/design/09-decisions.md` (the setting, the priority, and why one cap), and update `docs/design/04-sending.md` (SMTP/Campaigns/Outbox sections).

## Tests (test-first, public boundaries, injected clock, Mailpit or the SMTP test sink)

1. With `messaging.max_send_rate = 5`, a campaign to 50 subscribers plus 20 transactional `POST /api/tx` sends started at the same time: in every one-second window of injected-clock time, the sink receives at most 5 messages. Everything is eventually delivered. Use the existing SMTP sink's receive timestamps or the clock at accept time.
2. Priority: while a campaign to many subscribers is waiting on the cap, a transactional send is accepted by the sink within 1 s of injected time.
3. A sequence step is paced by the same cap (the outbox marketing kind).
4. `0` means no cap: the same load finishes without waiting on the limiter.
5. A settings change takes effect: lowering the rate mid-campaign slows the following sends, and raising it speeds them up.
6. Settings API: GET shows the default `14`, PUT validates (negative, non-integer and too large give 400), and a listmonk-style full PUT without the key keeps it (native key).
7. Shutdown during a wait stops cleanly. No message is sent after stop, and the test does not hang.
