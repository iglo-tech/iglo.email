# B51: New settings items never inherit another item's secret

Common rules: [_state-common.md](_state-common.md). Branch `task/B51-settings-secrets`. Lines from main at the commit that queued this brief.

## Source

Found during the #100 review and rated LOW by the reviewer. `src/settings/validate.ts:239-244`:

```ts
function preserve(item, old) {
  const previous = old.findLast((v) => v.uuid === item.uuid);
  if (!item.uuid) item.uuid = crypto.randomUUID();
  if (!item.password && previous) item.password = previous.password;
  if (!item.password) delete item.password;
}
```

A new item from the settings page has `uuid: ""`, so it matches the last stored item whose uuid is also empty and copies its password. The DKIM fallback at `:279` (`prior`) matches the same way and copies `dkim.private_key`. All three `preserve` callers are affected: SMTP (`:280`), bounce mailboxes (`:300`) and messengers (`:304`).

In the product, only the seeded defaults in `src/settings/defaults.ts` lack uuids: two SMTP items and one bounce mailbox, all with the placeholder `"password"`. So the leak is a placeholder unless a row was hand-written. Upstream listmonk at `6fcd95f` (`cmd/settings.go:206-292`) does the same.

## Fix (lead decision)

A new item never inherits another item's secret. This is a deliberate difference from upstream, with a concrete benefit: no secret silently moves to a different host.

1. `preserve`: look up `previous` only when `item.uuid` is non-empty.
   ```ts
   const previous = item.uuid ? old.findLast((v) => v.uuid === item.uuid) : undefined;
   ```
2. The DKIM `prior` at `:279`: match only when `server.uuid` is non-empty.
3. Give the seeded defaults in `defaults.ts` stable uuids, so a stored-but-never-saved default keeps its secret on the first save, matched by uuid. Check that this doesn't break the listmonk settings contract (`test/contract/settings-binding.ts` and related); if the contract compares defaults, mark the difference.
4. Docs: add a row to the deliberate differences in `docs/design/07-api-and-ui.md` and `src/openapi/differences.ts`: "a new SMTP server, bounce mailbox or messenger never inherits another item's password or DKIM key; upstream copies it from any stored item without a uuid".
5. Contract: mark the case as native in the settings contract suite, as other deliberate differences are marked.

## Tests (public boundaries, test-first)

1. On a fresh fixture, add a new SMTP item with a blank password through `PUT /api/settings`. The masked GET shows no password stored for it. Check through whatever the API exposes (for example, `password` is absent or empty for that item), not by reading the database.
2. The same for a bounce mailbox and a messenger, if they still exist in the settings API.
3. A new SMTP item with a blank DKIM private key does not get another item's key.
4. Saving an existing item (with its uuid) with a blank password keeps its stored password. This is the normal masked-save path and must not regress.
