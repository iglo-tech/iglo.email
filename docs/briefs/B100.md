# B100: the release pre-flight (template)

Every release brief points here and adds only the version, the previous release, the upgrade data and the release notes' sources (D185). B100 was the 1.3.0 release (#154); since B159d (D185) it is the current release gate for this host. Read [`_B97-common.md`](_B97-common.md) (this host, file rules, log capture) and the "Release gate" paragraph of [`chief-of-staff.md`](../chief-of-staff.md) first. This is the release commit: D145's reduced scope does not apply, every step runs.

## What the release brief fills in

- `<V>` the new version, `<P>` the previous release tag (`git describe --tags --abbrev=0 origin/main`), `<NNN>` the task number (containers and the gate directory are named `b<NNN>-…`).
- The changes: `package.json` `"version": "<V>"` and the Docker example tag in `docs/operations.md` (`ghcr.io/iglo-tech/iglo.email:<V>`), made with the Edit tool. README keeps `<version>`. Nothing else, no `docs/status.md`.
- The upgrade data for step 7: what the new migrations touch and how to create it on `<P>`.
- The release notes' sources: the merged PRs and D records since `<P>`.

## Conditions for every step

- Natively on the x86-64 host (D147), as the non-root user, in the foreground, one command per Bash call (timeout 600000 ms; split anything longer), exit codes unmasked. Never trigger CI.
- On `git archive` exports of the one release commit, never the worktree: `exp-a`, `exp-b` (check runs), `exp-c` (pre-flight), each with its own `bun install --frozen-lockfile`.
- `TMPDIR` on disk under `$HOME` for every command (`$G/tmp`). The tests, `mktemp`, the reference harness and Playwright all write to `TMPDIR`; the shared `/tmp` is an 8 GB tmpfs that filled up during four acceptances (#248–#251). Check `df -h "$HOME"` before each step group (keep 20 GB free). A run that fails only on the host's disk being full ("no space left on device", "database or disk is full") is invalid: free space, repeat it, and say so in the PR.
- Every step's output goes to its own file in the gate directory, named in the tables below. Capture follows `_B97-common.md` "Gate and acceptance logs": `tee` into `$G` only, with `pipefail`, and the exit code appended to the same log. Probe scripts are written with the Write tool into `$G/probes/` and run from there, so the reviewer reads exactly what ran.

Each command starts with this prefix (shell state does not persist between Bash calls):

```sh
G=$HOME/b<NNN>-gate; export TMPDIR=$G/tmp; set -o pipefail; cd "$G/exp-c"
```

and has this shape (`<log>` is the file named in the table):

```sh
uptime | tee "$G/logs/<log>"; <command> 2>&1 | tee -a "$G/logs/<log>"; echo "exit $?" | tee -a "$G/logs/<log>"; uptime | tee -a "$G/logs/<log>"
```

Set up once: `mkdir -p "$G"/{tmp,logs,junit,probes}`, then for each export `mkdir "$G/exp-x" && git archive <sha> | tar -x -C "$G/exp-x"`. Log `uname -a`, `nproc`, `df -h "$HOME"`, `bun --version`, `docker version` and the commit SHA to `logs/00-host.log`.

## Steps

Stop at the first failure, report it with its log and junit entry, change no code. A failure is classified under the runbook's rule (the foreign-load rule, the disk-full rule above); killed runs are not counted. A known flake is never rerun silently.

1. **10 valid `bun run check` runs** on `exp-a`/`exp-b`, two at a time while the 1-minute load stays at or under 12. Each run is the `check` chain with junit on the test step: `bun run format:check && bun run lint && bun run typecheck && bun run test --reporter=junit --reporter-outfile="$G/junit/check-NN.xml" && bun run build`. Log `logs/check-NN.log` (load before and after from the `uptime` lines; a 5 s load sampler, if used, writes `logs/check-NN-load.log`). A pair took 535 s at 2.2.0, close to the limit: if a run would exceed it, run its parts as separate commands into the same log and say so.
2. **arm64 build (D148)**, `logs/arm64.log`, from the probe `probes/arm64.sh`: `bun run assets:build`; `bun build --compile --target=bun-linux-arm64 ./src/main.ts --outfile "$G/arm64/iglo.email"`; `file` on it; `docker pull --platform linux/arm64 oven/bun:<packageManager version>` (always with the explicit platform: the local tag may hold the amd64 image) and `docker image inspect -f '{{.Architecture}} {{.Id}}'`; in container `b<NNN>-arm64` under QEMU: `uname -m` = `aarch64`, `--version` = `<V>`, `serve` with `IGLO_EMAIL_PORT=0` and a root URL, then `GET /health` = `{"data":true}`; remove the container and print `docker ps -a --filter name=b<NNN>-` (empty).
3. **`ci.yml` `check` job**, every `run:` step in file order on `exp-c`, `bun run pocketbase:download` before `bun run check`. Logs `logs/ci-NN-<script>.log` (`NN` the order, `:` in a script name as `-`, e.g. `ci-12-sends-batch-crash.log`). The "Configure and probe" step runs only its `bwrap --unshare-user --ro-bind / / --proc /proc --dev /dev /usr/bin/true` line (bubblewrap works as installed; no `apt-get`, no `sysctl`).
4. **`ci.yml` `reference-linux` job**, every `run:` step in order, natively through the user's Docker. Logs `logs/ref-NN-<script>.log`. This includes `sends:crash`, `sends:proofs` and `sends:production`; with `sends:batch-crash` from step 3 that is every `sends:*` script (check against `package.json`).
5. **Not in `ci.yml`:** `bun run scheduler:crash` (`logs/scheduler-crash.log`) until the owner adds it to the `check` job.
6. **`release.yml`**, on `exp-c`:
   - build job: `release:verify`, `bun test/contract/cli.ts owned production`, `release:package`, `test "$(./dist/iglo.email --version)" = "<V>"`, and `sha256sum --check --strict SHA256SUMS` plus `./iglo.email-linux-x64 --version` in `dist/release`. Logs `logs/release-NN-<step>.log`.
   - e2e job: `E2E_WORKERS=2 bun run e2e` takes longer than the 10-minute limit, so it runs as two independent stacks side by side: `bun run build` once in `exp-c` (lane A) and `exp-a` (lane B, between check runs), then rounds of `bun test/e2e/run.ts <spec files>` per lane, each round under the limit. Start from the 2.2.0 split (#255: three rounds, 479 tests) and put new spec files in the lighter lane. Every file in `test/e2e/specs` runs exactly once: list the split in `logs/e2e-split.log` (`ls test/e2e/specs` and each round's files). Logs `logs/e2e-r<N>-<A|B>.log`; report the passed/failed/flaky totals.
   - image smoke, `logs/image-smoke.log`, from `probes/image-smoke.sh` (the workflow's x64 matrix leg): check `dist/release/SHA256SUMS`, place `dist/release/iglo.email-linux-x64` at `dist/docker/amd64/iglo.email`, `docker build --platform linux/amd64 --build-arg REVISION=<sha> -t b<NNN>-smoke:<V> .`, `docker run --rm … --version` = `<V>`, `docker run -d --name b<NNN>-smoke -p 127.0.0.1:<free port>:9000 -e IGLO_EMAIL_ROOT_URL=http://127.0.0.1:<port> …`, `/health` = `{"data":true}` within 60 s, then remove the container and the image and print that none is left.
   - Skipped: the steps that publish, push images or need secrets (`publish`, `image`, the arm64 legs, which D148's step 2 stands in for). List them in the PR.
7. **Slow-runner check (one core):** the timing-sensitive suites the hosted runners failed on (#245) or that failed only on one core (#254): every `test/sources/*.test.ts`, `test/sequences/external.test.ts`, `test/conditions/source.test.ts`, `test/projects/guard.test.ts`, `test/messaging/ses-account.test.ts`, plus any the release brief adds. `taskset -c 0 bun test <files> --rerun-each 10 --reporter=junit --reporter-outfile="$G/junit/slow-cN.xml"` on `exp-b`, in chunks of at most ~450 s, one chunk at a time (never two on core 0). Logs `logs/slow-cN.log`. 0 failures; any failure stops the gate as a real intermittent failure (B158).
8. **Upgrade from `<P>`**, `logs/upgrade.log`, from `probes/upgrade.ts` (Write tool; gate-only, never committed). First `logs/prev-release.log`: `gh release download <P> -p 'iglo.email-linux-x64' -p SHA256SUMS -D "$G/prev"`, `sha256sum --check --ignore-missing SHA256SUMS`, `--version` = `<P>`. Then the probe: `<P>` on a fresh data directory under `$G/tmp`, the release brief's upgrade data created through the API, a clean stop; the new `dist/release/iglo.email-linux-x64` on the same directory: each new migration applied (`user_version` of the project and instance databases), `/health` answers, the data is kept and reads back through the API; both stops exit 0 with empty stderr.
9. **Release-notes check**, `notes-check.md` (Write tool), before the PR is opened. One row per statement of the notes: the statement, its PR, its D record and the code or text line that proves it. Rules from the 2.2.0 review (#255 r1, five wrong statements):
   - A behaviour change names every condition it depends on (a setting that switches it, e.g. `privacy.unsubscribe_header`), read from the D record and the code, not the PR title.
   - "Before …" wording is checked against `<P>`'s code (`git show <P>:<file>`), not inferred.
   - UI names are copied from `i18n/en.json` (give the key), routes and API names from `src/openapi/*`.
   - An effect ("retries at once", "ends the wait") is stated no stronger than the D record says.
   - Test-only and process work is left out: class (c) items, a D record's "Tests" lines, harness changes. A defect fixed only in a test is not a fix.
   - Each bullet ends with its D record; a bullet with no D record and no PR is removed.

## PR

Push and open the PR only when every step passed. The body has:

- The gate table: one line per run or step with result, load before → after, commit and **the log path** (`~/b<NNN>-gate/logs/…`, junit under `junit/`, probes under `probes/`). A step with no log does not count.
- The skipped steps and why.
- "Release notes" for operators: new features, changed behaviour and API changes (each with its D record), fixes grouped by area, known limitations an operator can hit (the accepted trade-offs in `status.md`), upgrade notes (migrations, anything to set). Plain sentences, no marketing tone. Name `notes-check.md`.

Ends with `🤖 Generated with [Claude Code](https://claude.com/claude-code)`. Commits end with `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`. No CI, tag or merge. Containers start with `b<NNN>-`. Last line: PR <URL>, head <SHA>, local checks <state>.
