## Behavior

1. **Unsent push journaled `unknown`.** In `deliver` (`src/messaging/outbox.ts:95-111`) a push that throws synchronously, before the message reaches a pool, becomes `Promise.reject` and is journaled `unknown`/`uncertain`. The restore hold (`refuse`, `src/messaging/email.ts:337`) throws exactly that way, so the message provably never left. Journal it as not sent: for the restore hold, release the claim back to `queued` without counting an attempt (the loop already skips claiming while `sendingHeld`, `outbox.ts:82`, so this cannot spin); for any other synchronous throw, mark the row `failed` with a concrete error. A rejection after the pool accepted the message stays `unknown` (at-most-once). Each `UPDATE` names its from-state and lease. Test both through the HTTP API (tx send while a restore hold is set, then release it and see exactly one Mailpit message).
2. **Clock skew between lease and push deadline.** The lease (`leaseMs`, `outbox.ts:16`) uses the injected clock, the 60 s push cutoff in `email.ts` does not. A forward jump of the injected clock over the lease while a push is live lets `expireLeases` mark a live send `unknown`. Either renew/extend the lease for rows whose push is still in flight in this process, or skip expiry of rows this process holds in `deliver`; pick the smaller change, keep crash recovery (another process or restart) unchanged. Test by advancing the injected clock during a held SMTP push (the Mailpit/held-SMTP peer the existing outbox tests use).
3. **`claimOne` guard.** `src/messaging/sends.ts:239` has a status guard with no test. Add one at the closest public boundary.
4. **Runner lease loss.** The two drop branches in `src/campaigns/runner/runner.ts` (around `:276-302` and `:630-631`) have no runner-level test; add them with the injected clock. Two store tests in the runner suite fail on old code only by return type; make them assert observable state. A stale runner that loses its lease mid-batch records its sent messages as `unknown` and does not add them to `sent` (undercount, never a double send): make the counts reflect what was actually sent if you can do it without a write under a lost lease; otherwise record why in D80.
5. **Wiped send at lease expiry.** #74 tested this at the `ended` hook only. Add a test through the webhook receiver: a send in flight, subscriber deleted (wiped), lease expires, no `send.failed` arrives (D85).

Marketing stays at-most-once. A guard-only change can be argued in one paragraph with a single run in `docs/perf/`; item 1/2 change sending, so record a short before/after outbox throughput run with the existing harness.
