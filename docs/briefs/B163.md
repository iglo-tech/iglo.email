Each fix has a test against the real PocketBase binary that fails without it (say how you checked: revert the fix, run, restore).

1. **One caller's abort fails every caller sharing the sign-in** (major, `pocketbase.ts` `signIn`). The memoized `signingIn` runs with the first caller's `signal` and `timeoutMs` and is handed to every concurrent caller, so an admin closing a timeline tab mid-sign-in rejects the campaign runner's lookup with a raw `AbortError` (not a `SourceError`); the runner then abandons the claimed batch as `unknown`, the scheduler leaves a claim until its lease, other requests answer 500. Fix: the shared sign-in runs on the adapter's own timeout and an internal signal, not any caller's; each caller races it against its own signal and timeout, so an abort rejects only that caller (with the error type that caller's path already handles). Also check `confirm()` and any other shared in-flight promise for the same pattern. Test: caller A aborts during sign-in while caller B completes; the runner/scheduler see no `AbortError` from another caller.
2. **Concurrent absent reads across a token rotation fail as transient** (major, `confirmed()`). `auth-refresh` mints a new token when the whole-second `exp` advances, `confirm()` stores it, and `confirmed()` skips confirming a read whose `used` token was merely superseded, so with three concurrent empty reads across two second boundaries the third throws "did not confirm…" and a campaign hands back its batch with PocketBase healthy. Fix: confirm the token the read used, whether or not it is still the held one (a superseded valid token passes `auth-refresh`, a revoked one gets 401); keep the B150a r1 guarantee that an empty answer is confirmed against the token that read used (D170 "Absent answers are confirmed"). Consider sharing one in-flight confirmation per token. Test: concurrent absent reads across forced rotations all succeed; a revoked token's empty answer is still not trusted.
3. **Going idle keeps stale markers, so a re-subscribed name replays the gap** (major, `stream.ts` around the `idle` branch). Spec section 4 and D171: a marker whose name is no longer subscribed is dropped, so a name subscribed again starts afresh. `keepMarkers` runs only inside `session()`, so when the last name is unsubscribed and there is no users topic the markers stay, and re-activating the sequence later catches up every event created meanwhile (subscribers, grants, enrollments for events nobody subscribed to). Fix: drop unsubscribed markers when the stream goes idle, in a write transaction, with no network call inside it. Test: unsubscribe the only name, create events while idle, subscribe again: none of the idle-time events is delivered.
4. **A changed address skips the domain policy when the holder is gone** (minor, `recipient-sync.ts` `planRecipient` and `applyRecipient`). Both skip `emailAllowed` whenever `conflict.kind === "gone"`, but that exemption is right only for the re-point branch (the user has no subscriber, the holder row already holds the address). When the user already has a subscriber, its address changes and spec section 5 ("a new or changed address outside the privacy domain policy" is a terminal failure) and D179 apply. Fix: exempt only the re-point branch, in both places. Test: an existing source-linked subscriber moving onto a gone holder's address in a blocklisted domain is refused, nothing written; the re-point case still works.
