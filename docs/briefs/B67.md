## Tests

New `test/e2e/specs/webhooks.e2e.js` (about 8 tests); bounce cases added to `bounces.e2e.js` (about 2).

1. A webhook registered through the API for subscriber events receives `subscriber.unsubscribed` when a person unsubscribes through a mail link, and `subscriber.blocklisted` when blocklisted. Assert the JSON payload names the person and the event.
2. The delivery carries a valid `X-Iglo-Email-Signature`: recompute it in the test from the webhook's secret, the timestamp and the raw body as `delivery.ts:77` defines it. A wrong secret must not match.
3. `subscriber.deleted` after a delete or a GDPR wipe; the payload follows D25 (no address or external ID where the product strips them).
4. A webhook that is disabled receives nothing for an event that would otherwise fire (bounded settle window on the receiver).
5. A receiver that answers 500 then 200: the delivery is retried and arrives once with 200 (read the retry schedule from `delivery.ts`; keep the test short; if the backoff makes this longer than about 60 s, test only that a 500 is recorded as failed in the delivery log the API or UI shows).
6. The webhook budget refusal shows its message in the UI.
7. With `webhooks.block_private_addresses` on, a loopback target is refused (save or delivery, whichever the product does) with its message; restore the setting in `afterEach`.
8. Bounces (`bounces.e2e.js`): a hard bounce posted to `POST /webhooks/bounce` with an API user that has `webhooks:post_bounce` blocklists the person per the bounce settings, the next campaign sends them nothing (sink), and a registered `bounce.recorded` webhook receives it.

Signed SES notifications stay at contract level (plan section 3, item 6). Do not add a production hook.

If a test reveals a real product bug, do not fix product code. Mark it `test.fail()` naming the bug and report it prominently in the PR.
