1. **The backup CLI fails on an instance database from v2.0.0** (blocker, `snapshot.ts` `registeredSlugs`). Instance migration 4 (B149b, D165) added `several_projects`, and `createRegistry()` prepares statements on it when it is built. `registeredSlugs()` builds a registry on a backup's or stopped data directory's `instance.db`, which may be older (`user_version` 3 for every v2.0.0 instance). So `backup --verify <v2.0.0 backup>`, `backup --release-hold` on a restored v2.0.0 directory and `backup` of a stopped v2.0.0 directory all exit 1 with `no such table: several_projects`, breaking the documented restore and upgrade paths. Also, `inspectWhole` reads the slugs when `instance.schemaVersion` is 0 and fails with a raw `no such table: projects` instead of refusing it as not a backup. Fix: a narrow read in `src/projects/registry.ts` (the module owns its tables) that lists slugs from `projects` only, present since instance migration 1, used by `registeredSlugs()`; refuse schema version 0 by name. Check every other CLI path that opens an older `instance.db` (restore, release-hold, upgrade checks) for the same eager-statement pattern. Tests through the compiled CLI against a real v2.0.0-shaped data directory and whole backup (instance at `user_version` 3, a project at its v2.0.0 version): `--verify` passes and names the version the server migrates to, `--release-hold --consent-reconciled` works, `backup` of the stopped directory works; schema version 0 is refused by name.
2. **Raising the send rate does not bring the SES quota refresh forward** (major, `ses-account.ts` `loop` and the settings subscription). `refreshDelay` switches from 5-minute to 1-minute reads when what is left is at most `max(10% of the quota, effective rate × 300 s)`, so the quota guard's `rate × 60 s` hold line is backed by fresh reads (14-projects section on the quota guard, D175). The settings subscription wakes the loop only when the SES credentials change, not when `messaging.max_send_rate` changes. Raising the rate (or setting it to 0, lifting the cap to the account's `MaxSendRate`) mid-sleep keeps the old 5-minute wait although the new rate needs 1-minute reads: with quota 10,000, 6,500 sent, rate 10 → 14, up to ~4,060 sends can go out before the next read and run past the quota, and the over-quota marketing sends fail for good. Fix: wake the sleeping loop when the effective rate changes; after a wake, recompute the wait from `lastAttempt` with the new rate and read only when it is due or the keys changed (no extra `GetAccount` when it is not due). Injected-clock test: the scenario above reads at 60 s after the last read, not at 300 s; a rate change that does not shorten the delay causes no extra read.
