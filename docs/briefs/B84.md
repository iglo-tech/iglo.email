# B84: consent-safe list grant on subscriber events

Common rules: [_B84-common.md](_B84-common.md). Branch `task/B84-event-list-grant`. PR title "B84: consent-safe list grant on subscriber events". Decision record: D99.

## Problem

An app grants marketing permission (legitimate interest) on every purchase. `PUT /api/subscribers/lists {"action":"add","status":"confirmed"}` turns an `unsubscribed` membership back into `confirmed`, so the app has to read the subscriber first and skip anyone with a membership: that races with an unsubscribe and every client has to know it. It must also grant before posting the event, because a sequence whose first marketing step waits `PT0S` is checked as soon as the event creates the enrollment; granting afterwards ends the enrollment `unsubscribed`.

## Decided API (D99)

`POST /api/subscriber-events` and each item of `/batch` accept `subscriber.grant_lists`: an array of 1–20 distinct positive list IDs (absent or `null` = no grant; `[]`, duplicates, non-integers, more than 20 → 400 `Invalid fields: subscriber.grant_lists`, as other event field errors are reported; in a batch, that item's error).

Inside the event's existing transaction, after the subscriber upsert and before the exit and trigger steps (05-sequences.md "Processing"), for each listed ID:

| Situation | Effect | `result` |
|---|---|---|
| Subscriber is blocklisted | nothing, for every list | `blocklisted` |
| No membership on that list | insert membership with status `confirmed` | `added` |
| Membership `unconfirmed` or `confirmed` | unchanged | `member` |
| Membership `unsubscribed` | unchanged | `unsubscribed` |

- A list that does not exist → 400 `Invalid fields: subscriber.grant_lists`, no write (the whole event is refused; in a batch only that item).
- A double opt-in list → same 400: a grant asserts consent the app already holds and cannot replace the opt-in mail. Single opt-in lists only.
- Authorization: besides `subscriber_events:create`, the caller needs `subscribers:manage` and manage scope on every listed list, the same rule as the targets of `PUT /api/subscribers/lists` (`src/subscribers/routes.ts`, list scope helpers). Otherwise 403 with no write (batch: that item). Revalidate inside the transaction the way the events route already revalidates its permission.
- The response gains `grants: [{"list_id": <id>, "result": "added"|"member"|"unsubscribed"|"blocklisted"}]` in request order; `[]` when no grant was asked. A repeated `idempotency_key` replays the first request's `grants` and changes nothing (store them with the replayed lists).
- The subscriber module owns `subscriber_lists`: add a function there for "insert if absent" and call it from the events store; do not query its tables from `src/events`. Whatever side effects an ordinary membership add has (list counts, webhooks if any), keep them consistent with `PUT /api/subscribers/lists` add.
- `PUT /api/subscribers/lists` does not change: it stays the listmonk-compatible admin override that can set any status. Say so in 07-api-and-ui.md and point API clients that must not undo an unsubscribe to the grant. (D89: one way per job.)

## Tests (test/events, plus test/sequences or test/scheduler where needed)

- The repro: grant → `added`/confirmed; one-click unsubscribe (or `action:"unsubscribe"`) → repeat the event with a grant → `unsubscribed`, membership still unsubscribed, no marketing mail.
- `member` keeps `unconfirmed` as `unconfirmed`; blocklisted subscriber → `blocklisted`, no membership row, event still stored.
- New subscriber created by the event (email only) gets the grant in the same request.
- Ordering: a sequence with `list_id` = the granted list and first step `PT0S` marketing; one event with the grant and the trigger → the enrollment sends the marketing mail (Mailpit) instead of ending `unsubscribed`.
- Validation and no-write: unknown list, double opt-in list, duplicates, 21 IDs, `[]`; batch with one bad item leaves the others recorded.
- Authorization: a token with `subscriber_events:create` but no manage scope on the list → 403, nothing written (event too).
- Idempotent replay returns the same `grants` and changes nothing even if the membership changed meanwhile.
