## Behavior

1. **Marketing admission** (tx and resend). The recipient must be an existing subscriber whose `list_id` membership is `confirmed`, or `unconfirmed` on a single opt-in list. Otherwise the send is `skipped` with a safe reason. Blocklist rules stay. Marketing remains at-most-once: no automatic retry, and ambiguous outcomes stay `unknown`.
2. **Frequency cap.** `marketing.min_interval` (ISO 8601 duration, default `P7D`, empty disables it). A tx marketing send that would break the cap is `skipped`. Count actual earlier marketing sends to the subscriber. Check the cap race-safely at admission, so concurrent requests cannot both pass.
3. **Unsubscribe.** Marketing messages get `unsubscribe_url` in the template context, plus `List-Unsubscribe` and `List-Unsubscribe-Post: List-Unsubscribe=One-Click` when `privacy.unsubscribe_header` is on. The URL is scoped to the send's list and carries the send UUID and subscriber UUID. The GET page confirms; the one-click POST works without login, CSRF token or CAPTCHA (RFC 8058) and sets the `subscriber_lists` status to `unsubscribed` for that list. The "all lists" and blocklist option (`privacy.allow_blocklist`) work as upstream. Forged or mismatched UUIDs are a safe 4xx and change nothing. Transactional sends get no unsubscribe link by default. Leave clearly named seams for M5 enrollment cancellation and M2.6 webhooks; don't build them.
4. **Tracking.** Add the `/m/:sendUUID` view pixel and link redirect for sends, following `privacy.individual_tracking` and `privacy.disable_tracking` as upstream does. There is no open redirect: only links recorded for that send/template redirect.
