## Items and D128

1. **Manage page with nothing to manage:** with no public lists to manage, the manage page offers only a name field. When the subscriber has no public list to manage, the unsubscribe page does not show the "manage preferences" link and the manage view shows the privacy actions only (export, wipe, if enabled) with no empty preference form; `privacy.allow_preferences` keeps working as the explicit switch. Adopters no longer need to turn it off by hand.
2. **"Also block all emails" stops transactional mail too:** a person who ticks it on the unsubscribe page cannot know it blocks receipts, payment reminders and password resets, and it can break an adopter's billing flow. D128: the public-page option becomes **"Unsubscribe from all mailing lists"**: it unsubscribes from every list and records a marketing suppression (B124's mechanism), so no marketing mail or marketing enrollment follows; transactional mail keeps flowing. The admin and API blocklist are unchanged and still stop all mail. Docs (`docs/operations.md`, privacy section) state exactly what an unsubscribe, the public "all lists" option, a suppression and an admin blocklist each stop. `privacy.allow_blocklist` keeps its name and gates the public option. This differs from listmonk (its public option blocklists): list it with the reason.

## Tests

Through HTTP + sink: manage link hidden and empty form absent with no public lists; present with one; the public "all lists" option unsubscribes from all lists, blocks marketing sends and enrollment, and a transactional send and a transactional sequence step still deliver; the admin blocklist still blocks transactional; webhooks fire as for an unsubscribe (not a blocklist).
