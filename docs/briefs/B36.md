## Question

What does a typical **newsletter**, **lifecycle (sequences)** and **transactional** email project need that iglo.email cannot do today? Where does iglo.email offer **two ways to do one job**? Check against what the product actually does now, not against what the docs claim.

## Method

1. **Inventory what exists.** Use the OpenAPI document (`src/openapi/*`, or run the compiled build and fetch `/api/openapi.json`; check `docs/operations.md` for the path), the admin navigation (`src/admin/views/`), public pages (`src/public/`), the MCP tools (`src/mcp/tools.ts`), CLI commands (`src/main.ts`), settings (`src/settings/defaults.ts`) and `docs/design/01-scope.md`. Read code to confirm a feature works end to end (route → store → effect). A setting with no reader is not a feature: B35 found five of those.
2. **Checklist.** Judge each item below as **present** (where: file or route), **gap**, or **duplicate**. Add items you find missing from the list.
   - Audience: import (CSV), export, segments/queries, custom attributes, double opt-in, preference centre (manage lists), unsubscribe (one-click RFC 8058 `List-Unsubscribe-Post` header), blocklist/suppression, GDPR export and wipe, subscriber activity history.
   - Campaigns: drafts, scheduling, test send, A/B subject (decide: needed or drop), pause/resume/cancel, throttling/rate limits, archive page and RSS, per-campaign analytics (views, clicks, unique vs total, bounces, unsubscribes), link tracking, list/segment targeting, attachments/media, plain-text alternative, preview.
   - Lifecycle: sequences with triggers, delays, exit conditions, per-step analytics, event ingestion API.
   - Transactional: API send with template + data, idempotency key, delivery status lookup, per-message events (webhooks out), attachments.
   - Deliverability: DKIM, SPF/DMARC guidance, SES configuration set, bounce and complaint handling with thresholds, sending domain checks, `List-Unsubscribe`, Message-ID.
   - Operations: users/roles/API keys, audit log, backup/restore, upgrade path, health, metrics/logging, rate limits, webhooks out (signed), settings UI, Docker, the MCP endpoint.
   - Templates: campaign/tx/archive templates, preview, Liquid reference, media library, thumbnails (decide).
3. **Duplicates.** List every place with two ways to do one job: two import paths, two auth paths for the same client, two bounce paths, settings kept only for listmonk API compatibility, two template languages, and so on. For each, say whether it stays (and why, for example a listmonk API contract D57 requires) or goes.
4. **Decide.** For every gap and duplicate, recommend: **task** (worth doing now: one line with scope, the modules it touches, rough size S/M/L), or **drop** (with the reason). Apply D89 strictly: add only what a typical project needs, and prefer one way.
