# B98: headless deploy behind a proxy

Branch `task/B98-headless-deploy`. PR title "B98: bootstrap API token, root-url message, proxy warning, deploy checklist". Decision records: D106 and D107 (lead, 2026-11-17). Read `docs/briefs/_B97-common.md` first.

## Problems (adopter report, items 3–6)

- A fresh instance has no API credential. A provisioning script had to GET `/admin/login`, scrape the nonce, post the form, read the `csrf` cookie and send `X-CSRF-Token` on every call to create an API user and role.
- The adopter's provisioning role lacked `media:*`; they found `media:get`/`media:manage` only from 403s.
- `IGLO_EMAIL_ROOT_URL=email-dev.example.com` (a PaaS variable holding a bare host) crash-looped the container; the log line did not make the fix obvious.
- Behind the PaaS's Traefik every client address was the proxy's until `security.trusted_proxies` was set, and the image has no shell, so a scheduled `iglo.email backup` task must run without a shell. Both are documented but were found by failing.

## D106: bootstrap API user from the environment

- `IGLO_EMAIL_API_USER` and `IGLO_EMAIL_API_TOKEN`: environment only, no flags (a token in argv shows in process lists), listed in the `--help` text beside `IGLO_EMAIL_ADMIN_*` (`src/config/bootstrap.ts`). Read only on the start where no users exist, exactly the condition of `bootstrapAdmin` (`src/users/bootstrap.ts`), and created in the same step: an API user (`type: "api"`) with the built-in Super Admin user role, whose token is the given value. Both or neither; one without the other is a startup error naming both variables. The admin pair and the API pair are independent: either or both may be set. Nothing is printed; the operator chose the token.
- Token validation: the same format and length the API accepts for generated tokens (read how `src/users/*` creates and stores API tokens and reuse that; if tokens are stored hashed, store this one the same way). A token that a generated one could not be is a startup error stating the required format, without echoing the value. The username follows the admin username rule and must differ from the admin's.
- After the first start the variables are ignored (documented: remove them, rotate the token in the UI). Considered: a CLI subcommand that prints a token (needs the server stopped and a shell, which the image lacks); a token derived from the admin password (couples two secrets); letting Basic auth with the admin password call the API (changes listmonk's auth contract).

## D107: deploy diagnostics

1. **Root URL message.** `validateRootUrl` (`src/config/bootstrap.ts:139`) errors name the received value and the fix: `Invalid root-url "email-dev.example.com": expected an absolute http:// or https:// URL, such as https://email-dev.example.com` (for a value without a scheme, suggest `https://` + the value; for other failures say which part is wrong: scheme, credentials, query or fragment). The value is a public URL, not a secret. A bare host stays refused: guessing `http` or `https` would silently produce wrong links and cookie flags. Check that the message reaches the container log in full from `src/main.ts` (whatever prints startup errors) and test it through the compiled executable.
2. **Untrusted forwarding warning.** When a request arrives with `X-Forwarded-For` from a peer that is not in `security.trusted_proxies` (`src/server/client-address.ts`), log one attention line (the existing logger used for "needs attention" lines, not informational output) naming the peer address and the setting and pointing to the operations section below, at most once per process, and once again after `security.trusted_proxies` changes. Bounded state (one flag), no per-request cost beyond a header check. No behaviour change to address resolution.
3. **Docs** (`docs/operations.md`):
   - A section "Deploying behind a reverse proxy or PaaS" placed after "Reverse proxy and TLS": a short checklist (root URL with scheme; `security.trusted_proxies` with the proxy's address or its network's CIDR, how to find it in a container network; `/health` probe; one container per volume; the backup command runs without a shell, so a scheduler must exec the binary directly: `iglo.email backup …` with the exact invocation; bootstrap admin and API variables, removed after first start). A Coolify note: use `SERVICE_URL_<NAME>` (has the scheme), not `SERVICE_FQDN_<NAME>`; scheduled task with "use shell" off. Keep it generic and short; no other PaaS.
   - "API user for an app integration": the permission sets per job: events and grants (`subscriber_events:create`, `subscribers:manage`, list manage scope for `grant_lists`), transactional (`tx:send`, `templates:get`), provisioning (`templates:manage`, `sequences:manage`, `lists:manage_all`, `settings:manage`, `webhooks:manage`, **`media:get`, `media:manage`**) with the `get` permissions each needs, and that each operation in `/api/openapi.json` lists its permissions under `Needs:`. Make the existing MCP sample role in the same file consistent with it.
   - Docker section: the API variables beside the admin ones.

## Tests (write first)

`test/bootstrap/` (compiled executable, temporary directory): fresh start with the API pair → `GET /api/settings` (or any guarded GET) with `Authorization: token <user>:<token>` → 200; second start with different values changes nothing (old token still works, new one 401); only one variable → exit non-zero with the message naming both; malformed token → message without the value; admin and API pairs together, and the API pair alone. Root URL: bare host, `ftp://x`, `https://u:p@x` → exit non-zero with the new messages on stderr. `test/server/` (or wherever client-address tests live): a request with `X-Forwarded-For` from an untrusted peer logs one attention line, a second request none, a trusted-proxies change re-arms it, a trusted peer never logs; addresses resolve as before.
