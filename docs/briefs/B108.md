# B108: test sends leave a trace (blocklisted message, async bounces), deploy doc notes

Branch `task/B108-test-send-trace`. PR title "B108: test-send bounces and blocklist message". Decision record: D114 (lead, 2026-11-19). Read `docs/briefs/_B97-common.md` first (container recipes, file rules, acceptance = the whole `ci.yml` check job). Source: the first adopter's v1.3.0 verification on its dev instance (SES us-east-1, SNS bounces).

## Findings

1. **Blocklisted recipient, unclear 400.** `POST /api/sequences/{id}/steps/{step}/test` with only a blocklisted address answered `400 Invalid fields: emails`. D105 and the tool description say a blocklisted address is skipped. Skipping is right; the all-skipped answer must say why.
2. **An asynchronous bounce of a test send leaves no trace.** SES accepts every recipient at SMTP time, so a test to `bounce@simulator.amazonses.com` returns `true`, nothing reaches `GET /api/logs` (B101's attention line covers SMTP-time failures only), and the SNS bounce that arrives seconds later matches no send (test sends are not journaled, D105) and is dropped silently. The real tx send in the same session got its bounce recorded within seconds. For SES, the only provider (D89), a bouncing test is therefore invisible to the person and to an agent.
3. **`get_logs` description** ("Recent error lines, without their text") does not tell an agent that fixed attention lines, such as a failed test send, are listed with their text.
4. **Deploy docs.** `security.trusted_proxies` with a single proxy IP breaks when the proxy container is recreated with a new address; recommend the proxy network's CIDR. Suggest scheduling `iglo.email backup --verify` after the nightly backup.

## Decision D114 (implement exactly this)

1. **All-skipped test send.** Step test send and campaign test send (`POST /api/campaigns/:id/test` keeps listmonk's existing behaviour and messages; change only the step route unless the campaign route has the same native-only path): when every address is skipped as blocklisted, answer `400` with `No recipients: blocklisted: a@x, b@y` (addresses the caller supplied, so echoing them leaks nothing). Mixed lists still send to the rest, and the response stays `{"data": true}`.
2. **Test-send records.** Each step and campaign test message gets its Message-ID recorded in a new table owned by the module that sends tests (or messaging, where the outbox pool lives; the worker picks the owner and states it): `message_id`, `kind` (`campaign` or `sequence_step`), the campaign ID or sequence and step IDs, the recipient address, `created_at`. Rows are deleted after 7 days by the existing retention loop (injected clock). Bounded: at most the test-send in-flight caps per request, and the 7-day window. These rows are never sends: no send row, no statistic, no webhook, no analytics.
3. **Bounce matching.** When the SES/SNS bounce (and complaint) handler finds no send for a notification, it looks up the notification's original Message-ID (SES `mail.messageId` is SES's ID; use `mail.commonHeaders.messageId` / the `Message-ID` header the sender set — verify which the SES fixtures carry and match on the one we set) in the test-send records. A match writes **one attention line** ("A test send bounced" / "A test send got a complaint", with its fixed text in the log buffer so `/api/logs` shows it, B98 pattern; the stderr line names kind, IDs, recipient and bounce type/subtype). It does **not** record a bounce, blocklist, touch the subscriber, or count anywhere: a test is a test. No match: behaviour unchanged.
4. **Agent guidance.** The `get_logs` operation description says it lists recent attention and error lines with their fixed text, including failed and bounced test sends. Update the MCP server instructions (`src/mcp/routes.ts`) and operations.md's authoring loop: a test that fails at SMTP time or bounces later appears in `get_logs`; a test the person does not receive and that shows nothing in `get_logs` may still be delayed or filtered by the receiver. Keep the instructions within ~1,500 characters; `test/mcp/agent-guidance.test.ts` keeps passing.
5. **Docs** (operations.md): the proxy checklist recommends the proxy network CIDR (how to find it in Docker / Coolify) and says why a single IP is fragile; the backup section suggests scheduling `backup --verify` after the backup, with the exact invocation for a shell-less scheduler.
6. **Considered (record):** journaling test sends as sends (D105 refused: they would count); matching by recipient and time (wrong for real mail to the same address); recording test bounces as real bounces (would blocklist subscribers because of a test); storing in memory only (lost on restart; bounces arrive after restarts).

## Tests (first)

Through HTTP, SMTP sink, and the existing signed SES/SNS fixtures (`test/bounces/*`): all-blocklisted step test → 400 with the message, mixed list sends to the rest; a step test and a campaign test each record their Message-ID; an SNS bounce notification carrying that Message-ID produces exactly one attention line visible in `/api/logs` and on stderr, no bounce row, no blocklist, no webhook; a complaint likewise; an unknown Message-ID changes nothing; rows older than 7 days are removed by the retention loop (advance the injected clock) and a bounce for them then changes nothing; MCP guidance test still passes.
