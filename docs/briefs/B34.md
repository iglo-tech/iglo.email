# B34: MCP endpoint for editing templates and campaign content (D89, D91)

Common rules: [_state-common.md](_state-common.md). Branch `task/B34-mcp`. Lines from main at 46ee9f4; re-check them.

## Source

Owner, 2026-11-07 ([D89](../design/09-decisions.md#d89-narrow-complete-product-scope-owner-2026-11-07)): no visual editor; instead make it easy for AI agents to edit templates through MCP. One way per job: MCP is a second *door* to the existing API, not a second implementation.

## Design (lead decisions; log them as D91)

- **Transport:** MCP Streamable HTTP at `POST /api/mcp`, answering JSON (`Content-Type: application/json`), stateless: no `Mcp-Session-Id`, no SSE stream. `GET /api/mcp` answers 405 as the spec allows for a server without a stream. Implement the small JSON-RPC 2.0 subset natively (`initialize`, `notifications/initialized`, `ping`, `tools/list`, `tools/call`; batch not required unless the negotiated version requires it); no runtime dependency. Read the current MCP specification (https://modelcontextprotocol.io/specification, latest dated version, "Basic > Transports" and "Server > Tools") and the protocol-version negotiation rules; do not work from memory. Validate `Origin` when present (spec security note) and reject unknown origins with 403 unless it matches the configured root URL.
- **Auth:** the existing API-user authentication on every request (`Authorization: token user:key` / Basic, exactly as `/api/*`), via `auth.middleware()` like the other routes. An unauthenticated request gets the API's normal 401 before any JSON-RPC processing.
- **One implementation:** every tool calls exactly one existing HTTP API endpoint **in-process** through the router (`src/server/router.ts:127` `handle(app, request, peer)`), forwarding the caller's `Authorization` header and peer address, and returns that endpoint's JSON body as the tool result (`structuredContent` plus a text copy, per spec). So permissions (`templates:get`/`templates:manage`, `campaigns:get`/`get_all`/`manage`/`manage_all` with list scoping), validation, Liquid bounds and errors are identical to the API. A non-2xx answer becomes a tool result with `isError: true` and the API's message. No tool reads or writes a table directly; `src/mcp` owns no SQL.
- **Tools** (snake_case names, JSON Schema `inputSchema` per tool, derived from the existing OpenAPI schemas in `src/openapi` where possible, short descriptions written for an AI agent):
  - templates: `list_templates` (GET /api/templates), `get_template` (GET /api/templates/:id), `create_template` (POST), `update_template` (PUT /:id), `delete_template` (DELETE /:id), `preview_template` (POST /api/templates/preview for unsaved body, /:id/preview for a saved one), `set_default_template` (PUT /:id/default).
  - campaigns: `list_campaigns`, `get_campaign`, `update_campaign` (PUT /:id, the editable content fields), `preview_campaign` (POST /:id/preview), `campaign_text` (the /:id/text endpoint), `send_campaign_test` (POST /:id/test).
  - reference: `template_reference` returns static text: the Liquid variables, tags and filters the renderer supports (from `docs/design/06-templates.md`, the "listmonk → Liquid" table and supported subset), with one example per template type. Embed it as a constant generated from that doc section, not a hand copy that can drift: add a test that the tool's text matches the doc section through the tool's public output.
  - Nothing else (no subscriber, list or sending-status tools): scope is template and campaign-content editing.
- **Admin UI / settings:** none. Document in `docs/operations.md` how to connect an MCP client, e.g. `claude mcp add --transport http iglo https://<root>/api/mcp --header "Authorization: token <user>:<key>"`, and recommend an API user with a role holding only the template/campaign permissions needed.
- **OpenAPI:** add `/api/mcp` to the document (the OpenAPI test requires every route).

## Tests (through the public boundary, compiled server via `ensureProductionBuild()`, temp dirs, no fixed ports)

1. The SDK client connects, `initialize` negotiates a version, `tools/list` returns exactly the tools above with valid schemas.
2. Create, update, preview, get and delete a template through MCP; the same template is visible through `GET /api/templates/:id` and vice versa.
3. Permissions: an API user whose role has `templates:get` but not `templates:manage` can list/get/preview but `create_template` returns `isError` with the API's 403 message and writes nothing; a user without credentials gets HTTP 401 on `/api/mcp`.
4. Campaign: update the body through MCP, preview it, and `send_campaign_test` delivers one email to Mailpit with the rendered content; a user limited to some lists cannot read a campaign outside them (same result as the HTTP API).
5. Invalid Liquid in `update_template` returns `isError` with the API's validation message, and the stored template is unchanged.
6. Malformed JSON-RPC (bad JSON, unknown method, missing `id`/params) gets the spec's JSON-RPC error codes, no crash, no write; request bodies are size-bounded like other API bodies.
7. `template_reference` matches the doc section.
