## Behavior

1. **API:** `GET /api/bounces`, `GET /api/bounces/:id`, `DELETE /api/bounces`, `DELETE /api/bounces/:id`, `PUT /api/bounces/blocklist`, `GET` and `DELETE /api/subscribers/:id/bounces`, and the authenticated `POST /webhooks/bounce`, with upstream's permissions, envelopes, filters, ordering, paging and validation. Delete-by-query, `all` and blocklist results must match what real clients get. Respect list-scoped visibility wherever upstream does.
2. **Recording:** the same matching as upstream by subscriber UUID, email and campaign UUID, plus `send_id` when the message identifies a send. A bounce for a transactional recipient with no subscriber is stored with a null `subscriber_id` (03). Unknown recipients and malformed input are safe. `bounce.enabled` and `bounce.webhooks_enabled` gate what they gate upstream.
3. **Actions:** per type (`soft`, `hard`, `complaint`), upstream's count threshold, then `none`, `unsubscribe`, `blocklist` or `delete`, from `bounce.actions`. Count the way upstream counts, including its window and its behavior for subscribers already acted on. The row, the action and the outbound webhook rows commit in one transaction. A repeated provider delivery must not double-count: say how you deduplicate. Network calls never run inside it.
4. **Mailgun:** `POST /webhooks/bounce/mailgun` is public, verifies HMAC-SHA256 of timestamp and token with a configured signing key in constant time, and refuses a stale timestamp and a replayed token. Refused requests change nothing, and a disabled or unconfigured endpoint refuses everything. Map `failed` permanent and temporary severities and `complained` to `hard`, `soft` and `complaint`. Find the send or campaign from what the message carries (Message-ID or a variable the sender sets); if sends need one more header or variable, add it through the messaging owner and say so. Bound body size. Apply the existing public rate-limit approach.
5. **Other providers** stay out, as 04 says. `POST /webhooks/service/:service` answers as a disabled provider does upstream, and the settings stored for them keep round-tripping. List this in 07.
6. **Webhook:** `bounce.recorded` follows 04's payload, adds the bounce type and source, and is queued only for bounces of a known subscriber or send. It obeys D61: a wiped subscriber's stored bounce delivery is cleared like the others. A `delete` action uses the administrative delete path.
7. **Permissions and privacy:** the bounce's stored `meta` can hold provider text with personal data. Say what you store, and make sure subscriber wipe and export treat it correctly.
