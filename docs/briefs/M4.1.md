## Behavior

1. **Foundation, the task's main output.** An `adminPage` helper equivalent to upstream's: session and permission check, the base layout with navigation filtered by permission, language, CSP and CSRF as the app does them, and a redirect to login for a page request. Later tasks add one view by writing one TSX file and one route, so keep it small and say how in the PR body. Global navigation links to views not yet ported stay in place and answer with a clear not-yet page, not a 500.
2. **Spec harness.** A repeatable, serial, local way to run adapted upstream Playwright specs against the compiled executable with a generated data directory and the SMTP sink, plus `agent-browser` for checks. Use the Chromium already in `~/.cache/ms-playwright` if it works, and add only dev dependencies the design permits, or record a decision. No CI gate. Say in the PR how a later task adapts one spec file.
3. **Login, 2FA and reset:** the login screen, first-time setup, TOTP enrolment and verification, forgot-password and reset screens at upstream's paths and with its form fields, on the M1.3 auth owners. Failure messages do not reveal whether an address exists. Rate limits and CSRF stay as they are.
4. **Dashboard:** `views/dashboard.html` with the counts, charts and campaign cards from `/api/dashboard/*`, and upstream's system stats if a route exists or can be read cheaply. Charts use the embedded assets. Views are escape-by-default: nothing from the database is emitted unescaped. Permission-scoped data stays scoped, and analytics read latency in the UI behaves sensibly while a read is queued (a 429 or a 422 is shown as a message).
5. **Copy and look:** match upstream's v7 appearance and i18n keys. Text comes from the translation owner.

## Acceptance

Tests verify rendered pages through HTTP and browser specs. Then, serially and in the foreground on this host: `bun install --frozen-lockfile`, `bun run assets:build`, `bun test test/jsx test/ui test/admin`, `bun run ui:verify`, `bun run check`, `bun run contract:auth`, `bun run contract:normal`, and the adapted specs.

- Adapted login and dashboard specs pass against the compiled executable, and the 2FA flow passes in the browser.
- Each of login, 2FA enrolment, reset and the dashboard is checked once with `agent-browser`; attach what you saw to the PR body in words. If a screenshot is committed, it is small and has no credentials.

`bun run check` should be clean; treat any failure as real. Report first failures and explain reruns. If a test fails intermittently, capture its name.

Out of scope: other admin views, the logs and maintenance screens.
