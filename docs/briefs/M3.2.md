## Behavior

1. **Scanning and claims.** Scan for `scheduled` campaigns whose `send_at` has passed and for `running` ones, on the injected clock. Process them with a lease, so a restart or a second loop can't run the same campaign twice.
2. **Recipients.** Stream recipients in ID order in batches of `app.batch_size`, using `last_subscriber_id` and `max_subscriber_id` as the cursor.
   - The audience is list members with the right status: `confirmed`, or `unconfirmed` for single opt-in lists. `unsubscribed` is excluded, opt-in campaigns target `unconfirmed` members of double opt-in lists, and blocklisted subscribers are always excluded.
   - A subscriber in several of the campaign's lists gets one message.
3. **At-most-once.** Advance the cursor for a batch in a committed transaction before sending that batch. A crash mid-batch may skip at most one batch and never sends twice. Log the skipped range for manual resend. No network I/O inside transactions.
4. **Throughput controls** as upstream: `app.concurrency`, `app.message_rate`, `app.message_sliding_window*`, and `app.max_send_errors` pausing the campaign. Pause, resume and cancel through the M3.1 status API take effect promptly. Progress (`sent` and the cursor) is written once per batch.
5. **Content.** Render per subscriber with the M3.1 renderer and its shared budget, with the unsubscribe URL and `List-Unsubscribe` headers.
   - **Record every tracked link the campaign renders in `campaign_links`**, or the campaign link redirect will 404.
   - Campaign deliveries count toward the marketing frequency cap (04 Frequency cap: campaigns aren't blocked by the cap, but their sends count). Record them so the M2.4/M5.4 cap check sees them.
   - Finish the campaign (`finished`) when the cursor passes `max_subscriber_id`.
6. **Errors.** Classify SMTP outcomes with the D24 rules. Never retry a campaign message automatically.

## Acceptance

Write the tests first, using the injected clock. Then, serially and in the foreground on this host: `bun install --frozen-lockfile`, `bun run check`, `bun test test/campaigns`, `contract:campaigns`, `contract:normal`, and:

- **Mailpit or SMTP sink:** send to 10,000 synthetic subscribers. Show that the rate, sliding window and concurrency limits are respected (measured send timestamps) and every eligible subscriber gets exactly one message.
- **Crash:** kill the compiled process mid-campaign at several points (before and after the cursor commit, mid-batch), restart, and show no duplicates, at most one skipped batch, and the skipped range logged.
- **D22 mixed load:** campaign sending at the target rate while 100 events/s arrive through the real API (M5.1 deferred this until campaigns existed). Record offered and completed counts, latency percentiles and backlog in docs/perf/M3.2-runner.md, with before/after numbers.

Keep runs bounded and clean up. `bun run check` should be clean; treat any failure as real. Report first failures and explain reruns.
