## Behaviour

1. **Page** (`/admin/instance/sending`, instance session; API credentials `401`, like the other instance pages; server-rendered TSX, Alpine.js, Oat, linked from the instance nav beside Projects and Logs):
   - **Rate:** the effective rate, `messaging.max_send_rate`, SES's `MaxSendRate`, and which one applies; rate `0` (unpaced) said plainly.
   - **Snapshot:** `Max24HourSend`, `SentLast24Hours`, remaining, `ProductionAccessEnabled` (sandbox said plainly), `SendingEnabled` (false shown as a warning, section 19 item 2), the read time and age, and while reads fail, that the snapshot is stale with the last error (the instance admin may see AWS's message, as on the check button).
   - **Guard:** whether marketing and campaign sending is held now, the hold line `max(2% of quota, rate × 60 s)` and the remaining quota against it.
   - **Forecast:** the instance's forecast for the 24 hours ending now (no candidate), through the same function `GET /api/sending/capacity` uses: still counted, baseline, planned, window demand, quota, headroom, fits. Instance totals only; this page may stay at totals (the per-project breakdown is not in the spec).
   - **No keys:** says there is no SES reading, forecast or guard without the API keys, and links to instance settings. Before the first good read: says it has not been read yet.
   - Rendered with the page; reload for newer values. No polling. Opening the page may trigger the existing on-demand read (snapshot older than 1 minute), never more than that rule allows.
2. **Index:** one migration on each project's `sends` table indexing the forecast's start time (`coalesce(attempted_at, sent_at)` as `sends.starts` reads it, or the equivalent the query planner actually uses; check with `EXPLAIN QUERY PLAN`), and the query changed only as needed for SQLite to use it. Results identical. If `campaign_deliveries` by `at` is the larger cost, D162 says whether it is indexed too.
