# B97: preview and test-send sequence steps with realistic data

Branch `task/B97-step-preview-test`. PR title "B97: step preview and test send with sample data". Decision record: D105 (lead, 2026-11-17). Read `docs/briefs/_B97-common.md` first.

## Problem (adopter report, items 1 and 2)

Sequence step templates are mostly `trigger.data.*`, `aggregates.*` and `subscriber.attribs.*`. Today:

- `POST /api/templates/preview` and `GET /api/templates/:id/preview` render with the fixed dummy context in `src/templates/routes.ts:84-108` (`trigger: { data: {} }`, no `aggregates`, empty attribs), so numbers are blank, `{{ trigger.data.x | track_link }}` renders empty and the name is the dummy's. The adopter rendered templates with a local LiquidJS and stand-in filters to see real output.
- The only way to receive a step in a real inbox is a test enrollment (`POST /api/enrollments`, `test: true`, `trigger_event_id`), which needs an existing subscriber and a stored event. For "show the owner step 3 in Gmail" the adopter created throwaway tx templates from pre-rendered HTML and used `POST /api/tx` with `subscriber_mode: external`.

## Decision D105 (implement exactly this)

### 1. Step render context, one builder

The scheduler builds a step's template data in `src/scheduler/scheduler.ts` (~lines 250-300: `subscriber`, `trigger` with `name`/`data`/`occurred_at`, `sequence`, `step`, `aggregates`, `unsubscribe_url`, `manage_url`) and renders subject and body with the step's template. Extract that into one function used by the scheduler **and** by the two new routes below, so a preview and a test send render exactly what a real send renders. No behaviour change for the scheduler (its existing tests must pass unchanged).

### 2. `POST /api/sequences/{id}/steps/{step}/preview`

`:step` is the step ID, as in reschedule. Needs `sequences:get`. JSON body, every field optional:

```json
{
  "subscriber_id": 12,
  "trigger_event_id": 345,
  "sample": {
    "subscriber": { "name": "Ada", "email": "ada@example.com", "external_id": "u_1", "attribs": { "plan": "pro" } },
    "trigger": { "name": "purchase", "data": { "items": 3 }, "occurred_at": "2026-11-01T10:00:00Z" },
    "aggregates": { "downloads": 1234567 }
  }
}
```

Context resolution, in this order:

- **Subscriber.** `subscriber_id` names a real subscriber; it must be readable by the caller under D103's rule (`subscribers:get`/`get_all` plus list scope), otherwise `404 Subscriber not found` exactly as for an absent one. Without it, the dummy subscriber (`John Doe`, `dummy@example.invalid`, `attribs: {}`) is used. `sample.subscriber` fields, when given, replace the corresponding fields of whichever subscriber was chosen (shallow; `attribs` replaced as a whole).
- **Trigger.** `trigger_event_id` must belong to that subscriber and be named as the sequence's `trigger.event` (the same rule and the same `400 Invalid fields: trigger_event_id` as `POST /api/enrollments`). Without it but with `subscriber_id`, the subscriber's **latest** event with the trigger's name is used (none: `trigger` is `null`, as for a manual enrollment). Without a subscriber, `trigger` is `{name: <sequence trigger event>, data: {}, occurred_at: now}`. `sample.trigger` fields replace the chosen trigger's fields (`data` as a whole).
- **Aggregates.** With a real subscriber, computed from their events exactly as the scheduler does at that step (measured from the trigger's `occurred_at`, or now). Without one, every aggregate the step names is `0`. `sample.aggregates` values replace named entries; a name the step does not define is `400 Invalid fields: sample.aggregates.<name>`; values must be finite numbers.
- **Links.** `unsubscribe_url`/`manage_url` are the real URL shapes with a placeholder UUID, and `track_link` returns its URL unchanged, `track_view` renders nothing (as the existing preview: nothing is registered or tracked).

`sample` is bounded like other template data (`parseTemplateData` limits in `src/templates/data.ts`); over-limit or malformed → 400, nothing rendered.

Response `200 {"data": {"subject": "...", "body": "<html>…", "context": {…the exact data rendered…}}}`. Returning `context` lets an agent see which event and aggregate values were used. Render errors answer like the template preview (400 with the compile/render message, 429 on render capacity). The step's own subject wins over the template's, as in the scheduler. It writes nothing.

### 3. `POST /api/sequences/{id}/steps/{step}/test`

Same body as preview plus `"emails": ["owner@example.com"]` (required, 1–5 distinct addresses, validated like subscriber emails). Needs `sequences:manage` **and** `tx:send` (it mails arbitrary addresses, which `tx:send` already permits through `POST /api/tx` external mode; revalidated before sending). Renders once per address with the context above (when `sample.subscriber.email` is not given, the subscriber `email` in the context is the recipient address), subject prefixed with the scheduler's existing `TEST_SUBJECT` marker, sent through the same emailer path campaign test sends use (`src/campaigns/routes.ts` `test` handler: `copies: false`, bounded in-flight test sends with 429, delivery not awaited). It is **not** journaled as a send, creates no enrollment, counts in no step or sequence statistic, registers no tracked link or view, and is never retried. An address belonging to a blocklisted subscriber is skipped; all skipped → `400`. Refused while a restore hold is active (as campaign tests). Response `{"data": true}`.

### 4. Template preview takes the same sample

`POST /api/templates/preview` accepts an optional form field `sample` (JSON string, same shape: `subscriber`, `trigger`, `aggregates`, plus `data` for tx templates), merged over the dummy context as above. Absent → today's output, byte-for-byte (listmonk clients unaffected). The MCP `preview_template` tool gains a `sample` object argument and its description says sequence steps are best previewed with `preview_sequence_step` (the generated tool name; check it) and to read `template_reference` first. Add `aggregates: {}` to the dummy context so `{{ aggregates.x | number | default: 0 }}` previews as `0`.

### Considered (record in D105)

Previewing a step through `POST /api/templates/preview` alone (a template does not know the step's aggregates, subject or trigger); journaling test sends (they would count in statistics and could be confused with real sends); test sends only to existing subscribers like campaign tests (the adopter's need is an owner's inbox; `tx:send` already allows arbitrary addresses); defaulting to a random subscriber's event (leaks another subscriber's data into a preview).

## Tests (write first)

`test/sequences/` (new file) through HTTP + sink + MCP: preview with no input (dummy, zeros); with `subscriber_id` picks the latest matching event and computes aggregates from stored events (advance the injected clock); `trigger_event_id` of another subscriber or other name → 400; unreadable subscriber → 404 body equal to absent; `sample` overrides each part; unknown aggregate name → 400; preview equals the body the scheduler sends for the same subscriber/event (enroll a real subscriber, drive the scheduler, compare the sink body with the preview body modulo the send UUID); test send reaches the sink for each address with the `[Test]`-style subject and untracked links, adds no send row (`GET /api/sends`), no enrollment, no step stat change; missing `tx:send` → 403 nothing sent; >5 emails → 400; template preview with and without `sample` (without: identical to before); MCP `tools/list` shows the two generated tools and `preview_template` with `sample`, and one MCP round trip each.
