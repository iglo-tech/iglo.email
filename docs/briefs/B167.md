Each fix has a compiled-CLI test that fails without it (say how you checked: revert with Edit, run, restore).

1. **A bare `instance.db` is verified as a project database** (major). `inspectBackup()` passes the instance schema version (`instanceMigrations.length`) and `INSTANCE_SETTINGS_FROM` only inside `inspectWhole()`; a bare `.db` file always goes to `inspect()` with the project version (38) and `PROJECT_SETTINGS_FROM`, and `cli.ts` `print()` picks the instance wording only for `place === "instance.db"`. The operations guide says pre-migration snapshots (`backups/pre-migration/instance-…`) are plain `.db` files that `--verify` reads, and that an older executable's `--verify` exits non-zero on a newer backup. Today: a bare `instance.db` at version 5 (ahead of this executable's 4) verifies with exit 0 and "the server migrates this backup to version 38"; every real `instance-*.db` snapshot prints `Uploads: 0 files`, the project hold wording and the wrong target version; a bare instance database at version 1–2 is refused for a missing `settings` table it should not have yet. Fix: recognise an instance database from its schema (decide the rule and record it in D195; for example the `projects` table present and `subscribers` absent — check every instance and project migration so no real database of either kind is misread, including a version-0 or empty file, which stays "has no schema"), inspect it with the instance version and settings threshold, and carry the kind on the inspection so `print()` drops `Uploads:` and uses the instance hold message. Tests through the compiled CLI: a bare pre-migration `instance-*.db` at v3 (says it migrates to 4), a current bare `instance.db` at v4 (ok, instance wording, no uploads line), one at v5 (refused as ahead), an instance database at v1 (verifies); a bare project database still verifies as now.
2. **A whole backup whose `instance.db` lacks `projects` fails with a raw SQLite error** (minor). `inspectWhole()` calls `registeredSlugs(db)` unconditionally, so an `instance.db` at version 1–4 without a `projects` table (hand-made, or version 1–2 with no tables) exits 1 with `no such table: projects`. Fix: an `instance.db` that should have `projects` at its version and does not is refused by name ("has no projects table at schema version N: not a backup"). Test through the compiled CLI.
