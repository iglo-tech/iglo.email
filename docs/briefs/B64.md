## Tests (new `test/e2e/specs/sending.e2e.js`, about 14 tests)

Each test makes its own data through the public API with `unique` names, and asserts on what the sink received. Drive the UI where a user would act (start, pause, resume, cancel, schedule from the campaign page). Use the API only for setup.

1. A campaign started from its page delivers exactly one mail to each subscriber of its lists. The listing's sent count equals the number of sink mails.
2. A subscriber on two of the campaign's lists receives one mail.
3. Unsubscribed (from that list) and blocklisted subscribers receive none.
4. Pause from the page while sending: the mail count stops growing within the settle window. Resume: the rest arrive. No address receives two mails.
5. Cancel while sending: the count stops and the status shows cancelled. Nothing more arrives after the settle window.
6. Schedule with `send_at` a short time ahead, chosen through the UI's date control. The campaign fires within one scheduler interval after `send_at`. Use real time: the e2e server has no clock control. Keep the wait as short as the scheduler allows, and read its interval from the code and docs, not from memory.
7. The body, subject, From and template layout in the received mail match the campaign, including a subscriber field in a Liquid tag.
8. `POST /api/tx` with a template and one attachment: the sink receives the mail with the attachment bytes intact. An unknown template id is refused with the API's error, and nothing is sent.
9. The test-send button on the campaign page delivers only to the given address.

## Harness

- Move `audience()` from `campaigns.e2e.js` into `helpers.js` unchanged, and use it in both files.
- Add a helper that counts the sink's mail for a set of addresses and waits until the count holds still for a fixed settle window (wall time, bounded; see `test/wait.ts` `waitWall` for the house pattern). Put it in `helpers.js`.
- Lower `app.message_rate` (or the sliding window) in this spec so pause and cancel land mid-send, and restore the original in `afterEach`/`afterAll` through the settings API. Specs never share a server (README), but restore anyway.
- No production test hooks. No fixed ports. No sleeps where a wait condition exists.

If a test reveals a real product bug, do not fix product code here. Mark that test `test.fail()` with a comment that names the bug, and report it prominently in the PR. The lead opens a fix task.
