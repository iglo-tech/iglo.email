## Owns

`test/perf/**` (or the existing harness locations), a `perf:mixed` package script, docs/perf/M6.1-performance.md with raw JSON records and the source and executable hash for each run. Authorized narrow fixes:

- **Outbox claim query** (src/messaging/sends.ts and its SQL): avoid sorting every queued row per claim, for example with a `(status, id)` or due-time index or a split query. Behavior must stay identical (D24 retry order, at-most-once).

Other bottlenecks you find: measure them and describe them with a concrete proposal in the PR; don't fix them unless they're one-line index changes in the same modules.

## Behavior to measure

Run the compiled build against a local SMTP sink, using real HTTP for every input:

1. **Baseline at the target:** a campaign at 50 messages/s sustained for at least 5 minutes, while events arrive at 100/s through `POST /api/subscriber-events` for the same window. Use worker settings that reach 50/s (M3.2 found per-worker headroom is needed) and record them.
2. **Mixed load:** the same, plus active sequences (some events trigger and exit enrollments; the scheduler queues sends) and a steady trickle of tx API sends. Show that events aren't slowed beyond their M5.1 baseline and that campaign sends hold 50/s.
3. **Outbox:** transactional and sequence delivery rate with a 10,000-send backlog, before and after the claim-query fix.
4. **Cap lookup:** timing at 100, 1,000 and 10,000 deliveries per subscriber, before and after the fix.

For each run, record offered and completed counts, rates per second, latency percentiles (events, tx), backlog growth, process RSS and MemAvailable, and errors. A run fails if a target isn't met. Say so plainly, with the bottleneck and a proposal, rather than tuning the test until it passes.
