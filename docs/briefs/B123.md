## 1. `subscriber_events:get` is declared but not enforced (authorization defect)

`src/subscribers/routes.ts:366` registers `route("subscriber-events", paged(activity.events))` with no permission check, while enrollments and sends check theirs. An API user without `subscriber_events:get` (the adopter's app role) read subscriber events including `data` through REST and MCP `get_subscriber_events`. Enforce the declared permission (and the subscriber read scope the sibling routes apply, D103) on REST and therefore MCP; revalidate as siblings do. Audit every route in `src/subscribers/routes.ts` and `src/events/*` against the OpenAPI `x-required-permissions` for any other declared-but-unenforced permission, and fix those too. Tests: a role without the permission gets 403 on REST and an `isError` 403 on MCP; with it, 200; add the case to the roles contract (`contract:roles`) if that suite covers subscriber routes.

## 2. The subscriber UUID alone can blocklist, wipe, export or rename

- `POST /subscription/:camp/:sub` with any random v4 `:camp` (existence never checked) and `blocklist=true` blocklists the subscriber; the manage form posts there too.
- `POST /subscription/export/:sub` and `POST /subscription/wipe/:sub` need only `:sub`.
- `/m/:send/…` routes check the send+subscriber pairing, but the manage page's privacy forms post to the sub-only routes, so the pairing protects nothing.

D121 (implement): every state-changing public action requires a pairing the server issued: the campaign POST requires an existing campaign whose send to that subscriber exists (or the D117 test placeholder, which stays inert), and `/m/:send/…` requires its send+subscriber pair (as today). The manage page's export, wipe, blocklist and preference forms post to `/m/:send/…` actions (new paired routes where missing) and the double-opt-in / tx preference links (nil campaign UUID, D117) keep working through their existing paired flow (verify each link type end to end: campaign unsubscribe, sequence unsubscribe, tx preference link, opt-in confirmation). The sub-only `POST /subscription/export/:sub` and `/subscription/wipe/:sub` are retired (404) — a deliberate difference from listmonk: a UUID in a forwarded mail must not let anyone erase or export the person. Unpaired requests write nothing and answer like the existing invalid-link page (no existence oracle).

Tests through HTTP: each attack in the audit fails and writes nothing (random `:camp` blocklist, sub-only export, sub-only wipe); each legitimate path from a real mail (campaign, sequence, tx preference, opt-in, manage page export/wipe/blocklist/preferences) works; webhooks fire only for real actions.

## 3. HIGH (scenario audit): a step test carries the real subscriber's UUID

A step test with `subscriber_id` renders `List-Unsubscribe` and `unsubscribe_url` as `/m/<nil send>/unsubscribe/<real subscriber UUID>`; the test page is inert, but that UUID unlocked the sub-only routes: `POST /subscription/export/<uuid>` mailed "Your data" to the real subscriber and `POST /subscription/wipe/<uuid>` deleted them. Test recipients are up to five arbitrary addresses chosen by an operator or an MCP agent. Fix both sides: (a) step test sends (and previews) use a placeholder subscriber UUID in every link and header, as B115 did for campaigns (the render data may keep the real subscriber's name and attributes; no link or header may carry a real subscriber or send UUID); (b) item 2 above removes what such a UUID can unlock. Test: a step test with `subscriber_id` contains no real subscriber UUID anywhere in the raw message (headers and body), and the audit's export and wipe repro writes nothing.
