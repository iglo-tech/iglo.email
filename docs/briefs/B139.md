## Goal

Settings split into instance keys, stored once in `instance.db`, and project keys, stored in each project's database. A project host reads and writes project keys only; the instance host's `/api/instance/settings` reads and writes instance keys only, behind B140's instance session and CSRF. Every project sees the one instance configuration. `ses.api_*` keys are accepted, validated and masked but not used yet. The admin Settings pages split the same way.

## Behaviour

1. **Classification (section 4 table).** Every key in `src/settings/defaults.ts` is classified instance or project exactly as the table says. A key the table does not name: D154 classifies it by the section 4 rule and lists it. The campaign pacing keys (`app.concurrency`, `app.message_rate`, `app.batch_size`, `app.message_sliding_window*`) stay as instance keys until B141 removes them (D154). `restore.hold` stays per database (it is not a setting). A test fails if a default key is unclassified.
2. **Storage.** Instance keys live in `instance.db` (a table the settings module owns, migrated from `migrations/instance/`); project keys stay in the project database. Fresh instance: instance defaults seeded once. A project database holds no instance key: the project migration removes them (no upgrade path is owed, D142). No cross-file transaction (invariant 6).
3. **Project API.** `GET`/`PUT /api/settings` on a project host return and accept project keys only. Any other key in a `PUT`, instance keys included, is `400` naming the key, nothing written. `app.root_url` stays read-only (D14). Permissions, masking and validation as today.
4. **Instance API.** `GET`/`PUT /api/instance/settings` on the instance host: instance keys only, the same validation, masking and secret round-trip rules as today's settings API, instance session plus CSRF (B140), API credentials `401`, not in OpenAPI or MCP (`src/openapi/excluded.ts` with "instance host, admin session only"). An unknown or project key is `400` naming it.
5. **SES keys.** `ses.api_region`, `ses.api_access_key_id`, `ses.api_secret_access_key` are instance keys: validated (region format, key id format, secret non-empty when set), the secret masked like other secrets, stored, and not read by any sender yet.
6. **One configuration (invariant 5).** Every project reads instance keys through one instance settings reader passed into `createProject` (no instance `Database` handed to a project). A change through `/api/instance/settings` takes effect in every project the way a settings change takes effect today in one install (the same reload or restart semantics, stated in D154). No project can hold its own copy of an instance key.
7. **Admin UI.** A project's Settings page shows only project keys, with a link "Instance settings" to the instance host. A new instance Settings page at `/admin/instance/settings` shows only instance keys, in B140's instance layout, with Alpine.js and Oat like the existing page. Tabs or fields with no keys left disappear from that page.
8. **One install.** A single primary project behaves as today except for the split itself: the same keys are reachable, project keys on the project's `/api/settings` and instance keys on `/api/instance/settings`.
