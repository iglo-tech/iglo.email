# M6.3: Release workflow

Goal: a GitHub Actions workflow that turns a `v*` tag into a tested linux-x64 executable attached to a draft GitHub release, per D42.

Repository https://github.com/iglo-tech/iglo.email. M6.2 is merged; main is at e191856 or later. One worker, one PR, no helpers. In your supplied isolated checkout, fetch origin/main and create `task/M6.3-release` from current origin/main. No other checkout.

`.github/workflows/release.yml`, a small script under `scripts/` if needed, the version source, `docs/operations.md` install and upgrade text, `test/release/**` for anything testable locally. Authorized narrow seams: `package.json`, a `--version` flag in the CLI.

## Behavior

1. **Trigger:** a pushed `v*` tag, and `workflow_dispatch` as a dry run that builds and smoke-tests without publishing. No other trigger. CI stays manual, so this workflow is the only automatic one.
2. **Build:** on `ubuntu-24.04` x64 only, with pinned action versions by commit SHA, a pinned Bun version and `bun install --frozen-lockfile`, using the repository's build. Linux arm64 and macOS stay post-MVP.
3. **Version:** the executable reports the tag's version with `iglo.email --version`, and the workflow fails if the tag and the reported version disagree. Say how the version reaches the compiled binary.
4. **Verify before publishing:** the built artifact, not the source, boots from an empty temporary directory, answers `/health` and passes a small smoke test, using the same steps the repository already has. `bun run check` passes first. No secrets, no real SMTP.
5. **Publish:** a **draft** release with the executable, a SHA-256 checksum file and the license and third-party notices the AGPL and bundled assets need. Tags containing `-` are marked prerelease. The workflow's permissions are the minimum: `contents: write` only on the publish job, `contents: read` elsewhere. Nothing else is uploaded, and no Docker image, as D3 says.
6. **Safety:** workflow inputs and tag names are never interpolated into a shell line. Run the script injection check by reading it: use environment variables.

## Acceptance

Locally, serially on this host: `bun install --frozen-lockfile`, `bun run check`, the `--version` behavior through the compiled executable, and a local dry run of the smoke steps. Validate the workflow's syntax with whatever is available, without installing new tools globally.

Do not push a tag or dispatch the workflow: the lead does that after merge. Say exactly what the lead should run and expect.

`bun run check` should be clean; treat any failure as real. Report first failures and explain reruns.

Out of scope: arm64, macOS, Docker, package managers, signing.
