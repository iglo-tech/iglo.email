## Tests (new `test/e2e/specs/operations.e2e.js`, about 10 tests)

Each test makes its own data through the API with unique names. Assert on the sink and the UI.

1. Notify-email setting: saving an invalid address is refused with the form's message; a valid list saves and reloads.
2. A campaign that finishes mails a notification to `app.notify_emails`; one that is cancelled does too. Check subject or body names the campaign.
3. A campaign auto-paused (find the product's trigger, e.g. the error threshold; make it happen with the sink only, never a real server) mails its notification, if the trigger can be reached from e2e without a production hook. If not, say so in the PR and skip it.
4. An import that finishes and one that fails mail their notifications.
5. Restore hold, on a third instance started from a snapshot written by the production `backup` CLI of a stack's data directory (D67 writes the hold into the snapshot):
   - the admin shell shows the hold banner and its reason;
   - `/health` answers 200 with the same body and the `X-Iglo-Email-Hold` header;
   - starting a campaign, a test send and `POST /api/tx` are refused with 503, and the sink gets nothing for that instance's addresses after a settle window;
   - an unsubscribe through a public page still lands while held;
   - after stopping the instance and running `backup --release-hold --consent-reconciled`, then starting it again, the banner is gone and a campaign start sends.
6. GDPR through the public preferences page: export mails the person's data (check the mail names their email and a list); wipe removes the subscriber (API 404 afterwards), and the next campaign to their former list sends them nothing.

If a test reveals a real product bug, do not fix product code. Mark it `test.fail()` with a comment that names the bug and report it prominently in the PR.
