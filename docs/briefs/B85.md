# B85: event aggregates in sequence step templates

Common rules: [_B84-common.md](_B84-common.md). Branch `task/B85-step-aggregates`. PR title "B85: event aggregates in sequence step templates". Decision record: D100. Depends on B84 (merged).

## Problem

05-sequences.md says "the sequence engine does not aggregate", so an app runs its own scheduler just to compute numbers. Real cases:

- A "your month" email 30 days after a subscription starts: "you pulled N items from M sources, and your assistant started K actions". The app already sends one `download_finished` event per download (`data.items`, `data.source_id`) and one event per assistant action. Over `P30D` it needs a sum of a `data` field, a distinct count of a `data` field, and an event count.
- A line shown only if the subscriber ever had event X. Today that takes two steps with opposite conditions and two near-identical templates.

## Decided API (D100)

A step gains an optional `aggregates` object (absent/`null` = none), declared on the step, computed when the step sends, and passed to its template as `aggregates`:

```json
"aggregates": {
  "items":   { "event": "download_finished", "since": "P30D", "fn": "sum", "field": "data.items" },
  "sources": { "event": "download_finished", "since": "P30D", "fn": "distinct", "field": "data.source_id" },
  "actions": { "event": "assistant_action", "since": "P30D" },
  "had_x":   { "event": "x", "where": { "data.kind": "y" } }
}
```

`{{ aggregates.items }}`, `{% if aggregates.had_x > 0 %}…{% endif %}`.

- **Names**: 1–10 per step, each matching `^[A-Za-z_][A-Za-z0-9_]{0,63}$`.
- **`event`** (required), **`where`** and **`since`**: exactly the condition language's `event` predicate semantics and validation (05-sequences.md "Conditions" rules: `data.*` equality with the same types and safe-number rule; `since` = `trigger` / `enrollment` / `last_step` / duration back from the injected clock's now, strictly after the bound, no upper bound; absent = no lower bound). Reuse `src/conditions` validation and SQL compilation pieces; do not write a second dialect.
- **`fn`**: `count` (default; number of matching events), `sum` (sum of `field` over matching events where it is a JSON number; others ignored; `0` when none; a JSON number result, exact for integers within ±(2^53−1)), `distinct` (number of distinct values of `field` over matching events, ignoring missing and JSON null; values compare as the condition language's `eq` does, so `5` and `5.0` are one value, `"5"` another). `field` is required for `sum`/`distinct`, refused for `count`, and is a `data.*` path with the conditions' path rules.
- `sql` is not available here.
- Validation runs on sequence save (field errors such as `steps[0].aggregates.items.field`, the same style as conditions) and on the step editor in the admin UI (a JSON editor beside the condition editor, like it; reuse the live validation route if that fits, otherwise validate on save).
- **When**: the scheduler computes the aggregates after the condition holds and the cap admits the step, before rendering, on the normal read path, one SQL query per aggregate using the `(subscriber_id, name, occurred_at)` index, bound to the subscriber. An error is handled like a condition error (release with backoff, attention log without personal data, never sends). `aggregates` joins the step fields whose change discards a stale decision at commit.
- Template data: `aggregates` is `{}` for a step without them. Transactional and marketing steps both get it. A test enrollment computes them like a real one.
- Storage: a new nullable JSON column on `sequence_steps` through a new migration file (not 0001); returned by the sequences API and stored/edited like `condition`.

## Bounds and measurements

Store before/after numbers in `docs/perf/B85-aggregates.md` with `test/scheduler/measure.ts` (or a sibling) on this host: scheduler throughput with steps without aggregates (must not regress), and one subscriber with 1,000, 10,000 and 100,000 matching events in the window for each `fn`. If 10 aggregates over 100,000 events each take more than 250 ms per decision, propose a bound in the PR (for example an event count limit per aggregate that ends in a condition-style error) instead of silently truncating; never return a partial total as if complete. Event retention bounds what exists; say so.
