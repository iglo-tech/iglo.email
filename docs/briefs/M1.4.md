## TOTP boundary

Implement standard six-digit SHA-1 HMAC TOTP, 30-second periods and the pinned upstream validator's accepted skew (inspect its pinned dependency source through a named cache or fetched exact source). Time comes only from the injected clock. Use independent vectors and end-to-end HTTP codes, not tests that simply call the implementation to generate its own expectation.

The provisioning API returns the compatible secret plus base64 PNG QR for an otpauth URI with issuer/account/secret/period/digits/algorithm matching the actual verifier. Check the QR is usable, including in the compiled binary, rather than accepting arbitrary PNG bytes. Do not use an external service. Newly generated secrets are random; setup validates supplied secret/code, eligible human password login and current factor state. Disable verifies the exact current password outside the write transaction and revalidates account/credential/factor state under the write lock before changing it. Caller/path identity cannot manage another user. API-token identities cannot masquerade as human password-login accounts, regardless of compatibility projection fields. Never return the stored factor key through user/profile/list responses.

Under D30, a successful password for a factor-enabled user creates only a bounded single-use challenge (five-minute TTL, 4,096-live cap, five failed code checks), not a normal session. Missing, wrong, expired, replayed, superseded/revoked or restarted challenges cannot authenticate. A code accepted by one challenge must not let that same challenge create another session. Wrong/malformed codes consume the appropriate attempt budget; enforce peer-IP limits before expensive work and use nonce/Origin protection on unsafe forms. Reuse existing D26 session cookies, exact-password, CSRF and safe-redirect behavior. Check current enabled human/password-login identity, unchanged credential and factor at completion; a stale password proof cannot survive password/type/factor changes or disable/re-enable. Challenge storage/limits are per auth instance, never global.

Factor enable/disable must revoke other sessions and pending challenges while retaining only the currently verified self-service session. Recheck current authentication after asynchronous password or QR work, just as M1.3 does after hashing. Test concurrent password/type/status/factor changes through deterministic HTTP barriers; retain failing-before/passing-after evidence for any discovered race. Freshly created sessions must still work on restart, while pre-session challenges fail closed after restart. Persisted factor secrets are existing user-owned private credential data, never log or serialize them in broad projections.

The functional second-factor page uses PublicShell/escaped TSX, existing assets, token/next/totp_code names and useful translated errors. Do not expose fake dashboard/reset/setup screens. Verify the actual rendered login-to-factor-to-protected-profile flow with agent-browser and record synthetic fixtures and exact outcomes in regular .md files. M4.1 still owns full integration/polish.
