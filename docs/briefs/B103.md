# B103: v1.3.0 release run: runner and media cache tests, root causes

Branch `task/B103-release-flakes`. PR title "B103: runner and media cache tests, root causes". Read `docs/briefs/_B97-common.md` first. Source: release run 44159976600 (tag `v1.3.0` on de36d91), both `build` jobs failed in `bun run check`; e2e passed; nothing was published. B101 changed both tests and did not fix them.

Diagnose with evidence first (reproduce, instrument, prove the cause), then fix. No retries, skips, or wider bounds as the fix.

## 1. Runner test (x64 job)

`test/campaigns/runner/runner.test.ts:574`, "tracked links personalized per subscriber do not accumulate across batches". Failure text:

```
drive: condition not reached after 9881850 iterations (wall limit 60000 ms, step 10 ms): last condition value false; wall 60001 ms; clock 2026-01-03T06:31:03.500Z (+98818500 ms); pushes 299, pending sends 0, sink messages 0; campaign 1 status finished sent 299 to_send 300 lease free
```

The campaign **finished** with 299 of 300 pushed; it did not stall. `f.drive` advances the injected clock 10 ms per iteration whatever the system is doing, so on a slow runner about 27 hours of fake time passed during CPU-bound rendering. Lead hypothesis (prove or refute): a clock-based bound in the campaign send path (send-rate wait bound, render/lease timeout, the 60 s SMTP cut-off, a lease expiry) fired for one message, which was then settled without a push, and the campaign correctly finished.

- Reproduce deterministically: make rendering slow relative to the clock (e.g. advance the clock by a large step per iteration, or slow the render in a scratch copy) and capture what happened to the 300th subscriber: its send/journal row, outcome, and which code path decided it.
- **Product check (decisive):** a marketing subscriber that is never pushed must end with a recorded, visible outcome (journaled failed/skipped with a reason, counted where the product counts such outcomes, and an attention log line if the product logs those) and must never be silently dropped or double-sent. If the product drops it silently, or counts it as sent, or the campaign's `sent`/`to_send` misreport it, that is a product defect: fix it in the owning module with a test through HTTP + sink that fails before (record D110, lead, 2026-11-17, and a perf note since sending changes). If the product is right, say so with the evidence.
- **Test fix:** the test proves link memory does not accumulate; it must not depend on fake time racing CPU work. Make the drive in this test not advance the clock while work is pending (or not at all, if nothing in it needs time), so all 300 messages are pushed on any host speed; keep the memory assertion and the count. Restore a wall bound with real margin and explain it.

## 3. Product defect found (lead decision 2026-11-19): wall-clock render deadline

B103 run evidence: `error rendering message (links) (p0091@x.test): template render limit exceeded`, the subscriber recorded `failed`, the campaign finishing with one fewer push. `src/templates/renderer.ts:195` sets liquidjs `renderLimit: 1000`, a deadline on real wall-clock time (`performance.now()`), so any render slower than 1 s under CPU load fails, on every path the shared renderer serves: campaign (subscriber marked failed, never retried), transactional, sequence step, opt-in, preview.

- **Decision D110 (lead, 2026-11-19):** remove the wall-clock `renderLimit` (set it to the library's no-limit value or omit it, whichever the library treats as unbounded) and the explicit `ctx.renderLimit.check(performance.now())` calls at `renderer.ts:365` and `:462` if they only serve it. Termination and cost stay bounded by the deterministic D54 budgets (work 10,000, emission 4 MiB, nesting 32, ranges 1,024, parse limit). This amends D54's "retain renderLimit as defense in depth": a cooperative wall-clock deadline cannot preempt anything the deterministic bounds do not already stop, and it turns host load into lost mail.
- **Evidence required:** a test that fails before and passes after, through a public boundary where possible (for example a campaign or tx render while `performance.now` is made to jump, or a stubbed clock seam if the renderer takes one; do not read source text). A perf note `docs/perf/B103-render-deadline.md`: the worst-case render time of a template that exhausts each deterministic budget (work, emission, nesting), median of 20, before and after, on this host, to show the deterministic bounds alone keep a render short.
- Owns, added: `src/templates/renderer.ts` (render limit only), D110 in `docs/design/09-decisions.md`, the D54 lines of `docs/design/06-templates.md` that describe `renderLimit`.
