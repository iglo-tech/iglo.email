# B2: Bounded retention

Goal: rows that only ever accumulate stop accumulating. Expired sessions and finished webhook deliveries are removed automatically, in small batches, and the history of sends gets a recorded retention decision.

## Behavior

1. **Sessions:** expired rows are deleted automatically. Denial of an expired session already holds and stays as it is.
2. **Webhook deliveries:** rows in a finished state are deleted after a retention period, 30 days unless you find a reason to differ. Pending and in-flight rows are never touched, and neither is any row the delivery loop can still claim.
3. **Send history:** decide what happens to `sends` and record it as a decision, for later owner review. Rule: nothing may be deleted that an old email's unsubscribe link, tracking link, bounce match, frequency cap or at-most-once check still needs. If keeping rows and clearing or compacting bodies or other data is what fits, do that; if keeping everything is right, say why with measured row sizes. Analytics numbers must not silently change.
4. **Batches:** each pass deletes a bounded number of rows in a short transaction, so a backlog of millions never holds the write lock long or starves sending. A loop takes an injected clock and follows the module ownership rule: each module deletes its own rows. A first start on a large table behaves the same way.
5. **Upstream:** listmonk's behavior for these routes stays. A deleted delivery leaves the list and count endpoints consistent.

## Acceptance

Time-dependent behavior is tested by advancing the injected clock. Tests prove: expired sessions go and valid ones stay; finished deliveries go after the period and pending ones never do; a pass honors its batch size; an unsubscribe link from an old send still works after a purge; analytics totals match before and after; restart resumes. Then `bun install --frozen-lockfile`, `bun run check`, `bun test test/server`, `bun run contract:normal`, serially, in the foreground.

This changes storage and scheduling, so store before/after measurements under `docs/perf/`: purge throughput and the write latency a concurrent send sees during a purge of a large synthetic backlog.
