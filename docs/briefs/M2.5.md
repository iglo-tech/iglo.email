## Behavior

1. **Subscription form.** `GET/POST /subscription/form`, `POST /api/public/subscription`, `GET /api/public/lists`, honoring `app.enable_public_subscription_page`, public-list visibility and `privacy.domain_*`. Existing subscribers aren't revealed: same response whether the address exists or not, as upstream. Double opt-in lists create `unconfirmed` membership and send the opt-in mail. This wires the automatic opt-in mail D38 deferred, and explicit `POST /api/subscribers/:id/optin` too.
2. **Opt-in.** `GET/POST /subscription/optin/:subUUID` confirms; GET alone doesn't confirm (a mail-scanner prefetch must not), as upstream.
3. **Preferences.** `GET/POST /subscription/:campUUID/:subUUID` and the `/m/` equivalent show the upstream preferences when `privacy.allow_preferences` is on. Forged UUIDs are a safe 4xx. Changes go through the existing unsubscribe effects, so enrollments exit in the same transaction.
4. **Export and wipe.** `POST /subscription/export/:subUUID` and `/wipe/:subUUID`, honoring `privacy.allow_export` and `privacy.allow_wipe`. Export returns upstream's data, including sends and events where they belong to the subscriber; say what you chose. Wipe deletes the subscriber atomically; cascades and enrollments behave as the schema says.
5. **View in browser and archive.** `GET /campaign/:campUUID/:subUUID`, and `/archive`, `/archive.xml`, `/archive/:id`, `/archive/latest`, `/api/public/archive`, honoring the archive settings. Archive pages show no personal data.
6. **Rate limits.** Subscribe, opt-in and unsubscribe are limited per IP in memory (07-api-and-ui), using the transport peer address as M1.3 login does. Bounded memory, on the injected clock. Excess requests get 429.
7. **Captcha.** Upstream's hCaptcha/ALTCHA settings: implement ALTCHA if it's small and native; otherwise leave it out and list it in the PR as a declared difference.
8. **Pages** are server-rendered TSX on the existing public shell; custom CSS/JS routes as upstream.
