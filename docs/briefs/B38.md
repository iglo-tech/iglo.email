# B38: Admin notification mails

Common rules: [_state-common.md](_state-common.md). Branch `task/B38-notify`. Lines from main at 5566120.

## Source

B36 audit ([12-completeness-audit.md](../design/12-completeness-audit.md), #88). `app.notify_emails` is stored and validated (`src/settings/defaults.ts:22`, `src/settings/validate.ts:83,97`), but nothing reads it. The upstream templates were ported and embedded (`src/templates/builtins/campaign-status.txt`, `import-status.txt`, `src/templates/builtins.ts:5-6,37-38`) but are never sent. As a result, a campaign that pauses itself on `app.max_send_errors` (`src/campaigns/runner/runner.ts:613-617`) leaves only a log line, and no operator hears about it. The admin field sits in the "Not available in this version" card (`src/admin/views/settings.tsx:205-218`).

## What to do

Port listmonk's admin notifications. Read upstream at the pinned commit `6fcd95f` from a local checkout (see `test/reference/README.md`), never from memory. Look for where upstream calls its notification sender for campaign status changes and imports (e.g. `internal/manager`, `cmd/notifications.go`, `cmd/import.go` / `internal/subimporter`), and match its triggers, subject lines and template data.

- **Campaign:** send `campaign-status` to every address in `app.notify_emails` when a campaign:
  - **finishes** (`store.finish` in `runner.ts:257, 300`);
  - is **cancelled** (status change to `cancelled` through the API, `src/campaigns/store.ts:332` area);
  - is **paused by the runner on `app.max_send_errors`** (`runner.ts:613-617`). A manual pause through the API does not notify, unless upstream does: follow upstream.
  - Include the counts the template expects (sent, to send, and so on).
- **Import:** send `import-status` when an import **finishes** or **fails** (`src/subscribers/import/importer.ts:292` and the `failed(...)` paths).
- **Delivery path:** use the existing durable send path, as `src/public/mail.ts:100-130` does for system mail: `sends.enqueueRequest` with `kind: "transactional"`. These sends have no subscriber, so check how an unlinked transactional send is represented (`src/messaging/sends.ts`, `src/tx/`) and use that form. Never send SMTP inside a transaction (AGENTS.md). Never send from inside the runner's claim transaction: enqueue after the status commit, or in the same write transaction as the status change if the sends module allows enqueue inside a caller's transaction. Check which one gives "exactly one notification per status change, even across a crash". With no addresses configured, send nothing.
- **From address:** `app.from_email` (first entry), as other system mail uses.
- **Module ownership:** the campaign runner and import modules must not query the sends tables directly. Pass a small notifier function into them from `src/main.ts` (no process-global state, no registry). The notifier lives in the module that owns system mail. Read `src/public/mail.ts` and choose the closest owner. A new `src/messaging/notify.ts` is fine if it only renders and enqueues.
- **Admin UI:** move "Admin notification emails" out of the `Unavailable` card into a live field on General settings. It is a comma-separated input bound to `app.notify_emails`, validated as addresses by the existing validation. Leave `app.lang` and `app.check_updates` where they are (B40 handles `check_updates`).
- **Docs:** add the notifications to `docs/design/04-sending.md` and `docs/operations.md` (one short paragraph). Remove `app.notify_emails` from any list of inert keys in `docs/design/07-api-and-ui.md` and `src/openapi/differences.ts`, if it is listed there.

## Tests (test-first, public boundaries, injected clock, SMTP test sink)

1. With `app.notify_emails = ["ops@example.com", "boss@example.com"]`, a campaign that finishes produces exactly one `campaign-status` mail to each address. The subject and body name the campaign and its final status and counts.
2. Cancelling a running campaign through the API produces one notification with status cancelled.
3. A campaign that hits `app.max_send_errors` (an SMTP sink that rejects) pauses and produces one notification saying paused. Manual pause behaves as upstream does.
4. An import that finishes, and one that fails on a bad CSV, each produce one `import-status` mail with the import's counts or error.
5. With `app.notify_emails = []`, nothing is sent for any of the above.
6. A notification never reaches a subscriber's activity, analytics or `send.failed` webhooks as if it were a subscriber send. Check what the unlinked transactional form does.
7. Admin settings page: the field is live, saving it round-trips, and invalid addresses get the existing validation error.
