## Goal

The dispatcher runs at the effective rate, the lower of `messaging.max_send_rate` and SES's `MaxSendRate`, and stops granting `marketing` and `campaign` slots when the remaining quota is at the hold line, resuming by itself when a newer snapshot is above it. Transactional is never held. Without API credentials nothing changes from today.

## Behaviour

Section 7 exactly:
- **Rate:** effective rate = `min(messaging.max_send_rate, MaxSendRate)` from the latest snapshot; without credentials, or before the first successful read, the setting alone. A new snapshot or a settings change calls `wake()` so the dispatcher re-reads `rate()`.
- **Guard:** `held()` is true while `Max24HourSend − SentLast24Hours ≤ max(2% of Max24HourSend, effective rate × 60 s)` on the latest snapshot. While held: marketing rows stay `queued` with no lease, running campaigns stay `running` with their heartbeat and their cursors do not move, transactional starts go on. A newer snapshot above the line clears it and calls `wake()`. One attention line when holding starts and one when it stops (no repeat while it stays held, no line on a failed read). A failed read keeps the last snapshot, so the hold state follows the last good one. No pause, no notification, no counter of the app's own. Without credentials: no guard.
- At-most-once: a hold never hands a claimed marketing row back as sendable twice; anything granted before the hold that already started is not retried.

## Tests

Mutants: hold line uses only 2% (10,000 case fails); transactional held too; resume without a new snapshot (on a timer); rate uses the setting even when SES is lower.
