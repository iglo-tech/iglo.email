The data directory becomes an instance: `instance.db` with its own migration manifest and the project registry, and each project in `projects/<slug>/`. One `Bun.serve` dispatches each request by `Host` to a project's router built by B138a's `createProject`. A fresh install is an instance with one primary project and behaves exactly as today. ## Behaviour

1. **Layout (section 1).** `instance.db` (+ wal/shm) at the data-directory root, migrated from `migrations/instance/` by the existing runner with the pre-migration snapshot rule; project databases at `projects/<slug>/iglo-email.db` keep `migrations/`, their `uploads/` and `stage/` move under the project directory. The instance lock (D69) stays one file at the root. Pragmas unchanged.
2. **Registry (section 3).** `src/projects/` owns the `projects` (slug, name, created time, primary flag) and `hostnames` (hostname, project, main or extra) tables. Slug format and uniqueness as in "Terms"; hostnames stored lowercase without port, unique across projects. At most one primary, and its main hostname is the instance host.
3. **Fresh install.** An empty data directory gets `instance.db` and one primary project. D149 fixes its slug (lead's default: `main`) and its name (the site name default). Seeding, initial users and the initial API credential behave as today for that project.
4. **Old layout refused.** A data directory with `iglo-email.db` at its root is refused at start with one plain message that the layout changed and nothing is converted (owner 2026-11-23: no upgrade path), exit non-zero, nothing written.
5. **Routing (section 2).** Lowercase `Host`, strip the port, look up main and extra hostnames; ignore `X-Forwarded-Host`. A project host goes to that project's router. The instance host and any unclaimed host go to the primary project when there is one. Without a primary: health answers on any host, `/admin` redirects to the instance host's `/admin/instance/projects` (the page itself is later work; the redirect target may 404 until then), everything else a plain-text `404` naming no project or hostname, with no per-request log line. The routing table is held by the instance object passed to the server, never module state, and supports adding and removing a project without restart (exercised by tests through the registry function; no UI or API yet).
6. **Root URL.** A project's `app.root_url` is `--root-url` with the host replaced by the project's main hostname (scheme, port, path kept), still read-only; links, Message-IDs, cookies, CORS and Origin checks derive from it as today. The primary project's root URL equals `--root-url`.
7. **Composition (section 3).** `main()` opens the instance, then calls `createProject` for each registered project; all are wired before the bind, loops start after it, and stop in reverse on shutdown. A project's modules see only its own `Database`; no `ATTACH`, no instance `Database` handed to a project. Any step writing two databases states its order and why a crash between the writes is safe.
8. **Process-wide budgets (invariant 7; B138a r1 backlog 2).** Every limiter, runner and budget that `createProject` builds today and that section 9 lists as process-wide (public rate limiters, the read-only query runner and analytics reader concurrency, the ALTCHA replay state, the tx attachment memory budget, helper child limits, VmRSS watchdogs) is created once by the instance and passed into `createProject` as a shared object, not a number. Each project may keep its own state inside that one budget. A test with two projects shows a budget is shared (for example the query runner's concurrency or the rate limiter's peer bound counted across both).
9. **Logs and health (section 9).** Each project has its own log buffer; `GET /api/logs` on a project host shows only its lines; stderr lines carry the slug or `instance` as prefix. With one primary project the stderr format change is the only visible difference: list it in 07 if a contract notices, otherwise in the PR. A project's health route reports that project. The instance health route is the same path on the instance host and unclaimed hosts without a primary; it is unhealthy if any project's loops are down. With a primary project, `/health` on the instance host keeps today's answer.
10. **Narrow options (B138a r1 backlog 3).** `ProjectOptions` no longer carries host, port, `initialAdmin`/`initialApi` or other instance-level config; the instance passes the project its root URL and what it seeds.
11. **Cleanups (B138a r1 backlog 1 and 4).** Move the five `no-unsafe-*` exceptions for `src/main.ts` in `oxlint.config.ts` to `src/projects/compose.ts` (only where still needed) and drop the inline disable in `compose.ts`. Update the header of `test/scheduler/runtime.ts` to name `createProject`.

## Tests

- **Host header first (section 15).** Check that Bun's `fetch` sends a caller's `Host` header unchanged to a loopback server; if not, add a small raw-HTTP test helper. No test depends on `*.localhost` resolution, fixed ports or DNS.
- **Two projects isolated.** A fixture registers projects `a` and `b` (plus a primary) through `src/projects` before starting the compiled executable on port 0. For every route family (subscribers, lists, campaigns, templates, sequences, sends, events, media, webhooks, settings, MCP `tools/call`, public pages): A's API credential and session cookie get 401/403 on B's host, B's rows never appear in A's responses, links and Message-IDs in A's mail carry A's hostname, and an unclaimed host reaches only the primary.
- **Routing table without restart:** a project added and removed through the registry function is served and then answers like an unclaimed host.
- **Without a primary:** unclaimed host → fixed 404; health answers; `/admin` redirects.
- **Old layout refused**, **fresh install layout**, **budgets shared**, **logs per project**, **health per project and instance**.
- **Invariant 2:** every existing HTTP-level test, contract suite and e2e spec passes against the primary project unedited. Allowed edits: tests that construct internal modules directly where a signature changed, and tests that assert the data-directory layout. List each edited test with its reason in the PR body.
- Each new test has a mutant that it catches (routing falls through to the wrong project, budget built per project, old layout accepted); name them in the PR.
