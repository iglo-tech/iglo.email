## Behavior

1. `GET /api/subscribers` takes upstream's parameters (`query`, `search`, `list_id` (repeatable), `subscription_status`, `subscriber_status` if present, `order_by`, `order`, `page`, `per_page` including `all`), its permissions (`subscribers:get_all` or `subscribers:get` with list scoping) and its response envelope and total. Match its results for the dashboard and SDKs. `search` uses FTS5 on name and email; match upstream's results for ordinary words and email addresses. Order-by columns are allow-listed.
2. Raw `query` (`subscribers:sql_query` where upstream requires it) is a SQLite `WHERE` fragment wrapped as in 03-data-model. It runs on a **read-only connection** and cannot write: test that INSERT, UPDATE, DELETE, ATTACH and PRAGMA writes are refused. Each query has a **real time limit** that actually stops the SQLite work, not just the HTTP wait. If bun:sqlite exposes no interrupt or progress handler, run the query in a Bun Worker with its own read-only connection and terminate it on timeout. Measure and document the choice. Bound result memory with paging. Fragments that inject a second statement or a comment terminator are refused. The SQLite-dialect difference stays marked.
3. Query-selected bulk actions (`/api/subscribers/query/delete`, `/query/blocklist`, `/query/lists`) select with the same rules and permissions as upstream, then apply the action atomically on the write connection in bounded batches. A concurrent change can't redirect the action, and list-scoped roles can't affect subscribers outside their lists.
4. Export (`GET /api/subscribers/export` or upstream's route) streams CSV with bounded memory, using upstream's columns and filters, and the same permissions.
