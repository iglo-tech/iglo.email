## Goal

One admin account lives in `instance.db` and is copied into every project as a normal, protected Super Admin user. Password and TOTP changes from any path write through to the instance and every copy. The instance host gets its own login, session, Account page and the handoff that signs the admin into a project with one sign-in. Project authentication, users, roles and API users stay exactly as today.

## Behaviour

1. **Account (section 5).** `instance.db` holds exactly one admin account: username, password hash, optional TOTP, optional email. The users module owns this table and its SQL. `IGLO_EMAIL_ADMIN_USER`/`IGLO_EMAIL_ADMIN_PASSWORD` create it on the first start with an empty account table, with today's validation. B138b's stand-in (seeding every project with no users from the same variables) is replaced by the copy. Without those variables and without an account, D153 fixes the behaviour (lead's default: no account, the instance login refuses everyone, projects behave as today).
2. **Copies.** Each project has exactly one user row marked as the admin's copy: same username, password hash and TOTP, Super Admin role, password login on. Written when a project is wired (start and runtime `add`), from `instance.db` to the project. A project row with the admin's username and no copy mark is adopted as the copy (it is B138b's seeded admin) and overwritten; D153 records it. `IGLO_EMAIL_API_*` still seeds the primary project only.
3. **Write-through, every path.** Password and TOTP changes from the project profile and 2FA routes, the email password reset (`issueReset` and its completion), the instance Account page and the CLI each write `instance.db` first, then every project's copy. Each copy gets the same session effect a project's own change has today (which sessions end). A crash between the writes is repaired at the next start because the instance is the source. State the order in D153 (invariant 6). Existing profile, 2FA and reset tests and e2e specs keep passing on the copy, unedited.
4. **Protection.** Through a project's API or UI the copy cannot be deleted, disabled, renamed or have its role or password-login flag changed: `403`, nothing written. Listing, viewing and its own profile/2FA work as today. This is the only change to project user behaviour.
5. **Reserved username.** Creating or renaming a project user to the admin's username (compare as the users module compares usernames today) is `409`, nothing written.
6. **Instance routes on the instance host.** `/admin/instance/**` and `/api/instance/**` on the instance host are served by the instance, before the primary project's router; every other path on the instance host still reaches the primary as today. On a project host these paths belong to the project (its 404s, as today). Instance routes never accept API credentials (`401`) and are not in OpenAPI or MCP.
7. **Instance login.** `GET`/`POST /admin/instance/login`, checked against `instance.db`, TOTP step when enrolled, with the same brute-force limits and lockout behaviour as today's project login (one shared budget, invariant 7). Session cookie `instance_session`, `Path=/`, the same attributes and lifetime as the project `session` cookie; both cookies coexist on the instance host. Logout and expiry per host. Every state-changing instance route needs the instance session plus CSRF, using the same CSRF scheme as project pages. After login go to a safe `next` or to the Account page (the Projects page is B143).
8. **Account page.** `/admin/instance/account`: change password (current password required) and enrol/disable TOTP, with the project 2FA flow's rules; write-through as in 3. Server-rendered TSX with the existing admin layout, Alpine.js and Oat; no instance navigation beyond Account and logout yet.
9. **Handoff.** With a valid instance session, `GET /admin/instance/open/<slug>?next=<path>` mints a random 32-byte token, held in memory by the instance (passed explicitly, invariant 8), single use, 60 s on the injected clock, bound to the slug; answers `303` to `<project root URL>/admin/handoff?token=…&next=…`. The project redeems it in-process through a narrow function, creates a normal session for its copy through the users module's `createSession(userId)`, sets today's cookie and answers `303` to `next`. `next` must start with `/` and not `//` (also reject backslashes and control characters), else `/admin`. A spent, expired, foreign-slug or unknown token is `403` with no session. Unknown slug is `404`.
10. **CLI.** `reset-password --user <name>` and `reset-totp --user <name>`: when `<name>` is the admin's username they act on the instance account and write through to every copy under the one lock (same session effects); otherwise they act on the primary project's user as after B138b. Update the help text.
