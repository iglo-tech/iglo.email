# B102: messaging TLS harness picks the host's Mailpit and fails fast

Branch `task/B102-tls-harness-arch`. PR title "B102: messaging:tls uses the host architecture's Mailpit". Read `docs/briefs/_B97-common.md` first. Source: B100 pre-flight on the arm64 container, `bun run messaging:tls` exit 124.

## Problem

`test/messaging/tls.ts:41` resolves `upstream/reference/mailpit-linux-amd64.tar.gz-mailpit`. `reference:prepare` (`test/reference/prepare.ts:23-31`) downloads the binary for the host (`linux-arm64` here), so on arm64 the spawn fails with ENOENT, and the script then waits until the 600 s `reference:run` deadline instead of failing. CI runs this step only on x64, so it never showed; the owner's "Local first" rule needs it to run on arm64.

## Task

1. Resolve the Mailpit binary for the running architecture with the same mapping `prepare.ts` uses (import it from the module that owns it, or export one small function there; no duplicated table).
2. A spawn failure (or Mailpit not becoming ready) fails the script immediately with a clear message, not at the outer deadline.
3. Check the other scripts the CI/release steps run (`test/messaging/*.ts`, `test/sends/*.ts`, `test/reference/*.ts`, `test/contract/*.ts`, `test/e2e/*`) for any other hard-coded architecture or platform-specific binary path, and fix them the same way.

## Owns

`test/messaging/*`, `test/reference/prepare.ts` (export only), any other test script found in item 3. No product code.

## Acceptance

In the container (reference recipe from `_B97-common.md`): `bun run check` (user `bun`), then as root with the Docker socket: `bun run reference:prepare`, `bun run messaging:tls`, `bun run messaging:corpus`, `bun run messaging:routing`, `bun run server:reference`. Also show the fail-fast path once (e.g. temporarily point at a missing file in a scratch copy, not committed) and that it exits in seconds.
