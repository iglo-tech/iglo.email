## Goal

`iglo.email backup` snapshots `instance.db` (instance settings including SMTP and SES, the admin account, the registry) and every project into one timestamped directory; `--project <slug>` snapshots one project. The restore hold (D67) is per database: a restored project database holds only that project's sending; a restored `instance.db` holds all sending until released.

## Behaviour

1. `backup` (no flag): one directory `<output>/<timestamp>/` with `instance.db` and `projects/<slug>/iglo-email.db` (+ `uploads/` as today) for every registered project. Each database snapshot keeps today's guarantees: the read-only helper, a verified copy, the restore hold written into the snapshot. One verification result for the whole set; a failure on any database fails the command and leaves no partial directory that looks complete (D158 says how).
2. `backup --project <slug>`: that project only, same guarantees. Unknown slug: non-zero exit, nothing written.
3. `--output` inside `<data>/projects/` (or inside the data directory where a restore would read it): refused with a plain message.
4. **Hold per database.** A project database with a hold holds only that project's sending. An `instance.db` with a hold holds sending in every project until released. `backup --release-hold` takes `--project <slug>` for a project database and releases the instance hold without it; D158 fixes the exact flags and messages.
5. Restore is still a file copy with the server stopped; `docs/operations.md` documents restoring one project, restoring the instance, and that the admin copy follows the instance account (B140).
