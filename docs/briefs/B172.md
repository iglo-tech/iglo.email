1. **Project-authored script runs in the origin that holds the instance admin's credentials** (blocker). `/admin/instance/login` and `/admin/instance/login/twofa` render `PublicShell`, which always loads `/public/custom.js` and `/public/custom.css`; on the instance host these resolve to the primary project, whose `appearance.public.custom_js` any primary-project user with `settings:manage_all` can set. The instance session and CSRF cookies are `Path=/` on that same origin, and the primary project's own public and admin pages are on it too. A primary-project user can therefore read the instance admin's password and TOTP on the login page, or, with a live instance session, call `/api/instance/*`. The requirement, to record in D200: **no project-authored content can run script in the origin where instance credentials are entered or sent.**
   - Find every way project-authored content can execute there: the public custom JS and CSS, uploaded media served from that origin (a `.js`, `.svg` or `.html` upload loaded by `script-src 'self'` or opened directly), campaign archive and template HTML, anything else under the CSPs in force. List each one in D200 with how it is closed.
   - Then choose and record the design. The instance login and 2FA pages must load no project custom assets. Beyond that, either separate the origins, or make sure nothing project-authored can execute on the instance host. Examples: the primary project's public custom JS is not served there; uploads are served there with `Content-Disposition: attachment` and `X-Content-Type-Options: nosniff`, never as script. The instance cookies' scope should also be tightened where it helps (`Path`, `__Host-`), noting that a cookie path alone does not isolate same-origin script.
   - Existing deployments' public URLs keep working, or the upgrade note says exactly what changes.
   - Tests: the instance login and 2FA pages reference no `/public/custom.*`. A primary-project custom JS is never served as script on the instance host, or never runs where instance credentials live, per the chosen design. Each other vector you list has a test showing it closed.
2. **Instance login is unstyled when there is no primary project** (major, `instance.ts`). With no primary project, only `/admin/static/` reaches the instance router, so the login page's `/public/static/style.css` and favicon return 404. Fix: forward `/public/static/` too, or have the instance pages use only `/admin/static/` assets, consistent with item 1. Test: delete the primary project; the login page's CSS and favicon answer 200.
3. **A project deleted and recreated under the same slug mid-backup publishes an inconsistent backup** (major, `snapshot.ts` `createBackup`). B170 compares slug lists only. The open handle keeps the old database while uploads are read from the new project's directory, so a delete-and-recreate passes both checks. Also, a `--project <slug>` deleted before `sealSnapshot` reports a misleading upload-path error instead of "Project <slug> was deleted while the backup ran". Fix: record each included project's identity (slug with `created_at`, plus the project directory's and database file's device and inode) before snapshotting. Verify it in the snapshotted `instance.db` and live before publishing; any mismatch fails with the existing errors. The failure path checks the live registry for `--project` too. Tests through the compiled CLI with the existing test-only publish hook: delete-and-recreate fails, whole and `--project`, with nothing published; the early-deletion case reports the documented message.
