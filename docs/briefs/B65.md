## Tests (new `test/e2e/specs/consent.e2e.js`, about 12–14 tests)

Each test makes its own data through the public API with unique names, and takes every link **from the received mail's body or headers**, never built from API UUIDs (section 3, items 4–5). Drive the public pages in the browser where a person would click.

1. Double opt-in: subscribing to a double opt-in list (public form or API) sends a confirmation mail; opening its `optin_url` and confirming (`GET` shows the page, `POST` confirms) makes the subscription `confirmed`, seen through the admin API.
2. A wrong or unknown subscriber UUID on the opt-in and unsubscribe pages changes nothing (status before equals status after) and shows the product's error page, not a crash.
3. The unsubscribe link in a campaign mail unsubscribes from that campaign's list only; the person's other list stays subscribed.
4. The next campaign to that list does not reach the unsubscribed person; a campaign to the other list does (count in the sink with `settledMail`).
5. The campaign mail carries `List-Unsubscribe: <url>` and `List-Unsubscribe-Post: List-Unsubscribe=One-Click`; a plain `POST` of `List-Unsubscribe=One-Click` to that URL (the way a mail client does it, no cookies, no CSRF token) unsubscribes the person.
6. The `/m/…` message page linked from the mail shows the message, and its unsubscribe action works.
7. "Unsubscribe from all" / blocklist from the public page: the next campaign to any of the person's lists sends them nothing.
8. Re-subscribing through the public form after unsubscribing follows the list's opt-in rule (single opt-in: subscribed again; double opt-in: a new confirmation mail, unconfirmed until clicked).
9. A sequence marketing step reaches a consenting (confirmed / subscribed) person in the sink (`sequences.e2e.js:103` covers only the refusal).
10. A waiting sequence enrollment exits when its person unsubscribes through the mail link, and another when the person is blocklisted: no later step mail arrives, and the enrollment shows as exited through the API or the explorer.

Use real time; the server has no clock control. Keep sequence waits at `PT0S` or the smallest the product allows, and read the scheduler interval from `src/scheduler/scheduler.ts`, not from memory. No sleeps where a wait condition exists; every wait bounded.

If a test reveals a real product bug, do not fix product code here. Mark that test `test.fail()` with a comment that names the bug, and report it prominently in the PR. The lead opens a fix task.
