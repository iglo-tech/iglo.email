# B101: test sends off the outbox pool; runner test timing

Branch `task/B101-test-pool-runner-timing`. PR title "B101: isolate test sends from the outbox pool; runner test timing". Decision record: D109 (lead, 2026-11-17), only if item 1 changes product behaviour. Read `docs/briefs/_B97-common.md` first (verification runs in the Linux arm64 container).

## 1. A stuck test send can cut real sends (B97 backlog)

`src/messaging/email.ts:524-540`: each started message has a 60 s cut-off; when it fires on a started operation, `cancelPool(pool)` destroys every socket of that pool and cancels every operation on it, so other started sends on the same pool settle `unknown`. Campaign test sends (`src/campaigns/routes.ts` `test`, `priority: "outbox"`) and B97's step test sends (`src/sequences/routes.ts`) push into the same keyed pool as real outbox, campaign and sequence sends. A test send to an address whose receiving path stalls (greylisting tarpit, slow relay) can therefore cut real marketing sends mid-transaction, which settle `unknown` (counted, never retried; at-most-once holds, but real mail is lost or ambiguous because of a test).

Task:
- **Prove it first** with a test through the SMTP sink fixture (a sink that stalls DATA for one recipient) and the injected clock: a stalled test send plus concurrent real sends on the same server; show real sends settle `unknown` before the fix.
- **Fix:** test sends (campaign and step) run on their own pool, separate from the keyed real-send pool. The emailer already has temporary pools (`temporary` in `push`/`createPool`, used for the SMTP settings test with a 10 s cut-off); prefer an option on `push` that gives test sends an isolated pool keyed separately (so tests share their own pool, not real sends'), with the normal 60 s cut-off. Real sends then never share a socket with a test. Keep the send-rate limiter accounting and restore-hold refusal as they are for test sends, and keep their 429 in-flight caps.
- After the fix the same test shows real sends `sent`, and the stalled test alone `unknown`/failed. Shutdown (D104) still drains/cancels the test pool.
- Measurements (sending change): `docs/perf/B101-test-pool.md`, before/after of the existing `sends:production` (or the closest existing sending measurement script) showing no regression for real sends, plus the stalled-test scenario counts.

## 2. Runner test timing

`test/campaigns/runner/runner.test.ts:575-615`, "tracked links personalized per subscriber do not accumulate across batches": 300 members, a 15 s wall bound in `f.drive` (comment: ~0.6 s locally, >3 s on the arm64 CI runner). Under `bun run test` (4 workers) in the arm64 container it timed out twice (17.5 s; once at sent 260/300), and passes alone in ~5 s. Find where the time goes (profile one run under load: heap stats calls, per-message work, the fixture's drive loop) and fix the test so its bound has real margin under 4-worker load on arm64 without weakening what it proves (personalized links must not accumulate across batches; keep a count large enough to span several batches). Acceptable: removing avoidable per-iteration work in the test or fixture; reducing members to the smallest count that still spans ≥3 batches; raising the wall bound only together with the test's own timeout and an explanation. Not acceptable: skipping, retries, or loosening the memory assertion. Show 20 consecutive passes of the file under `bun run test` load in the container (or 20 full `bun run check` passes if cheaper to script), and the before failure rate if reproducible.

## 3. Media cache test under load

"attachments over the cache budget are evicted and read again for the next batch" (find it with `grep -rn` under `test/`) failed twice in one B99 review (`bun run check`, 4 workers, arm64 container) and passes 3/3 alone; a `main` baseline passed. It checks memory reclamation. Find why it fails under parallel load (GC timing, a heap measurement that other work in the process disturbs, a wall bound) and make it deterministic without weakening what it proves (evicted attachments are re-read; the cache budget holds). Same evidence bar as item 2: 20 passes under 4-worker load.

## 4. A failed test send is logged nowhere (B99 fixer finding)

Campaign and step test-send routes attach `.result.catch((error) => logger.error(error))` to the emailer push, but `result` resolves with an outcome on every SMTP failure and never rejects, so a refused, rejected or timed-out test send leaves no trace: the caller got `true` (queued), and `GET /api/logs` stays unchanged. Fix: when a test send's outcome is not delivered (any non-sent outcome, including `unknown` and not-started at shutdown), write one attention line (the logger used for things that need attention) naming that it was a test send, the campaign or sequence/step ID, the recipient address and the SMTP stage/reason, with no message body. It must show its real text in `/api/logs` (add it to the log buffer's fixed messages like B98's XFF line; keep the address off the buffered text if `/api/logs` is not admin-only, as B98 decided, and on stderr only). Test through HTTP with a sink that refuses the recipient: the test send answers `true`, then the log line appears; a delivered test send logs nothing. Update the MCP server instructions in `src/mcp/routes.ts` and operations.md's authoring loop (B99) to say a failed test send appears in `get_logs`, and adjust `test/mcp/agent-guidance.test.ts` accordingly. In the same paragraphs (instructions, README agent section, D108), fix the B99 r2 wording: reading users and roles are tools (`get_users`, `get_user_roles`), only changes to them are excluded; say "bulk deletes and deletes addressed by query" so single deletes such as `delete_subscriber` are not read as excluded; and "Never repeat a send to check it" for real and test sends alike. Keep the instructions within ~1,500 characters.
