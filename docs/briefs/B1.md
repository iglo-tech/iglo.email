# B1: Enforce one process per data directory

Goal: a second `iglo.email` server pointed at a data directory already in use refuses to start, before it touches the database. D15 and the lease-based loops (outbox, scheduler, campaign runner) assume one process; today nothing enforces it, so an accidental second copy can break at-most-once marketing.

Repository https://github.com/iglo-tech/iglo.email. One worker, one PR, no helpers. In your supplied isolated checkout, fetch origin/main and create `task/B1-instance-lock` from it.

## Behavior

1. **Refuse:** the serving process takes an exclusive lock on the data directory before opening the database or running migrations. If it is held, the process prints one clear error naming the directory and exits nonzero. Nothing is written to the database.
2. **Crash release:** the operating system frees the lock when the process dies, including `kill -9`. A restart right after a crash starts normally. No stale-file cleanup, PID file or timeout. A leftover lock file on disk must not block anything.
3. **Mechanism:** no new runtime dependency. A suggested native route is a small dedicated SQLite file in the data directory held with `PRAGMA locking_mode=EXCLUSIVE` after a write, since SQLite's file lock dies with the process. Prove it holds across two compiled processes and say why you chose it. Do not take the lock on the main database: the read-only helpers (D62) and backups must keep working.
4. **Other commands:** check every command that writes (`reset-password`, restore, migrations and so on) and every one that reads (`backup`). A command that is unsafe beside a live server refuses with the same error; a command that is safe stays as it is. Say which is which in the PR. The read-only helper children must not take the lock.
5. **Data directories on shared filesystems:** say in `docs/operations.md` that the guarantee needs a local filesystem.

## Acceptance

Through the compiled executable, from temporary directories: second start refuses and exits nonzero with the first still serving and its data unchanged; `kill -9` then restart succeeds; graceful stop then restart succeeds; two different data directories run side by side; analytics and `backup` still work while serving; each refusing command refuses. Then `bun install --frozen-lockfile`, `bun run check`, `bun test test/server`, `bun run contract:normal`, serially, in the foreground. Startup is not a send path, so no `docs/perf` run is needed; report startup time before and after if it moves.

Tests use real processes; no sleeps beyond waiting on `/health`.
