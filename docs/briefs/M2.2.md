## Finite behavior

D53 is authoritative; implement all of its native contract, not just the happy path.

1. Expose a concrete owner API for enqueueing already prepared messages, lookup and lifecycle operations that M2.3/M5 can later call. Enqueue is durable, not an in-memory-only queue. One primary recipient per journal row, nullable external-recipient identity, automatic non-reused integer ID and unique UUID. Assign/store the stable Message-ID before commit and reuse it for proof-authorized retries. Capture immutable byte/header/attachment payloads with a versioned JSON schema, base64 for bytes, no local paths/URLs or SMTP passwords/keys. Bound the encoded payload at 8 MiB, each body/alt-body at 1 MiB, attachments at ten and 4 MiB decoded total, headers at 64 entries with 2 KiB values; validate address/subject/header shape and use finite decoding. Reject invalid input atomically, without creating a broken queue row or leaking payload. Caller mutation after enqueue must not change a send. No payload or secrets in journal HTTP projections.
2. Recover pre-existing sending rows to unknown at startup before new claims; do not interpret expired leases as permission to resend. Claim queued/due rows under BEGIN IMMEDIATE, committing sending/attempts/claimed_until before calling emailer.push outside the transaction. A small bounded claim (one at a time is acceptable for this component) must not mark an unbounded batch as sending or starve HTTP/shutdown. Wake promptly after owned enqueue, retain bounded idle polling/restart recovery and use the injected clock for all time/backoff. A loop failure must become visible to the process, not silently leave a healthy-looking server with a dead sender. No async transaction callback or write replay.
3. Use D24/D53 proof classification: accepted (including subset) -> sent with sent_at and safe partial context, never replay. Ambiguous -> unknown. Proven permanent/non-retryable -> failed. Only positively proven transient non-acceptance of a transactional message requeues after 1/2/4/8 seconds, at most five SMTP attempts total. No accepted recipient may be retried. Refusal is transient only for an actually observed TCP ECONNREFUSED; supported explicit AUTH4xx and all-RCPT rejection evidence must be concrete. Generic DNS/TLS/timeouts/disconnect/4xx/5xx labels or DATA/final-ACK failures never establish retry safety. Do not broaden M2.1 classifications just to make all failures retryable. Terminal safe categories only, no provider exceptions/logs, no credentials.
4. Use current subscriber-owned identity/blocklist checks at the final admission seam. Deleted or replaced linked identities and changed recipient addresses must not be silently reinterpreted as external recipients. Transactional external recipients require no synthetic subscriber. M2.4 supplies the real consent/cap/unsubscribe policy. Production marketing must fail closed until it exists, rather than accidentally exposing incomplete marketing sending through resend. For component tests, an explicitly injected policy may authorize marketing fixture messages through the same real outbox to verify no automatic retry/duplicate; label that evidence precisely. This staging is authorized completion of the outbox task, not a blocker or a claim that M2.4 is done.
5. Implement production GET /api/sends, GET /api/sends/:id and POST /api/sends/:id/resend exactly as D53. Reuse common auth/ID/error/envelope boundaries. sends:get is an explicit global journal read grant; sends:manage is required for resend, tx:send/list roles alone do not grant it. Collection has bounded paging, exact allowed filters and deterministic ID-desc order. Missing row404, malformed recognized input400, ineligible/payload-unavailable/policy-unavailable resend409. Keep precise 64-bit IDs, nullable references, safe statuses/categories and no private payload/idempotency/provider projections.
6. Resend accepts empty input or JSON {} within the existing body limit, drains/validates the body then revalidates current principal/permission/CSRF/Origin again inside the short creation boundary. Look up a pre-existing retry_of child before status rejections so retries return its current projection. Concurrent/repeated requests must create one new child at most, retaining the original and lineage, new UUID/Message-ID and no copied unique idempotency or enrollment/step claim identity. A failed/unknown child can itself be explicitly resent later. Do not send mail synchronously in this transaction or silently requeue the original unknown. An explicit resend may duplicate previous uncertain delivery; accurately document this limit.
7. Stop new claims first on shutdown, immediately start emailer.close's absolute five-second drain alongside HTTP stop, record completed/canceled outcomes while SQLite remains open, and only then close the journal/DB. Shutdown/restart never turns uncertainty into a retry. Current M2.1 settings SMTP diagnostics must keep working; no global cancellation/transport regression.
