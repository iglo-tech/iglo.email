# External sources

Status: planned for the next 2.x minor (owner direction 2026-11-25, [D169](09-decisions.md#d169-external-sources-pocketbase-first-owner-2026-11-25)); a switchable module with connectors since 2.3.0 ([D187](09-decisions.md#d187-sources-module-and-connectors-owner-2026-11-26), [D188](09-decisions.md#d188-the-sources-module-switch-and-the-connector-list-b162a-lead-2026-11-27)). Briefs: [B150](../briefs/B150.md), [B162](../briefs/B162.md). Each task adds an "As built" note to the section it implements.

An application that keeps its users' activity in its own PocketBase can let iglo.email read that activity there instead of pushing events to `/api/events`. PocketBase stays the only store of what users did: iglo.email copies none of it. The source is event-driven (a live subscription); nothing polls it on a timer.

The events API and the local `events` table stay for applications that push. A sequence uses one or the other, never both.

## 1. The interface

`ExternalSource` is a small interface with PocketBase as its first and only adapter (D89: one adapter until a second is needed; the interface exists so sequence code does not depend on PocketBase details). One source per project, configured in the project's settings.

| Operation | Meaning |
|---|---|
| `subscribe(topics, handler)` | Live records (events `create`, users matching the leaving filter) |
| `catchUp(topic, from, page)` | Keyset pages of records created (or updated, for users) at or after a bound |
| `recipient(externalId)` | The recipients-view row of one user: address, name, opt-out field, other fields; `null` when absent |
| `record(id)` | One events record; `null` on 404 |
| `latest(filter)` | The newest events record matching a filter |
| `count(filter, upTo)` / `exists(filter)` | A bounded count; existence |
| `scan(filter, fields, limit)` | Keyset pages over `(occurredAt, id)` for aggregates |

Every operation takes an `AbortSignal` and a timeout. Errors are classified as **transient** (network error, timeout, 5xx, 429) or **permanent** (400, 403, 404 where a record was not expected to vanish, a missing field). No operation ever runs inside a SQLite transaction.

### As built (B150a)

[D170](09-decisions.md#d170-source-settings-pocketbase-adapter-and-test-harness-b150a-lead-2026-11-25) records the choices this section left open. Where this list and the text above differ, this list is the code.

- **Modules.** `src/sources/source.ts` is the interface (`ExternalSource`, `SourceError` with `kind` transient or permanent and the answered `status`, `isSourceError`, `EventQuery`, `SourceEvent`, `ScannedEvent`, `SourceRecipient`, `PAGE_LIMIT` 1000, `SCAN_LIMIT` 100,000, `DEFAULT_TIMEOUT_MS` 15 s). `src/sources/pocketbase.ts` is the adapter (`createPocketBaseSource({config, clock, guard, transport?, maxResponseBytes?})`), `src/sources/filter.ts` the filter literals and dates, `src/sources/connect.ts` the private-address guard, `src/sources/json.ts` the typed JSON boundary. B150b adds `subscribe` and `catchUp` beside the adapter.
- **Queries.** An `EventQuery` is `{user?, names?, after?, through?, data?}`: the user relation equals, the name is one of `names` (an empty list matches nothing, at most 100), `occurredAt` strictly after `after` and at or before `through`, and each `data.<path>` equals a scalar. The adapter writes the filter from the mapped field names; every query also requires a non-empty `occurredAt`, so a record without one is never counted. B150c re-checks `data` strictly on fetched rows.
- **Operations.** `recipient(id)` and `record(id)` read one row; an ID outside `[A-Za-z0-9_-]{1,100}` is a permanent error before any request. `latest` sorts `-occurredAt,-id`, one row. `scan(query, fields, limit)` is an async generator of pages sorted `occurredAt,id`, keyset on the last row's raw `occurredAt` text and ID, `perPage` at most 1000, `skipTotal=1`, `fields=id,occurredAt` plus the requested mapped fields; `count(query, upTo)` scans IDs only up to `upTo`, and `exists` is `count(…, 1)` (`perPage=1`).
- **Absent answers are confirmed.** PocketBase 0.40.5 reads an invalid or revoked token as a guest: a rule-protected list answers `200` with no items and a view answers `404`, never `401` (measured). So `null`, an empty or short last page are confirmed with `POST /api/collections/<auth>/auth-refresh`: `200` proves the read was authenticated (a token is never revalidated once revoked); `401` signs in again and the read is repeated once. The check is of the token the read used, also when a renewal has superseded it as the held token (a superseded token still passes, a revoked one gets `401`). Checks are never shared: each is its own request on its caller's signal and time limit, since a `200` proves only reads that finished before the check was sent (B163, [D191](09-decisions.md#d191-post-release-audit-fixes-b163-lead-2026-11-27)). A `404` by ID is also checked against the collection (a missing collection is a `404` too, and is permanent); B168 ([D196](09-decisions.md#d196-last-audit-pass-fixes-in-the-sources-b168-lead-2026-11-27)): that probe must answer a PocketBase list (`items`, every one an object), as every page read must, so a `200` that is none (a proxy's `{}` or an empty body) is a permanent failure of the settings, never an absent record. A `401` or `403` on a read signs in again and repeats it once.
- **Tokens.** Signed in with `auth-with-password`; renewed half way to the token's `exp`, measured against the answer's `Date` header and kept on the injected clock (60 s when either is missing). One sign-in runs at a time, shared by every caller needing one meanwhile; it runs on the adapter's own 15 s limit and no caller's signal, and each caller waits for it on its own signal and time limit, so one caller's abort or timeout fails that caller only. A caller already aborted starts no sign-in and leaves the held token as it is (B163, D191).
- **Limits.** Each request has its own time limit on the injected clock and races the caller's signal (DNS cannot be cancelled). A body is read up to 32 MiB; a page over it is read again with a quarter of the page size it was sent with (B166, D194: of the `perPage` sent, so a short last page or an `exists` is not sent again as it was), down to one record, and a single record over it is permanent after that one request. A JSON body nested deeper than 64 levels is permanent. Redirects are never followed.
- **Errors.** Network failure and the time limit are transient, as are `429` and `5xx`; `400` (an unknown field in a filter, measured), `403`, a refused sign-in, a missing collection or mapped field, a body that is not JSON and the private-address refusal are permanent. A caller's abort rejects with the signal's reason, not a `SourceError`. B166 (D194): the permanent failures that are one record's own are `RecordUnreadable` (`src/sources/source.ts`), so a caller can tell them from the configuration's: a 2xx answer whose JSON nests deeper than 64 levels on any record read (a record by ID, `latest`, a `scan` page, a stream page), a single record over the limit (by ID, or a page already narrowed to one record), and a mapped field of a record not of its type. A 2xx body that is not JSON (a proxy's, SSO, login or maintenance page) is a plain permanent failure on every path, the configuration's, and so is a `200` record GET whose JSON is no object; a sign-in, token check, collection probe or realtime subscription answered with JSON nested too deep or an answer too large is plain permanent too. A permanent failure of the sign-in or the token check is `AuthRefused` whatever its status (PocketBase answers a refused sign-in `400`, as it does a refused filter). A filter the adapter cannot write is `UnfitQuery` (`src/sources/filter.ts`), the query's own. PocketBase 0.40.5 refuses a filter longer than 3,500 bytes (`400`, measured): `data` comparisons are written only while the filter stays within 2,900 bytes, the rest left to the caller's strict check (`EventQuery.data` is a narrowing).

## 2. Settings (project keys)

Secrets are stored and masked as the SES secret key is.

- URL; service-account credentials: an auth collection the operator creates for iglo.email (for example `services`), identity and password (secret).
- Events collection and field mapping: `user` (relation to the user), `name`, `data` (JSON), `occurredAt`, `key` (optional idempotency key).
- Recipients collection, typically a view, and its mapping: `email`, `name`, opt-out field. Addresses are read here, never from the auth collection (auth collections hide `email` from non-owners unless `emailVisibility` is on).
- Users collection to watch for people leaving and its filter (for example `deletedAt != ''`).
- **Guests must not read the events collection or the recipients view** ([D172](09-decisions.md#d172-sequences-and-conditions-on-a-source-b150c-lead-2026-11-25)): their list and view rules admit the service account only. PocketBase reads a revoked token as a guest and the adapter confirms its token only after a short or empty answer, so a guest-readable collection could answer a revoked token with a full page of what guests see and a `scan` or `count` would miss records. Test connection checks it (section 2's "As built (B150c)"); pages are not confirmed one by one.
- `grant_lists` rules: "an event matching P grants lists L" (P: event name plus optional `data.*` equality; L: list IDs of this project).

The source URL is refused by `webhooks.block_private_addresses` (instance key, D122) exactly as a webhook target is: a project admin chooses the URL, so the same server-side request guard applies. One narrow exemption (D169, amended): the instance key `sources.private_hosts`, a list of host names an instance admin sets, lets a source URL whose host is on the list resolve to a private, loopback, link-local or unique-local address while the block stays on. Matching is exact and case-insensitive on the URL's host (no wildcards, no IP ranges, at most 20 entries); the resolved address is still checked at every connection, so the exemption covers only those names. Project admins and API tokens cannot change it (instance key, instance session only). Webhook targets never use it. With the block off, nothing changes.

## 3. What iglo.email stores

- **Subscriber:** the address (needed for consent, suppressions, bounces, List-Unsubscribe and campaigns), consent and lists, the existing `external_id` ([03](03-data-model.md)) = the PocketBase user ID, and a display name refreshed from the source.
- **Enrollments:** as today, plus `trigger_external_id` and `trigger_occurred_at` (`trigger_event_id` stays for pushed events), `error_since`, and the `source_error` / `trigger_missing` exit reasons.
- **Send log:** as today.
- **Stream state:** one resume marker per subscription topic; a dedupe table `(record_id, record_created)`; a per-record retry queue (record, attempts, next attempt, last error, terminal flag).

Not stored: the events themselves, or any recipients-view field other than address and name.

## 4. Receiving records

- **Client.** A `fetch`-based SSE client for PocketBase's realtime protocol (Bun has no `EventSource`): `GET /api/realtime`, read `PB_CONNECT` for the client ID, then `POST /api/realtime` with `{clientId, subscriptions}`, authenticated as the service account. A topic with a filter is `events/*?options=<encodeURIComponent(JSON.stringify({query:{filter}}))>`. The token is refreshed before it expires; a 401 re-authenticates once. A reset or close at any point (PocketBase's idle and forced closes, a proxy cutting a quiet stream) is routine: reconnect with backoff and catch up, with no attention line. Attention is written only when connecting keeps failing for 15 minutes, or authentication or the subscription is refused permanently. The client sends no keepalive (PocketBase reads none); a source URL through a proxy that cuts quiet streams works but reconnects more often, so a direct internal URL is preferred (operations).
- **Topics.** Events `create`s, filtered to the union of names used by an active sequence's trigger, an active or paused sequence's `exit_on`, and the `grant_lists` rules; split into several topics past PocketBase's 2,500-character filter limit; re-subscribed when a sequence or rule changes. Users, filtered by the leaving filter. Only `create` acts for events.
- **Unsubscribed names never create a subscriber.** An event named by no trigger, exit or grant is never received. Conditions still query every name (section 6).
- **Start-up and reconnect.** Subscribe first and buffer live records; catch up with `created >= marker − 15 s`, the same filter, sorted `created,id`, in keyset pages, skipping IDs in the dedupe table; drain the buffer (dedupe again); continue live. The marker advances only after a batch is committed. Users leaving are caught up the same way on `updated`. The dedupe table is pruned relative to the marker, never by wall clock. A new source's marker starts at "now", never at epoch.
- **One record at a time.** All source reads for a record (the trigger condition, the recipient lookup) happen before one SQLite write transaction that applies the subscriber upsert, `grant_lists`, the existing exit-then-trigger path (with the record's `occurredAt`) and the dedupe entry.
- **Retry queue.** A transient failure puts the record in a persistent per-record retry queue (attempts, next attempt, backoff on the injected clock); a terminal failure is shown in attention. A queued record never blocks the stream.
- **Address conflict.** Another subscriber of the project may hold the incoming address. Check that holder's `external_id` in the recipients view:
  - the holder now has another address: update the holder's address;
  - the holder is gone or has no `external_id`: end its enrollments; then if the incoming user has no subscriber, re-point the holder row to them (blocklist, unsubscribes and cap history stay); otherwise, in one transaction, carry the holder's blocklist (through the normal blocklist path) and unsubscribes onto the incoming row, delete the holder and set the address. Grants still refuse over any carried unsubscribe;
  - two live users in the view with one address: a terminal conflict in attention.

### As built (B150b)

[D171](09-decisions.md#d171-realtime-stream-catch-up-and-retry-queue-b150b-lead-2026-11-25) records the choices this section left open. Where this list and the text above differ, this list is the code. B150b builds the stream and its tables; what a record does is B150d's `RecordHandler`, and the stream is started by whoever composes it with that handler (B150d), not by the server yet.

- **Modules.** `src/sources/realtime.ts` is the SSE client (`openRealtime`, `sseMessages`), `src/sources/stream.ts` the stream (`createSourceStream({db, clock, logger, config, guard, transport?, source, handler, names})` with `start`, `refresh`, `stop`, `state`, `retries`), `src/sources/stream-reads.ts` the adapter's part (`createPocketBaseSource(...).stream`: topics, the subscription, catch-up pages, a record re-read), `src/sources/stream-record.ts` the interfaces, `src/sources/stream-store.ts` with `stream.sql` the tables (migration 36), `src/sources/stream-names.ts` the subscribed names.
- **`RecordHandler`** (what B150d implements): `event(record: SourceEvent, commit, signal)` for an events `create`, `userLeft(record: SourceUser, commit, signal)` for a users record matching the leaving filter (`SourceUser` is `{id, updated, fields}`). Each method does its source reads first, then one SQLite write transaction that calls `commit.write()`: that writes the record's dedupe entry, and throws (rolling the handler's transaction back) when the record was handled already or a retry lost its claim. A method that writes nothing may return without calling it; the stream then writes the entry. A thrown error writes nothing: a permanent `SourceError` makes the record terminal at once, anything else puts it in the retry queue. The stream calls the handler one record at a time; the retry queue calls it too, so two calls may overlap on different records.
- **Client.** `GET /api/realtime` through the private-address guard with no keepalive; lines and each message's data are bounded at 1 MiB (a larger message is dropped and starts a catch-up). The first message must be `PB_CONNECT` within 15 s. B166 (D194): the request races that deadline and the stream's stop or settings switch, as the adapter's requests do, since the guard's address lookup cannot be cancelled; a response that comes after the race was lost has its body cancelled. The client closes the connection itself after 5 minutes 30 seconds without a byte (PocketBase's idle close is 5 minutes, so a silent connection is a dead one) and at 30 minutes (PocketBase's forced close), both on the injected clock. The subscription is `POST /api/realtime` as the service account with every topic in one request (at most 1,000), and the token is confirmed after it is accepted (a revoked token subscribes as a guest, D170); a first `401` or `403` signs in again once, and a second is that status's permanent refusal (B171, D199).
- **Topics.** Events: `<collection>/*?options=` with `occurredAt != '' && (name = 'a' || …)`, names packed into topics of at most 2,500 characters in order; a name too long for a topic alone is a permanent refusal. Users: the leaving filter in parentheses; `create`, `update` and `delete` act. The names are the union of active triggers, active or paused `exit_on` (the sequences store's `list`, paged) and the grant rules' events, read at each connection and compared every 15 s on the injected clock (`refresh()` compares at once): a change ends the session and the next one subscribes anew. B150c's `source` field on sequences is not filtered yet; B150d narrows the names to external sequences when it composes the stream.
- **Markers.** One marker per subscribed name (`event:<digest of URL, collection, name field>:<name>`) and one for the users filter (`user:<digest of URL, collection, filter>`); a marker whose name is no longer subscribed, or whose source, collection or filter changed, is dropped, so a name subscribed again starts afresh. That holds when the stream goes idle too (no name and no users topic): every marker is dropped then, in a write transaction with no network call (B163, D191). A new marker is the connection's `Date` (the source's clock) plus the lookback, so the first catch-up reads from the connection's time exactly: anything committed later arrives live, because the subscription comes first. Markers move forward only, to the stamp of the newest committed record of a catch-up page or a live record.
- **Catch-up.** Per topic, its names grouped by marker, each group from its marker minus 15 s: `created >= from` (users: `updated >= from` with the leaving filter), sorted `created,id` (`updated,id`), keyset `(stamp > s || (stamp = s && id > i))`, 1,000 per page, a page too large read again smaller (D170). B168 ([D196](09-decisions.md#d196-last-audit-pass-fixes-in-the-sources-b168-lead-2026-11-27)): a topic's groups are caught up in chunks, in order, each with its own filter of at most 2,500 bytes before the keyset (1,000 bytes are kept for the keyset and a confirming read's `id =` clause, under PocketBase's 3,500-byte limit); a group may be split by its names, each part keeping its bound, and a chunk's pages move only its own names' markers. Every record is checked against the dedupe table before the handler. Live messages are buffered meanwhile, up to 4 MiB of text; past that the buffer is dropped and the catch-up runs again (the source still has every record). Then the buffer drains through the same dedupe, and the stream is live.
- **Dedupe and pruning.** `source_stream_seen (kind, record_id, stamp)`: a user updated again is a new entry, an event never is. After each advance, entries of that kind stamped before the oldest marker minus twice the lookback are pruned: a catch-up never reads that far back.
- **Resets and attention.** A reset or close after connecting and subscribing (live or in a catch-up) is routine: no attention, reconnect after 1 s, doubling to 60 s until a session gets live. Failing to connect or subscribe doubles the wait the same way and writes one "Source stream cannot connect" line once 15 minutes have passed without getting live; a permanent error (a refused sign-in, a missing field, a refused address, a catch-up the source refuses after the subscription) writes one "Source stream refused by the source" line per cause and tries again every 5 minutes. Only a session that gets live (caught up) resets both; a connection alone does not. B171 ([D199](09-decisions.md#d199-audit-pass-4-fixes-in-the-sources-b171-lead-2026-11-27)): going idle resets both too, so a stream subscribed again after an idle spell starts its 15 minutes afresh and writes a refusal it meets again.
- **A configured field missing.** An events record without one of the configured `user`, `name`, `data`, `occurredAt` or `key` fields is a settings mismatch, a refusal of the whole stream: the stream stops at that record without consuming it or moving a marker, writes one "refused" line, and tries again every 5 minutes, so fixing the setting delivers every record. A retry meeting it keeps its row and waits, never terminal, and its 72-hour window starts again at that retry, so the wait does not use the window up. A retry's re-read that the source refuses (a `400` for a renamed `occurredAt` or a broken leaving filter, a `404` collection, a `403` lost access) is handled the same way: not terminal, the window restarts, one "refused" line per cause. B166 (D194): so is a record with no `id` or no `created` (users: `updated`) date, which only a collection other than the one the settings mean gives, and so is a page that is not JSON at all (a proxy in front of the source): only a page whose JSON nests too deep is narrowed to the record it holds. A record with every field but an invalid value, a permanent error from the handler, or a single record over the 32 MiB response limit is a per-record terminal failure.
- **Retry queue.** `source_stream_retries`: a record the handler failed on transiently is queued with its dedupe entry (so the stream goes on), retried by a loop on the injected clock (every 15 s, 20 at a time, leased for 5 minutes) after 1 minute, doubling to at most 1 hour. A retry reads the record again (`null`, a newer `updated`, or a user no longer leaving ends it quietly). A permanent failure, or one 72 hours after the first (a settings mismatch restarts that count and is never terminal), is terminal: a "Source record failed for good" attention line (one per cause until a record is handled again), and the row stays 30 days for B150d's view.
- **B155b ([D177](09-decisions.md#d177-source-stream-robustness-b155b-lead-2026-11-26)).** A record the stream cannot read is a per-record terminal item on the live, catch-up and retry paths: nested deeper than the 64-level JSON limit, over the response limit even alone, or with an ID outside `^[A-Za-z0-9_-]{1,100}$`. A page the adapter refuses as unreadable is read again smaller. One such record alone is read once more for its `id` and stamp only, then by that ID in full: still unreadable, those key the terminal row, so the keyset moves past it; readable (the ID-only read met another record committed meanwhile), it is delivered. An ID over 255 characters (PocketBase caps none) never enters the keyset filter: the bound is its first 255 characters followed by U+10FFFF. A live message the stream cannot parse starts a catch-up instead of being skipped, so the catch-up makes the record terminal before any live record later in `(stamp, id)` order moves the marker; a record tied with it on the stamp may move the marker to that same stamp, which the next catch-up's inclusive `>=` bound still reaches ([D182](09-decisions.md#d182-source-send-path-and-stream-wording-b159a-lead-2026-11-26)). The exception is a users `delete`, whose record no catch-up finds, and send time still stops mail to that user. A terminal line whose record failed the read alone and the read by its ID for different causes (it changed between the two) names the first cause, then the second. A record with no ID or no stamp at all still refuses the stream. Retry rows carry their source's digest (migration 38): a stream drops the rows of any other source before its loops start, and a row from before the migration is kept only when the stream's markers show the same source. Such a row left by an even older source, replaced while on 2.1.0, is taken by the current source as well: nothing records which source wrote it. `waiting` marks a row whose last attempt met a settings mismatch. Record-level lines are capped per kind, cleared only by a success of the same kind. B168 ([D196](09-decisions.md#d196-last-audit-pass-fixes-in-the-sources-b168-lead-2026-11-27)): a line's cause leaves out the IDs its message names (every word holding a digit or 15 or more ID characters), so one cause failing for many users (a blocklisted domain) writes one line, and at most 100 causes are kept per kind. A live record's marker move commits in the record's own transaction.

### As built (B150d)

[D173](09-decisions.md#d173-records-into-subscribers-consent-and-leaving-b150d-lead-2026-11-25) records the choices sections 3 to 5 and 7 ("Leaving") left open. Where this list and the text above differ, this list is the code.

- **Modules.** `src/sources/records.ts` is the `RecordHandler` (`createRecordHandler`), `src/sources/records-stream.ts` runs it per project (`createSourceRecords`, `storedGrantRules`): one stream with its own adapter while the project has a `source.url`, stopped and started again on new settings when the `source.*` keys change (compared every 15 s on the injected clock and at once after a settings save), never with the stream's test-only `tuning`. The server starts it with the other loops and stops it first.
- **An events record.** Source reads first: each active external sequence under the record's name whose `trigger.where` `data.*` equalities hold strictly gets its `trigger.condition` read through `evaluateTriggerCondition` (B150c); then, only when a grant rule or a sequence start applies, the user's recipients-view row, and for an address another subscriber holds, the holder's row. Then one write transaction: the conflict's resolution, the subscriber upsert keyed on `external_id` (address and name from the view; a new subscriber is `enabled` with the view's name, which may be empty), the grants, exit-then-trigger and the stream's dedupe entry. The transaction first checks that the subscribers the reads planned on are unchanged (the user's row, the address's holder and its `external_id`, a moved holder's new address) and that each started sequence's trigger is the one whose condition was read; otherwise it rolls back with a transient error and the retry queue reads again.
- **Nothing to grant or start.** A record that only exits (or matches nothing) reads nothing from the source and creates no subscriber: it ends a linked subscriber's enrollments whose external sequence's `exit_on` names it, and writes the dedupe entry.
- **The trigger.** A record whose `occurredAt` is more than 7 days before it is handled starts nothing (the events API's window); its exits and grants still apply. A `trigger.condition` that fails transiently makes the record transient (retry queue, nothing written). One the source refuses, or that no longer validates, starts nothing for that sequence and writes one "Sequence trigger condition failed: not started" attention line per cause; the record's grants and other sequences still apply. B166 (D194): that holds for the condition's own failures only (a query the adapter cannot write, `UnfitQuery`; an unreadable record of the user, such as an event nested deeper than 64 levels; a condition that no longer validates; a `400` to an events query that the probe below clears). A refusal of the settings during the evaluation (the private-address block, a refused sign-in or token check, `AuthRefused`, whatever its status, a `403` or `404` of the events collection, any permanent failure of the recipients view or a record by ID, a `400` there included, a page that is not JSON, a redirect: what `readRecipient` classifies as a `SettingsMismatch`) is a `SettingsMismatch` of the record: nothing is committed, the session ends refused, and the record starts its sequence once the settings work again. An events query's `400` that is not the sign-in's probes the events collection once per record: one `id` (`perPage=1`, `fields=id`) read with a filter naming every mapped field as `f = f`, the settings check's form, and no condition part, so it checks the mapped fields and the list rule whatever rows the collection holds and reads no record. A probe that fails for good (a renamed mapped field, a broken list rule, a page nested too deep, too large or not JSON, or a `200` that is no PocketBase list, such as a proxy's `{}`, or whose items are not records, B171, D199) makes it a `SettingsMismatch`, a transient one makes the record transient, an abort (the stream stopping or switching settings) or any other failure is thrown on as it is, so nothing is committed, and a probe that answers leaves the `400` as the condition's own, which skips only its sequence. Only a `200` page can be too large to read: a large error page (a proxy's `403` or `502`) is that status's failure on every read (a record or recipient by ID, a page, the probe, the sign-in, the token check and the realtime subscription), so a large `502` is transient.
- **The address.** The view's address goes through the events API's address rules (at most 1,000 bytes, sanitized, lower-cased); a user without a valid one is a per-record terminal failure. A new or changed address outside the privacy domain policy is one too. The name is trimmed; one with a NUL or over 2,000 bytes is stored empty.
- **Conflicts** (spec section 4, each read before the transaction): a holder with an `external_id` whose user the view has at another address is moved to that address (when another subscriber holds that one too, or it is outside the domain policy, the record is a terminal conflict); a holder whose user has the same address, or no valid one, is the two-live-users terminal conflict ("Source record failed for good" with the cause). A holder with no `external_id`, or whose user the view no longer has, is gone: its active enrollments end `canceled`, `subscriber_deleted`; with no subscriber for the incoming user the holder row is re-pointed to it (status, lists, unsubscribes, cap history and attributes stay); otherwise `carryConsent` moves the holder's blocklist (through the normal blocklist path: every membership unsubscribed, enrollments ended, webhooks) and each list it left onto the incoming row, the holder is deleted through the normal delete path, and the incoming row takes the address. Each of these writes changes only the address, name and user ID of a row read inside the transaction (a moved holder keeps its name): a status or attribute change made while the source was read, a blocklist for one, stays and decides the grants.
- **Settings refusals.** B166 (D194): every permanent failure of a recipients-view read except the record's own (an ID the source cannot have, and `RecordUnreadable`: over the response limit, JSON nested deeper than 64 levels, an address field that is not text) is a `SettingsMismatch`, a 2xx page that is not JSON or JSON that is no record included: a `400`, `401` after signing in again, `403` or `404` of the view, a redirect, a host the private-address block refuses, a mapped field its rows lack, a row with no `id`. Before B166 only the first three and a missing field were; it is classified by exception now, so a new refusal cannot make every record terminal. It is a `SettingsMismatch` (`src/sources/stream-record.ts`): on the stream path the session ends refused ("Source stream refused by the source") with nothing consumed and no marker moved (`stream.ts`'s `handle` now rethrows it instead of queueing it as terminal); a retry keeps its row and waits, as before. There is no admin view of the retry queue yet, so no "waiting for settings" label.
- **Leaving** (section 7). A users record matching the leaving filter, and an events record whose user the recipients view no longer has (a `null` read, confirmed by the adapter), remove the linked subscriber through the normal delete path, ending its enrollments first; nothing is created for an unknown user. A subscriber who withdrew consent (blocklisted, or unsubscribed from any list) first leaves a D125 marketing suppression keyed on its address and `external_id` (`removeLeaving` in `src/subscribers/store.ts`, in the same transaction as the delete, unless one already names it): a returning user, under the same address or the same user ID, gets `suppressed` for every grant and starts no marketing sequence, until the person confirms a public double opt-in or an operator's `DELETE /api/suppressions` clears it. A user who withdrew nothing is removed without one.

## 5. Consent

`grant_lists` rules on the source are applied before exit-then-trigger, so a zero-wait marketing step sees the consent. A grant is refused when the recipient's opt-out field is set, or iglo.email has the address unsubscribed from that list, suppressed (D125/D128) or blocklisted. A grant never overrides an unsubscribe.

### As built (B150d)

- Every rule whose `event` is the record's name and whose `data.*` equalities hold strictly (the condition language's type rules: `"1"` is not `1`) names its lists; the union is granted in the record's transaction, after the subscriber upsert and before exit-then-trigger. Each list is checked in this order and only the last writes: a list that is gone or double opt-in is `unavailable` (a grant cannot replace the opt-in mail, D99); a blocklisted subscriber `blocklisted`; a suppression (D125/D128) `suppressed`; any existing membership is kept as it is (`unsubscribed` or `member`); the view's opt-out field set `opted_out`; otherwise a confirmed membership is `added`. The results are not stored (there is no request to answer).

A user who returned under a new address is matched by the `external_id` key, so the operator sends the old address; the new one removes nothing. ## 6. Sequences on a source

- A sequence chooses its source: `"source": "events"` (default, pushed events) or `"source": "external"` (the project's source). A project without a configured source refuses `external`.
- **Trigger.** `trigger.event` and the `data.*` equality form of `trigger.where` match the record. New `trigger.condition` (external sequences only): a history condition evaluated against the source when the trigger arrives, with `since` durations counted back from the trigger's `occurredAt` and counts including the trigger (for example "2+ `order_paid` with `data.product = prepaid` within `P180D`"). It is what a `reentry: never` sequence needs, where a step condition would enroll, exit and block for ever. The condition form of `trigger.where` (evaluated inside the event transaction for pushed events) is refused on external sequences; `trigger.condition` is refused on pushed ones (D169: one way each).
- **Trigger reference.** `since: trigger`, reschedule and windows use `trigger_occurred_at` locally. `trigger.data`, step preview and the timeline fetch the record when needed; a 404 ends the enrollment with `trigger_missing` (the subscriber stays). Preview, test sends and manual or test enrollments accept a string `trigger_external_id`; `latest()` supplies a default.
- **Conditions and aggregates read the source.** Same condition language. `{event, since, where, count}` and step aggregates (`count`, `sum`, `distinct`) compile to PocketBase filters on the events collection: window strictly `occurredAt > since`; dates as PocketBase stores them (`YYYY-MM-DD HH:mm:ss.sssZ`); values escaped as filter literals (there are no bound parameters over HTTP).
  - Exists: `perPage=1&skipTotal=1`. Count thresholds read up to the comparand + 1.
  - Aggregates: keyset pagination on `(occurredAt, id)`, `skipTotal=1&fields=id,occurredAt,data`, capped at `AGGREGATE_LIMIT` on the window before `where`, as today.
  - PocketBase compares JSON loosely (section 9), so `where` is re-checked strictly, with the condition language's type rules, on fetched rows; where that matters for a count, pages continue until enough strict matches.
  - New condition kind `{ "recipient": "<field>", "op", "value" }` reads a recipients-view field, with `attr`'s operators and type rules.
  - `sql` predicates are refused on external sequences.
  - Evaluation is async.
- **Failures.** An error or timeout never counts as false or zero. Transient: retry with the scheduler's existing backoff for at most 72 hours (`error_since`). Permanent (400/403: a renamed field, a broken rule): fail fast. Terminal: the enrollment exits with `exit_reason = 'source_error'`, shown in the sequence UI and attention. A step never runs past an unevaluated condition.

### As built (B150c)

[D172](09-decisions.md#d172-sequences-and-conditions-on-a-source-b150c-lead-2026-11-25) records the choices this section left open. Where this list and the text above differ, this list is the code.

- **Modules.** `src/conditions/source.ts` evaluates conditions (`evaluateOnSource`, `evaluateStoredOnSource`), aggregates (`aggregateOnSource`) and `trigger.condition` (`evaluateTriggerCondition`) against an `ExternalSource`; `src/conditions/strict.ts` holds the condition language's type rules on JSON already read (`valueAt`, `compareStrict`, `predicateHolds`, `whereHolds`). `src/sources/project.ts` gives each project one adapter (`createSourceProvider`), rebuilt when the `source.*` settings change, shared by the sequence routes and the scheduler. Migration 37 adds `sequences.source` and the enrollment columns `trigger_external_id`, `trigger_occurred_at`, `error_since` and `error_last` (internal, not in the API).
- **Validation.** `validate(condition, {canUseSql, source: "external"})` accepts `recipient` and refuses `sql` (`<field>.sql: sql conditions are not available on an external source`); with `trigger: true` only `all`, `any`, `not`, `event` and `recipient`, and `since` only as a duration. A `recipient` field is a PocketBase field name (`[A-Za-z_][A-Za-z0-9_]{0,99}`), optionally followed by dotted JSON keys. `source: external` is refused while the project has no `source.url`, an external sequence cannot be activated without one, and `source` cannot change while the sequence has enrollments (an enrollment's trigger reference is one kind or the other).
- **Filters.** A window is `occurredAt` strictly after `since` (and, for a trigger condition, at or before the record), through the adapter's `EventQuery`. A step condition's or aggregate's window ends at the step's `now` plus `MAX_OCCURRED_AHEAD_MS` (15 minutes) inclusive ([D180](09-decisions.md#d180-conditions-the-scheduler-and-sequences-on-a-source-b155e-lead-2026-11-26)), so a record dated further ahead counts only once it no longer is. A `where` part goes into the filter only when PocketBase can state it as a superset: a path of at most 8 ASCII identifier keys, and no number written with an exponent; anything else is left to the strict check alone. The filter is never trusted: every row read is checked again with the strict rules (`true` is not `1`, `"10"` is not `10`, `5` equals `5.0`, a path walks object keys only, text compares by code point).
- **Counts.** Without `where`, `count(query, need)` with `need` one past the largest comparand that bounds above (`gte` itself), so a threshold reads at most `need` IDs. With `where`, keyset pages continue until `need` strict matches or the window ends; a count still undecided after `SCAN_LIMIT` (100,000) records is a permanent failure.
- **Aggregates.** One `scan` per aggregate over its window (`event`, `since`) of up to `AGGREGATE_LIMIT` + 1 rows; past the limit the step has no totals (`aggregate_limit`), as for pushed events, whatever `where` keeps. `sum` adds exact integers as BigInt and switches to floats at the first fraction, as SQLite's `sum` does; a stored integer past 2^53 or a total outside the exact integer range has no total. `distinct` counts distinct numbers, texts and booleans apart. Measured in [B150c-conditions](../perf/B150c-conditions.md): ten aggregates at the limit take about 3.5 s, one condition about 0.1 s.
- **`recipient`.** One `recipient(externalId)` read per evaluation, shared by every `recipient` predicate in it; a user the view no longer has holds no fields (`exists` false, `ne` true).
- **`trigger.condition` for B150d.** `evaluateTriggerCondition(source: ExternalSource, condition: unknown, userId: string, record: { occurredAt: Date }, options?: { signal?: AbortSignal }): Promise<{ ok: true; value: boolean } | { ok: false; kind: "transient" | "permanent"; message: string }>` in `src/conditions/source.ts`. It validates the stored condition again (a condition that no longer validates is permanent), counts durations back from `record.occurredAt` and ends every window at it inclusive, so the trigger record itself counts. It makes network calls only: call it before the write transaction, never inside one. B166 (D194): a `SettingsMismatch` the given source raises is thrown on, not returned (`evaluateOnSource` does so for every caller; only the record handler's `conditionSource` raises one).
- **Enrollments.** A manual or test enrollment of an external sequence reads its record before the write transaction: `trigger_external_id` (a record of the subscriber's `external_id` under the trigger's name, else 400), or the subscriber's `latest()` under the trigger's name, or none (the enrollment counts from its start). A subscriber without an `external_id` is a 409. `trigger_occurred_at` is the record's `occurredAt`; reschedules read it through `coalesce(event time, trigger_occurred_at)`.
- **Scheduler.** For an external enrollment the condition, the trigger record (by ID, before rendering; `null` ends it `trigger_missing`) and the aggregates come from the source. A transient failure releases the claim with the condition backoff, with no attention message, and records its outage window: `error_since` (the window's first failed read) and `error_last` (this one). It starts a fresh window (`error_since = error_last = now`) when none is open or `error_last` is more than `SOURCE_OUTAGE_GAP_MS` (2 hours, twice the backoff cap) earlier; otherwise it sets `error_last` only. A step decided by a later successful read clears both. The window is per enrollment: a step skipped `late` (`max_late`, `P2D` by default for marketing) or passed as deleted keeps both, and a late step past the window of a continuing outage (`error_last` within 2 hours) reads the trigger record once and ends the enrollment when that still fails. When it succeeds, the step is skipped `late` and both are cleared. A manual enrollment with no trigger record is skipped `late` without a read. When `now − error_since` reaches 72 hours within one window, or at once for a permanent failure or a project whose source was removed, the enrollment ends `exited`, `source_error`, with one attention message naming the enrollment and step only. The `trigger` template data is the record's `name`, `data` and `occurredAt`.
- **Preview, test send, timeline.** The step preview and test send take `trigger_external_id` (else `latest()`), read the trigger and aggregates once for all recipients, and answer 503 (with `Retry-After`) for a transient source failure and 502 for a refusal. The timeline reads the record for a viewer who may read the subscriber; a gone record shows `unavailable: "missing"`, a failed read `"source_error"`.
- **Pushed events never reach external sequences.** `sequences-triggered-by` and `exit-by-event` match `source = 'events'` only; delivering source records to triggers and exits is B150d's.

### As built (B155d)

- No behavior change. `test/sources/records.test.ts` now pins section 4's B150d trigger rules through the stream: a record older than 7 days exits and grants but starts nothing (one 6 days old starts), and a `trigger.condition` the source refuses (a `400` on its query) skips only that sequence, with one "Sequence trigger condition failed: not started" line per cause, while the record's grants and other sequences apply.

### As built (B162a)

[D188](09-decisions.md#d188-the-sources-module-switch-and-the-connector-list-b162a-lead-2026-11-27): while the instance's `sources.enabled` is off, creating a sequence with `"source": "external"`, changing one to it, or saving or activating an external one is a `400` naming `sources.enabled`, and the sequence routes that read a source (preview, test send) answer `409` "External sources are off on this instance.". Existing external sequences and their enrollments are held: the scheduler claims none of their enrollments, so nothing advances or ends and no `source_error` is written; turning the module on clears their outage windows and they continue. The sequence editor says so for an external sequence ("External sources are off on this instance: the enrollments of this sequence wait…"). B162a r1: a pushed sequence's step to a source-linked subscriber of a project that still stores a source waits too, as for an unreadable source (section 7's as-built note below). The claim hold has its own test: more held external enrollments than one claim batch, due first, do not keep a due pushed enrollment from running within the pass (`test/sources/module-held.test.ts`).

## 7. Sending and leaving

- **Fresh recipient at send time** (address and name), for sequence steps and for campaigns to source-linked subscribers. An address change goes through section 4's conflict and opt-out handling. The campaign runner fetches per batch before render and eligibility; on a transient error it pauses and rewinds the batch instead of failing deliveries (marketing at-most-once: a rewound message was never handed to the emailer).
- **Leaving.** A user absent from the recipients view is leaving: end the enrollments and remove the subscriber, at send time and in real time on a matching users update. PocketBase does not broadcast a hard delete of a user that does not match the subscription filter, so send time is the backstop. Leaving never forgets withdrawn consent: a leaving subscriber who was blocklisted or had unsubscribed from a list leaves a suppression (D125, [D173](09-decisions.md#d173-records-into-subscribers-consent-and-leaving-b150d-lead-2026-11-25)), so a returning user is not re-granted marketing.
- **Names.** A generic Liquid filter `first_name`: the first word if it starts with a letter, contains no `@` and is at most 24 characters, else empty (`{{ subscriber.name | first_name | default: "there" }}`). A source-linked subscriber's name may be empty; there is no name-from-email fallback.

### As built (B150a)

`first_name` (`src/templates/filters.ts`): the first whitespace-separated word of a text when it starts with a Unicode letter, holds no `@` and is at most 24 code points; any other text, and any value that is not text, is empty. It takes no argument.

### As built (B150e)

[D174](09-decisions.md#d174-send-time-campaigns-and-the-release-docs-b150e-lead-2026-11-25) records the choices this section left open. Where this list and the text above differ, this list is the code.

- **Modules.** `src/sources/recipient-sync.ts` is the record handler's recipient and conflict path, moved out of `src/sources/records.ts` unchanged so both callers use one: `planRecipient` does the reads (the user's row in the view and a conflicting holder's), `applyRecipient` writes the plan inside the caller's transaction after the same re-checks (`SubscriberChanged`, transient, when they fail), `leaveUser` removes a leaving user. `src/sources/send-time.ts` (`createSendTimeLookup`) puts them to use at send time: `read` (no transaction open) and `apply` (one short write transaction). The server builds one per project and gives it to the scheduler and the campaign runner.
- **Source-linked.** A subscriber with an `external_id` while the project has a source (section 3: it is the source's user ID). This covers every sequence, pushed or external, and every campaign. Without a source, or without an `external_id`, nothing is read.
- **Unchanged rows write nothing.** When the view has the address and name the subscriber already has, and no other subscriber holds that address, there is no transaction. A changed name or address goes through `applyRecipient`, as a record's would: a new address another subscriber holds takes section 4's conflict branches (moved, re-point is impossible here because the user already has a subscriber, carry and delete, two live users), and a new address outside the domain policy is refused. Only the address, name and user ID are written; status and attributes are read fresh inside the transaction (D173's rule). B166 (D194): an unchanged plan still hands the campaign batch the row the reads verified, so a subscriber the stream or a sequence step wrote after the claim is rendered and checked as it is now, not skipped as changed.
- **The user ID moved.** At send time the read is for one subscriber. If the user ID now belongs to another subscriber (or to none), nothing is created or re-pointed: the read is a `SubscriberChanged`, and the step or batch is read again. B166 (D194): for a user the view no longer has, the same holds when no subscriber has the user ID but the claimed subscriber still exists (its `external_id` cleared or changed during the read), at the read and again at the write, so it is read again instead of being reported as left.
- **Leaving.** A user the view no longer has (a confirmed `null`) leaves through `leaveUser`, in its own transaction: its enrollments end (`canceled`, `subscriber_deleted`), and a subscriber who withdrew consent leaves a D125 suppression before it is removed. The step or recipient is then not sent.
- **Sequence steps** (`src/scheduler/scheduler.ts`). The lookup runs once the condition, the template and the step's lateness have admitted the step, and before the marketing consent recheck, the trigger record, the aggregates and the render, so all of them see the fresh address. A late step is skipped without a read. A transient failure, and a recipients view the source refuses (`SettingsMismatch`), wait like any source read of the step: the claim is released with the condition backoff inside D172's 72-hour outage window, then `source_error`. A refused view is the settings' fault, not the subscriber's, so it is not ended at once. A permanent failure of this user (no valid address, two users with one address, a blocked domain) ends the enrollment `source_error` with D172's attention line. A `SubscriberChanged` releases the claim to be decided again. After a change, a subscriber the conflict path blocklisted (a carried blocklist) ends `exited`, `blocklisted`.
- **Campaign batches** (`src/campaigns/runner/runner.ts`). After the batch is claimed and before its attachments, renders or eligibility checks, every source-linked recipient is read, 8 at a time (`SOURCE_LOOKUPS`), with the lease renewed meanwhile. Only when every read has answered are the changes written, one short transaction each, and the batch's copies take the new address and name. A user who left, or whose address the source cannot give (permanent, per recipient, at the read or at its write's domain re-check), is skipped with the reason `subscriber_unavailable`; the second also writes "campaign recipient skipped: the source has no usable address".
- **Opt-out blocks marketing at send time.** The read checks the recipient's opt-out field (section 2) even when the address and name are unchanged. When it is set, a marketing sequence step ends `exited`, `unsubscribed` (the consent exit `marketingReason` gives), and a campaign recipient is skipped with the reason `unsubscribed`. Nothing is rendered or handed to the emailer, and no list membership changes: the flag stays the source's. A transactional step to the same user still sends.
- **Campaign outage.** A transient failure (or a `SubscriberChanged`) at any read or write of the batch hands the whole batch back before anything of it renders or is pushed: claims removed, cursor rewound to before its first recipient, pipe released. The campaign keeps its `running` status and its next batch waits 5 s, doubling to 5 minutes, then the batch is claimed and read again. A batch whose reads all succeed resets the wait. One "campaign waiting for its source: batch handed back" line per outage; a campaign paused, cancelled or finished while it waits starts a later outage afresh. Nothing was handed to the emailer, so at-most-once holds: every recipient is sent once, after the outage. A crash during the reads leaves the batch claimed and it is skipped as unknown, as before.
- **Campaign settings refusal.** A recipients view the source refuses (`SettingsMismatch`) hands the batch back and pauses the campaign ("campaign paused: the source refused a recipient read"), as missing attachments do: it does not recover by itself, so the operator fixes the settings and resumes.
- **Measured** in [B150e-send](../perf/B150e-send.md): a 10,000-recipient campaign with every recipient looked up runs at about 2,000 recipients/s on disk and 3,100 on tmpfs (a batch's lookups take 14 ms and 9 ms at p50), against 3,000 and 4,700 without a source. Without a source the throughput is unchanged from before.
- **Tests** (`test/sources/send-time.test.ts`, against the binary): a renamed user's next step uses the new name, and `first_name` renders it or the default; an address change mid-sequence; a hard-deleted user removed at send time; a transient failure that waits and then sends once; an address change through the conflict path carrying a gone holder's blocklist; a campaign batch with a rename, a new address, a deleted user, an unchanged user and an unlinked subscriber; a campaign outage inside its second batch, with every recipient pushed exactly once; the opt-out field ending a marketing step and skipping a campaign recipient `unsubscribed` while a transactional step still sends; a user with no valid address (a step ends `source_error`, a campaign recipient is skipped `subscriber_unavailable` and the rest are sent); a refused recipients view (a step waits out the 72-hour window, then `source_error`; a campaign pauses); and the campaign wait doubling from 5 s to its 5-minute cap on the injected clock. One protocol stub: a 503 from the n-th recipients read, because the binary cannot fail at an exact read. Every source request records whether a SQLite transaction was open; none may be.

### As built (B162a r1)

[D188](09-decisions.md#d188-the-sources-module-switch-and-the-connector-list-b162a-lead-2026-11-27): the opt-out flag and leaving stay the source's, and only a send-time read sees them. So while the instance's `sources.enabled` is off, a project that still stores a source (a connector and a URL, `sourceHeld`) treats its source-linked subscribers (those with an `external_id`) as unreadable, never as unlinked. Nothing is sent to them; unlinked subscribers are sent as before.

- **Campaign batches.** Every source-linked recipient of the batch is skipped with the reason `subscriber_unavailable` before anything is read, rendered or pushed. It is never sent later: the skip is final, as for a user the source has no usable address for (marketing at-most-once). One attention line per run of the campaign: "campaign recipients skipped: external sources are off".
- **Sequence steps.** After the condition and template admit the step, a step of any kind to a source-linked subscriber is released with the condition backoff (1 minute up to 1 hour). Nothing is sent, the enrollment is not ended, and no outage window is written. A marketing step held past its lateness (2 days) is skipped `late`, unsent. External sequences are held earlier, at the claim. Turned on again, the step runs with its send-time read: an opted-out user's marketing step exits `unsubscribed`, and a user who left is removed.
- **Turned off during a batch or a step (r2).** The send-time read checks on every call, so a toggle while a campaign batch's reads are in flight cannot make the later reads look unlinked: a read that finds no source while held throws `SourceHeld`, never the `null` that means no source. The campaign skips that recipient `subscriber_unavailable` as above (the reads already answered keep their outcome, such as an opt-out); a sequence step waits as above.
- **Re-enable.** The outage windows cleared when the module turns on again are every active enrollment's, pushed sequences' included: only source reads open them (D180).
- **Tests** (`test/sources/module-held.test.ts`, an in-process instance on a test clock against the binary and the SMTP sink): module off, a linked user opted out in the source, a linked user not opted out and an unlinked subscriber. A campaign reaches only the unlinked one, skips both linked ones `subscriber_unavailable` with one line, and sends them nothing after the module is on again. A marketing step reaches the unlinked one and holds both linked ones for hours. On again, it sends once to the user not opted out and exits the opted-out one `unsubscribed`. Also: the start line for a project opened while off, said once. And the toggle during a batch's reads (r2): with PocketBase paused mid-read and the module then turned off, none of 21 opted-out linked recipients gets mail; the reads in flight skip them `unsubscribed`, the later ones `subscriber_unavailable`.

## 9. PocketBase facts (0.40.5, measured 2026-11-25)

- **Realtime.** Each message is sent from its own goroutine on an unbuffered channel, so a live connection blocks rather than drops; loss happens only around a disconnect. Records created in a transaction are broadcast after commit. Order is not guaranteed. Connections close after 5 idle minutes and after 30 minutes regardless, so reconnect and catch-up are routine. A subscription filter applies to every action, so a hard delete of a user that does not match is not broadcast.
- **Filters.** `data.n > 5` also matches the string `"10"`; `data.b = true` matches `1` and the reverse; `= 10` and `= "10"` are exact; a missing key matches `= null` but not `= ""`; `!=` includes missing keys.
- **Paging.** `perPage` is silently capped at 1000; `skipTotal=1` returns `totalItems: -1`.
- **Errors.** A duplicate unique value is a 400 with `data.<field>.code = "validation_not_unique"`.
- **Auth collections** hide `email` from non-owners unless `emailVisibility` is on.
- **Invalid tokens** (B150a): an invalid, expired or revoked token in `Authorization` is read as a guest, not refused: a list with a rule answers `200` with no items and a view by ID `404`. Only routes that require auth (`auth-refresh`) answer `401`.
- **Filter literals** (B150a): a single-quoted literal with each `\` and `'` escaped by a backslash reads back exactly; escaping only the quote breaks on a trailing backslash (`400`). An unknown field in a filter or sort is a `400` "Something went wrong while processing your request.". Dates are stored as `YYYY-MM-DD HH:mm:ss.sssZ` text and compare as text. A new auth collection's token lasts 7 days; the minimum is 10 s.
