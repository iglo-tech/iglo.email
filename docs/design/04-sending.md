# Sending

## SMTP

- `nodemailer` SMTP transports, one pool per configured SMTP server (listmonk's "messengers"). Settings: host, port, TLS mode, auth, max connections, idle timeout, retries, custom `HELO` name, custom headers.
- Multiple servers can be enabled. Campaigns pick one by name (`messenger` column, as in listmonk). Individual sends use the default unless the API call names one.
- DKIM signing is supported through nodemailer when configured; most providers sign for you.
- Every message gets a `Message-ID` generated by iglo.email (`<send-uuid@root-domain>` or `<campaign-uuid.subscriber-uuid@root-domain>`), so it is known before the SMTP call and stored in `sends.smtp_message_id`.

M0.8 verified predetermined IDs, MIME and DKIM through a synthetic Mailpit path in Bun and a compiled fixture ([evidence](../perf/M0.8-nodemailer.md)). Nodemailer 10.2.1 defaults pool requeues to five; M2.1 explicitly sets maxRequeues to 0 for D12 delivery paths under D24; the application alone owns proof-based transactional retries. SMTP acceptance alone does not establish delivery or an unambiguous retry classification.

D49 defines M2.1's protected SMTP-test activation, safe response/errors and
bounded temporary transports. D50 supplies optional native SMTP DKIM settings
with masked key retention/null-clear and validated RSA configuration. The M2.1
owner implements these paths; the reference and performance notes describe the
bounded evidence.

The D49 owner deadlines are absolute: 60 seconds from ordinary dispatch,
10 seconds for a temporary SMTP test, and five seconds to drain after shutdown
starts. Forced cancellation closes owned work and remains ambiguous unless
non-acceptance was independently established. HTTP drainage must not postpone
the messaging shutdown deadline. Injected-clock connection and queue tests,
and a compiled-process held SMTP-test shutdown, exercise these bounds. The
transport itself does not implement the durable outbox or a retry engine.

D51 requires configured authentication to be advertised and complete before
MAIL/DATA. An accepted owner outcome can include rejected recipients: native
delivers once to the accepted subset, without replay. The protected test
reports partial acceptance explicitly with a safe 500, rather than claiming
every recipient succeeded or that nothing was sent.

D52 keeps exact full-address matching first, then uses the actual mailbox
domain even when a quoted local part contains @. This deliberately corrects
upstream's first-separator bucket selection; paired coverage names both providers.
LOGIN remains challenge-driven for the pinned supported prompt names.

## Campaigns

Ported from listmonk's `internal/manager`:

- The campaign runner scans for `scheduled` campaigns whose `send_at` has passed and for `running` campaigns.
- Subscribers are streamed in ID order in batches (`app.batch_size`), using `last_subscriber_id` and `max_subscriber_id` on the campaign as a cursor. A restart continues from the cursor.
- Recipients are list members with the right subscription status: `confirmed`, or `unconfirmed` for single opt-in lists, and `unsubscribed` excluded. Opt-in campaigns target `unconfirmed` members of double opt-in lists. Blocklisted subscribers are always excluded.
- Concurrency (`app.concurrency`), per-second rate (`app.message_rate`), sliding window (`app.message_sliding_window*`) and an error threshold that pauses the campaign (`app.max_send_errors`), as in listmonk.
- Progress (`sent`, cursor) is written once per batch.

Delivery guarantee: **at-most-once per subscriber per campaign.** The cursor is advanced for a batch before the batch is sent. A crash mid-batch can skip at most one batch of recipients; it never sends a campaign twice to the same person. The skipped range is logged so it can be resent manually.

## Transactional API

`POST /api/tx`, compatible with listmonk's request body (`subscriber_email`, `subscriber_id`, `subscriber_emails`, `subscriber_ids`, `subscriber_mode`, `template_id`, `data`, `headers`, `messenger`, `subject`, `from_email`, `content_type`, multipart attachments).

New optional fields:

| Field | Meaning |
|---|---|
| `subscriber_external_id` | Address the subscriber by the app's ID |
| `kind` | `transactional` (default) or `marketing` |
| `list_id` | For `marketing`: the list whose membership grants permission and which the unsubscribe link leaves |
| `idempotency_key` | A repeated call with the same key returns the first result and sends nothing |
| `async` | `true`: queue in the outbox and return immediately (default `false`: send before responding, as listmonk does) |

New response body (listmonk returns only `true`):

```json
{ "data": { "sends": [{ "id": 123, "uuid": "…", "status": "sent", "smtp_message_id": "<…>" }] } }
```

Rules:

- **Any address can receive a transactional email.** `subscriber_email` does not have to belong to a subscriber, and no subscriber is created. If the address belongs to a subscriber, their data is available to the template and the send is linked to them; otherwise the send has only `to_email`. `subscriber_mode` is accepted for compatibility: `default` and `fallback` both behave this way, and `external` skips the lookup. `subscriber_id` and `subscriber_external_id` must still name an existing subscriber, because there is no address without one. This is a deliberate difference from listmonk, whose default mode rejects unknown addresses ([API and admin UI](07-api-and-ui.md#api-compatibility-policy)).
- **Transactional sends ignore list status** but never go to blocklisted subscribers. A transactional email is something the person needs (receipt, access, password).
- **Marketing sends require permission:** this is consent, not bookkeeping, so it stays. A marketing send has exactly one SMTP recipient, the admitted subscriber: a request `Cc` or `Bcc` header with `kind: "marketing"` is a 400 with no rows and no SMTP, and `Cc`/`Bcc` from the SMTP server's `email_headers` are not applied to marketing sends (outbox, synchronous dispatch and resend). Transactional sends keep filtered copies. The recipient must be an existing subscriber whose membership of `list_id` is `confirmed`, or `unconfirmed` on a single opt-in list. Otherwise the send is recorded as `skipped` with a reason and the API returns it with `status: "skipped"`. Marketing sends also count toward and respect the frequency cap.
- Every send is a row in `sends`, whatever its outcome.

M2.3 implements this endpoint in `src/tx`. JSON and listmonk's multipart form (`data` plus `file` parts) are accepted with `tx:send`. A synchronous call commits `queued` rows and then has the outbox owner claim and send exactly those rows before responding, so the outcome is journaled first; a proven transient rejection leaves the row `queued` for the outbox retry schedule. An `idempotency_key` is stored, hashed, as `tx:<sha256>:<request fingerprint>:<index>` in the existing unique `sends.idempotency_key` column, so a multi-recipient request needs no schema change. A matching key replays its first rows right after parsing and live authorization, before lists, templates or subscribers are read, so later edits to them do not change a retry; the enqueue transaction repeats the lookup for concurrent first requests. Every queued row is rechecked against the current blocklist by normalized destination address at outbox admission and manual resend, linked or not; blocklisted `Cc`/`Bcc` mailboxes are dropped from the envelope and headers, the rest still send, and the row records only `skip_reason = copies_blocklisted:<n>`. `kind: "marketing"` requires an existing `list_id`; M2.4 replaced the D58 staging with the consent, cap and unsubscribe policy below ([D58](09-decisions.md#d58-stage-marketing-transactional-sends-until-m24)). Differences are listed in [API and admin UI](07-api-and-ui.md#api-compatibility-policy); measurements are in [M2.3](../perf/M2.3-tx.md).

## Outbox

Async transactional sends and all sequence sends go through the `sends` table:

1. Insert with `status = 'queued'`.
2. The outbox loop claims rows, sets `status = 'sending'`, then sends with no transaction open.
3. On success: `sent`, with `sent_at`. On proven permanent non-acceptance: `failed`. Only transactional messages with proven non-acceptance may return to `queued` with backoff, up to 5 attempts. Marketing messages are never retried automatically; ambiguous acceptance becomes `unknown` ([D24](09-decisions.md#d24-disable-library-requeues-and-classify-smtp-outcomes-before-retry)).
4. A row found in `sending` after a restart becomes `unknown` and is **not retried**. For marketing, a duplicate is worse than a missed email. An admin can resend it from the send log.

### M2.2 durable boundary and staged callers

[D53](09-decisions.md#d53-durable-outbox-boundaries-and-native-send-log-contract)
defines the native send-log schema/API, safe projections, proof-based retry
schedule and idempotent manual-resend lineage. Messaging owns prepared payloads
and journal SQL. M2.3 supplies the tx producer/rendering later; M5 supplies
sequence producers. M2.2 exercises production ownership through a separately
compiled test-only producer, with no extra production route or flag.

Every queued send has its stable Message-ID before commit. Retry is limited
to positively proven transient non-acceptance, five attempts total with
1/2/4/8-second backoff; neither marketing, partial acceptance nor uncertainty
replays automatically. Startup sending rows become unknown, never queued.
Manual resend of a failed/unknown row creates one new retry_of child; repeated
requests return that child. It is an intentional new send, potentially duplicating
an earlier unknown acceptance. Journal payloads and transport secrets are never
returned by its HTTP routes, and collection/detail reads fetch only public
metadata. Attachment media types must be syntactically valid before enqueue.
Existing sends:get and sends:manage grants are global
journal grants, independently of list roles and tx:send.

M2.4 finished this staging: production wires the real marketing policy
(`src/unsubscribe/policy.ts`) into enqueue, outbox admission and manual resend.
A journal created without a policy still fails marketing closed
(`policy_unavailable`); the compiled test producer injects a permissive policy
only as at-most-once component evidence. Transactional linked subscribers
are rechecked before sending, including blocklist and identity replacement.

## Unsubscribe

- **Campaigns:** as in listmonk. `unsubscribe_url` in templates, plus `List-Unsubscribe` and `List-Unsubscribe-Post: List-Unsubscribe=One-Click` headers (RFC 8058) when `privacy.unsubscribe_header` is on.
- **Marketing sends (tx and sequences):** the same URL and headers, scoped to `list_id`. The URL contains the send UUID and subscriber UUID.
- **Transactional sends:** no unsubscribe link by default. A template may still include `manage_url` for preferences.
- **What unsubscribing does:** sets the `subscriber_lists` status to `unsubscribed` for the scoped list (or all lists when the preferences page says so, or when `privacy.allow_blocklist` and the person chooses "never email me"). Then it cancels the subscriber's active enrollments in sequences tied to those lists (`exit_reason = 'unsubscribed'`), and queues a `subscriber.unsubscribed` webhook.
- The one-click POST endpoint never requires a login or a CAPTCHA, as RFC 8058 requires.

M2.4 implements this for tx marketing sends. The producer fixes the send UUID before rendering; `unsubscribe_url` and `List-Unsubscribe` are `<root>/m/<send-uuid>/unsubscribe/<subscriber-uuid>`, and the generated header pair replaces caller values of the same names. The GET page confirms (as listmonk's `subscription` page, without the M2.5 preferences and data links); a `POST` (RFC 8058 `List-Unsubscribe=One-Click`, the page form, or JSON) needs no login, CSRF token, Origin or CAPTCHA. It re-reads the send and current subscriber inside one write transaction, marks the send's list `unsubscribed` (with `blocklist=true` and `privacy.allow_blocklist`: blocklists the subscriber and unsubscribes every list, as listmonk's unsubscribe-by-campaign query), then calls `UnsubscribeEffects.unsubscribed` in the same transaction. That seam is where M5 cancels enrollments and M2.6 queues webhooks; both are no-ops until then. Malformed UUIDs are 400; unknown, transactional or mismatched sends are 404 and change nothing.

## Frequency cap

- Setting: `marketing.min_interval` (ISO 8601 duration, default `P7D`; empty disables it).
- It applies to marketing sends from sequences and the tx API. Campaigns are deliberate broadcasts and are not blocked by the cap, but their sends count toward it.
- When a marketing send would break the cap, the step's `cap_policy` decides: `defer` (default) moves `due_at` to the earliest allowed time; `skip` records the send as skipped and moves on. For tx API marketing calls, the send is `skipped`.
- M2.4 counts the subscriber's other marketing `sends` that are `sending`, or `sent`/`unknown` with `coalesce(sent_at, created_at)` inside the window; `failed` and `skipped` rows do not count. At enqueue, inside the `BEGIN IMMEDIATE` journal write, `queued` rows also count, so concurrent requests cannot both pass. Outbox admission and manual resend recheck consent and the cap without counting queued rows or the row's own `retry_of` lineage, so a resend is still one intended message. Calendar parts subtract in UTC, clamped to month ends. Campaign deliveries (M3) must be added to this count.

## Tracking

- View pixel and redirect links as in listmonk (`privacy.individual_tracking`, `privacy.disable_tracking`).
- M2.4: `{{ url | track_link }}` registers the URL in `links` and renders `/m/<send-uuid>/link/<link-uuid>`; `{{ track_view }}` renders listmonk's hidden 1x1 image for `/m/<send-uuid>/px.png`. With `disable_tracking` both render as untracked and the routes record nothing. A redirect (307) requires that the link path was rendered into that send's stored message, so link UUIDs cannot be replayed on other sends (no open redirect). Clicks and views record `send_id`, and `subscriber_id` only with `individual_tracking`; the send row itself still names its recipient, so per-send analytics are inherently individual.
- Sends from the outbox are tracked against `send_id`; campaign messages against `campaign_id`. Both appear in analytics, and sends are grouped by template and by sequence step.

## Bounces

- `POST /api/bounces` (listmonk-compatible) and provider webhooks. v1 adds a **Mailgun** webhook (signature verified), which listmonk lacks. Other providers are later.
- Bounce actions per type (`soft`, `hard`, `complaint`) as in listmonk: count threshold, then `none`, `unsubscribe`, `blocklist` or `delete`.
- A bounce is matched to a campaign or a send by `Message-ID` or by the `X-Iglo-Email-Send` / `X-Listmonk-Campaign` headers.
- Blocklisting queues a `subscriber.blocklisted` webhook and cancels active enrollments.

## Outbound webhooks

Signed `POST` requests to URLs configured in settings.

| Event | When |
|---|---|
| `subscriber.unsubscribed` | Unsubscribed from one or more lists |
| `subscriber.blocklisted` | Blocklisted by an admin, a bounce rule or the preferences page |
| `subscriber.deleted` | Deleted (including by bounce rule or data wipe) |
| `bounce.recorded` | Any bounce |
| `send.failed` | A send ended as `failed` or `unknown` |

Body: `{ "id": "<delivery uuid>", "event": "…", "occurred_at": "…", "data": { … } }`, where `data` includes `subscriber.id`, `uuid`, `email`, `external_id` and the affected list IDs. Header `X-Iglo-Email-Signature: t=<unix>,v1=<hex HMAC-SHA256 of "t.body">`. Receivers must treat deliveries as at-least-once and dedupe by `id`.
