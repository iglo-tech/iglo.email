# API and admin UI

## API compatibility policy

Owner policy [D57](09-decisions.md#d57-compatible-client-results-and-safe-input-hardening): compatibility means matching results for realistic clients, not reproducing upstream implementation. Safe malformed/custom transport error differences are hardening backlog; formats, authentication, permissions, atomicity and actual security remain mandatory. A blocking review finding names the realistic client/request and concrete failure. Existing deliberate differences and safety checks remain.

The listmonk HTTP API is worth keeping where it is sound: there are SDKs, an n8n node and scripts written against it. Compatibility is the default, not a goal in itself. When listmonk's behavior comes from a poor design decision and makes the API awkward or wrong for its callers, iglo.email fixes it in the port instead of copying it. Each such fix is a deliberate difference: listed below with its reason, and marked in the contract suite.

For every **ported** endpoint, unless a difference below says otherwise, iglo.email keeps:

- the path and method;
- request field names and types;
- the `{ "data": … }` response envelope and `{ "message": "…" }` errors;
- pagination (`page`, `per_page`, `per_page=all`), with `total`, `per_page` and `page` in responses;
- authentication: `Authorization: token <api_user>:<token>` and HTTP Basic auth.

## Authentication and permissions

- **Admin users:** username and password (hashed with `Bun.password`, argon2id), sessions in SQLite, `HttpOnly` + `SameSite=Lax` cookies, and CSRF tokens on state-changing cookie requests. TOTP uses a bounded, single-use password challenge and the functional second-factor form under D30.
- **API users:** same model as listmonk (`type = 'api'`, token per user).
- **Roles:** listmonk's user roles and list roles, with the same permission names. New permissions:
  - `sequences:get`, `sequences:manage`;
  - `subscriber_events:create`, `subscriber_events:get`;
  - `sends:get`, `sends:manage`;
  - `webhooks:manage`.
- **Rate limits:** login and public endpoints (subscribe, opt-in, unsubscribe, export, wipe) are rate-limited per client address in memory, on the injected clock. The client address is the transport peer unless `security.trusted_proxies` says otherwise (D60). M1.3 login uses the explicit injected policy under D26. Public budgets are listed in the differences above.

M1.3's `GET /admin/login` supplies a pre-login nonce in the form and a host-only
HttpOnly cookie; `POST /admin/login` requires both. A successful login issues a
new seven-day session cookie and a readable host-only `csrf` cookie, both with
`Path=/` and `SameSite=Lax`; HTTPS root URLs add `Secure`. Cookie-authenticated
unsafe API requests, including logout, send the `csrf` cookie value as
`X-CSRF-Token`. A supplied foreign `Origin` is rejected. Header-authenticated
API clients do not need CSRF cookies. The default login limit is 20 POSTs per
client per minute, with at most 4,096 live records. Forwarded IP headers are
ignored unless the transport peer is in `security.trusted_proxies` (D60). Invalid explicit Authorization never falls back to a cookie.
Public `/health` remains public; `/api/health` requires a real identity.

M4.2 ports the subscribers and lists screens the same way: the server renders the shell, permission-dependent controls and everything derived from the URL (sort links, filter badges, hidden fields), and `subscribers.js`/`lists.js` read rows from the paged API, so stored text only reaches the page through `x-text` and `x-bind` and the API stays the one owner of filters, list scope and masking. Deliberate differences from upstream's pages, none visible to an API client: the SQL query is sent by GET in the page URL, not POST, as the API it calls is GET; the row "download data" link uses `GET /api/subscribers/export?id=`, as `/api/subscribers/:id/export` has no port; `per_page=all` in a page URL is ignored. Subscriber activity and charts, and list charts, have no endpoint here, so those tabs show the record and link to analytics.

M4.3 ports the templates and campaigns screens the same way: rows and records come from `/api/templates` and `/api/campaigns`, so names, subjects, tags and API messages reach the page only through `x-text` and `x-bind`. Editors load from the embedded assets, and a body reaches an editor as its value. Authored HTML never enters the admin document as it is ([D66](09-decisions.md#d66-authored-html-in-the-admin-page-goes-through-an-allow-list)): the rich-text editor copies load, paste, drop, the source and insert dialogs and format switches through an allow-list, and the content converters read HTML in an inert document. The body stays as stored until someone edits it in that editor, and a warning names what the editor left out, so a save without an edit changes nothing. Previews render in an `<iframe sandbox="">`, which allows nothing, not upstream's `allow-scripts allow-popups allow-popups-to-escape-sandbox`. A saved item is a GET into the frame, with the API's sandbox CSP. Unsaved content and the archive preview are POSTs that need the CSRF header, which a form cannot send, so the page fetches the HTML and writes it to `srcdoc`, after a `<!doctype html><html><head>` and the same policy in a `<meta>`, ahead of every authored character: text before the policy would start the body, where a parser ignores it. Status controls show only with `campaigns:send` and the manage scope of the campaign's lists, as the status route checks; a click asks once, sends once, and a refusal shows the API's message and re-reads the status. Those controls take no save without `campaigns:manage` or `campaigns:manage_all`: such a role sees a read-only form and starts the saved campaign, and a role that can edit saves first. A save keeps what it did not change: archive metadata while the archive is off, and the stored `send_at` to the millisecond unless the control, which shows minutes, changed. Live stats read `/api/campaigns/running/stats` one at a time, two seconds apart, up to 30 s after failures, and only while the page shows a running campaign and is visible; the read is one indexed select and never touches the runner. Deliberate differences from upstream's pages, none visible to an API client: the form does not send the subject as `archive_slug` on create, since two campaigns with one subject would conflict, and turning the archive on proposes a slug from it instead; the visual format is offered only for a campaign that already has it, shown as HTML (D54), and visual templates cannot be made; the rich-text editor sanitizes what it mounts (D66), where upstream mounts it as it is; the form is read-only without a campaign manage permission and starts a campaign without saving, where upstream saves first and is refused; the media picker is a dialog over `/api/media` until M4.5 ports the media screens, not a framed page; template search has no `type` parameter on the API, so the page filters by type.

M4.4 ports the settings, users, roles and profile screens the same way. Settings come from `GET /api/settings`, so masked secrets stay masked in the page, and a save is that object with the shown fields edited: `PUT /api/settings` replaces everything, so what the form does not show goes back as it was read (`privacy.exportable`, `security.oidc`, `maintenance.db`, DKIM, UUIDs). A masked secret goes back empty, which the API reads as "keep", and the form is read again after a save, so what was typed is masked at once. The form has `novalidate`: the API decides what is valid, and the logo, favicon and from fields take what it takes, because an input rule stricter than the API would hold back a save from a tab that is not showing. The root URL is a bootstrap flag (D44), so it is read-only and is the one setting that says it needs a restart; every other setting applies at once. Settings with no effect here keep round-tripping and show as unavailable, disabled: S3, the bounce mailbox, bounce providers other than Mailgun, messengers (postback is out of scope), captcha (nothing serves a challenge), `app.lang`, `app.notify_emails` and `app.check_updates`. The native keys sit beside their neighbours: `marketing.min_interval` under Performance, `security.trusted_proxies`, `security.public_rate_limit` and `webhooks.block_private_addresses` under Security, the Mailgun signing key under Bounces. SMTP test connection posts the form's unsaved values to `POST /api/settings/smtp/test`, including the headers in its text box. That route has no stored password to fall back on, so a masked password must be typed again, and a masked DKIM key cannot sign, so the test goes out unsigned.

M4.5 ports the bounces, media, import and forms screens the same way: rows, files, the import status and lists come from `/api/bounces`, `/api/media`, `/api/import/subscribers` and `/api/lists`, so a source, `meta`, file name, log line or list name reaches the page only through `x-text` and `x-bind`. Deliberate differences from upstream's pages, none visible to an API client. A bulk action over all that match sends the filters exactly as the page read them, untrimmed, because a source is stored text and a trimmed value selects another source's bounces. The gallery and the picker put a file in `<img>` only when `thumb_url` ends in `.png`, `.gif`, `.jpg` or `.jpeg`. `thumb_url` is the original, so the image is lazy and sized by the page, and an SVG, whose `thumb_url` the API still gives as upstream, shows its extension: it is opened in its own tab, under the M3.5 serving rules, and never drawn in the admin page. The campaign form's attachments follow the same rule. Uploads go one at a time, because the API admits eight in progress, and a refused file keeps the page with the API's reason, such as a refused root (D64), where upstream's reload loses it. Copy URL is added to the gallery; the copied text has `'` percent-encoded as well, so a name stays inside a pasted attribute. The campaign form's picker is upstream's: `/admin/campaigns/media/fragment` in an iframe, posting the picked file to a parent that checks origin and source. Import polls with one read at a time, a second after the last ended, instead of a fixed 500 ms interval. It stops when the import ends and after five failures or 3,600 reads, pauses while the page is hidden, and keeps the last status on a failure. The page shows the last 1,000 log lines. M4.6 ports the analytics, logs and maintenance screens the same way. The analytics page arrives at once with the form and one card per chart. `analytics.js` reads each chart from the M3.3 routes and the selected items from `/api/campaigns/:id` and `/api/lists/:id`, so a name reaches the page only through `x-text`, a tag or a canvas, and a 429, 422 or 500 shows in its own card. Upstream reads everything before it sends the page, which would hold the page behind a queued read. An ID the viewer may not read shows its message and the rest still draw. The date form is in UTC, as the API reads it; upstream's presets send the browser's wall clock to a server that reads it in its own zone. The logs page polls `/api/logs` every 10 seconds, and an empty buffer shows the empty state, as a healthy server logs nothing here. A line shows its time, what failed and the error's class, such as `inline image not embedded: no such media (Error)` or `unexpected error (TypeError)`, and the page says that names, addresses and error text are left out and that the full error is in the server's own output. The maintenance page has upstream's sections without Database: VACUUM is Postgres, nothing here runs it, and `maintenance.db` stays in what a full settings save returns. The webhook budget is stated beside the subscriber delete, which has no selection to narrow: what to do is delete in smaller selections from the subscribers page. The import screen adds a hint after a stopped import, read from the log, as the API status stays `finished`.

Maintenance does not cover this project's own tables. Delivered `webhook_deliveries`, expired `sessions` and views and clicks of sends grow with traffic and need a retention rule in the hourly loop, not a button, and their owners (`src/webhooks`, `src/users`, `src/messaging`) are outside M4.6. Bounded automatic retention of delivered webhook rows and expired sessions is on the backlog for before 1.0; views and clicks of sends need a history-retention decision first. `bounce_receipts` needs nothing: accepted requests prune it (D63).

Appearance settings run as authored. `settings:manage` sets them, through this form or the API. `appearance.admin.*` loads on every page rendered by `adminPage`, for every signed-in user, from `/admin/custom.css` and `/admin/custom.js`, which themselves sit behind the session check. It does not load on the login, 2FA, forgot, reset or error pages, or in preview frames. `appearance.public.*` loads on public pages for every visitor. Admin JavaScript runs with the permissions of whoever opens the page, and public JavaScript runs on the admin origin, so `settings:manage` amounts to administrator access. Upstream is the same; the tab says so.

Users and roles come from their APIs. Upstream's server-side filters on the users page (`type`, `status`, `user_role_id`, `list_role_id`) are applied in the browser, as the API takes none. The role selects arrive with the page, because `users:manage` alone cannot read `/api/roles/*`. A role has no read endpoint of its own, so its record arrives through the escaped bootstrap, and a missing one is the admin 404 page. The permission grid is built from what `/api/roles/users` accepts, so native permissions have boxes and a save cannot drop one unseen; a new role starts with upstream's defaults and no native permission. The list selector on a list role reads `/api/lists`, so it offers only lists the viewer may read, and a list already on the role keeps its row. Deliberate differences from upstream's pages, none visible to an API client: on your own record the role selects and password login are read-only, and the form sends `0`, the API's "keep"; a user role or list role you hold is read-only. The API still takes these changes from a caller with `users:manage` or `roles:manage`, and such a user can still give another account any role. The last administrator's status, role and delete are refused by the API and the refusal shows as a toast; password login is the one the API would take, so the read-only switch is what protects it. Profile saves through `PUT /api/profile`: a password change ends the user's other sessions and keeps this one. A token for a new API user shows once, in a dialog, and is not stored anywhere in the page afterwards.

At 1,000,000 subscribers `GET /api/lists` holds the server about 1.3 s for its counts with `app.cache_slow_queries` off. The lists index and list pages need those counts and make that one read after the shell has arrived; the subscriber screens and the list selector use `minimal=true`, which skips them. The listing uses the API's page of 20; a bulk action over all matches runs on the server.

M1.5 list writes accept JSON and XML through the bounded list decoder. XML
field names follow the Go model's case-sensitive local names, with repeated
`Tags` elements; JSON uses Go's case-insensitive field aliases and ordered
repeated writable fields. D36 ignores response-only and unknown metadata in
both formats; those fields cannot assign identity, timestamps or counts. D35's
declaration, depth, body and normalized tag limits and XML character/reference
integrity are covered by paired cases; the suite does not claim complete XML parity.

D37 replaces the XML implementation with a strict streaming parser. XML UTF-8,
syntax and characters are validated only through the consumed first root;
unconsumed suffix bytes are ignored as in pinned encoding/xml.Decode. The
64 KiB body, 64-level depth and no-DTD bounds remain. JSON retains its existing
replacement decoding. This corrects compatibility defects, not a new API exception.

M1.6 implements numeric-ID subscriber CRUD and ID-selected bulk actions. Collection/
search/SQL/query-selected bulk/export remain M1.7. M2.5 wires automatic and explicit
(`POST /api/subscribers/:id/optin`) opt-in mail as transactional outbox sends.
D38 defines the normal-only external_id field and GET/PUT/DELETE lookup routes,
exact nullable identity, safe conflict/no-write and current-scope behavior.

D39 adds a query-selector external route for every D38 opaque ID. Bun-normalized
dot path segments cannot encode those identities; . and .. remain valid and
use the query form. Selector values are decoded exactly once, never recursively.
The path convenience form and query form share permissions and atomic behavior.

M1.2 supplies persisted settings and authenticated routes, including
the D44 settings boundary; M2.1 activates the SMTP test under D49. Newly issued sessions capture their expiry;
legacy sessions retain the original seven-day policy. Subscriber mutations use
the current domain policy. `app.lang` is retained as configuration, but the
current runtime translation remains English; changing it does not hot-switch the
language. Later-owner settings do not implement their engines.

D47 pins native cron location validation to the complete case-sensitive
identifier set in Go 1.27.2's IANA 2026c archive, plus Go's empty/UTC/Local
special names. Valid aliases such as US/Eastern work without a production
timezone file. Names outside that set, including host-only extensions, return
the safe unknown-location error with no write. The reference runner supplies
the same checksum-pinned archive through ZONEINFO to make named-zone cases
reproducible; the earlier unaligned host lacked US/Eastern and rejected it.
This does not add a cron or timezone-offset engine.

D48 binds repeated settings arrays using their current logical elements.
Shrinking discards the truncated tail; later growth starts new elements from
field zero values rather than resurrecting Go decoder backing-array contents.
The paired SMTP cases show native 400/no-write when the only enabled server was
discarded, versus reference 200 with that server retained. When the first server
is enabled, both accept, but native's newly grown second element stays zero-valued.
This prevents removed configuration from reappearing through allocation history;
ordinary ordered prefix merging and null/empty rules remain unchanged.

Settings JSON strings follow Go's per-invalid-byte UTF-8 replacement decoding.
Under D44, this same typed decoding applies to recognized per-key candidates:
native accepts structurally valid repaired strings, while pinned raw per-key
bytes reach PostgreSQL and return 500/no-write. The common corpus explicitly
pairs both outcomes and complete reference rollback; valid UTF-8, malformed JSON
syntax, field-shape rejection and XML's existing strict boundary are preserved.

Shared compiled and reference corpora exercise binding, safe error envelopes,
numeric ranges, supported document and per-key types, address and cron cases.
This finite coverage is representative; reproduced unlisted differences must
still be corrected. A compiled test-only caller exercises the unmasked settings owner through local authenticated SMTP and Mailpit, including retention after restart.

M2.1 activates the SMTP test under D49: real authorized send, bounded admission,
safe errors and 200 data:[] rather than process-wide buffered logs. Its explicit
400/429/500 categories and limits are paired against the pinned route; other
authentication/cookie and settings behavior remains governed by existing policy.
D51 requires configured PLAIN/LOGIN/CRAM to be advertised and successfully
authenticated before MAIL/DATA, with no unauthenticated fallback or secret
transmission to a peer that does not advertise the selected mechanism. A
noncompliant peer that would accept the unadvertised method gets native
500/no AUTH/no intake versus reference200/authenticated/one intake; this
strict capability difference is paired explicitly for all three mechanisms.
PLAIN also preserves Go's TLS-or-exact-localhost guard before transmitting
credentials. Each To entry remains one parsed mailbox, not an address list;
invalid entries fail without SMTP and use the safe diagnostic 500. Exact
routing uses Go-compatible quoted-local parsing/simple Unicode casing; D52
defines the actual-domain exception for a quoted local @. Accepted null
header-map entries behave as empty maps. The other listed items are compatible
corrections, not newly permitted sending behavior.
Native keeps partial recipient acceptance and exposes both subsets to its
caller instead of aborting before DATA as upstream does. The protected test
returns safe 500 SMTP test was accepted for some recipients only. for that
case, with one intake for the accepted subset versus upstream500/no intake;
this is not proof that nothing was sent or permission to retry. Full
acceptance remains 200/data:[] and D24 forbids automatic replay.
D50 adds native-only optional SMTP dkim:{domain_name,key_selector,private_key}.
GET masks the key; empty key retains by UUID, null clears, invalid candidates
fail atomically. The Bun and compiled test-only callers verify signing, retained credentials,
restart and clearing. Full and per-key invalid candidates roll back, including nested shape,
key type, strength and size failures. The owner uses absolute 60-second send,
10-second test and five-second shutdown deadlines; forced active cancellation is
ambiguous and queued work that never started is locally rejected. These are
SMTP observations, not a final-delivery or durable-outbox guarantee.

D46 rejects NUL in final normalized writable settings strings and map keys
atomically with native HTTP 400 `Invalid data.` and no write; pinned PostgreSQL
returns HTTP 500 with no write. Ignored, overwritten and legitimately normalized
input retains its documented behavior. This settings-specific decision is
separate from subscriber D43 and requires no pending policy disposition.

D52 explicitly corrects SMTP domain routing for a quoted local part containing
@. After exact full-address matching, native uses the actual final domain;
pinned getPool uses the first @ of the unquoted address. With From
Sender <"sender@x"@route.test>, no full match, valid Return-Path and mappings
x@route.test / route.test, pinned selects x@route.test while native selects
route.test, one accepted message each. This prevents local-part contents
from steering mail to an unrelated configured provider bucket. The paired
routing corpus marks this exact difference; ordinary controls remain compatible.
