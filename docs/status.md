## Accepted trade-offs

- B155 (lead, 2026-11-26; [brief](briefs/B155.md) "Proposed accepted trade-offs", D176–D181): entry assets keep fixed names (a suite that imported the old manifest reads new contents under the old `assetVersion`); the PocketBase test binary is verified only on download; an on-demand SES read during the loop's sleep can add one GetAccount; a scheduler stall or `sending.hold` over 2 h during an outage restarts an enrollment's 72 h window (only lengthens retrying); a manual enrollment with no trigger record is skipped `late` past the window (nothing sent); the stream names check counts active enrollments every 15 s; the stream and scheduler use separate adapters (two service-account sign-ins per project); Test connection sees rows, not rules (D179 item 9, D181 item 5); a step condition is read before the trigger record, so a deleted record with a false condition ends `condition`, not `trigger_missing` (D180 item 7).
- On macOS the journal refusal test (`test/sends/journal.test.ts`) cannot hold its port: macOS drops a connection to a bound socket that does not listen instead of refusing it. There it uses a port free a moment earlier and fails by name within 2 s if something took it. The suite's platform is Linux (D89), where the refusal is certain (lead, 2026-11-26).
- The B118k Go-duration check in `test/reference/upstream-db.ts` differs from Go's parser on a few values the settings corpus never sends (B118k r1). It guards the corpus, not arbitrary input (lead, 2026-11-25).
- `test-send-trace.test.ts` counts the sink after draining the emailer with `close()`; a leak deferred past `close()` would not be counted (B118j r1 B1). No send path defers a push past the emailer, and the old 50 ms sleep had the same limit (lead, 2026-11-25).
- `plain-executable.test.ts` `/health` comparisons (`:290`, `:336`): in a normal run the send has finished before `/health` is asked, so they catch a missing converter cap only through its multi-second send (B118j r1 B2). They pass with a 40–60 ms effective bound; if one fails, the fix is to ask while the conversion provably runs, not a wider bound (lead, 2026-11-25).
- Media: under parallel load one extra campaign attachment buffer (at most one batch, 10 MiB or less) stays reachable after GC, with the holder unidentified ([D141](design/09-decisions.md), #196). The bound is measured, and a fix without the holder would be a guess (lead, 2026-11-25).
- "Delivered test send logs nothing" waits 20 ms after the sink receives the message (`test/messaging/test-send-log.test.ts`). A delivered test send logs nothing by design (D109), and no settled signal is observable through a public boundary (B118d). A regression would have to log after that window, which needs a code change, not timing (lead, 2026-11-25).
- Runner cost of about 9 ms per message (`docs/perf/B101-test-pool.md`): the measured product render cost of the largest allowed message (8 tracked links of 7 KB, the 64 KB template cap), not a defect (lead, 2026-11-25).
- Harness and kept sleeps (`docs/perf/B118d-sleep-sweep.md`): 16 sleeps in Docker, browser and opt-in harness scripts are each the poll interval of a loop that waits for an observable state with a named deadline, and none asserts a duration. 4 kept sleeps wait for a state nothing exposes, with the reasons recorded there (lead, 2026-11-25).
- The B118f stack fixture's logger skips the in-app log buffer. Unexpected-error stacks go only to stderr (`src/app.ts`), and the buffer takes only safe attention messages, so no `/api/logs` proof needs it (lead, 2026-11-25).
- Compiled-server readiness is a stall window on the child's CPU time (#210), not event-driven. No wall budget decides a start that is still computing, and the mutation test shows it (lead, 2026-11-25).
- `withProduction` stops 9 s before the test deadline (8 s kill grace plus 1 s). The margin is by design. A "lifetime" error in a gate run counts as a failure (lead, 2026-11-25).

- Send-rate cap and receipt latency (lead, B120, 2026-11-21): the cap holds at grant and SMTP hand-off (B120 trace: exactly 200 ms apart, at most 5 per rolling second); receipts at the server include each connection's latency, so two receipts one interval apart can fall in one second. Inherent to SMTP; operations.md tells operators to set the cap slightly below SES's maximum send rate.

- Anonymous view counting (lead, B123, 2026-11-20): with individual tracking off, the view pixel names no subscriber, so a request for a delivered campaign's dummy-subscriber pixel adds a view whoever sends it. Anonymous counting cannot tell a real open from a repeat by design; the campaign UUID reaches only that campaign's recipients; a recipient's own client reloading the image counts the same way; view counts are approximate anyway (image proxies, blocked images). Unpaired campaigns record nothing (D126).

- GET-then-PUT lost update in MCP read-modify-write tools and the admin UI (#86, #91): two concurrent edits of one campaign or sequence can overwrite each other. Endpoints have no version check; the agent or admin re-reads before a change it depends on (D91). A version column is not worth it for a single-owner instance (lead, 2026-11-08).

- A hand-typed host change on a saved SMTP server keeps its stored password (lead, B51 #102): editing a host is deliberate, only `settings:manage` admins can, and upstream does the same. A provider template, which swaps the host as a side effect, clears it instead.

- Enrollment listing and delete show numeric subscriber IDs outside the caller's lists (lead, B91 #143): IDs only, no address; a sequence manager needs the whole progress of its sequence. D103 revisit.

Decided by agents and logged; not open work. Reopen only on a new failure or a new realistic client.

- Role numeric JSON IDs above JavaScript safe integer range: safe rejection remains (D34). B10 left it: IDs are allocated from 1 by AUTOINCREMENT, so a list ID above 9007199254740991 needs about 9e15 inserts and exists only when a test advances the allocator; a lossless parse of numeric JSON would touch every JSON body reader for no realistic client.
- Paced event retention drains about 380 rows/s (the price of not holding back sends, [D74](design/09-decisions.md#d74-synchronous-attachment-sends-share-a-memory-budget-event-retention-joins-the-paced-loop)).
- B7 staging ([#57](https://github.com/iglo-tech/iglo.email/pull/57)): a read queued during a forced WAL gap can wait the full 30 s and get 429 (the gap is D62's price for restarting the WAL under continuous polling; a long read holds it open, and an earlier admission would block the checkpoint); analytics responses over 64 KiB are chunked with no Content-Length (B10 tried an explicit header: Bun ignores it on streamed bodies, and sending the bytes whole would drop the egress accounting that releases when the client has read them).
- Wiped sends ([#74](https://github.com/iglo-tech/iglo.email/pull/74)): D85 also silences `send.failed` for admin deletes without a wipe.
- Event latency tail: commit fsync waits only after B32 ([evidence](perf/B31-event-tail.md), [D88](design/09-decisions.md)); D86 accepts them and keeps FULL.
- Settings fold map ([#84](https://github.com/iglo-tech/iglo.email/pull/84)): a module-level `WeakMap` memo over the static shapes, filled on first use, instead of a load-time constant; it holds only derived constants.
- Tx burst ([#80](https://github.com/iglo-tech/iglo.email/pull/80)): 40 x 4 MiB gated peaks 212-254 MiB against D87's 256 MiB, a thin margin; if a later run exceeds it, lower `MAX_ATTACHMENT_SENDS` or the budget (do not re-measure until a run passes). The gate still charges for the copies B28 releases (stricter than needed, safe).
