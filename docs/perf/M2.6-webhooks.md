# M2.6 outbound webhooks

Changes to the unsubscribe and send paths add writes, so this records their cost. Serial, opt-in, not a CI threshold. `bun test/webhooks/measure.ts <executable> <hooks> [n]`: a compiled build over real HTTP on ext4, 1,500 subscribers, then 1,500 events and 1,500 one-click unsubscribes, one client at a time, with a loopback receiver.

Host: shared VM, load average 3 to 4, Bun 1.4.4. `before` is main at afd74d6 and `after` is this branch. All rows below come from one contiguous window, because the same `before` binary measured earlier at a quieter time gave ingest p50 1.8 to 2.2 ms and unsubscribe p50 6.6 to 8.8 ms. Compare within the window, not with those.

| Build | Webhooks | Ingest p50 / p95 / p99 ms | Unsubscribe p50 / p95 / p99 ms | Delivered | Drained after last request |
|---|---:|---|---|---:|---:|
| before | 0 | 5.60 / 8.60 / 11.46 | 10.80 / 17.81 / 21.80 | | |
| after | 0 | 5.71 / 9.39 / 11.78 | 10.88 / 17.93 / 21.72 | | |
| after | 0 | 5.44 / 7.68 / 11.73 | 12.31 / 17.99 / 21.82 | | |
| after | 1 | 5.75 / 9.70 / 12.69 | 17.51 / 26.97 / 31.90 | 1,500 | 27 ms |
| after | 1 | 5.05 / 7.03 / 10.81 | 16.30 / 25.03 / 29.40 | 1,500 | 28 ms |
| after | 20 | 5.69 / 9.28 / 12.04 | 46.16 / 68.39 / 77.96 | 30,000 | 77 ms |

- **Event ingest** does not touch the webhook path; it stays within noise at every webhook count.
- **Unsubscribe with no webhooks** stays within noise: only the extra lookups in the consent path and one read of the enabled webhooks.
- **Unsubscribe with webhooks** adds the delivery rows to its transaction, and the serial client then shares the single writer with the loop's claim and settle commits. Delivery itself stays asynchronous; the request never waits for a receiver.
- **Settling:** the first build committed each outcome separately and took unsubscribe p50 to 148.94 ms with 20 webhooks, 24.10 ms with 1. Finished attempts now settle together in the next claim's commit, which gave the numbers above and is why the outcome of a finished attempt can be lost to a crash (the delivery repeats with the same `id`).

## Bulk actions at the budget

A bulk action may queue 50,000 deliveries ([Sending](../design/04-sending.md#outbound-webhooks)). Bulk rows now go through one `INSERT … SELECT` per 500-subscriber batch. `bun run webhooks:measure:bulk <executable> <hooks> <subscribers>`: a compiled build over real HTTP on ext4, with subscribers seeded into the file and `hooks` enabled webhooks on all consent events. It bulk-blocklists half the subscribers (two events each), then bulk-deletes all of them while the loop drains the first batch to a loopback receiver. A second client polls `/health`, and its longest round trip is how long other requests waited. The whole action is one synchronous transaction, so request time and that wait are the same hold, apart from probe spacing.

Host: shared VM, load average 2.2 to 2.9, Bun 1.4.4. `before` is the reviewed head 5acdd03 and `after` is this change. Two runs of each, alternating, one contiguous window; the zero-webhook rows came straight after.

| Build | Webhooks × subscribers | Deliveries each | Blocklist ms | Blocklist longest `/health` ms | Delete ms | Delete longest `/health` ms |
|---|---:|---:|---|---|---|---|
| before | 20 × 2,500 | 50,000 | 1,050 / 1,025 | 1,177 / 1,120 | 1,463 / 1,554 | 1,463 / 1,555 |
| after | 20 × 2,500 | 50,000 | 724 / 744 | 850 / 865 | 1,390 / 1,258 | 1,390 / 1,258 |
| after | 0 × 2,500 | 0 | 52 | 45 | 78 | 74 |
| before | 1 × 50,000 | 50,000 | 2,185 / 2,238 | 2,193 / 2,236 | 3,964 / 4,114 | 3,976 / 4,126 |
| after | 1 × 50,000 | 50,000 | 1,403 / 1,336 | 1,401 / 1,336 | 3,410 / 3,291 | 3,411 / 3,291 |
| after | 0 × 50,000 | 0 | 513 | 505 | 2,030 | 2,029 |

- **Set-based queueing** cut blocklist by about 30 to 38%. Delete gains about 10 to 17%, because it also clears the deliveries the blocklist just queued, which was already one statement per batch.
- **The budget caps the webhook share, not the action.** At the budget, the longest hold measured is about 0.9 s for blocklist and 1.4 s for delete at 20 × 2,500, and 1.4 s and 3.4 s at 50,000 × 1, and other requests wait that long. About 2.0 s of the last figure is deleting 50,000 subscribers with no webhooks at all, which has no budget.
- **An action over budget** costs a read of the enabled webhooks and one `COUNT` inside the write transaction, then a 400, and writes nothing.
- **WAL:** 54 MB after both actions at 20 × 2,500 (5 MB with no webhooks), and 60 MB at 50,000 × 1 (33 MB with no webhooks).
