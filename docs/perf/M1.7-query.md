# M1.7 subscriber query, search and export measurements

Measured 2026-10-29 on Linux x86-64 with Bun 1.4.4 (16 GiB VM, `nice -n 10`),
through the in-process HTTP router of `test/subscribers/fixture.ts` over a
fresh WAL database in a temporary directory (removed afterwards). Command:
`bun run subscribers:query:measure` (`test/subscribers/measure-query.ts 100000`).
Synthetic data only: 100,000 subscribers `userN@exampleK.test` (K = N mod 50)
with a city attribute, half of them in list A. The fixture time limit was 2 s
for this run; production uses 10 s. Peak RSS is the parent process, sampled per
streamed response chunk. The run overlapped for its last ~2 s with the 2-second
`worker-terminate.ts` probe below, so the final bulk timings may be slightly high.

This adds new read paths and query-selected writes; it does not change the
schema, storage format or sending. There is no earlier endpoint to compare
with, so these are new costs rather than before/after figures. One plan
regression found during measurement is recorded below.

Seeding 100,000 rows with their FTS5 trigger rows took 7,993 ms.

Responses stream in bounded batches (200 projected rows, 500 export rows), so
`per_page=all` and full exports keep the parent within ~30 MiB of its baseline
while sending 50 MB and 20 MB bodies. Bulk actions select and write in batches
of 500 IDs inside one write transaction; a raw selection holds its matching IDs
(8 bytes each) in memory between the child and the transaction.

## Time limit and the choice of a child process

bun:sqlite 1.4.4 has no `interrupt()` or progress handler, `PRAGMA
hard_heap_limit` is accepted but not enforced (a 500 MB `randomblob` succeeded
under a 128 MiB limit), and Bun's SQLite symbols are not exported for FFI.
`test/subscribers/worker-terminate.ts` shows that terminating a Worker does not
stop a running SQLite step:

```json
{"name":"worker-terminate","cpuSecondsIn1500msAfterTerminate":1.49}
```

The process kept burning one CPU after `terminate()`. Raw fragments therefore
run in a child process of the same executable (`iglo.email __subscriber-query`,
or `src/subscribers/query-child.ts` from source) with its own read-only
connection. The parent counts only the time it waits for the child and sends
SIGKILL at the limit, then awaits its exit. After the timed-out query above:

```json
{"name":"after-timeout","childrenBefore":0,"childrenAfter":0,"parentCpuSecondsInNextSecond":0.03}
```

A /proc resident-memory watchdog (20 ms samples) kills a child above 256 MiB;
the 1 GB blob query was stopped after 609 ms. At most two children run at once.

Child round trip for `SELECT 1`, five samples:

| Child | ms |
|---|---|
| source module (`bun query-child.ts`) | 13, 12, 16, 18, 13 |
| compiled executable | 136, 156, 151, 142, 165 |

The compiled child evaluates the whole application bundle before dispatching;
this ~150 ms is paid only by requests with a raw `query`. Built-in filters and
search run in-process on the read-only connection.

## Plan regression found and fixed

The first version always joined `subscriber_lists` with `ON (0 AND ...)` so that
fragments may name its columns as upstream allows. SQLite then scanned the
join table per subscriber: page 1 took 81,189 ms at 100,000 rows (3 s at
20,000). The unfiltered join now reads `ON (subscriber_lists.subscriber_id =
subscribers.id AND subscriber_lists.list_id IS NULL)`: `list_id` is `NOT NULL`,
so it matches nothing, but the primary-key search is used (20,000 rows: 7 ms).
