# M1.2 settings draft storage measurements

Measured 2026-10-28 with Bun 1.4.4, Linux `/dev/sda1` ext4, fresh
synthetic databases, and the production connection's WAL, `synchronous=FULL`,
foreign keys and 5 s busy timeout. The exact M1.6 merge control was
`7764c13084fce10c52fb7c13ab295e756085a5d3`, built from a `git archive`
and frozen install; its executable SHA-256 was
`7d92a75c82b5159e691ee5969a078eccf62b4249bf5ac345e1473ef0ba48ce4c`.
The candidate code commit was `713a0d2c83a7ce753b33e6cc1b35946468359d4d`,
and its executable SHA-256 was
`74c54605616fe44824be33c7ea5a978497ede40d5f2bf5946421073ac7ba4e0e`.
The subsequent measurement record does not alter the executable. Both builds
used `bun run build`.

After acceptance, password tests, builds and hashing, the three control runs
preceded the three candidate runs, all serially. The same existing
`test/subscribers/measure.ts` workload ran in `candidate` mode on both binaries.
`TMPDIR` pointed at an owned empty directory on the ext4 filesystem; the
harness removed its temporary server copies and synthetic data directories, and
that directory was empty afterward. The synthetic bootstrap for the existing
workload was `m16-measure-admin` / `m16-measure-password`; the settings-specific
synthetic fixture is recorded in `test/settings/fixtures.md`. No mail or network
service outside the loopback test process was used.
