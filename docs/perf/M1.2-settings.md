# M1.2 settings draft storage measurements

Measured 2026-10-28 with Bun 1.4.4, Linux `/dev/sda1` ext4, fresh
synthetic databases, and the production connection's WAL, `synchronous=FULL`,
foreign keys and 5 s busy timeout. The exact M1.6 merge control was
`7764c13084fce10c52fb7c13ab295e756085a5d3`, built from a `git archive`
and frozen install; its executable SHA-256 was
`7d92a75c82b5159e691ee5969a078eccf62b4249bf5ac345e1473ef0ba48ce4c`.
The candidate code commit was `713a0d2c83a7ce753b33e6cc1b35946468359d4d`,
and its executable SHA-256 was
`74c54605616fe44824be33c7ea5a978497ede40d5f2bf5946421073ac7ba4e0e`.
The subsequent measurement record does not alter the executable. Both builds
used `bun run build`.

After acceptance, password tests, builds and hashing, the three control runs
preceded the three candidate runs, all serially. The same existing
`test/subscribers/measure.ts` workload ran in `candidate` mode on both binaries.
`TMPDIR` pointed at an owned empty directory on the ext4 filesystem; the
harness removed its temporary server copies and synthetic data directories, and
that directory was empty afterward. The synthetic bootstrap for the existing
workload was `m16-measure-admin` / `m16-measure-password`; the settings-specific
synthetic fixture is recorded in `test/settings/fixtures.md`. No mail or network
service outside the loopback test process was used.

Each existing workload had five warmups. Health and filtered list query used
50 samples; list and subscriber create/update/delete used 20 cycles; PATCH,
unsubscribe and blocklist used 30; bulk membership removal used 10; and list
counts used 50 samples after creating 100 synthetic subscribers and 200 initial
memberships. Means are milliseconds per operation or cycle:

| Workload | Control 1 / 2 / 3 | Candidate 1 / 2 / 3 |
|---|---|---|
| Protected health | 0.532 / 0.525 / 0.427 | 0.448 / 0.420 / 0.472 |
| List create + update + delete | 7.568 / 7.725 / 7.797 | 7.978 / 7.950 / 8.085 |
| Filtered list query | 0.824 / 0.856 / 0.709 | 0.837 / 0.547 / 0.745 |
| Subscriber create + PUT + delete | 6.933 / 7.113 / 6.781 | 6.466 / 6.858 / 6.663 |
| Subscriber PATCH | 1.927 / 2.152 / 2.178 | 2.236 / 1.404 / 1.756 |
| Single unsubscribe | 1.447 / 1.753 / 1.780 | 2.063 / 1.074 / 1.428 |
| Single blocklist | 1.209 / 1.522 / 1.309 | 1.609 / 0.959 / 1.060 |
| Bulk membership removal | 1.233 / 1.844 / 1.512 | 1.204 / 1.441 / 1.347 |
| List count query | 0.852 / 0.860 / 0.766 | 0.803 / 0.498 / 0.521 |

The settings endpoint did not exist on the control, so these are new costs,
not before/after comparisons. After the six equivalent runs, three serial
candidate runs used `test/settings/measure.ts`, each with a new process and
data directory. GET used 50 samples after five warmups; full and per-key PUT
used 20 samples after five warmups; restart plus authenticated settings GET
used three samples after one warmup. Means in milliseconds:

| New workload | Run 1 | Run 2 | Run 3 |
|---|---:|---:|---:|
| Settings GET | 1.076 | 1.227 | 0.907 |
| Full settings PUT | 3.113 | 3.084 | 3.064 |
| Per-key PUT | 3.784 | 2.856 | 2.806 |
| Restart and settings GET | 333.428 | 329.055 | 306.005 |

This is a bounded local experiment. It makes no guarantee about speed, scaling
or exclusive use of the host, and establishes no CI timing threshold. The
settings implementation is still a draft with the validation and session
limitations identified in the PR; these numbers do not establish functional
acceptance.

## Completion-fixer measurements (draft)

The earlier measurements above remain historical. On 2026-10-28 the equivalent
workloads were repeated after acceptance and password tests using Bun 1.4.4 on
Linux `/dev/sda1` ext4. Fresh synthetic databases used the production WAL,
`synchronous=FULL`, foreign-key and 5-second busy-timeout settings. The exact
M1.6 control was `7764c13084fce10c52fb7c13ab295e756085a5d3`, exported with
`git archive` and built after a frozen install; its executable SHA-256 was
`7d92a75c82b5159e691ee5969a078eccf62b4249bf5ac345e1473ef0ba48ce4c`.
The measured candidate source commit was
`330b8f84069b17a6e4abf8120255e8e89d9b9b15` (tree
`3d65820c555abd3465ba05a7421302a8693ce7f9`); its compiled executable SHA-256 was
`5dfbc4d19b803b8f81cf983dc9dfb6bfe513db1c5b57d2fb032b30a1d20040aa`.
Both were built with `bun run build`. The runtime/build inputs and both hashes
were checked again after timing.

The three control repetitions preceded the three candidate repetitions,
serially, using the same `test/subscribers/measure.ts` workload in `candidate`
mode for each executable. Each used a new process and data directory under an
