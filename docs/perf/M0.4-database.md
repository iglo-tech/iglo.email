# M0.4 database measurement

The parent has no application storage. The before workload is a direct native
bun:sqlite primitives baseline, not an existing-product benchmark.

## Filesystem correction

The initial pre-implementation baseline and report used the system temporary
directory. On this host /tmp is tmpfs. Those 9–13 ms insert results measure a
memory-backed filesystem and do not include durable-storage commit cost. They
are retained in the original test-first commit and the prior PR head, but are
superseded as storage evidence by the disk-backed runs below.

Corrected on 2026-10-27 after council round 1: both the original baseline program
from commit 89b81c35934137743f80f44c821ba23d4c652d1d and the current native/helper
program were rerun on ext4, /dev/sda1, mounted at /. The measurement directory
was this worktree's upstream/measurements; statfs reports type 0xef53 and
df -T confirms ext4. Bun 1.4.4, SQLite 3.53.4,
Linux 6.12.113+deb13-amd64 x86_64. The code for the original baseline is unchanged;
these are new runs of that pre-implementation program, not historical timings.

The current command defaults to upstream/measurements beneath its checkout
(ignored by Git), reports its resolved directory, filesystem type and platform,
and rejects known tmpfs/ramfs filesystems. Set IGLO_EMAIL_PERF_DIR to select
another target. Check that target's actual backing filesystem; merely passing
the memory-filesystem guard does not prove physical durability.

Reproduce the original program on the same target, then the current comparison:

    mkdir -p upstream/measurements
    git show 89b81c35934137743f80f44c821ba23d4c652d1d:test/db/measure.ts > upstream/measurements/native-baseline.ts
    TMPDIR="$PWD/upstream/measurements" bun upstream/measurements/native-baseline.ts
    bun run db:measure

For a custom current target:

    IGLO_EMAIL_PERF_DIR=/path/on/disk bun run db:measure

Each mode uses three fresh databases, inserting 10,000 synthetic rows in
100 transactions of 100 rows with BEGIN IMMEDIATE, bound inserts, WAL,
foreign keys, synchronous=FULL and busy_timeout=5000. It then performs 10,000
bound lookups and a VACUUM INTO snapshot. Count (10,000), ID sum (50,005,000),
every lookup value and snapshot contents are checked. The measured database
directories are owned and removed by the program.

## Current native/helper comparison on ext4

The native mode repeats the same workload, then the helper mode uses the
connection, named-query, write-transaction and migration helpers. The helper
snapshot column includes integrity/version verification, publication and a
small schema migration; the native column times VACUUM INTO alone. Both reopen
the snapshot and check count/sum; the helper snapshot precedes the schema
change. Main/WAL sizes are sampled before connection close.

The disk-backed runs exercise the selected FULL commit path rather than the
original memory-filesystem path. Native and helper insert ranges overlap in
this run; three short sequential repetitions do not establish a stable helper
overhead or performance gain. This is not a FULL-versus-NORMAL experiment,
and filesystem/timing differences prevent attributing the entire gap from
the old tmpfs run solely to fsync.

## Busy-loop fairness before and after the round 1 fix

Command: bun test test/loops/loop.test.ts --test-name-pattern 'busy synchronous'.
The HTTP fixture owns 5,000 eligible synthetic rows, claims one per batch and
processes synchronously. Before the fix, microtasks drained all work before
HTTP could deliver stop. The regressions were committed at 7c147f4 before
changing production code. The fixed helper awaits the injected clock after
each busy batch; no network or processing occurs in its claim transaction.

| Public HTTP observation | Before | After (this run) |
|---|---:|---:|
| Fake clock: items started before the explicit zero-time advance | 5,000 | 1 |
| Real clock: items processed before the HTTP stop request takes effect | 5,000 | 1 |

The fake-clock case then advances by zero, observes the second item, stops,
and advances further with no new work. The real-clock count varies with I/O
scheduling; its contract is that HTTP can stop the loop before all 5,000 items
are processed, followed by no additional starts. These fixtures use temporary
synthetic databases to observe scheduling/stop behavior, not to time durable
commits. They are not a latency or throughput benchmark; the ext4 storage
measurements above cover the chosen FULL write path separately.

These are single-VM, cache-sensitive observations, not a production throughput
target or a power-loss test. Guest ext4/fsync measurements do not verify the
host storage cache or hardware's power-loss guarantees. Snapshot timings
include different amounts of validation/schema work as described above.
VACUUM INTO needs additional disk space, runs synchronously, can change
implicit rowids without an explicit INTEGER PRIMARY KEY, and does not offer
the incremental scheduling of the online backup API. The code does not
promise directory-entry durability across sudden power loss. Loop scheduling,
network I/O and concurrent sustained traffic are not represented.
M0.7 owns the sustained sending/event and FTS spike.
