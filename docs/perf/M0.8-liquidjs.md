# M0.8 LiquidJS: Bun rendering spike

Control evidence recorded before the compile-once comparison. The baseline and first paired comparison used an ordinary empty map; the final rerun below corrected that map to a null-prototype object. This fixture is synthetic; M1.8 owns the production engine, data boundary, built-ins and acceptance.

## Baseline

On 2026-10-28, Bun 1.4.4, LiquidJS 10.30.0, Linux x64 6.12.113+deb13-amd64, AMD Ryzen 5 1600 (6 logical CPUs), 16,775,880,704 bytes host memory. `bun run runtime:spike:liquid --control-only` rendered 10,000 generated recipients in three repetitions after a 200-recipient warmup. Parse body/layout/subject per recipient: body 266, layout 109 and subject 63 UTF-8 bytes; three list elements, `upcase`, fixture translation/tracking filters. HTML engine used `outputEscape: escape`, `ownPropertyOnly`, empty in-memory `templates`, parse 65,536, render 1,000 ms, allocation 1,000,000; subject was plain text. Values and digest checked for every recipient. Timing is real monotonic elapsed, RSS sampled every 100, not a memory peak guarantee.

## Actual boundaries and corrections for the lead

[LiquidJS 10.30.0 options](https://github.com/harttle/liquidjs/blob/v10.30.0/src/liquid-options.ts), [parser](https://github.com/harttle/liquidjs/blob/v10.30.0/src/parser/parser.ts), [render loop](https://github.com/harttle/liquidjs/blob/v10.30.0/src/render/render.ts), [context](https://github.com/harttle/liquidjs/blob/v10.30.0/src/context/context.ts) and [limiter](https://github.com/harttle/liquidjs/blob/v10.30.0/src/util/limiter.ts) were checked against the pinned installed package. All three limits default to infinity in this version.

- `parseLimit` charges the JavaScript string length, in UTF-16 code units, for a parse operation. Four units (`😀😀`) passed limit 4 and five failed. It is not a byte or render-output limit.
- `renderLimit` is milliseconds measured against a monotonic deadline and checked at rendering steps. It cannot preempt a synchronous filter or other long operation. A deliberately bounded 50 ms trusted filter completed before a 5 ms render limit was reported: 51.170 ms in the source child, 50.921 ms compiled. No short timing threshold or sleep is used as evidence.
- `memoryLimit` is cumulative library accounting in operation-specific units (such as string or array lengths), not a process memory, byte or output cap. A range of 100 exceeded a 10-unit limit, but outputting an existing 4,096-character raw value succeeded at that limit. The source and compiled child both reproduced this contradiction to a general hard-output-limit interpretation.
- `ownPropertyOnly` blocks direct inherited object/index lookup in the fixtures, but a generated sparse array with an inherited element rendered `|inherited-fixture`: direct `arr[0]` was hidden while iteration exposed the element. The [option's own documentation](https://github.com/harttle/liquidjs/blob/v10.30.0/src/liquid-options.ts) distinguishes property access from iteration/filter semantics. It is not a complete data sanitization boundary.
- Default filesystem lookup is not isolation. An initial empty ordinary-object mapping wrongly resolved inherited names: `constructor` rendered `function Object() { [native code] }` in a bounded local probe. The corrected fixture supplies an empty null-prototype in-memory `templates` mapping and denies `constructor`, `toString` and `__proto__` as well. `include`, `render` and `layout` each failed for a fixture-owned existing canary file and a loopback HTTP trap; the trap received zero requests. This exercises the selected configuration, not all LiquidJS extensions or possible host integrations. No DNS or network fetch is required for template lookup.
- HTML output escaping covered metacharacters and explicit `raw`; the plain subject remained unescaped. The body was escaped once and inserted into the layout with `{{ content | raw }}`. This is an explicit trusted composition boundary, not general context-aware URL or script sanitization.

Both source and compiled children completed the same bounded probes and HTTP-render case. The compiled fixture ran from an invocation-owned ext4 directory with empty `PATH`, inside Linux bubblewrap exposing the directory and system runtime libraries but not the repository or `node_modules`; it exited successfully. The opt-in compiled check requires Linux `bwrap` with user namespaces. This is a test-only filesystem isolation tool, not a production service. `--smoke` uses smaller workloads and is correctness evidence only. Linux results do not certify other platforms.

**M1.8 proposal for lead decision:** retain Liquid but correct the broad sandbox/hard-limit wording: use an allowlisted in-memory resolver and plain, recursively sanitized data including dense arrays; enforce input sizes and a separate bounded-output strategy, and treat render time as cooperative rather than a hard deadline. Review trusted custom filters, HTML/URL contexts, raw/layout insertion and synchronous work before selecting production limits. A post-render size check alone cannot prevent a large allocation; the owner must choose an enforceable output mechanism and test it. The fixture has no production template store, preview API, Markdown rendering or converted built-in library. Go-template byte parity is intentionally not claimed under D9.
