# M1.1: v1 schema mapping and measurements

`migrations/0001_init.sql` translates `/home/t3-code/upstream/listmonk/schema.sql` at `6fcd95f32bb633d3a62a06c383c0b3322eecc898`. The upstream checkout was read-only. `queries/lists.sql` (list and chart consumers), `queries/misc.sql` (dashboard counts and charts), and `queries/subscribers.sql` (cached counts) informed the four stored summary shapes. No endpoint, scheduler, sender, summary refresh or production validation route is implemented by this change.

## Mapping and choices

- The 16 retained tables are `subscribers`, `lists`, `subscriber_lists`, `templates`, `campaigns`, `campaign_lists`, `campaign_views`, `media`, `campaign_media`, `links`, `link_clicks`, `settings`, `bounces`, `roles`, `users` and `sessions`. Their upstream columns and enum value sets are retained, with SQLite integer IDs, app-supplied UUID text, JSON text, checked 0/1 booleans and sortable UTC text timestamps. Upstream timestamp defaults become `strftime` UTC millisecond strings; nullable upstream timestamps remain nullable. Sessions retain `id`, `data`, `created_at`; session data and setting values accept any valid JSON value.
- Upstream status, ID/status, name, date, lookup and relationship indexes are retained, including partial unsubscribed and default-template indexes, role uniqueness, and campaign/list/media and analytics indexes. The unique `LOWER(email)` index is represented by the `NOCASE` unique email column; SQLite's built-in folding is ASCII-only. SQLite's nullable unique indexes allow several unset external IDs and keys. The Postgres composite membership primary key implies non-null members despite its explicit `list_id NULL` spelling, so both columns are explicitly non-null in SQLite.
- New storage is `events`, `sequences`, `sequence_steps`, `enrollments`, `sends`, `webhooks`, `webhook_deliveries`, plus external-content `subscribers_fts` and insert/update/delete triggers. New indexes cover event lookup and per-subscriber idempotency, active step order, scheduler due work, enrollment lookup, send outbox and cap queries, unique enrollment/step sends and transaction keys, tracking by send, and webhook due work. No trigger invents send or retry transitions. Soft-deleted steps do not reserve an active position. Exit and skip reasons remain extensible; payload can be cleared to SQL NULL.
- Four ordinary empty summary tables retain upstream's exact column shapes: dashboard counts/charts `(updated_at, data)`, list counts `(updated_at, list_id, status, subscriber_count)`, and list charts `(list_id, date, subscriptions, unsubscriptions, campaign_views)`. List count `list_id = 0` and `status IS NULL` represent the upstream all-subscriber total, so there is deliberately no list FK on that summary. Future owners populate and refresh summaries.
- Persistent integer identities use `INTEGER PRIMARY KEY AUTOINCREMENT` to avoid reuse of automatically allocated committed IDs after deletion, preserving upstream SERIAL/BIGSERIAL allocation behavior and protecting retained session and external/JSON references from aliasing replacement entities. The initial implementation applied this only to subscribers; both council members identified that deleting the highest user ID allowed an old session to resolve to a replacement user. A public HTTP-fixture regression now deletes a user while retaining its session, reopens the database and creates a replacement with a different role; the retained identity must remain unresolved. It also checks list/template/campaign non-reuse across that restart. Application owners must still allocate IDs automatically and never insert explicit lower/previously used IDs; SQLite permits explicit IDs and cannot enforce that policy by this declaration alone. All integer PKs preserve signed 64-bit values. Tests exercise `9223372036854775807` through the safe-integer connection. UUID generation stays with future owners.
- On deletion, memberships, events, enrollments and subscriber bounces cascade with their subscriber. Event retention sets `enrollments.trigger_event_id` NULL. Tracking subscriber references and send subscriber/enrollment references become NULL, preserving analytics and send history. Campaign or send deletion cascades its tracking rows; link deletion cascades clicks. Campaign list/media records retain copied names when a list/media item is deleted. Lists/templates on sequence and send records become NULL; steps and sequences referenced by enrollments are restricted, while steps are normally soft-deleted. Deleting a webhook cascades its delivery rows. These actions use SQLite foreign keys; they do not perform consent, scheduler or recovery decisions.
- `bounces.send_id` and a nullable `bounces.subscriber_id` extend the upstream shape so a bounce for a transactional send to an address with no subscriber can be recorded; subscriber-associated bounces still cascade on subscriber deletion. `webhook_deliveries.uuid` supplies the delivery ID required by outbound webhook bodies. These are schema choices for the designed new features, not implemented bounce/webhook behavior.
- JSON objects are required for subscriber attributes, event properties, sequence triggers and object-valued upstream metadata; JSON arrays are required for headers, tags, permissions, exit events and webhook event lists. Optional JSON and nullable FK values retain SQL NULL where designed. Timestamp columns store sortable UTC strings, but SQLite does not validate supplied timestamps. Application owners must provide UTC values from their injected clock.

The translation omits all upstream `DROP` statements, `CREATE TYPE`, `pgcrypto`, Postgres materialized views and their compute queries: the migration is non-destructive fresh-install DDL, and the summary rebuild belongs to M3.3. All installer `settings` rows are omitted, including app, privacy, security/CAPTCHA/OIDC, upload/S3, SMTP, messenger, bounce/provider/mailbox, appearance and maintenance defaults. M1.2 owns settings defaults and validation; later owners handle deferred features. No role, permission, user, password, list, subscriber, campaign or template is seeded; M1.3/M1.4 and M1.8 own those decisions. No upstream migration history is replayed. Later-feature columns and enum values remain for storage shape and do not implement those features.

## Reproduction and method

Run `bun run schema:measure`. It uses fresh invocation-owned subdirectories below ignored `upstream/measurements` (or disk-backed `IGLO_EMAIL_PERF_DIR`), rejects tmpfs/ramfs, uses the production `openDatabase`, migration and transaction helpers, and removes only its own subdirectory. It runs three sequential repetitions of an empty catalog versus the embedded v1 catalog. These are initialization costs on different schemas, **not equivalent production workload throughput**. It times connection/pragmas, migration, integrity and FK validation, checkpoint/close/reopen validation, and a no-op restart separately. File sizes are lengths, not total bytes written. The 32 non-internal SQLite tables include 27 ordinary product/summary tables, the FTS virtual table and its four shadow tables.

Each FTS pair starts with the same v1 schema and synthetic inputs, and alternates order. It inserts 2,000 generated subscribers in transactions of 100, updates 500 and deletes 250, then rolls back 100 updates. It verifies integrity and foreign keys before and after, counts actual `MATCH` results at each stage, checks rollback and reopen, and checks FTS external-content integrity when triggers are enabled. The control drops the three FTS triggers **only in its measurement database**; its index remains empty, so its zero search results confirm the disabled-index limitation, not equivalent search behavior. Search checks occur outside the individual mutation timings. This reduced workload is not a sustained M0.7 benchmark or a delivery guarantee.

Measured 2026-10-28 on Linux 6.12.113+deb13-amd64 x64, six logical CPUs (AMD Ryzen 5 1600), 16,775,880,704 bytes reported memory, Bun 1.4.4, SQLite 3.53.4. ## Council identity-allocation correction

Both round-1 reviewers reproduced reuse of the highest deleted users.id, which allows an unchanged sessions.data user_id to identify a different replacement account. A regression added through the synthetic HTTP fixture failed on head `35d7bd2` with resolvedSessionUser = replacement after database reopen; it passes after the correction. It retains the session deliberately and checks that replacement user, list, template and campaign IDs are greater than their deleted predecessors. Production auth remains M1.3; this tests the storage identity invariant it depends on.

The correction preserves non-reuse for every persistent integer identity, consistent with the pinned upstream SERIAL/BIGSERIAL allocation assumption, rather than special-casing users. IDs generated automatically for committed rows are not reused; explicitly inserting old IDs is still forbidden by the application ownership rule. Original measurements above describe the prior declaration set and are retained. The [complete before/after aggregate records](M1.1-id-allocation.jsonl) include all phases, file sizes, validation and FTS observations without raw recipient data.

The lead reran the unchanged full schema:measure command under the measurement lock before the DDL correction at 08:42:37 UTC and after it at 08:44:50 UTC, on the same ext4 host/runtime and with the identical FULL/WAL settings and inputs described above.
