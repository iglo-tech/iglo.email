# M5.1 subscriber events API measurements (D22)

Serial, foreground runs on the shared Linux x86-64 development VM (Bun 1.4.4,
`nice`, no parallel test runs), 2026-10-29. Reproduce with `bun run events:measure`
(`bun test/events/measure.ts [sends|events|mixed|all]` after a build;
`EVENTS_MEASURE_SEND_RATE` sets messages/s, default 50; `EVENTS_MEASURE_WINDOW_MS`,
default 60000). Raw results, including 1 s samples, are in
[M5.1-results.jsonl](M5.1-results.jsonl). These are local observations, not CI
thresholds or production capacity claims.

## Method

- **Target:** the compiled `dist/iglo.email`, started by the contract harness with a
  fresh data directory on ext4 disk (`upstream/measurements`, never tmpfs), WAL and
  FULL synchronous commits (D19/D22 unchanged). Real HTTP over loopback with an API
  credential provisioned through the real login.
- **Events:** open-loop `POST /api/subscriber-events` at fixed 10 ms deadlines (100/s,
  6,000 offered per 60 s window). Each names one of 2,000 subscribers by `external_id`
  and `email`, changes `attribs`, carries ~50 bytes of `data` and a unique
  `idempotency_key`; the first 2,000 create subscribers, the rest update them.
- **Synthetic send load:** campaigns do not exist until M3, so no campaign runner is
  exercised; M3.2 repeats the end-to-end campaign check. Instead, async
  `POST /api/tx` at fixed deadlines: four fifths transactional (external mode), one
  fifth marketing (one per preconfirmed list subscriber, inside the 7-day cap). The
  production outbox delivers them to an in-process loopback SMTP sink that records
  only per-subject receive times.
- **Recorded:** offered and completed counts; completions inside the window and the
  drain after it; **acceptance latency** (scheduled deadline → HTTP response) and
  **commit latency** (request start → response; a 200 is sent only after the commit);
  driver lateness; delivery latency (deadline → SMTP receipt); 1 s samples of client
  in-flight requests, outbox status counts and stored events from a read-only
  connection, and server RSS. The client caps in-flight requests at 500 and counts
  any request beyond that as **shed** (offered but never sent), so overload stays
  visible.
- Warmup (20 events), provisioning and subscriber setup are outside the window. Each
  scenario starts a fresh server.
- `free -m` before/after the runs: available 8,983 → 9,117 MiB (before set),
  8,165 → 8,519 MiB (after set), 8,250 → 8,618 MiB (20 msg/s pair). Swap was already
  full on the host before the runs. Server RSS stayed at 63–105 MiB.

A probe on the same disk measured one FULL-sync single-row commit at p50 4.36 ms
(p95 4.70 ms), and 300 rows in one commit at 5.20 ms. Commits are fsync-bound and
block the single JavaScript thread.

## Before and after

**Before** commits each event request in its own transaction. **After** (the shipped
code) uses group commit: requests that are queued while a commit runs share the next
transaction, each in its own savepoint with its own authorization and result. An idle
server still flushes on the next event-loop turn, with no added delay.

## Findings

- **Events alone meet 100/s.** In both versions all 6,000 events committed inside the
  window, with no drain, no shed requests and no backlog growth. Client lateness
  stayed at p99 ≤ 2.5 ms.
- **The window boundary (D22).** At 100 ev/s + 20 msg/s every event completed in the
  window. At 50 msg/s, 3 of 6,000 events finished 14.6 ms after the window. These are
  requests that were still in flight at the boundary. Their commits were not lost, and
  the window does not count them. Both effects are reported separately above.
- **Group commit removes the event-side collapse.** At 100 events/s plus 50 msg/s,
  per-request commits saturated the thread: 1,120 requests shed, ~4 s latency, 894
  events outside the window. With group commit there is no shedding, 5,997 events
  land in the window and the client never exceeds 61 requests in flight.
- **Events do slow sends.** At 20 msg/s, a rate the outbox sustains alone (all
  delivered in the window, p95 52 ms), adding 100 events/s raised delivery latency to
  ~6.2 s. The queue settled at ~114–137 rows after about 20 s instead of growing, and
  drained 1.65 s after the window. At 50 msg/s the outbox could not keep up even
  without events (338 queued at the window end), and with events it was starved
  (543 delivered in the window).
- **Cause:** on this disk every commit costs ~4.4 ms on the one thread. The outbox
  claims and sends one row at a time, with a claim commit and a finalize commit per
  message, and each async tx request also commits once. Events add CPU and grouped
  commits on top of that. So the D22 target "100 events per second without slowing
  sends" is **not met** for tx-API send load on this host. Batching inside the events
  module cannot fix the send side. Outbox batching and per-message commits belong to
  the messaging owner. M3.2 (campaign progress commits per batch, not per message)
  and M6.1 must measure this again.
- **First failure, kept:** the first sends-only 20/s run exited nonzero. 30 of 1,200
  tx requests never returned, and there was a ~2.4 s stall (tx commit p95 1,291 ms).
  Its stderr was overwritten by the next scenario, so the cause was not captured.
  The host had ~2 GiB free memory and full swap at the time. The immediate rerun was
  clean (1,200 / 1,200, p95 52 ms), and the table uses the rerun. Both runs are in
  the JSONL.
