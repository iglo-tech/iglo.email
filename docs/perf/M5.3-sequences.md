# M5.3 event ingest with active sequences

Serial, foreground run on the shared Linux x86-64 development VM (Bun 1.4.4, `nice -n 10`,
no parallel test runs), 2026-10-29. Reproduce with `bun run sequences:measure`
(`bun test/sequences/measure.ts [baseline|sequences|all]` after a build;
`SEQUENCES_MEASURE_WINDOW_MS`, default 60000). Raw results are in
[M5.3-results.jsonl](M5.3-results.jsonl). These are local observations, not CI thresholds
or production capacity claims.

## Method

- **Target:** the compiled `dist/iglo.email` started by the contract harness with a fresh
  data directory on ext4 (`upstream/measurements`, never tmpfs; removed afterwards), WAL
  and FULL synchronous commits (D19/D22 unchanged). Real HTTP over loopback with an API
  credential provisioned through the real login.
- **Events:** the M5.1 events-only driver shape: open-loop `POST /api/subscriber-events`
  at fixed 10 ms deadlines (100/s, 6,000 offered per 60 s window), 2,000 subscribers by
  `external_id` and `email`, changed `attribs`, ~50 bytes of `data`, a unique
  `idempotency_key`, and at most 500 requests in flight (excess counted as shed). Each
  subscriber alternates `signup` and `order_paid` on successive rounds of 2,000 events.
- **Sequences:** none (baseline), or 20 active sequences with two steps each: 10 triggered
  by `order_paid` (5 with a `data.currency` shorthand filter, all `reentry: always`) and 10
  triggered by `signup` that exit on `order_paid`. Every event therefore runs the exit
  query and the trigger lookup; every `signup` starts 10 enrollments; every `order_paid`
  exits 10 and starts 10, all in the event's transaction. Because each start or exit is
  returned with an idempotency key, each such event also stores its replay result.
- **Recorded:** acceptance latency (deadline → response; a 200 is sent only after the
  commit), commit latency (request start → response), started/ended counts from the
  responses, server RSS, and enrollment counts from a read-only connection.

## Results

| 60 s window | Events done in window / offered | Acceptance p50 / p95 / p99 / max (ms) | Commit p50 / p95 (ms) | Shed | Started / ended | RSS peak (MiB) |
|---|---|---|---|---|---|---|
| M5.1 after, events only (reference) | 6,000 / 6,000 | 6.8 / 12.1 / 18.0 / 144 | 6.1 / 11.3 | 0 | n/a | 63–105 |
| M5.3 baseline, no sequences | 6,000 / 6,000 | 6.0 / 9.4 / 13.3 / 44 | 5.4 / 8.6 | 0 | 0 / 0 | 72 |
| M5.3, 20 active sequences | 6,000 / 6,000 | 9.3 / 20.6 / 32.6 / 227 | 8.6 / 19.5 | 0 | 60,000 / 20,000 | 74 |

The 20-sequence run wrote 80,000 enrollment changes (ten per event on average) inside the
event transactions and still completed every event inside its window with no drain and no
shedding; group commit absorbs the extra statements. The p95 roughly doubles over the
baseline because each grouped transaction now does more work before its single fsync.
The baseline on this branch matches the M5.1 events-only reference, so the change in the
event path without sequences (one indexed lookup and one exit statement per event) is
within run-to-run noise. `free -m` available memory: 6,866 MiB before, 6,847 MiB after;
swap was already full on the host before the run.
