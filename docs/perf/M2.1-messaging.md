# M2.1 messaging measurements

These are bounded local observations, not a provider capacity, final-delivery or
universal speed claim. Runs were serial on 2026-10-29, Linux x86-64
6.12.113+deb13-amd64, Bun 1.4.4, nodemailer 10.2.1, Mailpit 1.32.0, AMD Ryzen 5
1600 (six logical CPUs). SQLite data and temporary production copies were on
ext4 with WAL and `synchronous=FULL`; no tmpfs or parallel timing was used.
Mailpit and the relay were invocation-owned loopback services.

## Sending comparison

`TMPDIR=<ext4-dir> bun run reference:run -- bun test/messaging/measure.ts`
compared the M0.8-style new non-pooled transport per message with the actual
`createEmailer` production owner. Both used the same generated UTF-8 plain
messages, synthetic 2048-bit RSA DKIM key, four concurrent producers and a
four-connection cap. Each mode warmed up 100 sends and then ran three serial
1,000-send repetitions, each in ten 100-message windows. The owner used
`maxMessages:100`, `maxRequeues:0` and a 30-second idle setting. The control
waited for each observed socket close before its producer began another send,
so its measured latency includes that close. This bounds physical connections
rather than using the eight producers of the original M0.8 spike. The benchmark
script SHA-256 was
`a61282ade4eda0fccf5937faabcb1778d876b7779458a5fab5642b6e4bf0f896`.

Warmup send times were 415.990 ms control and 274.200 ms owner. All warmup
and measured messages were accepted, with no rejected recipients or errors,
and distinct supplied IDs matched Mailpit. One signature per window was
verified with the generated public key: ten per measured repetition and one per
warmup. Relay counts show reuse; every repetition ended with zero live relay
connections and no remaining owned messages. RSS is sampled after each window
in the benchmark process, not a true process peak. Send time excludes message
observation/removal. The owner was slower in repetition 2.

An earlier discarded run saw five relay sockets during pool turnover despite a
four-resource pool. The owner now waits for socket closure before opening a
replacement; the table is the complete rerun after that change. A prior
control run that allowed transient socket overlap was also discarded.

## Protected SMTP-test cost

`TMPDIR=<ext4-dir> bun run reference:run -- bun test/messaging/measure-smtp-test.ts`
measured the compiled protected route separately, using one sequential client,
five warmups and 30 samples. All 35 requests returned acceptance; Mailpit
contained 35 distinct Message-IDs and the test removed all 35 owned messages.
The 30 HTTP latencies were p50 6.790 ms, p95 12.604 ms, p99/max 22.354 ms.
This includes authentication, notification rendering and a temporary SMTP
connection; it is not a campaign-send measurement. Script SHA-256:
`095efa6ca8f6ccf468ca97dcc6e731050ff4a23c761aab467144ef253f59b30d`.

## Common compiled HTTP and settings workload

The same `test/settings/measure.ts` script was run first against the control,
then the final candidate, three serial repetitions each, with separate fresh
ext4 databases. It measures empty list GET and a synthetic individual subscriber
GET as well as health, settings and session operations. Each read uses five
warmups and 50 samples; full and per-key writes use five warmups and 20 samples;
restart uses one warmup and three samples; login uses two warmups and ten samples.
Each cell is the mean in milliseconds. The settings snapshot is unconfigured for
DKIM, so these figures do not measure RSA parsing or signing. Script SHA-256:
`5e6dafd10d506e07fdb96d7fcd82ffb7eefc96d722b8408642de46add615e71e`.
