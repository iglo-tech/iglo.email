## Sending comparison

`TMPDIR=<owned-ext4-dir> bun run reference:run -- bun test/messaging/measure.ts`
compares a M0.8-style new non-pooled transport per message with the actual
production createEmailer owner under Bun. Separately compiled caller/HTTP gates
verify compiled correctness; this sending timing run itself imports the owner
under Bun. Both modes send the same UTF-8 plain messages with a fresh synthetic
2048-bit RSA signing key, four concurrent producers and four physical connections.
Each mode warms up 100 sends, then runs three serial 1,000-send repetitions in
ten 100-message windows. Owner settings: maxMessages100, maxRequeues0, idle30s.
The control waits for observed socket closure before beginning its next send;
its latency includes that closure. This differs from the original M0.8 spike's
eight producers and avoids transient overlap beyond the physical connection cap.
Authentication is explicitly none in this timing scenario; no AUTH-handshake
latency claim follows from it. Advertised/required authentication correctness is
covered by the paired and local protocol gates, not inferred from these timings.

## Protected SMTP-test cost

`TMPDIR=<owned-ext4-dir> bun run reference:run -- bun test/messaging/measure-smtp-test.ts`
measured compiled production with one sequential client, five warmups and
30 samples. All35 requests returned full acceptance, with35 distinct Message-IDs
and35 owned messages removed. HTTP latency p50 7.622 ms,
p95 14.445 ms, p99/max 18.566 ms.
This includes authentication of the API request, rendering and a temporary SMTP
connection, with SMTP auth set to none; it is not a campaign or AUTH-handshake
measurement. D51 partial/failed cases are covered by correctness contracts.
