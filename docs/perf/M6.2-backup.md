# M6.2 backup at 1,000,000 subscribers

Serial, foreground runs on the shared t3-code VM (6 vCPU, Linux 6.12, Bun 1.4.4, SQLite 3.53.4,
dynamic memory), 2026-10-31, under `nice`, one run at a time. Data is on ext4 under
`upstream/measurements`, never tmpfs, and is removed after each session. Storage uses the D19
settings (WAL, `synchronous=FULL`). These are local observations on one host, not CI thresholds
or capacity claims.

Before each session `free -h` showed 8.3-11 GiB available and `df -h /` 43-44 GiB available
(63-64% used). Afterwards the disk was back at the same figure and `upstream/measurements` was
empty.

Raw records, one JSON object per run, are in [M6.2-results.jsonl](M6.2-results.jsonl).

## Harness

`bun run backup:measure [subscribers] [runs]` (`test/backup/measure.ts`) builds the compiled
executable and generates 1,000,000 subscribers with one list membership each, plus 200 upload
files of 1 MiB. Then, with the compiled server running, four HTTP clients add subscribers through
`POST /api/subscribers`, about 75-80 writes a second in all. Each run has three windows:

- **before:** 20 s with no backup;
- **during:** `iglo.email backup` as a separate process, with
  `test/maintenance/measure-probe.ts` beside it, which tries `BEGIN IMMEDIATE` every few
  milliseconds and reports the longest wait for the write lock;
- **after:** 20 s with no backup, then a timed `backup --verify`.

Phases are read from the destination while the backup runs, sampled every 20 ms: the snapshot ends
when the upload directory appears, the copy when the manifest does, and the rest is the integrity
check and the rename. The compared code is `17acff0`, which syncs the snapshot once at the end, and
`ef1ef90`, which adds the helper that syncs it every 200 ms. Later commits change tests, documents
and one `--verify` error message.

## Reading these

**Write lock.** `VACUUM INTO` on a read-only connection takes no write lock, and the median write
does not notice it. The stall in the first column is not a lock of ours. In the runs timed for it,
each stall began where the snapshot's flush did, 2.4-3.7 s into the run. The evidence fits a commit
whose own `fsync` of the WAL waits on ext4 for the flush of the dirty snapshot. The server's thread
is synchronous, so that commit held the write lock, and every request, for up to 1.9 s. It should
grow with the database.

**The fix.** To check the cause, four more runs on `17acff0` alternated no flush with an external
`sync -d` of the output about every 150 ms: the worst lock wait went from 819 and 1,435 ms to 224
and 159 ms. Those runs are not in the JSONL file, since they used a temporary change to the
harness. The helper is that loop in a process of the executable, every 200 ms. Short stalls of
320-450 ms remain, at about 0.8, 1.4 and 2.0 s into the run, which are the p99 above: this is a
smaller, bounded form of the same contention. Syncing while writing also made the snapshot
faster here and kept the WAL smaller.

**Reading the rest.** The integrity check costs about as much as the rest of the backup, and
writes go on unaffected through it (the snapshot is a separate file). It reads the snapshot, so
it needs disk bandwidth and no lock. A backup then needs about 16 s per 600 MiB of database here.

The 73 MiB is this workload's peak, not a bound for every data directory. SQLite's page cache is
bounded and file contents go through filesystem copies, but listing the upload directory, the
stored names and the media rows of the check are held in memory, so memory grows with the number
of media files. This workload had few.

**WAL.** The peak was reached during the snapshot and stayed as the file's size afterwards. SQLite
reuses that space. It does not shrink until the last connection closes, as with any WAL.

## Not measured

A database with a year of analytics rows (M4.6 had 822 MiB at this subscriber count), a campaign
sending during the backup, larger uploads, and disks other than this VM's.
