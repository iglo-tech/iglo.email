# M0.8 nodemailer: Bun SMTP spike

Control evidence recorded before the pool comparison. This is not production delivery or proof of at-most-once; M2.1 owns the SMTP implementation and M2.2 owns delivery classification and recovery.

## Baseline

On 2026-10-28: Bun 1.4.4, nodemailer 10.2.1, Mailpit 1.32.0, Linux x64 6.12.113+deb13-amd64, AMD Ryzen 5 1600 (6 logical CPUs), 16,775,880,704 bytes host memory. `bun run reference:run -- bun run runtime:spike:smtp --control-only` uses a new non-pooled transport for each message, eight producers, three sequential 1,000-message repetitions after 100-message warmup. To stay below Mailpit's default 500-message retention limit, each repetition is ten 100-message send windows; observation, ID matching and removal are timed separately. Messages are generated `.test` addresses and small Unicode plain text. RSS is sampled after each window, not a true peak.

| Control 2 | 1000 / 0 / 0 | 1000 | 738.895 | 1353.4 | 131.783 | 5.165 / 10.660 / 13.131 / 18.580 | 92540928 |

The loopback Mailpit returned `250 2.0.0 Ok: queued`; accepted recipients indicate SMTP acceptance, not final delivery. Two representative predetermined IDs matched nodemailer's completion information and Mailpit's raw headers; a third library-generated ID also matched. Text, HTML/alternative, Unicode, binary and CID bytes, custom header, To/Cc, envelope sender and three envelope recipients were observed. The per-run RSA-SHA256 DKIM signature/body verified locally with the generated public key; a corrupted body failed.

An initial assertion that Mailpit's stored raw message lacks Bcc failed: Mailpit 1.32.0 inserts a Bcc header for envelope recipients absent from visible headers. The corrected check asserts that observed reconstruction. A second attempt using stream transport also failed because that transport intentionally retains Bcc. The corrected public SMTP stream-plugin check reads the generated MIME before signing and verifies that Bcc is absent; Mailpit then reconstructs it from the envelope. Source: [Mailpit v1.32.0 SMTP save path](https://github.com/axllent/mailpit/blob/v1.32.0/internal/smtpd/main.go). This is a sink transformation; Mailpit's stored raw bytes alone do not prove what was transmitted before storage.

## Paired comparison

The full `bun run reference:run -- bun run runtime:spike:smtp` interleaved the same non-pooled control with a pooled transport (`maxConnections: 4`, `maxMessages: 50`, `maxRequeues: 0`, `idleTimeout: 30000 ms`), with eight producer promises and ten 100-message windows per repetition. Each small text body was 47–49 UTF-8 bytes, with the same generated recipient/message shapes in both modes. Send time is the sum of windows and excludes Mailpit observation/removal, so it is not continuous end-to-end throughput. Warmup: 195.562 ms control and 108.376 ms pooled, each 100 messages.

Nodemailer's public structured logger recorded 20, 21 and 21 pool resources created and closed, a maximum of four live resources in each repetition, and at most 50 assignments per resource. It recorded 1,000 assignments each time, showing reuse and turnover in these runs rather than merely assuming them from the pool option. Eight was the maximum outstanding producer count; the producer observed `isIdle()` false before 960 sends per pool repetition. This is backpressure information, not a measured internal queue length. Calls completed before explicit close; logger events reported closure of all created resources. The separately compiled pooled success and missing-recipient failure both closed and the child exited within its process guard. This does not exercise connection loss during DATA or prove all possible shutdown behavior.

The compiled SMTP child ran the same Mailpit MIME/ID/DKIM boundary in an invocation-owned ext4 directory with empty `PATH` and a Linux bubblewrap filesystem view without the repository or dependency sources; only the loopback reference and system runtime libraries were available. It received no caller credentials. `--smoke` reduces workload and is correctness evidence only. The compiled test requires Linux `bwrap` with user namespaces; Linux results do not certify macOS or other architectures. The reference runner uses a disposable Postgres as part of its lifecycle; this fixture has no database.

## Interpretation and M2.1/M2.2 follow-up

The selected [nodemailer 10.2.1 pool](https://github.com/nodemailer/nodemailer/blob/v10.2.1/src/smtp-pool/index.ts) defaults `maxRequeues` to **5**, so M2.1 must explicitly disable pool requeues for paths governed by D12; setting `pool: true` is not evidence of at-most-once. Compare the [pool resource](https://github.com/nodemailer/nodemailer/blob/v10.2.1/src/smtp-pool/pool-resource.ts), [SMTP transport](https://github.com/nodemailer/nodemailer/blob/v10.2.1/src/smtp-transport/index.ts), [MIME Bcc handling](https://github.com/nodemailer/nodemailer/blob/v10.2.1/src/mime-node/index.ts) and [stream transport](https://github.com/nodemailer/nodemailer/blob/v10.2.1/src/stream-transport/index.ts). The fixture controls connection/message caps and producer concurrency; it does not test real provider TLS, authentication, limits or delivery.

The verified fixture signature used `rsa-sha256` and `relaxed/relaxed` canonicalization, with a fresh 2048-bit synthetic RSA key and public-key verification entirely in-process. Its verifier supports this single fixture shape, not general DKIM, multiple signatures, DNS or all canonicalizations. The body corruption negative control failed verification. [Pinned signing implementation](https://github.com/nodemailer/nodemailer/blob/v10.2.1/src/dkim/sign.ts); [body canonicalization](https://github.com/nodemailer/nodemailer/blob/v10.2.1/src/dkim/relaxed-body.ts).

The `accepted`, `rejected`, envelope, SMTP response and completion Message-ID are useful observations but do not prove final delivery or resolve an ambiguous network failure. **M2.1** should verify partial recipient rejection, TLS/auth modes, connection loss before and after DATA acceptance, errors and shutdown with the production API and the pinned upstream comparison. **M2.2** must classify only proven non-acceptance as retryable and keep ambiguous marketing outcomes from automatic resend. No retry policy, campaign/outbox loop, multi-server routing, settings, SMTP test endpoint, production guarantees or provider behavior is implemented here. Raw mail, generated keys and recipient datasets are not retained.
