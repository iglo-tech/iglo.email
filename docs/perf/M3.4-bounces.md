# M3.4 bounces

Bounce ingest adds writes, so this records its cost at the action threshold. Serial, opt-in, not a CI threshold. `bun test/bounces/measure.ts <executable> <hooks> [n]`: a compiled build over real HTTP on ext4, 500 fresh subscribers per row, each getting one signed Mailgun `failed` event, one client at a time, with a loopback receiver subscribed to `bounce.recorded`, `subscriber.blocklisted` and `subscriber.deleted`.

Host: shared VM, load average 5 to 8, Bun 1.4.4. There is no `before` for ingest, since the endpoint is new. All rows come from one contiguous window, so compare within it.

- **Reaching the threshold** costs little without webhooks: blocklist and unsubscribe stay within noise of a plain row, and delete adds about 2 ms for the anonymizer, the unlinked-send lookup and the cascade.
- **Webhooks** add one row per webhook and event, and the serial client then shares the single writer with the delivery loop's claim and settle commits, as in [M2.6](M2.6-webhooks.md). Blocklist and delete queue two events, which is why they cost more at 20 webhooks. Delivery stays asynchronous; the request never waits for a receiver.
- **Bounds:** the count reads `idx_bounces_sub_id` and stored rows stop at the configured count, so that read cannot grow with a subscriber's bounces. Each accepted request deletes expired receipts through `idx_bounce_receipts_expires`, and `bounce_receipts` holds at most a day of events plus 30 minutes of tokens.
- **Delete paths** gain one indexed lookup of unlinked sends, the same `idx_sends_unlinked_to` scan the anonymizer already runs. It was not measured separately for bulk deletes.

A burst from one provider address past the unsubscribe budget (300 a minute by default) gets 429, which Mailgun retries. Mailgun's documentation does not say whether a retry is signed afresh. If it repeats the original signature, a retry more than 15 minutes after the event is refused as stale, and that bounce is lost rather than counted twice.
