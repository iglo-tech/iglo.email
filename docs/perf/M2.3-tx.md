# M2.3 transactional API measurements

Serial, in-process measurements on the shared Linux x86-64 development VM
(Bun 1.4.4, `nice`, no parallel test runs), 2026-10-29. Reproduce with
`bun run tx:measure` (`TX_MEASURE_N` sets the count, default 200). These are
local observations, not CI thresholds or production capacity claims.

Setup: production owners (SQLite journal, outbox loop, nodemailer transport
with up to four connections, M1.8 renderer) and a loopback SMTP sink, real
clock. Each tx message renders a small Liquid template.

**Before** is the M2.2 path that existed without a tx producer: the
journal's `enqueue` followed by outbox-loop delivery. **After** is
`POST /api/tx` through the router, auth, parsing, recipient resolution,
rendering and the same journal/outbox owners.

| Workload (N = 200) | Result |
|---|---|
| Before: journal enqueue per row | mean 0.21 ms, p50 0.22 ms, p95 0.40 ms |
| Before: enqueue + loop delivery | 365 messages/s |
| After: sync request (render, journal, SMTP, outcome) | mean 1.94 ms, p50 1.67 ms, p95 3.16 ms; 514 sent/s sequential |
| After: async request (render, journal) | mean 0.37 ms, p50 0.34 ms, p95 0.43 ms |
| After: async enqueue + loop delivery | 389 messages/s |
| After: one sync request with 100 recipients | 78.2 ms |
| After: idempotent repeat (no write, no SMTP), 50 runs | mean 0.28 ms, p50 0.26 ms, p95 0.32 ms |
| After: sync multipart request with a 4 MiB attachment | 388.7 ms |
| Process RSS | 53 MiB at start, 173 MiB at end (includes the 4 MiB attachment case) |

Observations:

- The sync path sends the just-committed rows directly through the outbox
  owner (`dispatch`) instead of waiting for the loop's next claim, so a
  synchronous caller pays for one SMTP round trip, not the loop interval.
- Async throughput is bounded by the M2.2 loop, which claims and sends one
  row at a time; M2.3 does not change the loop.
- Idempotent repeats are a single indexed range read on the existing unique
  `idempotency_key` index.
- Request memory is bounded: 5 MiB request body, 4 MiB attachments, 100
  recipients and 16 MiB of prepared message bytes per request. A
  multi-recipient request repeats attachment bytes per journal row by design
  (each row is an independently retryable message).
