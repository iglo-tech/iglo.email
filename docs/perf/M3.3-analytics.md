# M3.3 analytics

`bun run build && bun run analytics:measure` on a generated database: 1,000,000 subscribers
(2% on no list, 40% on two), about 1.4 million memberships, 100 campaigns, 1,000,000 campaign views
and 500,000 clicks over a year, half of them on one campaign, 10,000 bounces, and 100,000 sends
with 100,000 views and 50,000 clicks. 727 MiB on the VM's disk, seeded in 28 s. No `ANALYZE`,
as production has none. The FTS insert trigger was dropped in this throwaway file only: no
measured query reads the index. Five runs of each, median and max, serial, in the foreground.

## Why reads run in a child

bun:sqlite is synchronous and the server has one thread, so these times would also stall every
pixel, redirect and send. The measure writes a pixel-sized `campaign_views` row every
millisecond on the server's thread while one read runs:

| During the read               | Rows written | p50 gap ms | p99 gap ms | Max gap ms |
| ----------------------------- | -----------: | ---------: | ---------: | ---------: |
| List unique views, in process |            3 |        2.9 |      2,733 |      2,733 |
| The same read, in the child   |        1,153 |        2.4 |        6.6 |       10.4 |
| Summary refresh               |          961 |        2.1 |        6.4 |       11.0 |

So every read route spawns one child with a read-only connection, as raw subscriber queries do
(M1.7), under the limits in [D62](../design/09-decisions.md#d62-read-only-helper-processes-for-slow-reads).
The child writes the response body, so a large result is never parsed on the server's thread.
Bun Workers were not used, because M1.7 showed a running SQLite step cannot be stopped.

The compiled child adds about 150 ms to start:

| Through the compiled child      | Median ms | Max ms |
| ------------------------------- | --------: | -----: |
| Dashboard counts                |       613 |    730 |
| Dashboard charts                |       244 |    253 |
| Campaign views, a year by day   |       678 |    686 |
| List unique views, all 20 lists |     2,920 |  3,225 |
| Sends by template               |       565 |    671 |

## Dashboard campaigns card

`bun run build && bun run analytics:measure:card`: the same 1,000,000 subscribers, 1,000,000 views
and 500,000 clicks, but the six newest campaigns are finished and hold every view, click and
bounce, about 166,667 views and 83,333 clicks each. This replaces an earlier 2.9 ms figure, which
measured empty drafts. Five loads each, in two seeded runs; ranges show both.

The card's rows count their events synchronously, so in process it held the thread:

| Card                       |  Median ms | Max ms |
| -------------------------- | ---------: | -----: |
| In process                 |   52 to 56 |     82 |
| Through the compiled child | 207 to 226 |    232 |

| During five card loads           | Rows written | p50 gap ms | p99 gap ms | Max gap ms |
| -------------------------------- | -----------: | ---------: | ---------: | ---------: |
| No read (second pass; see below) |          225 |        2.5 |        3.6 |        4.9 |
| In process                       |           13 |        2.5 |       79.2 |       79.2 |
| In the child                     |          529 |        2.3 |        4.4 |        6.2 |

That is a stall at a size the design expects, so the card moved behind the reader: it pays about
170 ms of start-up on a page load and pixels no longer wait. Its results are unchanged.

The table is the second seeded run, which ran the control first. In each seeded run a single
early insert took much longer: 1,024 ms in the control with no read, and 909 and 645 ms in the
first run, which had no control. None appeared in later passes, so the table leaves them out. The
likely cause is the first commit or checkpoint on the freshly seeded file, which was not proven.

## Reader limits on a large report

`bun run build && bun run analytics:measure:report`: every ID has one view in every hour of a
year, the densest result those IDs can return, 438,000 views in all. It is well below a million
rows because the result's size is the variable. Through the compiled child:

| Report                                 |    ms |   Served | Peak child RSS MiB |
| -------------------------------------- | ----: | -------: | -----------------: |
| Campaign views, 20 IDs, a year by hour |   783 | 10.6 MiB |                 85 |
| List views, 20 IDs, a year by hour     |   983 | 12.6 MiB |                 88 |
| Campaign views, 50 IDs, a year by hour | 1,565 | 26.7 MiB |                100 |
| List views, 50 IDs, a year by hour     | 2,134 | 31.7 MiB |                110 |

Rows stream, so memory grows slowly with the result: 50 IDs of 8,760 hours fit under both the
256 MiB and the 32 MiB limit, and real campaigns are far sparser than one event in every hour.
The largest list report is close to the output limit by design: anything larger is refused, and
narrowing the range or interval answers it.

Send analytics now filter by `sent_at`, which has no usable index, instead of `created_at`. One
day of 100,000 sends goes from 0.2 ms to 20.1 ms for that step. It runs in the child, so no index
was added; the 421 ms and 338 ms rows above were not re-measured and include the old step.

## Summary refresh

| Step                                                 | Median ms | Max ms |
| ---------------------------------------------------- | --------: | -----: |
| Whole refresh, compiled child included               |     2,091 |  2,237 |
| Write transaction: parse, three upserts, FULL commit |       2.0 |    3.2 |

The read holds no write lock (WAL). It does hold a read snapshot, which can delay a checkpoint
for at most the 30 s limit.

## Decisions from these numbers

- **Dashboard and analytics stay live by default.** Off the server's thread, half a second for
  a dashboard card is acceptable, and caching by default would change the numbers clients see.
- **One summary table, for `app.cache_slow_queries` only.** That setting is what a client can
  see of upstream's materialized views, and it also spares `GET /api/lists` its 1.3 s.
- **No hour or day rollup tables.** `from` and `to` are arbitrary and unique counts cannot be
  added across periods, so a rollup would not serve these routes.
- **No new indexes.** The reads no longer touch the hot paths, and each index would add a cost
  to every pixel and redirect to save a fraction of a second on an admin report. The same holds
  for `sends.sent_at`.

## Not changed

With caching off, `GET /api/lists` still counts memberships on the server's thread: 1.3 s at
this size, as before M3.3. It is the lists module's synchronous `counts.all()`, outside this
task. Enabling `app.cache_slow_queries` removes it.
