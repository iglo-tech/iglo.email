# M1.9 CSV import

`bun run import:measure` on the compiled build, 2026-10-30, on this VM with other agents running. One serial run of 100,000 generated rows with a name and JSON attributes, a 3.9 MiB file, on an empty database. This is new code, so there is no before; the idle row is the baseline for the same probes. The batch size came from this measurement: at 500 rows the median write-lock hold was 40 ms and the worst gap 94 ms.

A pixel-sized write is `GET /campaign/:uuid/:sub/px.png`, one `campaign_views` row. A public request is `GET /subscription/form`. Each client loops with a 2 ms sleep, so its longest round trip is the worst gap it saw. Commits use FULL synchronous, as in production.

| New subscribers, one list                   | 100,000 | 23.0    | 4,344  | 4.9 / 36.7 / 52.3          | 5.9 / 29.0 / 50.3           |

The largest write-lock hold cannot be seen from outside, so the same batches ran in the measuring process on the real store, each timed around its transaction, 100 rows a batch. The hold includes the commit.

Peak memory, the server's VmHWM: 137 MiB after start and setup, still 137 MiB after all three imports, so an import did not raise the peak. A 99 MB file, close to the upload limit and about 2 million rows, took the peak from 134 to 176 MiB. That was the upload and first reads of a run stopped at once. A larger file does not cost more: the upload streams to disk, the reader holds one 64 KiB chunk and at most one chunk of parsed rows, and the log is capped at 1 MiB.

## Reading the numbers

- The worst gap is about 50 ms against 14 ms idle, roughly the longest batch plus a commit of the probe's own. A new row costs about 100 µs: the `subscribers` insert with its FTS trigger, five indexes on `subscriber_lists`, and a share of the fsync.
- After a batch the importer sleeps as long as the batch took, at least 1 ms, so it never takes more than about half of the thread. That is why a run takes 23 s where the sum of holds is about 11 s. Sends, pixels and requests run in the other half. No campaign ran during these runs, so the effect on send rate is inferred from this share, not measured.
- A file is read twice. The first pass over 3.9 MiB is a small part of a run and yields at each 64 KiB chunk.
- These are single runs on a shared VM. Read them as the bounds holding and as a reason for 100 rows, not as a throughput target.
