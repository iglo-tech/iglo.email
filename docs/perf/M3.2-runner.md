# M3.2 campaign runner measurements

Serial, foreground runs on the shared Linux x86-64 development VM (Bun 1.4.4, `nice`,
no parallel test runs), 2026-10-30, against the compiled `dist/iglo.email`. Reproduce
with `bun run runner:measure` (all) or `bun run build` then
`bun test/campaigns/runner/measure.ts limits|crash|mixed`; `bun run runner:crash` runs
the crash points only. `M32_CONCURRENCY` (default 5) and `M32_SCENARIOS`
(`events,campaign,mixed`) select the D22 runs. Raw results are in
[M3.2-results.jsonl](M3.2-results.jsonl). These are local observations, not CI
thresholds or production capacity claims.

## Method

- Each scenario starts a fresh server with a fresh data directory on ext4
  (`upstream/measurements`, never tmpfs), WAL and FULL synchronous commits (D19/D22),
  and removes it afterwards. Setup goes through the real API with a credential from the
  real login: settings (SMTP pointed at the sink, runner limits), lists, subscribers,
  campaign, then `PUT /api/campaigns/:id/status`.
- Mail goes to an in-process loopback SMTP sink. It records the MAIL FROM time, the
  recipient and the time of its accepting reply, and the peak number of open
  transactions (MAIL to reply). It counts only messages it accepted. For crash points
  it can hold every final dot after a given number of acceptances without replying.
- The rate and window checks use MAIL FROM times. A worker's next message can't start
  before its previous one has finished plus the one-second rate sleep, so MAIL times
  bound the runner's pushes from above.
- `free -m` available memory stayed between 7.6 and 8.4 GiB during the runs. No run used
  `/tmp` for data.

## Code measured

The tables below are the final runner code (`c73ade7`; later commits change only
documentation). Rows in the results file without a `head`, from 01:27 to 01:46 UTC, are an
earlier run of the same harness. That code lacked the per-message consent recheck added
before the push. Its crash and 10k results were the same in every invariant, and they are
summarised under each section.

## 10,000 subscribers (limits)

Settings: `app.concurrency` 5, `app.message_rate` 10 (at most 50/s), `app.batch_size`
1000, sliding window on, `1m`, 2,500 messages. Audience: 9,000 subscribers on a single
opt-in list and 1,000 on both lists (single plus a double opt-in list, confirmed), plus 20
unconfirmed members of the double opt-in list, 20 unsubscribed and 20 blocklisted, who must
receive nothing.

| Check | Result |
|---|---|
| Delivered / unique / eligible only | 10,000 / 10,000 / yes |
| Campaign `sent` / `to_send` / status | 10,000 / 10,000 / `finished` |
| Most messages in any 1 s (configured 50) | 50 |
| Messages per sliding window (limit 2,500) | 2,500, 2,500, 2,500, 2,500 |
| Pause between windows | 2.1 s, 5.0 s, 3.8 s |
| Most messages in any 60 s interval | 2,630 (see below) |
| Peak open SMTP transactions (concurrency 5) | 5 |
| Elapsed / errors logged | 237.3 s / 0 |

Seeding 10,060 subscribers through the API took 59 s, outside the timed section.

The sliding window is upstream's: a window starts at the first message after the previous
one ended, so an arbitrary 60 s interval that straddles two windows can hold more than the
window rate (here 2,630). Each runner window held exactly 2,500.

**First failure and rerun.** The first 10k run (earlier code) checked fixed 60 s spans
anchored at the first MAIL time and reported 2,505 / 2,500 / 2,500 / 2,495. Every other
check passed. The first MAIL comes some milliseconds after the runner's first push because
the SMTP connection has to be set up first, so the first five messages of window 2 (pushed
exactly 60 s after the first push) fell into that span. The harness now groups windows by
the pause between them, as the runner counts them. The rerun on the same code passed with
2,500 per window, as does the final run above.

## Crash points

600 subscribers in one list, created sequentially so IDs ascend, `app.batch_size` 100,
`app.concurrency` 2. The compiled process gets SIGKILL, then restarts on the same data
directory. The restarted runner waits for the 30 s lease to expire, then resumes.

| Kill point | Delivered at kill | Cursor at kill | Delivered total | Duplicates | Missing | Logged range | Resume |
|---|---|---|---|---|---|---|---|
| After batch 3's cursor commit, before any of it was accepted (sink holds after 200) | 200 | 300 | 500 | 0 | 100 (IDs 201–300) | 100 claims, 201–300 | 31.4 s |
| Mid-batch (holds after 250) | 250 | 300 | 550 | 0 | 50 (within 250–300) | 100 claims, 201–300 | 31.5 s |
| Last message of a batch, before the next batch's cursor commit (holds after 299) | 299 | 300 | 599 | 0 | 1 (300) | 100 claims, 201–300 | 31.5 s |
| Unheld: killed as soon as 420 had arrived, whatever the process was doing | 462 | 500 | 562 | 0 | 38 (463–500) | 100 claims, 401–500 | 30.9 s |

In every case the skipped subscribers lie inside one batch and inside the logged range.
With two workers, messages finish out of order: in the mid-batch kill, 251 was accepted
while 250 was held. The log names every subscriber of the abandoned batch, because the
runner can't know which of them the SMTP server accepted. The campaign finished each time.
`sent` was 500 in every run: messages of the abandoned batch that were accepted before the
kill are not counted, because the batch's progress transaction never ran. Their delivery
rows are `unknown`. The earlier run gave the same results, apart from where the unheld kill
landed (425 delivered at kill, 75 missing).

## D22 mixed load

As in [M5.1](M5.1-events.md): open-loop `POST /api/subscriber-events` at fixed 10 ms
deadlines (100/s, 6,000 offered per 60 s window), each naming one of 2,000 subscribers by
`external_id` and `email`, changing `attribs`, ~50 bytes of `data` and a unique
`idempotency_key`; client in-flight cap 500 (requests beyond it are shed). Acceptance
latency is scheduled deadline to HTTP response. The campaign has 3,900 preconfirmed
subscribers, so it is still sending at the end of the window, and the window starts once the
first campaign message has arrived. Before = each load alone; after = both together. Each
row is a fresh server. Settings are `app.concurrency` × `app.message_rate`.

| 60 s window | Events in window / offered | Event acceptance p50 / p95 / p99 / max (ms) | Shed | In flight at end | Campaign messages in window | Campaign rate | Most in any 1 s | `sent` / `to_send` at end |
|---|---|---|---|---|---|---|---|---|
| Before: events only | 6,000 / 6,000 | 3.9 / 9.1 / 12.5 / 20 | 0 | 1 | n/a | n/a | n/a | n/a |
| Before: campaign only, 5 × 10 | n/a | n/a | n/a | n/a | 2,637 | 44.0/s | 50 | 2,000 / 3,900 |
| After: mixed, 5 × 10 | 6,000 / 6,000 | 7.8 / 22.0 / 31.4 / 64 | 0 | 1 | 2,203 | 36.7/s | 50 | 2,000 / 3,900 |
| Before: campaign only, 6 × 10 | n/a | n/a | n/a | n/a | 3,195 | 53.3/s | 60 | 3,000 / 3,900 |
| After: mixed, 6 × 10 | 6,000 / 6,000 | 8.7 / 24.8 / 36.6 / 71 | 0 | 1 | 2,679 | 44.7/s | 60 | 2,000 / 3,900 |
| After: mixed, 7 × 10 | 6,000 / 6,000 | 8.9 / 25.2 / 36.8 / 57 | 0 | 1 | 3,012 | **50.2/s** | 70 | 3,000 / 3,900 |

- **Target met with 7 × 10:** the campaign sent 50.2 messages/s while all 6,000 events
  (100/s) completed inside the window, with none shed and at most 6 in flight.
- **Configured rate is not throughput.** listmonk's `app.message_rate` is per worker, and a
  worker sleeps a full second after that many messages, on top of SMTP time. So 5 × 10
  delivers about 44/s alone. Under event load each message takes longer, because FULL-sync
  event commits block the single JavaScript thread for a few milliseconds each. The fixed
  one-second sleep then leaves more of each second idle: 5 × 10 fell to 36.7/s and 6 × 10
  to 44.7/s. The earlier code measured 41.8/s and 49.4/s for the same two runs. The final
  code adds three primary-key/JSON reads per message (the consent recheck), but the spread
  between runs on this shared host is of the same order. Reaching a target rate under
  load means configuring headroom above it, as with upstream.
- Event acceptance rose from p99 12.5 ms alone to 31–37 ms with sending, and p50 from 3.9 to
  8–9 ms. Nothing was shed, and the client backlog stayed at 1 request at the window end.
  The earlier code's 6 × 10 mixed run had one event of 6,000 complete just after the window
  (the D22 window-boundary effect). The final runs had none.
- The campaign backlog at the window end is `to_send` − `sent` from the API. `sent` is
  written once per 1,000-message batch, so it lags the sink count by up to a batch.
- For comparison, M5.1's shipped mixed run used outbox sends (one journal row and commit
  per message) at 50/s: 5,997/6,000 events in the window at p50 40.9 ms. Campaign sending
  commits per batch rather than per message. The runs are on the same host on different
  days, so this is indicative only.

## Storage

Per batch the runner commits two short transactions on top of message I/O. The first
advances the cursor and inserts one `campaign_deliveries` row per subscriber. The second
adds `sent` and updates each row's outcome. Each message rereads the campaign status twice
and rechecks the subscriber's memberships (primary-key reads). A lease renewal is written
every 10 s. Campaign deliveries add one
row per recipient: about 10,000 rows for the 10k campaign.
