# M3.2 campaign runner measurements

Serial, foreground runs on the shared Linux x86-64 development VM (Bun 1.4.4, `nice`,
no parallel test runs), 2026-10-30, against the compiled `dist/iglo.email`. Reproduce
with `bun run runner:measure` (all) or `bun run build` then
`bun test/campaigns/runner/measure.ts limits|crash|mixed`; `bun run runner:crash` runs
the crash points only. `M32_CONCURRENCY` (default 5) and `M32_SCENARIOS`
(`events,campaign,mixed`) select the D22 runs. Raw results are in
[M3.2-results.jsonl](M3.2-results.jsonl). These are local observations, not CI
thresholds or production capacity claims.

## Method

- Each scenario starts a fresh server with a fresh data directory on ext4
  (`upstream/measurements`, never tmpfs), WAL and FULL synchronous commits (D19/D22),
  and removes it afterwards. Setup goes through the real API with a credential from the
  real login: settings (SMTP pointed at the sink, runner limits), lists, subscribers,
  campaign, then `PUT /api/campaigns/:id/status`.
- Mail goes to an in-process loopback SMTP sink. It records the MAIL FROM time, the
  recipient and the time of its accepting reply, and the peak number of open
  transactions (MAIL to reply). It counts only messages it accepted. For crash points
  it can hold every final dot after a given number of acceptances without replying.
- The rate and window checks use MAIL FROM times. A worker's next message can't start
  before its previous one has finished plus the one-second rate sleep, so MAIL times
  bound the runner's pushes from above.
- `free -m` available memory stayed between 7.6 and 8.4 GiB during the runs. No run used
  `/tmp` for data.

## 10,000 subscribers (limits)

Settings: `app.concurrency` 5, `app.message_rate` 10 (at most 50/s), `app.batch_size`
1000, sliding window on, `1m`, 2,500 messages. Audience: 9,000 subscribers on a single
opt-in list and 1,000 on both lists (single plus a double opt-in list, confirmed), plus 20
unconfirmed members of the double opt-in list, 20 unsubscribed and 20 blocklisted, who must
receive nothing.

| Check | Result |
|---|---|
| Delivered / unique / eligible only | 10,000 / 10,000 / yes |
| Campaign `sent` / `to_send` / status | 10,000 / 10,000 / `finished` |
| Most messages in any 1 s (configured 50) | 50 |
| Messages per sliding window (limit 2,500) | 2,500, 2,500, 2,500, 2,500 |
| Pause between windows | 3.1 s, 3.0 s, 5.4 s |
| Most messages in any 60 s interval | 2,620 (see below) |
| Peak open SMTP transactions (concurrency 5) | 5 |
| Elapsed / errors logged | 238.6 s / 0 |

Seeding 10,060 subscribers through the API took 78 s, outside the timed section.

The sliding window is upstream's: a window starts at the first message after the previous
one ended, so an arbitrary 60 s interval that straddles two windows can hold more than the
window rate (here 2,620). Each runner window held exactly 2,500.

**First failure and rerun.** The first 10k run checked fixed 60 s spans anchored at the
first MAIL time and reported 2,505 / 2,500 / 2,500 / 2,495. Every other check passed. The
first MAIL comes some milliseconds after the runner's first push because the SMTP
connection has to be set up first, so the first five messages of window 2 (pushed exactly
60 s after the first push) fell into that span. The harness now groups windows by the
pause between them, as the runner counts them. The rerun above is the same code and the
same settings.

## Crash points

600 subscribers in one list, created sequentially so IDs ascend, `app.batch_size` 100,
`app.concurrency` 2. The compiled process gets SIGKILL, then restarts on the same data
directory. The restarted runner waits for the 30 s lease to expire, then resumes.

| Kill point | Delivered at kill | Cursor at kill | Delivered total | Duplicates | Missing (IDs) | Logged range | Resume |
|---|---|---|---|---|---|---|---|
| After batch 3's cursor commit, before any of it was accepted (sink holds after 200) | 200 | 300 | 500 | 0 | 100 (201–300) | 100 claims, 201–300 | 31.5 s |
| Mid-batch (holds after 250) | 250 | 300 | 550 | 0 | 50 (251–300) | 100 claims, 201–300 | 31.5 s |
| Last message of a batch, before the next batch's cursor commit (holds after 299) | 299 | 300 | 599 | 0 | 1 (300) | 100 claims, 201–300 | 31.4 s |
| Unheld: killed as soon as 420 had arrived, whatever the process was doing | 425 | 500 | 525 | 0 | 75 (426–500) | 100 claims, 401–500 | 30.9 s |

In every case the skipped subscribers lie inside one batch and inside the logged range.
The log names every subscriber of the abandoned batch, because the runner can't know which
of them the SMTP server accepted. The campaign finished each time. `sent` was 500 in every
run: messages of the abandoned batch that were accepted before the kill are not counted,
because the batch's progress transaction never ran. Their delivery rows are `unknown`.

## D22 mixed load

As in [M5.1](M5.1-events.md): open-loop `POST /api/subscriber-events` at fixed 10 ms
deadlines (100/s, 6,000 offered per 60 s window), each naming one of 2,000 subscribers by
`external_id` and `email`, changing `attribs`, ~50 bytes of `data` and a unique
`idempotency_key`; client in-flight cap 500 (requests beyond it are shed). Acceptance
latency is scheduled deadline to HTTP response. The campaign has 3,900 preconfirmed
subscribers, so it is still sending at the end of the window, and the window starts once the
first campaign message has arrived. Before = each load alone; after = both together. Each
row is a fresh server.

| 60 s window | Events in window / offered | Event acceptance p50 / p95 / p99 / max (ms) | Shed | In flight at end | Campaign messages in window | Campaign rate | Most in any 1 s | `sent` / `to_send` at end |
|---|---|---|---|---|---|---|---|---|
| Before: events only | 6,000 / 6,000 | 3.8 / 9.9 / 14.1 / 25 | 0 | 1 | n/a | n/a | n/a | n/a |
| Before: campaign only, 5 × 10 | n/a | n/a | n/a | n/a | 2,626 | 43.8/s | 50 | 2,000 / 3,900 |
| After: mixed, 5 × 10 | 6,000 / 6,000 | 5.2 / 12.8 / 20.5 / 35 | 0 | 1 | 2,505 | 41.8/s | 50 | 2,000 / 3,900 |
| Before: campaign only, 6 × 10 | n/a | n/a | n/a | n/a | 3,240 | 54.0/s | 60 | 3,000 / 3,900 |
| After: mixed, 6 × 10 | 5,999 / 6,000 | 5.7 / 15.3 / 24.6 / 41 | 0 | 3 | 2,961 | 49.4/s | 60 | 2,000 / 3,900 |

- **Configured rate is not throughput.** listmonk's `app.message_rate` is per worker, and a
  worker sleeps a full second after that many messages, on top of SMTP time. So 5 workers ×
  10 deliver about 44/s, not 50. With 6 × 10 the campaign sends 54/s alone and 49.4/s while
  100 events/s arrive.
- Events were not slowed materially by sending: p99 rose from 14 to 21–25 ms. Nothing was
  shed and the client backlog stayed at 1–5 requests. In the 6 × 10 mixed run one event of
  6,000 completed just after the window: the same window-boundary effect D22 recorded,
  with about 3 requests in flight at the end. Every event completed.
- The campaign backlog at the window end is `to_send` − `sent` from the API. `sent` is
  written once per 1,000-message batch, so it lags the sink count by up to a batch.
- For comparison, M5.1's shipped mixed run used outbox sends (one journal row and commit
  per message) at 50/s: 5,997/6,000 events in the window at p50 40.9 ms. Campaign sending
  commits per batch rather than per message, and event acceptance stays near its unloaded
  latency. The runs are on the same host on different days, so this is indicative only.

## Storage

Per batch the runner commits two short transactions on top of message I/O. The first
advances the cursor and inserts one `campaign_deliveries` row per subscriber. The second
adds `sent` and updates each row's outcome. Each message rereads the campaign status (a
primary-key read), and a lease renewal is written every 10 s. Campaign deliveries add one
row per recipient: about 10,000 rows for the 10k campaign.
