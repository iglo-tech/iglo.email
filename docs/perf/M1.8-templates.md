## Shared renderer comparison

`bun test/templates/measure-render.ts` compares the exact M2.2 synthetic compile-once control with the owner using the same supported HTML body/layout, plain body and subject, three interests, interpolation, `for`, `upcase` and `raw`. Each had 200 warmups and three serial 10,000-recipient repetitions. The owner serializes and parses bounded context per render, adds application budget checks and has no retained instance cache; a caller may hold an immutable snapshot. Render includes data construction and total includes assertions and digest bookkeeping. RSS is sampled every 100 recipients. Translation, tracking and Markdown are excluded from this shared comparison because the control does not implement equivalent production behavior.

The owner was slower in all three render repetitions on this non-exclusive host. The initial draft's control table had fewer numeric fields than column labels; its exact parse and RSS fields were not recoverable from that table. The following are new measurements, not guessed reconstructions. Each repetition produced 2,952,450 bytes and digest `dda60c611426db35a65fb54e8f7921fcb843e5516130a6060c2c96465fba2e74`.

## SMTP observation

`reference:run -- bun test/templates/measure-smtp.ts` sent six actual protected diagnostics to invocation-owned Mailpit, two per variant. Control and candidate had distinct message IDs and matching subjects. Whitespace-normalized bodies matched for empty and populated `https://example.invalid/logo.png` settings. With `javascript:alert(1)` as the synthetic logo setting, the candidate omitted it and the bodies differed. This confirms SMTP intake and the observed body only, not downstream provider delivery.
