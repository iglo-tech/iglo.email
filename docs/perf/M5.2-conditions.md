# M5.2 sequence conditions: measurements

Measured on 2026-10-29 on the t3-code VM (Bun 1.4.4, dynamic memory, shared with other work),
serially, with `nice -n 10`. Raw output: [M5.2-results.jsonl](M5.2-results.jsonl).

```sh
TMPDIR=/var/tmp bun test/conditions/measure.ts 100000 1000000
```

The script builds a migrated synthetic database in `TMPDIR` (on disk, not the `/tmp` tmpfs),
with 100,000 subscribers, 50,000 list memberships and 1,000,000 events (about ten per
subscriber, five names, 60 days). It is 190 MiB after a checkpoint and is deleted at the end.
Seeding takes about 18 s. Before the first condition the process RSS is about 65 MiB.

Each condition is validated and compiled 10,000 times, then evaluated for 2,000 subscribers
(50 for `sql` conditions, which start a child each), cycling across the whole ID range.

| Condition | validate µs | compile µs | eval p50 ms | eval p95 ms | eval max ms | child |
|---|---:|---:|---:|---:|---:|---|
| `attr` eq | 2.3 | 1.4 | 0.008 | 0.018 | 1.1 | no |
| `attr` in (3 values) | 1.7 | 3.3 | 0.010 | 0.021 | 0.9 | no |
| `attr: "status"` eq | 0.7 | 0.7 | 0.006 | 0.010 | 0.1 | no |
| `list` with status | 1.0 | 0.8 | 0.007 | 0.015 | 0.2 | no |
| `not event since trigger` | 1.4 | 1.3 | 0.039 | 0.056 | 0.8 | no |
| `event since P30D where data.source count gte 2` | 2.0 | 2.4 | 0.060 | 0.093 | 0.8 | no |
| onboarding: `all` of 5 incl. `any`, 2 events, list, 2 attrs | 4.4 | 8.3 | 0.095 | 0.126 | 1.2 | no |
| `sql` fragment | 1.6 | 0.3 | 26.8 | 34.0 | 36.3 | yes |
| `sql` + event | 4.7 | 2.2 | 26.3 | 30.6 | 31.2 | yes |

RSS stayed between 63 and 75 MiB during evaluation; no condition raised it noticeably.

Conditions without `sql` run as one statement on the read-only connection: 6–95 µs per
evaluation. A `sql` predicate costs one child process per evaluation (about 26 ms here, almost
all of it starting the child), bounded by M1.7's 10 s time limit, 256 MiB memory limit and two
concurrent children. That is fine for an escape hatch evaluated once per due step. A scheduler
that evaluated many `sql` conditions per tick would be limited by the two child slots; batch
evaluation is out of scope for M5.2.

## Query plans

`EXPLAIN QUERY PLAN` of the compiled statements (from the JSON lines):

- Every statement starts with `SEARCH subscribers USING INTEGER PRIMARY KEY (rowid=?)`.
  Attribute and status comparisons are expressions on that one row.
- `list`: `SEARCH subscriber_lists USING INDEX sqlite_autoindex_subscriber_lists_1
  (subscriber_id=? AND list_id=?)`.
- `event` without `where`: `SEARCH events USING COVERING INDEX idx_events_subscriber_name_time
  (subscriber_id=? AND name=? AND occurred_at>?)`; without `since` it is
  `(subscriber_id=? AND name=?)`.
- `event` with `where`: the same index (`USING INDEX`, not covering), with a table lookup per
  candidate row for `data`.

The `(subscriber_id, name, occurred_at)` index already exists (migration 0001), so no migration
was added. Counting stops one past the largest `count` comparand (`LIMIT`), so an event predicate
reads at most that many matching rows. With `where`, rows that fail the data comparison are still
visited; the cost is bounded by the subscriber's events of that name in the `since` window.

## Fuzzer

`test/conditions/fuzz.test.ts` compares 10,000 generated conditions per run (depth up to 4,
every predicate, combinator, `since` form, comparator and type mix) against the in-memory
reference evaluator over 80 generated subscribers. Default seed: `0x5eed0502` (1592591618).
Rerun with another seed or size:

```sh
FUZZ_SEED=12345 FUZZ_CASES=20000 bun test test/conditions/fuzz.test.ts
```

Seeds 1, 2 and 777 with 20,000 cases each also agreed. The 10,000 default cases take about 1 s.
