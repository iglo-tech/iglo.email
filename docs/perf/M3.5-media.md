# M3.5 media: runner before and after

`bun run runner:crash` on the compiled build, 2026-10-30, on this VM: before at eca3c9b, after with the attachment seam. The run kills the runner mid-batch and resumes it. These campaigns have no media, so this measures the unchanged send path. Each cell is before / after.

No run sent a subscriber twice. Run 4's kill lands at a timing-dependent point in a batch, so its delivered count varies between runs on either build; those subscribers are logged as unknown and not resent.

`runner:measure limits` did not finish within 280 seconds on the baseline, so no throughput comparison was taken.

What the change adds to a send:

- One indexed `campaign_media` query per pipe, before its first batch, outside the claim transaction.
- With media, one read of up to 10 files and 10 MiB per pipe. Each message in flight adds a copy in the emailer, so at most `app.concurrency` × 10 MiB before base64.
- Nothing per message for a campaign without media.

A failed read returns the batch's claims before anything is pushed, so at-most-once is unchanged: `test/media/media.test.ts` covers the pause and the resume.
