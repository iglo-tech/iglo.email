# M3.5 media: runner before and after

`bun run runner:crash` on the compiled build, 2026-10-30, on this VM: before at eca3c9b, after with the attachment cache and inline images. The run kills the runner mid-batch and resumes it. These campaigns have no media, so this measures the unchanged send path. Each cell is before / after.

| Run | Cursor at kill  | Delivered | Unique    | Duplicates | Missing | Resume (s)  | Final               |
| --- | --------------- | --------- | --------- | ---------- | ------- | ----------- | ------------------- |
| 1   | 300 / 300       | 500 / 500 | 500 / 500 | 0 / 0      | 100/100 | 31.6 / 31.8 | finished, 500 sent  |
| 2   | 300 / 300       | 550 / 550 | 550 / 550 | 0 / 0      | 50 / 50 | 31.6 / 31.5 | finished, 500 sent  |
| 3   | 300 / 300       | 599 / 599 | 599 / 599 | 0 / 0      | 1 / 1   | 31.6 / 31.5 | finished, 500 sent  |
| 4   | 500 / 500       | 540 / 539 | 540 / 539 | 0 / 0      | 60 / 61 | 31.0 / 30.9 | finished, 500 sent  |

No run sent a subscriber twice. Run 4's kill lands at a timing-dependent point in a batch, so its delivered count varies between runs on either build; those subscribers are logged as unknown and not resent.

`runner:measure limits` did not finish within 280 seconds on the baseline, so no throughput comparison was taken.

What the change adds to a send:

- One indexed `campaign_media` query per pipe, plus one indexed filename lookup per distinct `data-embed` image, at most 10.
- For each batch, one row read and one `lstat` per file of the campaign. Bytes come from the cache when the file's size and modification time still match.
- Nothing per message for a campaign without media.
- For a transactional send, one indexed filename lookup per distinct `data-embed` image of its template and one row read and `lstat` per image found. A template with no `data-embed` costs one substring check.
- For a public campaign page or archive entry, one indexed filename lookup per distinct `data-embed` image, at most 100.

## Attachment memory

`bun test/media/measure.ts`, 2026-10-30, on this VM: before at 3331d3c, after with the instance-wide cache. It uses the real emailer and MIME composition against a loopback sink, and batch size equal to concurrency. The figures are the peak `arrayBuffers` above the level before sending, after a full GC, sampled every 100 ms of injected clock, and peak RSS. Each cell is before / after.

| Scenario                                    | Messages | Peak buffers (MiB) | Peak RSS (MiB) | Seconds     |
| ------------------------------------------- | -------- | ------------------ | -------------- | ----------- |
| 6 campaigns, 1 shared 8 MiB file            | 24       | 64 / 8             | 155 / 111      | 3.7 / 3.8   |
| 6 campaigns, own 8 MiB files                | 24       | 64 / 48            | 159 / 145      | 3.6 / 3.4   |
| 12 campaigns, own 8 MiB files               | 48       | 112 / 72           | 210 / 184      | 6.9 / 8.1   |
| 6 campaigns, 1 shared 8 MiB file, 4 workers | 96       | 88 / 8             | 199 / 122      | 11.5 / 11.5 |

The third scenario is over the budget: it evicts and reads the files again for each batch, about 17% slower in this run, and peaks at the 64 MiB cache plus the 8 MiB of the batch in flight. These are single runs with a small sample, so read them as the bound holding, not as a throughput result. With a measurement that stays under the budget for ordinary campaigns, 64 MiB stands.

A test send's slot is held until its messages settle. `bun test/media/measure.ts`, 2026-10-30, 16 serial test sends of distinct 8 MiB files, with SMTP stalled after its greeting. Before is the same head with the slot released when the handler returns:

| Scenario                  | Answers          | Peak buffers (MiB) | Peak RSS (MiB) |
| ------------------------- | ---------------- | ------------------ | -------------- |
| Before: slot ends with handler | 16 × 200         | 128                | 232            |
| After: slot ends at settle     | 4 × 200, 12 × 429 | 32                 | 133            |

The refused requests read nothing. Slots come back when the messages settle, at the latest at the emailer's 60-second deadline.

### Every admitted producer

Attachment bytes held by one instance, before base64:

| Producer | Bound | Why |
| --- | --- | --- |
| Attachment cache | 64 MiB | One cache, whatever the number of running campaigns |
| Attachment loads | 40 MiB | Four loads at a time, 10 MiB each, for campaign batches, test sends and transactional templates. A caller in the queue holds nothing, and concurrent reads of one file version are shared |
| Campaign batch in flight | 10 MiB | One batch at a time (`createCampaignRunnerRegistry`), pinned if the cache evicted its files |
| Test sends | 40 MiB | Four admitted until settled, 10 MiB each, pinned the same way |
| Transactional outbox | 40 MiB | 10 rows decoded per batch, each with at most 4 MiB of attachments. This predates M3.5 |

That is at most 194 MiB, with one exception. A synchronous `POST /api/tx` holds its prepared message while it waits for SMTP, up to 4 MiB of attachments, and the route has no limit on concurrent requests. That was already true of a caller's own attachments, and inline images fall under the same 4 MiB. Uploads are separate: up to 8 × 25 MiB of request body.

Body and MIME overhead, on top of the attachment bytes:

- A test send's rendered bodies and headers are at most 32 MiB each, so 128 MiB for four, which only many recipients with large bodies reach.
- Base64 adds about 37%. Without DKIM, nodemailer streams it to the socket in small chunks, as the 4-worker row shows.
- With DKIM it holds each encoded message in memory until it is signed. From reading nodemailer that is up to `app.concurrency` × about 13.7 MiB. One sampled run, 16 signed messages of an 8 MiB file, 4 workers, a sink that stops reading for 2 ms after each chunk: peak RSS 174 MiB against 134 MiB for the unsigned 4-worker row, and peak `arrayBuffers` stayed at 8 MiB, so the signed copy is not visible in that counter. This is one small sample, not a measured upper bound.

Messages in flight share these buffers: the emailer no longer copies them, which was `app.concurrency` × 10 MiB.

## At-most-once with attachments

`bun run runner:crash` still runs campaigns without media. The attachment step adds one window, covered in `test/media/media.test.ts`. A failed read returns the batch's claims and cursor before anything is pushed, so resuming sends the rest once, also when the file is lost between batches. A process that dies before that transaction leaves the batch claimed: startup marks those subscribers unknown and logs them, and they are not sent.
