# M4.6 maintenance

`bun run maintenance:measure`: one serial run through real HTTP on the compiled build, once for each operation, because each consumes its rows. Opt-in, not a CI threshold.

The database is generated: 1,000,000 subscribers (10% blocklisted, 20% orphans, 20% unconfirmed on a double opt-in list, the rest on one or two of 20 lists), about 1.1 million memberships, 100 campaigns, 1,000,000 views and 500,000 clicks attributed to subscribers over a year, and a sent message for each blocklisted subscriber and half the orphans. 822 MiB, seeded offline in 103 s with the FTS triggers on. It is removed after the run. `free -h` showed 10 GiB available beforehand.

Host: shared VM, load average 4 to 5, Bun 1.4.4, `synchronous = FULL`. There is no `before`, since the endpoints are new.

- **Pixel p99 and worst:** a client requests a view pixel every 5 ms, each one short write on the server's thread.
- **Largest lock wait:** a second process tries `BEGIN IMMEDIATE` every few milliseconds (`test/maintenance/measure-probe.ts`). Its longest wait is the longest hold, within a retry, and includes anything else on the host that delayed either process.

**Read the worst column with care.** The idle row's worst pixel is 1.2 s, and the export clicks row, which writes nothing, has the second-largest p99, so spikes of a few hundred milliseconds come from this host (disk, checkpoints, other work) and do not measure a batch. Pixel p99 is the better figure for the batches themselves.

## What the runs changed

- **Export:** the first version only enqueued in `pull`, which Bun calls again before it serves any socket, so a million-row export held every pixel for its whole 55 s. It now awaits the clock after each page, and the worst pixel is 26 ms.
- **Date walk:** `(created_at, id) > (?, ?)` plans as a search on `created_at` from the start of the range, so each page rescanned everything before it: 65 ms a page at row 900,000 of a million, against 0.3 ms for `created_at >= max(?, ?) AND (created_at > ? OR id > ?)`.
- **Analytics batch:** 2,000 rows held the lock about 100 ms and 500 rows about 35 ms. The total time did not get worse (35.5 s for half the views before, 21.9 s now), though the walk fix is part of that gain.
- **Subscriber batch:** 500 at a time held the lock about 100 ms on a 20,000-subscriber run, then 200 at a time on a million:

The worst figures do not separate the two, for the reason above. 100 stays: a row costs about 280 µs, because each subscriber's cascade, FTS row, anonymized sends and webhook rows are written, so 100 rows cost about 30 ms against 55 ms, and the extra 20 to 30% of total time is paid by a one-off operation.

## One statement instead

On the same file, one `DELETE` of 500,000 views on one connection took 1,372 ms, with the write lock held throughout and every pixel, send and loop stopped behind it, since the server shares one thread. The batched delete is slower in total and that is the trade. A one-statement delete of those rows is also cheaper than its share of the table above: they were inserted together, so they sit on contiguous pages, where the seeded rows are spread through the indexes.

## Long requests

`Bun.serve` closes a request idle for 10 s, and these deletes run for minutes, so the route calls `server.timeout(request, 0)`; the 143 s run above is one request that ended with its count.

## Review round 1

Same host, load average about 7, 2026-10-31, one serial run of each.

- **Log line:** the first version ran its redaction patterns on the server's thread, and they grew with the square of the text. A missing image's name took 49.8, 191.7 and 539.9 ms at 10, 20 and 40 KB. The buffer now reads no text of an error, and a line took 0.7 to 2 µs at the same sizes, the average of 1,000.
- **Delivery budget:** each delete batch adds one read of the enabled webhooks, 23 µs at the cap of 20 webhooks, the average of 1,000, against about 30 ms for a batch of 100. The table above was not run again: nothing else in a batch changed, and a million-row run on this host would not resolve 23 µs.
