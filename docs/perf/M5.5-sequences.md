# M5.5 sequence screens: scheduler before and after, list reads at scale

Measured on 2026-10-31 on the shared t3-code VM (6 vCPU, Linux 6.12, Bun 1.4.4, dynamic memory),
serially, with no other test run in parallel. Data is generated in temporary directories and removed
after each run; mail goes to the in-process loopback sink. Storage uses the D19 settings. These are
bounded synthetic numbers for this host, not capacity guarantees.

## What changed on the sending path

- `enrollments.test` (migration 13). The one-active unique index is now one partial index for real
  enrollments and one for tests, and `idx_enrollments_sequence_status` gains `test`.
- The scheduler reads `e.test` in its context query. A step's due time goes through `after`, which
  shortens a test's wait. A test's subject gains `[Test] `. A real enrollment takes neither branch.
- `any-enrollment` and `active-enrollment`, read by event ingest, add `test = 0`.

Nothing else in the claim, decision or commit changed.

## Scheduler, before and after

`bun run scheduler:measure 10000 3`, the M5.4 workload: before on main at 579abad, after on this
branch. Three runs of each, seconds and rate.

| Workload | Before | After |
|---|---|---|
| 10,000 transactional decisions | 2.84, 2.92, 3.08 s (3,246–3,521/s) | 2.89, 2.98, 2.84 s (3,358–3,523/s) |
| 10,000 marketing decisions | 3.32, 3.45, 3.48 s (2,875–3,012/s) | 3.35, 3.39, 3.18 s (2,948–3,141/s) |
| 2,000 sends, outbox alone | 2.13, 1.83, 1.68 s (938–1,188/s) | 2.02, 1.66, 1.67 s (989–1,203/s) |

The scheduler's decision rate, peak RSS (87–137 MiB after, 89–136 MiB before) and the outbox rate
with the scheduler running (519–605/s before, 603–631/s after) are within the variation of these
runs. No regression is visible. The raw JSON of both runs is not kept; the command repeats them.

## The list's reads at 1,000,000 enrollments

`bun run sequences:measure:counts 1000000 5`: 20 sequences of 3 steps, each enrollment with its own
subscriber and one send, on a real file. Five runs on the server's connection, so the first two rows
are what the server thread pays.

| Read | Where it runs | ms |
|---|---|---|
| A page of 20 sequences with `active_enrollments` | server thread | 19, 17, 16.2, 15.9, 16 |
| Explorer total with no filter | server thread | 4.9, 5.3, 5.1, 5.2, 5.3 |
| `/api/sequences/counts` query for 20 sequences | analytics reader child | 3,170, 3,069, 3,131, 3,267, 3,070 |

The per-step counts visit each enrollment's sends and each send's views and clicks, so they grow
with the sequences on the page: about 3 seconds at a million rows. That is why they run in the reader
child (D62), with its time, memory and concurrency limits, and arrive after the rows. The list itself
needs only the index: `active_enrollments` counts `idx_enrollments_sequence_status`. Sends are reached
through the sequence's enrollments and `UNIQUE (enrollment_id, step_id)`, so no read scans `sends`.
A list with `status` or `exit_reason` filters on `/api/enrollments` is M5.3's bounded page with a
`count(*)`, unchanged here. Filtering on `exit_reason` alone has no index, which is acceptable for an
admin filter and was not measured.
