# M0.7 synthetic SQLite write-load spike

This is a synthetic storage experiment, not a send, delivery, HTTP API or
production-schema benchmark. The first control observations are in
[M0.7-results.jsonl](M0.7-results.jsonl); the later comparison observations are
appended with their run labels. Original observations are retained.

## Method

The opt-in command creates invocation-owned directories under the ignored
`upstream/measurements`, or `IGLO_EMAIL_PERF_DIR` if explicitly set. It resolves
and reports the actual path and filesystem, rejects known tmpfs and ramfs, and
prints `df` and mount evidence. The SQLite connection uses the existing M0.4
helpers: WAL, foreign keys, FULL synchronous, 5,000 ms busy timeout, safe
integers and synchronous `BEGIN IMMEDIATE` transactions. It verifies these
settings and uses one process and one connection per run; no networking takes
place inside a transaction. Checking the guest filesystem and these pragmas is
not proof of physical power-loss durability.

Each sustained scenario starts from a fresh disk database with 100,000 generated
subscribers. The reduced subscriber table has ID, unique case-insensitive email,
name, status and timestamps, with status, ID/status, and timestamp indexes and
an external-content name/email FTS5 table maintained by insert/update/delete
triggers. A reduced campaign row has a maximum ID, durable cursor and progress;
selection is ID-ordered and the cursor is committed before processing. There are
no list membership/consent joins, templates, send logs, campaign attributes,
other product tables or full listmonk indexes. Events have a subscriber foreign
key, name, JSON, two timestamps and an idempotency key, with the designed
subscriber/name/time and unique subscriber/key indexes. Their synthetic JSON
contains an integer order, amount, currency and source; it is approximately 65
bytes, varying with the order number. All recipients, events and addresses are
synthetic.

Seed and FTS canary warmup are outside the measured window. Arrivals are due at
fixed independent deadlines: one simulated campaign recipient every 20 ms, one
event every 10 ms, and one subscriber churn cycle every 200 ms. A churn cycle
inserts a new subscriber, updates name and email, then deletes it. The single
in-process driver wakes on an anchored 100 ms schedule, skips obsolete wake ticks after a long
blocking operation, and also wakes at the final 20 ms and 10 ms deadlines. It records the intended deadline and actual progress commit,
event admission and commit, transaction time, timer wake delay and synchronous
driver-block duration. Wake-delay observations are for actual scheduled wakes;
the duration of a driver call is the interval in which synchronous SQLite work
can block unrelated event-loop activity. The virtual backlog
is calculated from generated sequence numbers, so a late driver does not erase
missed offered work. Campaign progress counts simulated processing only after
reservation; there is no SMTP or rendering. Event admission is the driver's
observation, not an HTTP request latency.

Seed, warmup, the fixed measured window, post-window drain, integrity checks,
checkpoint and reopen are timed separately. An item counts toward the window
only if its commit finishes before its end. Any work finishing afterward is
reported as drain even if the final synchronous transaction crossed the window
boundary. The JSON records all repetitions, transaction counts, backlog peaks,
latency percentiles/maxima, sizes and applied settings. The driver checks exact
counts and idempotency uniqueness, cursor/progress, integrity, foreign keys, FTS
content consistency and reopened persistence. A canary separately checks FTS
insert/update/delete and rollback. Deterministic fixture tests advance an
injected fake clock; the benchmark injects the real clock and explicitly records
elapsed monotonic time.

## Reproduction

```sh
bun install --frozen-lockfile
bun test test/perf/sqlite-write-load
bun run db:spike
```

Select a disk-backed location with `IGLO_EMAIL_PERF_DIR=/path/on/disk bun run
db:spike`. The default full run is opt-in and is not in `bun test`, `bun run
check` or CI. `bun run db:spike --control-only` runs the unbatched control, and
`bun run db:spike --smoke` is a short correctness check, not performance
evidence. Databases and synthetic row data are removed when the invocation
finishes normally. The output JSON contains observations, not the generated
rows.

## Initial per-record control, before batching

On 2026-10-28, the initial unbatched control completed three 60-second windows
on `/dev/sda1` ext4, with Bun 1.4.4 and SQLite 3.53.4. Every run offered 3,000
recipients, 6,000 events and 300 FTS churn cycles. Counts below exclude the
catch-up drain; all offered work persisted after drain and reopen.

| Run | Recipients in window | Events in window | Peak sampled recipient / event backlog | Drain ms | Recipient lag p99 ms | Event commit lag p99 ms | Transaction p99 ms |
|---:|---:|---:|---:|---:|---:|---:|---:|
| 1 | 2,996 | 5,991 | 7 / 13 | 73.87 | 97 | 146 | 4.621 |
| 2 | 2,999 | 5,998 | 26 / 55 | 12.06 | 447 | 672 | 8.219 |
| 3 | 2,996 | 5,991 | 35 / 74 | 72.97 | 540 | 907 | 8.887 |

These initial observations are preserved in the first four lines of the results
file and committed before implementing the batched comparison. During inspection,
two comparison issues were identified: the synthetic event timestamps were
based on each run's wall-clock start, rather than identical across modes, and
the last arrivals were not offered a flush until 10 ms before the boundary.
Also, the original `wakeLagMs` tracks accumulated overdue scheduler ticks; it
is not a reliable event-loop responsiveness measurement and must not be used as
one. The final comparison corrects these points, repeats the control, and adds a
bounded synchronous driver-block duration observation. The original counts,
transaction timings, event/campaign latency and drain observations are retained.

## Comparisons and verification

The final command interleaves repetitions of the per-record mixed control, the
batched mixed workload, and the batched campaign-only control. Batched mode
reserves and records progress for at most 50 due recipients at a time, commits
at most 50 due events together, and groups up to 20 due subscriber churn cycles;
the control commits each recipient reservation, progress, event and subscriber
mutation separately. Each scenario uses the same generated recipients and,
where applicable, the same fixed event keys, timestamps, payloads and churn.
The campaign-only run omits events and churn, so its comparison with batched
mixed load measures their combined pacing effect, not the effect of either one
alone. Batch dispatch deliberately adds up to roughly 100 ms waiting time.

The independent FTS isolation starts with the same seeded dataset and compares
identical 3,000 insert/update/delete cycles in transactions of 25 cycles. Every
tenth transaction is additionally attempted and rolled back before it is
committed, for 300 rolled-back cycles. The control drops the three FTS triggers
after seeding; the enabled case retains them. Both finish with the original
subscriber contents, and both validate FTS content and persistence afterward.
The comparison includes ordinary subscriber indexes and commit cost in both
cases; its difference estimates trigger maintenance for this particular churn,
not the cost of arbitrary subscriber changes or searches. Isolation repetitions
are sequential and their enabled/disabled order alternates.

The result's `overInterval` counts commits or admissions more than one offered
interval after their deadlines (20 ms for campaign work, 10 ms for events).
Backlog maxima are sampled at driver wakes and final observation, not a proof of
an absolute instantaneous cap. The program bounds each dispatch and materializes
only that batch; the generated queue is represented by counters. The workload
makes no claim that its queue remains bounded under a higher or indefinite load.

## Upstream comparison and scope

The read-only reference was listmonk v7.0.0-beta.1 commit
`6fcd95f32bb633d3a62a06c383c0b3322eecc898`. Its `schema.sql` supplied the
subscriber identity/index and campaign progress-column comparison for the
reduced fixture schema. `queries/campaigns.sql` supplied the ordered subscriber
selection and progress-count comparison, and `internal/manager/manager.go` and
`pipe.go` supplied the fetch/progress flow comparison. The fixture deliberately
follows the iglo.email design's durable reservation before simulated processing;
upstream's in-memory fetch cursor and completed-work checkpoint are different.
It does not implement list selection or campaign delivery.

`queries/subscribers.sql` and its count companion use PostgreSQL name/email
matching; their endpoint semantics are not ported by this spike. Subscriber FTS5,
its triggers, the events fixture, and the workload itself are new SQLite design
experiments. No production migration, route, API parity or delivery guarantee is
implemented here.

A first attempt at the final comparison was interrupted after one control and
one batched run: the injected `Date` clock has integer-millisecond resolution,
and its boundary and the monotonic elapsed timer were started at slightly
different instants. The batched run recorded 59,999.75 monotonic milliseconds.
Those two observations are retained with `run: "aborted-timing-offset"` and are
not used as the final comparison. The corrected command waits until the elapsed
monotonic duration is at least 60,000 ms; logical deadlines still use the
injected real clock's millisecond resolution, so their alignment is within
approximately one millisecond. The complete comparison is labeled
`run: "comparison"`.
