# M1.4 bounded roles and TOTP measurements

Measured 2026-10-28 with Bun 1.4.4 on this host. `df -T` identified the
worktree temporary root as ext4 on `/dev/sda1`; SQLite uses the application's
FULL/WAL settings. Each of three repetitions used fresh synthetic disk-backed
data and a separate compiled process, removed on exit. Runs were sequential,
with no CI timing threshold and no external SMTP or webhook. Argon2id uses
Bun's default `m=65536,t=2,p=1`; password work was serial. The before control
was `origin/main` 2286d22, and after was this task's implementation. Both used
`TMPDIR="$PWD/.m14-measure" bun run auth:measure` and the same script.

The auth measurement warms each health route five times, then samples 80 serial
requests per route. The public and protected routes return identical bodies but
have different authorization semantics; this compares overhead, not equivalent
security. Login/logout has one warmup and three serial samples. User updates
have one warmup, ten metadata and three password samples. Scheduling and fsync
noise affect these small observations; they do not establish a speed change.

New paths were measured separately with `TMPDIR="$PWD/.m14-measure" bun run
roles:measure`, three fresh processes, one warmup and three sequential samples
per process. Role timings cover a create, update and delete together. Factor
setup and disable each include HTTP and storage; disable also verifies Argon2.
Two-step login includes password verification, form GET, TOTP verification and
session creation. The fixed synthetic key is not used outside the disposable

## Completion fix: concurrent password proof isolation

The labelled HTTP barrier stops a verified password before session creation.
With the M1.4 starting head, updating account B's display name while account
A's proof was paused made A's login return the login form (HTTP 200, no
session), even though A was unchanged. With account-scoped, bounded active
proofs, the same test issues A's session and its protected profile returns
200. A second barrier case disables and re-enables A before release: the stale
proof does not issue a session, and a fresh password login succeeds. Proof
entries exist only while requests are in flight and are capped at 4,096; a
challenge issuance no longer invalidates proofs belonging to other accounts.
These are observable HTTP tests, not a benchmark or a replacement for the
FULL/WAL measurements above.
