# M5.4 sequence scheduler: throughput, send load and crash evidence

Measured on 2026-10-29 on the shared t3-code VM (6 vCPU, Linux 6.12, Bun 1.4.4, dynamic
memory), serially, with no other test run in parallel. Data is generated in temporary
directories under `/tmp` and removed after each run; mail goes to the in-process loopback sink
(`test/tx/sink.ts`). Storage uses the D19 settings (WAL, `synchronous=FULL`). These are
bounded synthetic numbers for this host, not capacity guarantees.

Commands: `bun run scheduler:measure` (`test/scheduler/measure.ts 10000 3`) and
`bun run scheduler:crash`.

## Scheduler throughput, 10,000 due enrollments

Each enrollment is due now on a one-step sequence. The scheduler runs alone (no outbox) from
start until all 10,000 are `completed` with 10,000 `queued` sends. Each decision renders the
template (subscriber name, unsubscribe URL) and commits the send insert and the advance in one
`BEGIN IMMEDIATE` transaction with a FULL commit.

| Step kind | Run 1 | Run 2 | Run 3 | Peak RSS |
|---|---|---|---|---|
| transactional | 2.44 s (4,103/s) | 2.47 s (4,054/s) | 2.36 s (4,229/s) | 86–125 MiB |
| marketing (consent + cap queries, unsubscribe headers) | 2.87 s (3,483/s) | 3.05 s (3,276/s) | 2.86 s (3,499/s) | 92–130 MiB |

Batches are 100 claims per `BEGIN IMMEDIATE`; the claim uses `idx_enrollments_due`.

## Send load before and after

"Before" is the outbox alone, as on main before this change: 2,000 queued transactional sends
are drained to the sink. "After" drains the same 2,000 while the scheduler processes another
10,000 due enrollments on the same process and database (it queues 10,000 more sends).

| | Run 1 | Run 2 | Run 3 |
|---|---|---|---|
| Before: outbox alone | 5.72 s (350/s) | 5.39 s (371/s) | 5.22 s (383/s) |
| After: with 10,000 scheduler decisions | 13.50 s (148/s) | 13.48 s (148/s) | 12.86 s (155/s) |

In every "after" run the scheduler completed all 10,000 enrollments within the window.

An earlier run of the same code without the per-decision I/O yield measured 139, 135 and
128 sends/s "after" (scheduler 4,236–4,387/s alone). The scheduler now yields to I/O with
`setImmediate` between decisions; it costs about 4% scheduler throughput.

**Finding for the messaging owner (not changed here).** The remaining slowdown comes mostly
from the outbox claim, not from scheduler CPU: the scheduler finishes in about 3 s, but the
send rate stays low while 10,000 extra rows are queued. `sends.claim` runs
`WHERE status='queued' AND (next_attempt_at IS NULL OR next_attempt_at <= ?) ORDER BY id LIMIT 1`,
whose plan is `SEARCH sends USING INDEX idx_sends_outbox (status=?)` plus
`USE TEMP B-TREE FOR ORDER BY`, so every claim sorts all queued rows. Before M5.4 queues were
small (tx requests); a sequence burst makes the queue as long as the burst. A follow-up for
the messaging owner could add a `(status, id)` index or split the claim into the null and due
`next_attempt_at` cases. This task does not own that query.

## Crash safety against compiled builds

`bun run scheduler:crash` builds `dist/iglo.email` and the test-only `dist/scheduler-crash`
(`test/scheduler/crash-entry.ts`: the production scheduler, outbox and owners, with no HTTP),
seeds one enrollment on a two-step sequence (transactional `PT0S`, marketing `PT0S`), kills
the process with SIGKILL at a barrier, restarts it with its injected clock six minutes later
(past the 5-minute lease) and waits until the enrollment completed and no send is queued or
sending.

| Kill point | Rows when killed | After restart | SMTP messages |
|---|---|---|---|
| after claim (before the decision) | none | step 0 sent, step 1 sent | 2 |
| after send insert, before advance (inside the transaction) | none (rolled back) | sent, sent | 2 |
| after advance, before commit | none (rolled back) | sent, sent | 2 |
| after commit, before the outbox wake | step 0 queued | sent, sent | 2 |
| during SMTP delivery (DATA held, then SIGKILL) | step 0 sending, step 1 queued | step 0 unknown, step 1 sent | 2 (step 0 once, unacknowledged) |
| production `dist/iglo.email`, during SMTP delivery | step 0 sending, step 1 queued | step 0 unknown, step 1 sent | 2 |

Every step has exactly one `sends` row and reached SMTP at most once. The interrupted
delivery becomes `unknown` and is never retried (D24). Insert and advance commit together,
so "send exists but enrollment not advanced" cannot be produced by a crash; the scheduler
still handles that state (`test/scheduler/scheduler.test.ts`, "an existing send for the
step is only advanced past").
