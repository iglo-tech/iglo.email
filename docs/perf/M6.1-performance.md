# M6.1 performance against the targets

Serial, foreground runs on the shared t3-code VM (6 vCPU, Linux 6.12, Bun 1.4.4, dynamic
memory, swap already full before the runs), 2026-10-30, under `nice`, one run at a time. Data
directories are on ext4 under `upstream/measurements` (never tmpfs) and are removed after each
run. Storage uses the D19 settings (WAL, `synchronous=FULL`). These are local observations on
one host, not CI thresholds or capacity claims.

Raw records, one JSON object per run, are in [M6.1-results.jsonl](M6.1-results.jsonl). Each
record carries `head`, `dirty`, `source` (SHA-256 prefix over every tracked file under `src/`
and `migrations/` as measured) and, for compiled runs, `executable` (SHA-256 prefix of
`dist/iglo.email`).

## Harnesses

- `bun run perf:mixed [events|baseline|mixed]` (`test/perf/m61/mixed.ts`): builds and starts
  the compiled `dist/iglo.email` with a fresh data directory. All input is real HTTP: login and
  API credential, settings (SMTP at a loopback sink, campaign workers), lists, subscribers,
  campaign, templates, sequences, events, tx. The sink records only the recipient and the
  accept time of each message. Defaults: 300 s window, campaign workers 8 × 10, tx 2/s.
  `M61_WINDOW_MS`, `M61_CONCURRENCY`, `M61_RATE`, `M61_TX_PER_SECOND` and `M61_AUDIENCE`
  override them.
  - Events: open loop, `POST /api/subscriber-events` at fixed 10 ms deadlines (100/s), as in
    M5.1 and M3.2: 2,000 subscribers by `external_id` and `email`, changed `attribs`, ~50 bytes
    of `data`, a unique `idempotency_key`. The client caps in-flight requests at 500 and counts
    anything beyond as shed. Acceptance latency runs from the scheduled deadline to the HTTP
    response.
  - Campaign: one list of preconfirmed subscribers, sized so that the campaign is still
    sending when the window ends. The window opens once the first campaign message arrives.
    The rate counts campaign messages the sink accepted inside the window.
  - Mixed only: two active sequences. Every tenth event is `signup` instead of `order_paid`
    (10/s). `welcome` (trigger `signup`, `reentry: always`) has a `PT0S` transactional step, so
    the scheduler queues a send for every signup, then a `P1D` step. `nudge` (trigger `signup`,
    `exit_on: ["order_paid"]`) is exited by that subscriber's next `order_paid`. Async
    transactional `POST /api/tx` (external subscriber) at 2/s. tx delivery latency runs from
    the scheduled deadline to SMTP acceptance.
  - Recorded: offered and completed counts, rates, latency percentiles, campaign rate per
    10 s bucket and the busiest 1 s, campaign `to_send`/`sent` and outbox status counts at the
    window start and end (backlog), and 5 s samples of server RSS (`/proc`), `free -m`
    MemAvailable and outbox counts. `serverErrorLines` counts stderr lines; the application
    logs only errors.
- `bun test/perf/m61/outbox.ts [backlog] [repetitions]`: the production scheduler, outbox and
  owners in-process (`test/scheduler/runtime.ts`, as in M5.4) with a loopback sink. The
  scheduler queues `backlog` sequence sends, half transactional steps and half marketing
  steps, with the outbox stopped. Then 1,000 tx sends are enqueued after them, and the outbox
  alone drains everything. The no-backlog case drains the 1,000 tx sends only. Before the
  drain, the production `sends.claim` is timed 200 times on the full queue, each call rolled
  back.
- `bun test/perf/m61/cap.ts [iterations]`: the production journal, marketing policy (`P7D` cap)
  and campaign runner store over generated history. For N = 0, 100, 1,000, 10,000, one
  subscriber has N marketing journal rows (mostly `sent`, some `unknown` and `failed`) and N
  campaign deliveries, all older than the window. The cap therefore admits, and each lookup has
  to rule out the whole history. Times are the 2,000 calls that follow 50 warm-up calls.

## Fixes

**Outbox claim** (`src/messaging/sends.ts`). The claim was
`WHERE status='queued' AND (next_attempt_at IS NULL OR next_attempt_at <= ?) ORDER BY id LIMIT 1`
with plan `SEARCH sends USING INDEX idx_sends_outbox (status=?)` + `USE TEMP B-TREE FOR ORDER BY`:
every claim sorted every queued row, payloads included. It now takes the lower of
`min(id)` over `status='queued' AND next_attempt_at IS NULL` and `min(id)` over
`status='queued' AND next_attempt_at <= ?`. Both halves read the existing
`idx_sends_due (status, next_attempt_at, id)`, and the first is a single covering-index probe.
The result is the same row: the lowest id that is new or due for retry. D24 retry timing and
at-most-once are unchanged, because claiming, leasing and outcomes are untouched. A new
journal test pins the order: a retry waits for its deadline while newer rows go first, then
precedes higher ids.

**Frequency-cap lookups** (`src/messaging/sends.ts`, `src/campaigns/runner/store.sql`,
migration 8). Each lookup scanned the subscriber's whole history:
`idx_sends_cap (subscriber_id, kind, sent_at)` and
`idx_campaign_deliveries_subscriber (subscriber_id, at)` could not filter on status. Migration 8
replaces both indexes under the same names, as
`sends(subscriber_id, kind, status, coalesce(sent_at, attempted_at, created_at))` and
`campaign_deliveries(subscriber_id, status, at)`. The queries keep their predicates, split into
one branch per status:

- journal admission: `sending`, `queued` when pending, and `sent`/`unknown` newer than the
  window start, each excluding the resend lineage;
- `capFreeAt`: the maximum of four per-status maxima;
- campaign `last-delivery`: the maximum of three per-status maxima, plus `EXISTS` on `claimed`.

Each branch is an index seek or the last entry of an index range. Semantics are identical: the
same statuses, the same time expression, the same lineage exclusion, and a `claimed` campaign
row or `sending`/`queued` journal row still holds the cap at any age. The existing cap tests
(`test/unsubscribe`, `test/campaigns`, `test/scheduler`) pass unchanged.

### Bottleneck

Every loop and every request share one JavaScript thread. Each FULL-sync commit blocks it
for about 4–5 ms (M5.1 probe). In the mixed run the thread commits event groups, enrollment
and exit writes (two sequences per signup, an exit per `order_paid`), scheduler decisions,
campaign batch progress, and **three separate commits per outbox message**: the claim, the
`skip_reason` update in `admit`, and the outcome in `finish`. The outbox also sends one
message at a time (`batchSize: 1`).

- Campaign workers lose throughput twice. listmonk's limiter sleeps a full second after
  `message_rate` messages, on top of the time those messages took, so every millisecond the
  thread spends elsewhere comes off the rate. At 8 × 10 each worker managed 6.1 messages/s,
  which leaves about 64 ms per message, against about 38 ms in the baseline (7.2/s per worker).
- Events wait behind the same commits. Group commit (M5.1) keeps them from collapsing, but
  their latency rises with every other writer.

### Proposals (not implemented; outside this task's authorized changes)

1. **Outbox commits** (messaging owner): fold `admit`'s `skip_reason` write into the claim
   transaction, or skip it when it stays `NULL`. That saves one of three fsyncs per message.
   Then claim a small batch per transaction and push it in parallel on the pool, journaling
   outcomes in one commit. At-most-once holds, because each claim still commits before SMTP.
   This should roughly halve thread time per outbox message, and it lifts the ~85/s backlog
   drain on this host.
2. **Campaign pacing** (campaigns owner, decision record needed): sleep for the rest of the
   second (`max(0, 1 s − elapsed)`) instead of a full second after each `message_rate`
   messages. Throughput then stays at the configured rate under load and doesn't swing with
   per-message latency. It is a deliberate difference from listmonk under D57. Until then,
   operators should configure about 2× headroom (concurrency × rate ≈ 100 for 50/s), as the
   10 × 10 row shows.
3. **Write coalescing across loops** (storage, D19/D22): one shared group-commit point for
   events, scheduler and outbox writes would cut fsyncs further, at the cost of a small
   per-write delay. The alternative, `synchronous=NORMAL` in WAL, changes durability and
   needs a decision.
4. **Due-retry half of the claim**: the `next_attempt_at <= ?` half still reads every due
   retry row. That is normally a handful, but during a long SMTP outage it can be the whole
   transactional queue, up to five attempts each. Not measured here. If it shows up, a
   partial index on due retries keyed by id would make it a probe as well.
