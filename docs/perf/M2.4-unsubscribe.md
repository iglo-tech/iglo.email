# M2.4 unsubscribe and frequency-cap measurements

Serial, in-process measurements on the shared Linux x86-64 development VM
(6 vCPU, Bun 1.4.4, `nice`, no parallel test runs), 2026-10-29. Reproduce with
`bun run unsubscribe:measure` (`UNSUB_MEASURE_N` sets the count, default 200;
`MEASURE_PART=tx` runs only the transactional section). These are local
observations, not CI thresholds or production capacity claims.

Setup: the production owners used by `test/tx/fixture.ts` (SQLite journal,
outbox, nodemailer with up to four connections, M1.8 renderer, M2.4 policy,
tracking and public routes) and a loopback SMTP sink, real clock. The template
contains one `track_link`; the marketing template adds `unsubscribe_url` and
`track_view`.

**Before** is merged main (ee66bae) with the same script's transactional section
(main's `track_link` returns the URL unchanged and marketing is staged as
`skipped`, so no marketing comparison exists). **After** is this branch, where
every tx send also pre-assigns its UUID, registers tracked links and, for
marketing, checks consent and the cap in the enqueue transaction.

## Transactional sync sends (N = 200, linked subscribers)

Two runs on main and three on this branch, interleaved:

| Run | Before (main) | After (M2.4) |
|---|---|---|
| 1 | mean 2.28 ms, p50 1.85, p95 4.33; 437 sent/s | mean 2.39 ms, p50 1.92, p95 3.95; 419 sent/s |
| 2 | mean 2.28 ms, p50 1.84, p95 3.93; 438 sent/s | mean 2.61 ms, p50 2.08, p95 4.69; 382 sent/s |
| 3 | — | mean 2.24 ms, p50 1.76, p95 3.89; 446 sent/s |

The difference is within run-to-run noise on this VM; the added work is one
link-registration upsert per distinct URL per request plus an in-memory cache.

## Marketing and public routes (after only)

Journal preloaded with 20,000 delivered marketing rows across the 200
subscribers, 30 days old (outside the 7-day window), so the cap query runs
against a populated `idx_sends_cap`.

| Workload (N = 200) | Result |
|---|---|
| Marketing sync send (consent + cap + render + SMTP + outcome) | mean 2.39 ms, p50 2.18, p95 3.79; 419 sent/s |
| Marketing send skipped by the cap (no SMTP) | mean 0.51 ms, p50 0.49, p95 0.59 |
| `GET /m/:send/px.png` (view recorded) | mean 0.07 ms, p95 0.10 |
| `GET /m/:send/link/:link` (body check, click recorded, 307) | mean 0.08 ms, p95 0.11 |
| `GET /m/:send/unsubscribe/:sub` page | mean 0.09 ms, p95 0.14 |
| One-click `POST` (write transaction) | mean 0.16 ms, p95 0.19 |
| Process RSS | 54 MiB at start, 115 MiB at end (101 MiB for the transactional section alone, as on main) |

Observations:

- The cap check is one indexed lookup per marketing recipient inside the
  existing enqueue transaction; a capped send costs about a quarter of a
  delivered one because it skips SMTP.
- The link redirect reads only the stored body fields of one send
  (`json_extract`), bounded by the 1 MiB body limit; small messages dominate here.
- No measurable regression of the transactional path.
